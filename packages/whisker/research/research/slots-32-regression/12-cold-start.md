# 12 - Cold-Start-Auditor

**Verdict:** ruled-out — cold-start effects (empty prefix cache, post-ready JIT/CUDA warmup) can explain at most ~50–150 s front-loaded overhead, not the full +398 s (+57%) spread across an 18-minute batch; the bundled `--max-num-seqs 16→32` config change is a stronger sustained-regression suspect.
**Confidence:** medium

## Quantified estimate (seconds attributable to cold start, with reasoning)

| Component | When it runs (vLLM 0.24 V1 default) | Estimated extra seconds vs warm steady-state | Reasoning |
|-----------|-------------------------------------|---------------------------------------------|-----------|
| `torch.compile` / Inductor | **Before** `/v1/models` returns 200 | **0** (in batch wall time) | V1 guarantees all compilation finishes before serving; no request triggers new compile ([torch.compile design doc](https://docs.vllm.ai/en/latest/design/torch_compile.html)). Paid during the ~5 min post-reboot wait, not during the 1090 s batch. |
| CUDA graph capture (67 default shapes) | **Before** ready — model warmup step 3.4 | **0** (in batch wall time) | Default captures at engine init, not lazily ([issue #19824](https://github.com/vllm-project/vllm/issues/19824), [RFC #20098](https://github.com/vllm-project/vllm/issues/20098)). Tensorfuse: ~54 s for wide capture on 8B; Llama-70B-FP8 TP8: ~60 s ([issue #19824](https://github.com/vllm-project/vllm/issues/19824)). Absorbed in startup, not batch. |
| `--enable-ep-weight-filter` | **Before** ready — model loading only | **0** (in batch wall time) | Filters disk I/O at load time, not per-request runtime ([PR #37136](https://github.com/vllm-project/vllm/pull/37136), [PR #37351](https://github.com/vllm-project/vllm/pull/37351)). |
| Post-ready first-request JIT (PTX, Triton, uncaptured shapes) | **After** ready — lazy on first real traffic | **30–120** | Documented 30–60 s first-request penalty even after healthy startup ([issue #19824](https://github.com/vllm-project/vllm/issues/19824)); MoE FP8 measured 43 s TTFT on first request with `/health=200` ([issue #39163](https://github.com/vllm-project/vllm/issues/39163)); Qwen3.5 MoE 30 s–4 min ([issue #37175](https://github.com/vllm-project/vllm/issues/37175)). One-time spike, not distributed across 18 min. |
| Lazy CUDA graph capture (if `use_cudagraph_delayed_capture` or uncaptured batch size) | First occurrence of each missing shape | **0–60** | Default is startup capture; lazy mode adds ~1.1 s/shape ([PR #8888](https://github.com/vllm-project/vllm/pull/8888)). Reboot with `max-num-seqs=32` should pre-capture sizes ≤32 at startup ([discuss.vllm.ai](https://discuss.vllm.ai/t/why-is-cuda-graph-capture-sizes-limited-by-max-num-seqs/954/2)). Upper bound: ~20 new shapes × 1–3 s if any were missed. |
| Prefix-cache repopulation (~2.9k shared system+schema) | First cache-miss requests after reboot | **2–65** | APC stores KV blocks; one unique prefix → one prefill of ~2.9k tokens, then all 400+ calls hit ([prefix caching docs](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/)). At ~15k prefill tok/s (vLLM maintainer, [issue #4917](https://github.com/vllm-project/vllm/issues/4917)): 2.9k/15k ≈ **0.2 s** per miss. With client concurrency 32, up to **32 parallel first-wave misses** before blocks are installed: 32 × 0.2–2 s ≈ **6–65 s**. Not 400 × 2.9k — that double-counts; steady-state warm cache benefits all calls equally after the first wave populates. |
| **Total cold-start ceiling in batch wall time** | Front-loaded (first 1–3 min) | **~50–150 s** | Sum of post-ready JIT + prefix first-wave + residual lazy captures. Even aggressive MoE first-request (120 s) + 32 prefix misses (65 s) = **185 s** hard ceiling. |

**Distribution check:** +398 s over 1090.2 s (18.2 min) implies ~1.04 s extra per paper on average. Cold-start mechanisms are **front-loaded** (concentrated in minutes 0–3), not uniform. If cold start were the primary cause, the first ~50 papers would show outsized latency and the tail would converge toward the 692 s baseline rate (~1.8 s/paper effective). A uniform +57% across the full run is structurally inconsistent with one-time warmup costs unless every request were a "first request" (it is not).

**Confound (not cold start, but co-timed with reboot):** `--max-num-seqs 16→32` changes scheduler admission and CUDA-graph capture sizes for the entire run. Measured TPOT/ITL rise ~14% at fixed request rate when doubling `max-num-seqs` ([issue #17598](https://github.com/vllm-project/vllm/issues/17598)). On a decode-heavy ~400-call batch, sustained per-token slowdown from 32-wide sharing vs 16-wide could add **~100–150 s** independently of cache state. This is a **config regression**, not cold start, but was changed in the same reboot.

**Bottom line:** Cold start plausibly costs **tens of seconds to ~150 s early in the run**. It is **capped** well below 398 s and cannot explain a +57% penalty that persists across all 381 papers unless the batch is dominated by repeated first-request penalties (contradicted by 400+ calls with shared prefix).

## Findings

- [HIGH] **`torch.compile` and default CUDA-graph capture run at startup, before serving, in V1.** Evidence: [torch.compile design doc](https://docs.vllm.ai/en/latest/design/torch_compile.html) ("all compilation finishes before we serve any requests"); [issue #19824](https://github.com/vllm-project/vllm/issues/19824) (step 3.4 model warmup = CUDA graph capture). Impact: reboot-to-`/v1/models` latency includes these costs; they do not belong in the 1090 s batch timer if the batch started ~5 min after ready.

- [HIGH] **Post-ready first-request latency spike (30–120 s) is documented for MoE even when health checks pass.** Evidence: [issue #19824](https://github.com/vllm-project/vllm/issues/19824) ("first request takes 30–60 seconds"); [issue #39163](https://github.com/vllm-project/vllm/issues/39163) (43 s first-request TTFT, `prefix_cache_hits_total=0`); [issue #37175](https://github.com/vllm-project/vllm/issues/37175) (MoE first request 30 s–4 min, Triton kernels not warmed). Impact: adds a one-time front-loaded penalty at batch start; does not scale with 381 papers.

- [HIGH] **Prefix-cache cold repopulation for one shared ~2.9k prefix is small (≪2 s per miss, ≪65 s for 32 concurrent misses).** Evidence: [issue #4917](https://github.com/vllm-project/vllm/issues/4917) (~15k prefill tok/s → 2k tokens in 0.13 s); [prefix caching docs](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/) (reuse after first computation); prior repo measurement `research/concurrency-381/10-vllm-scheduler.md:22` ("saves <1 s/call when warm"). Impact: losing warm prefix cache costs one first-wave of misses, not 400 × 2.9k prefills; **~2–65 s** attributable, not hundreds.

- [MED] **EP weight filter is load-time I/O optimization, not runtime warmup.** Evidence: [PR #37136](https://github.com/vllm-project/vllm/pull/37136), [ep_weight_filter API](https://docs.vllm.ai/en/latest/api/vllm/model_executor/model_loader/ep_weight_filter/). Impact: zero batch-wall-time contribution after `/v1/models` returns.

- [MED] **Lazy CUDA-graph capture exists but is not default; delayed capture moves startup cost into first requests.** Evidence: [RFC #20098](https://github.com/vllm-project/vllm/issues/20098), [PR #23184](https://github.com/vllm-project/vllm/pull/23184) (ON HOLD). Impact: unless pod uses `--lazy-capture-cuda-graph` or `use_cudagraph_delayed_capture`, graphs are pre-captured at startup; residual lazy capture for odd batch shapes adds seconds per shape, not minutes per paper.

- [MED] **`/v1/models` returning 200 does not guarantee all lazy GPU work is finished.** Evidence: [issue #23787](https://github.com/vllm-project/vllm/issues/23787) (warm-up can pay compile/graph upfront, but PTX/Triton gaps remain); [health-check docs](https://theneuralbase.com/vllm/learn/advanced/health-check-health-endpoint/) (`/health` returns 200 before model fully warm). Impact: starting the batch 5 min after ready reduces but may not eliminate first-request spike; still bounded to first minutes.

- [LOW] **Known vLLM 0.17–0.19 regressions: first-batch slowness from unwarmed Triton kernels persists across minor versions.** Evidence: [issue #37175](https://github.com/vllm-project/vllm/issues/37175) (fix promised 0.18, still present); [issue #4917](https://github.com/vllm-project/vllm/issues/4917) (Triton JIT on first `context_fwd_attention`). Impact: pattern is real but magnitude is first-request-scale, not full-batch-scale.

## What would confirm/refute this (a specific cheap re-test)

**Confirm cold-start ceiling (~50–150 s):** On the live pod, run the same 381-paper batch **without rebooting** a second time (prefix cache now warm, graphs compiled). If wall drops to ~692–750 s, cold start contributed ~340–400 s — refutes this report. If wall stays ~1000+ s, cold start was minor and `max-num-seqs=32` (or another sustained factor) is primary.

**Isolate cold start from config (cheapest definitive test):** Reboot pod back to `--max-num-seqs 16` (revert only that flag), wait for `/v1/models` 200, immediately send **one** synthetic warmup request matching production shape (~2.9k system prefix + typical paper body, `max_tokens` equal to judge/triage), then run the 381-paper batch at client concurrency 32. Compare: (a) time-to-first-token of warmup request (expect 30–120 s if post-ready JIT is active), (b) total batch wall. If batch returns to ~692 s, cold start was not the driver — config was.

**Metric probe during cold batch:** Scrape `prefix_cache_hits_total` and `request_prefill_time_seconds` from vLLM metrics on the slow run. If hits rise to >90% after the first ~32 requests and prefill times normalize, prefix-cache cold cost is confirmed small; sustained elevation across all 381 papers implicates scheduler/config, not cache.
