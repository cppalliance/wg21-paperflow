# 11 - MoE-Batch-Scaling-Analyst

**Verdict:** primary-cause — MoE decode on EP8 single-node is governed by the union of distinct experts activated per forward pass, not token-count amortization; doubling `--max-num-seqs` 16→32 pushes per-GPU active experts toward saturation and inflates HBM weight traffic, slowing every decode step ~1.6× despite more parallel slots.
**Confidence:** high

## Findings

- [HIGH] **MoE decode cost scales with the union of activated experts, not batch size the way dense models do.** Evidence: ELDR paper (https://arxiv.org/html/2607.00466v1) — "growing the active-expert count from 16 to 128 raises MoE-layer latency 4.7× at fixed batch size, while batch size at fixed active-expert count barely moves it"; Perplexity multi-node DeepSeek deployment (https://research.perplexity.ai/articles/lower-latency-and-higher-throughput-with-multi-node-deepseek-deployment) — on single-node EP8, batch 1 activates ~2 experts/GPU, large batch activates all 32 experts/GPU (256/8), "significantly increasing memory bandwidth pressure" and reducing output speed. Impact: at `--max-num-seqs 32` vs 16, each decode forward pass loads roughly twice as many distinct expert weight sets from HBM, directly explaining the 692.3 s → 1090.2 s (+57%) regression on identical 381-paper workload.

- [HIGH] **Measured regression matches MoE superlinear decode penalty, not a client or queue artifact.** Evidence: `packages/whisker/research/llm-batching/20-sweep-results.md:76-91` — 381 papers at client c=32 with server `--max-num-seqs 16` completed in 692.3 s; user baseline with `--max-num-seqs 32` took 1090.2 s (ratio 1.57×); per-call mean was ~30 s at 16 slots (`17-latency-decomposer.md:10`, `11-throughput-auditor.md:66`). Impact: wall time grew faster than the naive 2× speedup expectation because per-token decode slowed ~57%, not because the client changed.

- [HIGH] **DeepSeek V3/V4 routes 8 experts per token across 256 routed experts on EP8 = 32 experts/GPU local shard.** Evidence: Perplexity article (https://research.perplexity.ai/articles/lower-latency-and-higher-throughput-with-multi-node-deepseek-deployment) — "256 routed experts… each token dispatched to 8 different routed experts… EP8: each GPU manages 256/8 = 32 routed experts"; DeepSeek-V3 hardware paper (https://arxiv.org/html/2505.09343). Impact: with 32 concurrent decode tokens (one per seq), the per-step expert union approaches the full 32-expert local shard; with 16 tokens it stays nearer the ~16–20 expert range — a nonlinear jump in bytes read per MoE layer × 58 MoE layers per forward.

- [MED] **vLLM confirms TPOT rises when `max-num-seqs` rises at fixed request rate (dense-model analogue).** Evidence: vLLM issue #17598 (https://github.com/vllm-project/vllm/issues/17598) — at request rate 16, mean TPOT 8.23 ms at `max-num-seqs 16` vs 9.41 ms at 32 (+14%); maintainer comment: higher simultaneous sequences allocate less compute per request. Impact: the pattern is expected in vLLM scheduling; on MoE the mechanism is amplified by expert-union growth, explaining why our MoE regression (+57%) exceeds the dense-model +14% benchmark.

- [MED] **H200 DeepSeek EP setups show low-concurrency decode sensitivity and EP communication overhead.** Evidence: vLLM #28887 (https://github.com/vllm-project/vllm/issues/28887) — "even at higher concurrencies, performance still worse than EP=False" on H200 DeepSeek-R1 TEP8; #28882 (https://github.com/vllm-project/vllm/issues/28882) — MoE backend selection causes perf degradation at conc ≤ 8; vLLM EP docs (https://docs.vllm.ai/en/stable/serving/expert_parallel_deployment/) — AllToAll dispatch/combine per MoE layer, DeepEP kernels tuned for disaggregated prefill/decode. Impact: at 32 in-flight sequences on EP8, dispatch/combine volume doubles alongside expert weight traffic; contributes but secondary to HBM expert-union cost.

- [MED] **KV-cache pressure at `--max-model-len 393216 --gpu-memory-utilization 0.95 --kv-cache-dtype fp8` may compress available batch headroom.** Evidence: `05a-web-concurrency-knee.md:21` — MoE models leave minimal KV headroom after loading all expert weights; Paralleliq recommends `max-num-seqs 4–8` on 8×H100 for DeepSeek V3, "setting higher will immediately OOM" at long context; our pod runs 393k context with 0.95 util. Impact: raising slots 16→32 increases concurrent KV footprint; may trigger preemption, chunked-prefill deferral, or memory-bandwidth contention (`docs.vllm.ai/.../optimization/` — preemption "adversely affects end-to-end latency"). Contributing, not primary.

- [LOW] **`--enable-ep-weight-filter` is load-time I/O only; ruled out as runtime regression cause.** Evidence: vLLM PR #37351 / `ep_weight_filter.py` docs (https://docs.vllm.ai/en/latest/api/vllm/model_executor/model_loader/ep_weight_filter/) — "Skip non-local expert weights during model loading… drastically reduce storage I/O"; no runtime batching interaction. Impact: flag does not change decode expert routing or weight access patterns; safe to keep enabled; not implicated in 16→32 slowdown.

- [LOW] **Sweet spot for this H200×8 DeepSeek-V4-Pro pod is `--max-num-seqs 16`, not 32.** Evidence: measured 692.3 s at 16 vs 1090.2 s at 32; `20-sweep-results.md:110-114` — CTO confirmed cap was 16, client default matched; community H200×8 DeepSeek-V4 configs use 8 (`05a-web-concurrency-knee.md:31`, GitHub #42265); Vultr DeepSeek-V3.2 sweep shows throughput gains only until saturation ~512 concurrent on 2 TB VRAM (https://docs.vultr.com/inference-cookbook/cuda/model-guides/deepseek-v32) — not applicable to our tighter 1.1 TB EP8 footprint. Impact: keep server at 16, client at 32 (back-fill as slots free per `20-sweep-results.md:86-90`); do not raise server slots further without wide-EP or prefill/decode disaggregation.

## The mechanism in one paragraph (for a non-GPU-expert reader)

In a normal (dense) model, putting more requests in a batch is efficient because every token reuses the same set of weights: load once, apply to all tokens. DeepSeek-V4-Pro is a Mixture-of-Experts model: each token picks 8 of 256 experts, and on your 8-GPU pod each GPU permanently stores 32 of those experts. When 16 requests decode together, the GPU might need to touch, say, half of its local experts in a given step; when 32 decode together, it often needs almost all 32, so memory traffic per step jumps much more than 2×. Decode is already limited by how fast the GPU can read weights from memory, not by math throughput, so this extra reading makes each output token slower. Doubling `--max-num-seqs` therefore trades "more parallel slots" for "heavier work per slot," and on MoE at EP8 the second effect wins — your 381-paper batch took 57% longer, not half the time.

## What would confirm/refute this

**Confirm:** Run the same 381-paper corpus twice with `--max-num-seqs 16` vs 32, client c=32, and capture vLLM metrics or nsys on one MoE layer: (a) count of distinct experts activated per decode step, (b) mean TPOT / MoE-layer latency. If expert-union count and TPOT rise ~1.5× at 32 slots while token throughput falls, primary cause is confirmed.

**Refute:** If expert-union counts are identical at 16 and 32 slots but wall time still diverges, look instead at KV preemption rate, AllToAll dispatch bytes, or MoE backend kernel selection (`VLLM_MOE_USE_DEEP_GEMM`, FlashInfer FP8 path per #28882). If `--max-num-seqs 32` with client c=16 (not 32) restores 692 s wall time, the regression is scheduler/contention at over-subscription (32 slots × 32 client), not expert union — but prior 20-paper sweep at c=32/c=16 showed client overfill helps, not hurts, when server cap is 16.
