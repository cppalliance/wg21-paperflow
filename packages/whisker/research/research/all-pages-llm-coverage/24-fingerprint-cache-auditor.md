# 24 - fingerprint-cache-auditor

**Verdict:** usable-with-conditions (+ baseline line 44 correctly calls for a separate fingerprint, but today's `_compute_fingerprint` encodes no coverage mode, so shipping `--all-pages` without a new per-run fingerprint field would silently reuse capped sidecars under `--incremental`; a `_LANE_VERSION` bump alone is necessary on ship but not sufficient for mode discrimination.)
**Confidence:** high

## Findings
- [CRITICAL] **Fingerprint payload has no coverage-mode dimension.** `_compute_fingerprint` returns exactly twelve keys: `md_sha256`, `source_sha256`, `prompt_sha256`, `model`, `lane_version`, `lane`, `schema_sha256`, and four optional ideal fields (`cli.py:543-565`). Neither `--exhaustive-units`, `--inspect`, nor any future `--all-pages` flag is read or hashed. Impact: two runs on identical source/markdown/prompt/model/lane that differ only in how many units/pages are LLM-checked produce identical fingerprints and are treated as cache hits.
- [CRITICAL] **Incremental skip is fingerprint-only; sidecar audit is never consulted.** When `incremental` is true and ideal read succeeds, the worker computes `fp` and calls `_fingerprint_matches`; on match it logs `"skipped (fingerprint match)"` and returns without re-adjudicating or validating `unit_coverage` / page audit fields (`cli.py:1091-1105`, `_fingerprint_matches` at `cli.py:581-588`). Impact: a capped 5-unit sidecar is reused as authoritative for an `--all-pages` golden review if fingerprints collide; operator gets a false sense of full-page verification.
- [CRITICAL] **`--exhaustive-units` already has the same cache-poisoning bug on the text/HTML lane TODAY.** Text adjudication passes `exhaustive=args.exhaustive_units or args.inspect` (`cli.py:1186-1187`), which changes `run_unit_checks` from `MAX_UNIT_CHECKS` cap to all routed units (`unit_judge.py:283-304`), but fingerprint computation before and after the call uses the same `_compute_fingerprint(...)` signature with no exhaustive argument (`cli.py:1093-1097`, `1154-1158`, `1233-1237`). Impact: `--incremental` after a capped text-lane run silently skips an exhaustive rerun (and vice versa: exhaustive sidecar reused for capped fleet run).
- [CRITICAL] **PDF lane makes exhaustive/inspect flags irrelevant to both behavior and fingerprint.** `judge_pdf_extraction` is invoked with only `pid`, `backend`, `judge_agent`, `debug_log` (`cli.py:1120-1127`); `run_unit_checks` inside `pdf_judge.py` is called without `exhaustive` (`pdf_judge.py:843-850`). Fingerprint still uses the same PDF contract (`cli.py:1080-1084`, `971-972`). Impact: `--exhaustive-units`/`--inspect` do not change PDF fingerprints today (masking the bug), but `--all-pages` wired the same way would change behavior without changing fingerprint, reproducing the text-lane defect on the PDF golden path.
- [HIGH] **`_LANE_VERSION` bump is a global invalidation lever, not a per-mode cache key.** `_LANE_VERSION = 8` with changelog at `cli.py:98-111`; it is copied into every fingerprint as `lane_version` (`cli.py:548`). Bumping it forces all incremental sidecars to miss once, but capped and all-pages runs within the same version still share a fingerprint if no mode field exists. Impact: relying on a version bump at `--all-pages` ship fixes stale cache once, then the capped↔all-pages collision returns on the next incremental run; it does not let capped fleet and all-pages golden caches coexist correctly.
- [HIGH] **Required fix: add an explicit per-run `coverage_mode` (or equivalent) to `_compute_fingerprint`, not page count alone.** Must encode at minimum: default capped routed (`MAX_UNIT_CHECKS=5`, `constants.py:223`), exhaustive routed (`exhaustive=True` on text lane today), and planned all-pages (every `page:N` required). Page count is already indirectly bound via `source_sha256` (`cli.py:545`) and does not distinguish capped vs all-pages on the same PDF; timeout partial runs need sidecar audit validation on skip, not page count in the hash alone. Impact: without this field, baseline's "separate fingerprint" (`00-baseline.md:44`) is not implementable.
- [MED] **Reverse direction (all-pages sidecar → fleet incremental skip) is lower severity but real.** Fleet bare run enables incremental by default (`cli.py:1011-1014`, `298-305`); explicit-PID golden runs need `--incremental` opt-in. If an all-pages sidecar exists and fingerprint matches a subsequent capped fleet invocation (same missing mode field), fleet skips and retains the higher-coverage artifact without re-running (`cli.py:1098-1105`). Impact: not a false-pass on defects (superset coverage), but breaks fleet cost/latency assumptions and can leave sidecar audit fields shaped for all-pages semantics in a capped workflow.
- [LOW] **Tests assert fingerprint stability on content/prompt/model/lane/schema/ideal but never on coverage mode.** `test_incremental.py:148-238` lists required keys; no test covers `--exhaustive-units`, `--inspect`, or mode transitions; `test_lane_version_covers_fail_closed_source_checks` only pins `_LANE_VERSION == 8` (`test_incremental.py:110-111`). Impact: the exhaustive/all-pages cache bug can ship undetected.

## False-pass hypothesis
Operator runs fleet capped PDF adjudication (incremental on by default, `cli.py:1011-1014`), producing a sidecar with at most 5 scoped unit checks (`unit_judge.py:304`, `pdf_judge.py:843-850`). Later they run golden review `whisker-tapetum-llm P1068R11 --all-pages --incremental` (or `--review-all --incremental` after a capped sidecar exists). Fingerprints match because source, markdown, prompts, model contract, lane, and `lane_version` are unchanged (`cli.py:543-565`). CLI logs `"skipped (fingerprint match)"` (`cli.py:1099-1100`) and leaves the capped sidecar in place. Operator believes all 15 pages were individually LLM-judged; only the earlier capped subset was.

## False-fail hypothesis
Adding `coverage_mode: "all_pages"` to new fingerprints without a one-time `_LANE_VERSION` bump is not a false-fail: `_fingerprint_matches` requires every new key to match the old sidecar (`cli.py:588`), so old sidecars missing the field fail match and force re-evaluation (same pattern as `schema_sha256` migration, `test_incremental.py:751-758`). False-fail risk is operational: if ship bumps `_LANE_VERSION` only and omits `coverage_mode`, the entire corpus re-runs once, then capped/all-pages collisions resume; if ship adds `coverage_mode` but golden operators habitually pass `--incremental` after capped fleet, they get a full re-run (correct behavior, higher wall-clock).

## What would change my mind
An implemented branch where `_compute_fingerprint` accepts and persists a `coverage_mode` field derived from CLI flags, `test_incremental.py` asserts capped vs exhaustive_routed vs all_pages fingerprints differ while all other inputs are equal, and an integration test proves `--incremental` does not skip when upgrading from capped to `--all-pages` on the same PID.
