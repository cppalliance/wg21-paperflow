# 11 - Tokenizer-Serving-Quirks

**Verdict:** usable-with-conditions — V4-Pro is servable on vLLM with mandatory `deepseek_v4` parser flags, but our stack assumes V3/R1-era output shapes; BPE cleanup stays as defense-in-depth, think-block handling is fragile unless the RunPod pod runs vLLM ≥0.21.0 with all three parsers, and tapetum's schema-in-prompt path still hits JSON/fence failures independent of tokenizer class.
**Confidence:** medium

## Findings

- [CRITICAL] vLLM requires a V4-specific serving flag triad not declared in `SERVICES.toml`. Every official path — vLLM blog (2026-04-24), `vllm-project/recipes` DeepSeek-V4-Pro.yaml, vLLM issue reproductions — launches with `--tokenizer-mode deepseek_v4 --reasoning-parser deepseek_v4 --tool-call-parser deepseek_v4 --enable-auto-tool-choice`. Without these, tokenization, DSML tool markup, and `<think>` boundary detection fall back to generic parsers built for R1/V3. Evidence: https://vllm.ai/blog/2026-04-24-deepseek-v4; https://github.com/vllm-project/recipes/blob/main/models/deepseek-ai/DeepSeek-V4-Pro.yaml; `00-baseline.md` §2 (SERVICES.toml lines 47–74 list no parser flags). Impact: Misconfigured pod → wrong decode, think tags leaking into `content`, JSON routed to `reasoning` with empty `content` — all silent until parse fails.

- [HIGH] V4 does **not** share the HF Transformers v5 LlamaTokenizer BPE regression path that broke V3/R1, but ByteLevel BPE cleanup should stay. V3/R1 checkpoints declare `"tokenizer_class": "LlamaTokenizerFast"` while V4-Pro declares `"tokenizer_class": "PreTrainedTokenizerFast"` (HF hub, `deepseek-ai/DeepSeek-V4-Pro/tokenizer_config.json`). The #45488/#45920 bug is LlamaTokenizer installing Metaspace over a ByteLevel `tokenizer.json`; HF fixed routing in Transformers ≥5.7.0. V4's `tokenizer.json` still uses a ByteLevel pre_tokenizer (same GPT-2-style family as V3), but vLLM's `--tokenizer-mode deepseek_v4` is a separate, purpose-built path. Evidence: HF #45488; V4 `tokenizer_config.json` vs V3 (`LlamaTokenizerFast`); `model_backends.py:77–90` (`_clean_bpe`). Impact: BPE U+0120/U+010A false-fail on evidence grounding (see `02-community-feedback-miner.md` false-fail hypothesis) is **lower probability** on correctly served V4 than on V3/R1, but `_clean_bpe` remains cheap insurance when the model quotes tokenizer-adjacent text or the pod runs an older vLLM without `deepseek_v4` mode.

- [HIGH] Minimum vLLM version for production V4-Pro: **0.20.0 floor, 0.21.0+ recommended**. vLLM recipes set `min_vllm_version: "0.20.0"`. Issue #43753 documents `deepseekv4-cu130` (the blog's reference image) timing out at 128K+ context; stable `vllm/vllm-openai:v0.21.0` clears 128K–1M real-prose checks with the same parser flag set. Structured-output bug #41132 (JSON landing in `reasoning` field when thinking enabled) was fixed in PR #41199 (merged ~2026-04-29). Evidence: https://github.com/vllm-project/vllm/issues/43753; https://github.com/vllm-project/vllm/issues/41132; recipes YAML. Impact: Alliance RunPod pods must be verified at ≥0.21.0; the blog's `deepseekv4-cu130` tag alone is insufficient for our 393K configured window.

- [HIGH] V4 thinking mode requires explicit `enable_thinking` activation; our backend passes `thinking_token_budget` instead. vLLM reasoning docs state DeepSeek-V4-Pro "require `enable_thinking: true` in their chat template kwargs to activate thinking mode — without it, reasoning tokens are never generated." `VllmThinkingBackend` sends `extra_body={"thinking_token_budget": N}` when `thinking_budget > 0` (`model_backends.py:294–298`); tapetum sets `thinking-budget: 1024/4096` in `tapetum_llm.md`. It does **not** set `chat_template_kwargs.enable_thinking`. Evidence: https://docs.vllm.ai/en/stable/features/reasoning_outputs/; `packages/whisker/src/whisker/tapetum_llm/tapetum_llm.md` lines 116, 137. Impact: Behavior depends on pod-level `--default-chat-template-kwargs '{"enable_thinking": true}'`. If absent, thinking may be off (less reasoning, different JSON reliability); if on via pod default, shared `max_tokens` budget still splits between think block and JSON (baseline §2, `00-baseline.md` retry logic).

- [HIGH] `VllmThinkingBackend` reads only `delta.content` in streaming and strips `<think>` client-side; it ignores the vLLM `reasoning`/`reasoning_content` field. Streaming accumulation (`model_backends.py:317–328`) concatenates `choice.delta.content` only, then `_strip_think_block` regex-removes embedded tags. When `--reasoning-parser deepseek_v4` works, JSON should appear in `content` and reasoning in a separate field — which we discard (fine). When the parser is missing or bug #41132 regresses, `content=None` and JSON sits in `reasoning` → our backend raises `MalformedModelOutputError`. Evidence: `model_backends.py:48–101, 306–352`; vLLM #41132 reproduction. Impact: Pod parser flags are load-bearing; client-side think stripping is a fallback, not a substitute for server-side parsing.

- [MED] V4 introduces DSML tool-call markup and a dedicated tool parser; our tapetum lane avoids native tool calling but serving flags still matter. V4 tool calls use DSML tokens parsed by `--tool-call-parser deepseek_v4` (#41240, fixed #41801). `SERVICES.toml` sets `tools_capable = true` for dissect/agora paths. tapetum uses schema-in-prompt (no tools), but a shared pod with broken DSML parsing can leak `<｜DSML｜...>` fragments into free-text `content` (community report `02-community-feedback-miner.md`, #40801). Evidence: vLLM #41240; `00-baseline.md` §5.3. Impact: Even advisory JSON extraction can fail on markup pollution in `content`.

- [MED] MTP speculative decoding + thinking + structured output is an open failure class on V4 serving stacks. vLLM #34650: with `--speculative-config method=mtp` and `enable_thinking`, 223 tokens generated but both `reasoning_content` and `content` empty — FSM misses `</think>` boundary when speculative tokens advance before detection. vLLM blog Pro recipe enables MTP; disabling MTP or thinking is the workaround. Evidence: https://github.com/vllm-project/vllm/issues/34650; vLLM blog Pro docker flags. Impact: If RunPod enables MTP (blog default), intermittent empty responses → tapetum `partial` demotion or hard JSON failure; determinism risk under shared pod load.

- [LOW] MODELS.md workaround inventory is mostly sufficient for V4-Pro with two additions and one downgrade. **Keep:** BPE cleanup (lower trigger rate, zero-cost), `<think>` strip (fallback when tags in `content`), schema-in-prompt + JSON extract + retry (tapetum sighting: 196/201 success, 5 hard `JSONDecodeError`, pervasive ```json fence wrapping per `tapetum-sighting-run-2026-07-01.md`). **Add to ops checklist (not code):** verify pod runs vLLM ≥0.21.0 with all three `deepseek_v4` parsers; prefer `--no-enable-flashinfer-autotune` if eval garbage appears (#41524). **Future backend hardening (optional):** read `message.reasoning`/`reasoning_content` when `content` is empty; pass `chat_template_kwargs.enable_thinking` explicitly for V4; strip nested markdown fences before `_extract_json`. Evidence: `MODELS.md` workaround table; `packages/whisker/research/tapetum-sighting-run-2026-07-01.md` §Weaknesses. Impact: Current workarounds cover the happy path on a correctly configured pod; gaps explain the 2.5% hard JSON failure rate and BPE false-fail edge case.

## False-pass hypothesis

RunPod serves V4-Pro without `--reasoning-parser deepseek_v4`. The model emits `<think>...long reasoning...</think>{"verdict":"pass",...}` entirely in `content`. `_strip_think_block` removes the think section, but reasoning text contained a `{` substring that confuses `_extract_json` depth counting, extracting a truncated inner object that validates as `Adjudication` with `verdict=pass` and empty `evidence_spans` — schema-valid, grounding vacuous, false pass.

## False-fail hypothesis

Pod runs vLLM ≥0.21 with `--reasoning-parser deepseek_v4` correctly; JSON lands in `content`, but the model wraps it in ` ```json ` fences (observed in tapetum sighting). `_FENCE_RE` strips opening fences; a trailing fence or a think-block remnant leaves `"line 49 column 17"` parse errors after both retry attempts — a structurally correct adjudication discarded as `JSONDecodeError`, demoting to `partial`/failure despite readable reasoning in the separate `reasoning` field we never inspect.

## What would change my mind

A RunPod deployment manifest (or live `GET /v1/models` + `GET /version` showing vLLM ≥0.21.0) confirming `--tokenizer-mode deepseek_v4 --reasoning-parser deepseek_v4 --tool-call-parser deepseek_v4`, plus a 30-day tapetum metric: ≥99% first-attempt Adjudication parse success, ≤1% responses with U+0120/U+010A in `evidence_spans`, and zero `content=None` + populated `reasoning` responses on the schema-in-prompt path — would upgrade verdict to **usable** and retire think-block stripping from hot-path concern.
