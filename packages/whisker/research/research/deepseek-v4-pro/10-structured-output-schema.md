# 10 - Structured-Output-Schema

**Verdict:** usable-with-conditions — V4-Pro can emit valid Adjudication JSON under our schema-in-prompt path, but vLLM thinking-mode serving bugs, the absence of constrained decoding, and V4's permanent thinking/tool_choice limits make first-attempt parse success materially below what constrained backends achieve; operational retries and pod version gates are mandatory.
**Confidence:** medium

## Findings

- [CRITICAL] Our production path is schema-in-prompt + free-text JSON extraction, not constrained decoding. `VllmThinkingBackend.run()` appends `_schema_instruction(output_type)` to the system prompt and parses JSON from streamed `delta.content` only (`packages/pipeline/src/pipeline/model_backends.py:285-362`). No `response_format`, no `guided_json`, no tool binding. Evidence: `00-baseline.md` §2; `MODELS.md` workaround inventory. Impact: Structural compliance depends on voluntary model cooperation plus regex/brace-depth extraction. Industry guidance and vLLM docs treat prompt-only JSON as "best effort" (~80–90% without enforcement) vs near-100% under constrained decoding (TECHSY 2026 structured-output guide; vLLM Structured Outputs docs).

- [CRITICAL] vLLM #41132 (fixed PR #41199, May 2026): with `response_format` + thinking enabled, valid JSON landed in the `reasoning` field while `content=None` on DeepSeek-V4-Pro. Reproducer used `--reasoning-parser deepseek_v4 --tokenizer-mode deepseek_v4`. Evidence: [vllm-project/vllm#41132](https://github.com/vllm-project/vllm/issues/41132). Impact: We do not use `response_format` today, but the same parser stack serves our RunPod pods. If the pod runs a pre-#41199 vLLM build, or if schema-in-prompt output is mis-routed to `reasoning` instead of `content`, our stream accumulator (`delta.content` only, lines 322–328) sees empty text and `_extract_json` fails. **Upgrade gate:** vLLM ≥ version containing #41199; smoke-test Adjudication with thinking enabled and verify JSON appears in extractable content, not only in `reasoning`.

- [HIGH] DeepSeek V4 rejects `tool_choice="required"` and dict function binding in permanent thinking mode (HTTP 400). Community report documents **~40% fallback to free text** when frameworks suppress `tool_choice` and rely on voluntary tool calls. Evidence: [deepseek-ai/DeepSeek-V3#1376](https://github.com/deepseek-ai/DeepSeek-V3/issues/1376); DeepSeek Oh My Pi guide (`supportsToolChoice: false`). Impact: Confirms we cannot migrate tapetum_llm to pydantic-ai tool-calling on V4-Pro without accepting ~40% structural refusal unless we add a multi-turn repair loop. Our schema-in-prompt path sidesteps `tool_choice` entirely but inherits the same "model may answer in prose" failure mode without server-side schema enforcement.

- [HIGH] Published JSON compliance rates for V4-Pro on **vLLM + thinking + nested schema** are sparse; nearest hard numbers are adjacent settings. DeepSeek API JSON mode (`response_format={"type":"json_object"}`) on V4-Flash: **997/1000 parseable (99.7%)**, 2 empty, 1 truncation — flat schema, official API, not our stack ([deepseekai.guide performance review](https://deepseekai.guide/reviews/deepseek-performance-review/), 2026). SOB benchmark (Apr 2026, vLLM, greedy, schema-in-prompt): all 21 models **≥84% JSON Pass Rate** on text; DS-R1-Distill-32B at **96.0%** — **V4-Pro not evaluated**. Gap between JSON Pass and Value Accuracy is 15–25 pp across all models ([arXiv:2604.25359](https://arxiv.org/html/2604.25359v1)). NVIDIA DGX Spark community harness on V4-Flash via vLLM: Structured Output category **67% (8/12)** on one recipe, **100% (2/2)** after parser/config fix ([NVIDIA forums TC-44–TC-65](https://forums.developer.nvidia.com/t/deepseek-v4-flash-official-fp8-running-across-2x-dgx-spark-tp-2-mtp-200k-ctx-recipe-numbers/370309?page=7)). Impact: Expect **high but not guaranteed** syntactic JSON on simple shapes; the 7-field Adjudication schema (nested `list[AxisFinding]`, `list[EvidenceSpan]`, enum literals) is materially harder. Budget **≥95% first-attempt parse** as an operational target; treat anything below as a pod/config defect until measured on our stack.

- [HIGH] Schema-in-prompt vs constrained decoding: SOB ablation (audio, n=115) shows constrained decoding moves JSON Pass +8–10 pp for some models but **Value Accuracy ±0.03 or less** — structural enforcement helps reliability of shape, not correctness of values (SOB Table 3). vLLM docs: `guided_json` / `response_format json_schema` enforce token-level validity; prompt-only `json_object` without schema dict still allows wrong keys/types ([vLLM Structured Outputs](https://docs.vllm.ai/en/stable/features/structured_outputs/)). vLLM reasoning table lists `deepseek_r1` and `deepseek_v3` with json/regex structured output support; **DeepSeek-V4-Pro requires `--reasoning-parser deepseek_v4`** and is not listed in the legacy compatibility matrix — unified parser #32713 still in progress (`MODELS.md`). Impact: We are on the weaker branch of the reliability ladder until unified parser or `guided_json` + reasoning-parser integration is validated on our pod. Constrained decoding would likely raise parse rate; it is not available in `VllmThinkingBackend` today.

- [MED] Thinking mode effects on structured output are net-negative for routing, mixed for quality. (1) **Token budget:** reasoning and JSON share `max_tokens`; `_RETRY_MAX_TOKENS_GROWTH` (1.5×) handles truncation (`model_backends.py:377–387`) but nested Adjudication on 7 axes can exhaust budget mid-`axis_findings`. (2) **Field routing:** thinking + structured output misroutes JSON to reasoning (#41132). (3) **MTP/spec-decode:** open issues #34650, #43388 can yield empty `content` and `reasoning_content` with markdown fences breaking extraction ([02-community-feedback-miner.md](02-community-feedback-miner.md)). (4) **Quality upside:** DeepSeek docs and vendor materials claim V4 improved agentic/JSON training over V3; thinking may improve verdict reasoning before JSON commit (`Adjudication.reasoning` field is first by design, `models.py:80`). Impact: Keep thinking enabled for triage quality, but treat serving config (MTP off or patched, parser version, `max_tokens` ≥16384) as part of the structured-output contract.

- [MED] The MODELS.md **5-field stability finding does not apply** to V4-Pro on our path. Measured May 2026 on **Qwen3-30B via Fireworks** with **constrained decoding** (tool calling): 3-field schemas showed high run-to-run variance; 5-field schemas stabilized claim counts; field *names* were irrelevant (`MODELS.md:35–53`). Mechanism: constrained decoding adds structural checkpoints per field. `VllmThinkingBackend` uses **schema-in-prompt without constrained decoding**; `Adjudication` has **7 top-level fields** plus nested objects — more prompt anchoring, no token-level gates. V4-Pro uses **`tokenizer-mode deepseek_v4`**, not Qwen BPE; the `unused1`/`unused2` RawClaim padding is a **Qwen3Backend** workaround only. Impact: Do not expect Qwen-style determinism from field count alone. The 7-field Adjudication layout may help prompt compliance but is unmeasured on V4-Pro; repeating the 10-run identical-paper experiment on alliance-pod would be the only valid test.

- [LOW] Internal retry budget is thin for structural refusal. `max_attempts = min(2, request_limit)` (`model_backends.py:300`); malformed JSON gets one conversational retry nudge; truncation gets `max_tokens` growth without context bloat. No retry for "valid JSON, wrong enum" beyond Pydantic `ValidationError` on same path. Impact: A model that emits `{ "verdict": "maybe" }` fails hard after two attempts; tapetum marks `partial` and demotes — acceptable for advisory lane, but inflates operational failure rate vs backends with `output_retries=3` on Agent path.

## False-pass hypothesis

V4-Pro returns syntactically valid Adjudication JSON with all 7 fields populated, `confidence: 0.81`, and `evidence_spans` containing plausible paraphrases that are not verbatim substrings. Schema extraction and Pydantic validation pass; `ground_spans` drops ungrounded quotes; if one span accidentally fuzzy-matches a nearby substring (`EVIDENCE_FUZZY_FLOOR = 0.90`), Decide accepts a structurally perfect but semantically wrong pass.

## False-fail hypothesis

V4-Pro emits valid JSON wrapped in `<think>` … `` … `{...}` but vLLM's reasoning parser splits incorrectly on an older build, placing the JSON only in the non-streamed `reasoning` field while `delta.content` stays empty. Backend raises `MalformedModelOutputError` after two attempts; tapetum marks the call failed despite the model having produced correct structured content in an unobserved channel.

## What would change my mind

Two weeks of alliance-pod telemetry on live tapetum triage: **≥98% first-attempt Adjudication JSON parse** (before retry), **≤2% MalformedModelOutputError** after retries, vLLM version logged per call, Adjudication schema unchanged — would upgrade verdict to **usable** and demote #41132/MTP concerns to historical footnotes.
