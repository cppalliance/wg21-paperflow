# 25 - Retry-Economist

**Verdict:** usable-with-conditions (+ retries and ideal ordering are priced correctly at ~3–4% of the 3003 s cold run; neither lever reaches the 5–10 min target without call elimination elsewhere)
**Confidence:** high

## Findings

- [CRITICAL] **55 model retries cost ~100 s fleet wall (~3.4% of 3003 s), not minutes.** Evidence: measured footer in `00-baseline.md:18-19,60-61`; counter via `_RetryCountFilter` matching `_RETRY_WARNING_MARKERS` (`cli.py:223-227,237-241`); implied ~20 s/call at 16 slots (`00-baseline.md:24-25`). Arithmetic: 55 × 20 s / 16 ≈ **69 s** (lower bound) to ~100 s (with retry context bloat). Impact: eliminating every retry saves **≤100 s** on the cold fleet; **quality risk: none** if retries preserve same validated output.

- [CRITICAL] **Retries are serial backend re-issues inside one `AgentBackend.run` call, not parallel or pydantic-ai `output_retries`.** Evidence: `max_attempts = min(2, request_limit)` loop (`model_backends.py:300-302`); tapetum judge path `run_judge_task` → `agent.run` (`judge_task.py:68-74`) with zero whisker `output_retries`/`ModelRetry`; ideal path inherits same budget via `run_task` → `agent.run` (`ideal_verify.py:151-158`, `tasks.py:57-64`). On JSON parse/validation failure the backend **appends** the failed assistant turn plus a user nudge before re-issuing (`model_backends.py:394-405`), so attempt 2 carries **inflated context** and pays **full decode latency again** (~20 s). Truncation retries re-issue with grown `max_tokens` without appending (`model_backends.py:377-393`). Transient API retries sleep then `continue` (`model_backends.py:341-350`). Impact: each counted retry ≈ **one extra full HTTP completion per call slot**; at 55 retries, **~55 duplicate decodes**, not overlapped work.

- [HIGH] **BPE corruption root cause is HF Transformers Metaspace pre-tokenizer leakage (U+0120/U+010A), not missing JSON grammar enforcement.** Evidence: `_clean_bpe` docstring cites HF [#45920](https://github.com/huggingface/transformers/issues/45920) (`model_backends.py:77-90`); retire condition in `MODELS.md:117-118`. Client applies cleanup before think-strip and JSON extract (`model_backends.py:95-106`). `VllmThinkingBackend` deliberately uses **schema-in-prompt + raw JSON extract**, not vLLM guided/structured output, because tool-calling and unified parser are broken on thinking models (`model_backends.py:227-232,285-286`). **Server-side guided JSON would constrain token *syntax*, not tokenizer decode artifacts inside string fields**, and olmOCR measured **12% retry rate while explicitly rejecting guided JSON** to avoid repetition collapse (`05-web.md:47-48`). Impact: upstream tokenizer fix or vLLM unified parser (`MODELS.md:118-120`) may shrink the `"Raw JSON parse failed"` class; **guided decoding alone will not eliminate retries** (truncation and `Transient API error` remain in `_RETRY_WARNING_MARKERS`, `cli.py:223-226`).

- [HIGH] **`IdealVerificationError` runs after the full source-aware cascade; reordering ideal verify first saves ≈10–13 calls, not ~24.** Evidence: `_attach_ideal` is invoked only after `judge_pdf_extraction` returns (`cli.py:1222-1239`) or after `adjudicate_paper` (`cli.py:1297-1317`); `verify_against_ideal` needs only `candidate_md` + `ideal_md` (`ideal_verify.py:134-159`). Fail-closed tombstone on any exception (`cli.py:1373-1387`, `_write_error_tombstone` `747-769`). Prior fleet forensics: **2/4** identified errors were `IdealVerificationError` after full PDF/text cascade (P4182R0 ≈ monolith+metadata+5 units+ideal; P4228R0 ≈ tier-1+units+ideal), **2/4** were early `PdfLaneError` before units (`research/tapetum-llm-throughput/07-retry-timeout-auditor.md:14-16`). v10 baseline reports **6 error** tombstones (`00-baseline.md:18-20`) but metadata census shows only **4 papers skipped metadata** (377 vs 381 first-pass, `10-call-graph-accountant.md:8`), so **≤2 ideal failures** can benefit from fail-fast; the other **≥4 errors fail mid-cascade** where ideal-first does nothing. Impact: ideal-first saves **~10–13 LLM calls (~200 s serial, ~12–15 s fleet wall)** on the ideal-failure subset only; **quality risk: LOW** for ordering (same checks, same fail-closed semantics) but **design tension** with "independent source judge first" (`ideal_verify.py:26-38`).

- [MED] **Ideal verification is a negligible fleet call class (≈4 papers, 1 success in prior census) but dominates wasted work on its failures.** Evidence: only four tomd ideals exist (`packages/tomd/tests/fixtures/golden/ideals/*.md`); call-graph accountant counts **~1 ideal call** in fleet (`10-call-graph-accountant.md:24,49`); ideal uses `run_task` through global `Semaphore(1)` (`ideal_verify.py:151`, `tasks.py:57`) unlike judge calls (`judge_task.py:10-15,63-66`). Impact: fail-fast helps **at most 2 error papers per measured pattern**, not all 6; **no material contribution to 5–10 min goal**.

- [MED] **Three distinct retry classes share one footer counter; BPE is only one hypothesized driver of `"Raw JSON parse failed"`.** Evidence: markers aggregate parse fail, truncation, and transient API (`cli.py:223-226`); backend branches (`model_backends.py:341-350,377-406`); batch-mode suppression comment attributes retries to "model token-corruption artifact, attempt 2 succeeds" (`cli.py:218-221`). Truncation path grows `max_tokens` by 1.5× (`model_backends.py:64-73,384-387`); judge agent caps at 1536 tokens (`cli.py:1029-1035`). Impact: server-side output-cap or thinking-token levers interact with truncation retries separately from BPE.

- [LOW] **Retry elimination is a rounding error vs call-graph levers.** Evidence: unit checks = 1510/2284 calls (~66%, `00-baseline.md:22-23`, `10-call-graph-accountant.md:8`); retries = 55 extra completions (~2.4% of base calls). Impact: even **zero retries** leaves **~2900 s** wall; speedup study must prioritize call elimination and per-call latency, not retry tuning.

## False-pass hypothesis

Adopting vLLM guided JSON on the judge lane to kill parse retries could trigger olmOCR-class **repetition collapse** on long structured outputs (`05-web.md:47-48`), producing schema-valid but truncated or degenerate `missing_content`/`defects` lists that pass pydantic yet omit real defects — a silent quality regression masked as fewer retries.

## False-fail hypothesis

Moving ideal verification before the source-aware cascade would still raise `IdealVerificationError` on fabricated multi-heading quotes (`ideal_verify.py:107-110`) and write the same error tombstone (`cli.py:1373-1387`), discarding work — but if implemented as "ideal fail → skip cascade" instead of "ideal fail after cascade," the **current fail-not-partial semantics** would change: papers like P4182R0 would never produce the independent PDF-judge `review` verdict already computed before ideal failed in prior runs (`research/tapetum-llm-throughput/07-retry-timeout-auditor.md:28`).

## What would change my mind

Per-call debug transcripts for all 55 retried completions tagging failure mode (BPE marker in raw content vs `finish_reason=length` vs `ValidationError` field path vs `APITimeoutError`) showing **>80%** are BPE/parse and **drop to near-zero** after a server tokenizer upgrade — would upgrade guided-decoding / upstream-fix from "partial" to "primary retry lever."
