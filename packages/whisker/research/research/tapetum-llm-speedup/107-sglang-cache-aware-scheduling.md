# 107 - sglang Cache-Aware Scheduling

**Verdict:** usable-with-conditions (+ client-side paper-affinity batching is portable on vLLM FCFS today; full radix benefit needs server `--schedule-policy lpm` or vLLM APC retention fix from 05-web Q1)
**Confidence:** high

## Findings

- [CRITICAL] SGLang's default cache-aware policy is **LPM (longest prefix match)**: before each prefill pass the scheduler walks the radix tree for every waiting request, sets `req.num_matched_prefix_tokens`, then sorts the waiting queue descending by that count so requests with the longest cached prefix run first. Evidence: `research/repos/sglang/python/sglang/srt/managers/schedule_policy.py:147-151,208-215,311-322` (`CacheAwarePolicy.LPM`, `_sort_by_longest_prefix`). vLLM/alliance-pod default is FCFS (`schedule_policy.py:157,791` default `"fcfs"`). Impact: on our 3003 s cold run, server-side LPM or client-side paper-affinity approximates what LPM does without migration; vLLM PR #43447 (05-web Q1) measured 0%→74.3% prefix hits and ~4.5× throughput at concurrency 16 on DeepSeek-V4-Pro — same model/slot count as us. Quality risk: **none** (scheduling order only; prompts unchanged).

- [CRITICAL] **In-batch prefix caching** further coalesces duplicate prefixes within the waiting queue: requests with ≤32 tokens matched against the global radix tree but ≥32 tokens matched against a simulated in-queue radix tree are **deprioritized** so only one request with a shared cold prefix prefills first (others reuse after insert). Evidence: `schedule_policy.py:73-86,261-309` (`IN_BATCH_PREFIX_CACHING_*`, `_compute_prefix_matches`). Impact: with FCFS + 32-paper interleave, this server-side optimization never activates for our workload (each paper's document prefix is unique). Paper-affinity waves create temporal batches where the mechanism could help if we migrate to SGLang. Quality risk: **none**.

- [HIGH] LPM **falls back to FCFS when waiting queue > 128**, explicitly to avoid expensive prefix matching at scale. Evidence: `schedule_policy.py:237-241`. Impact: at fleet scale (381 papers, 32 client workers) a SGLang server would degrade to FCFS during bursts — client paper-affinity still required. Quality risk: none.

- [HIGH] **Our dispatch pattern is anti-locality by design.** Client runs `_DEFAULT_CONCURRENCY = 32` papers via `asyncio.gather` + `asyncio.Semaphore(32)`; each worker holds its slot for the full serial chain (monolith → metadata → escalations → unit checks) but **32 different papers** therefore have 32 different in-flight requests on the server while `--max-num-seqs 16` (00-baseline:34-36,65-66). Evidence: `cli.py:127,1097-1112,1397-1398`; serial chain `pdf_judge.py:646-753`, `unit_judge.py:379+`. Impact: steady-state **32 unique document prefixes** compete for **16 KV-cache slots**; LRU/APC evicts paper A's call-*k* prefix before call-*k+1* arrives because up to 31 other papers' calls land in between (temporal distance ~20 s × interleaved arrivals). Expected prefix hit rate on calls 2–6 of the same paper: **≈0%** (scan-pollution / capacity argument from 05-web Q4 UniCache + gingerlabs shared-doc pattern). At ~2284 calls and ~20 s/call, even recovering prefill on 5/6 calls for half the papers (~5 s prefill saved × 5 × 190 papers / 16 slots) is **~300 s wall** (~10%); if vLLM retention fix restores 74% hits fleet-wide, upper bound approaches 05-web's ~4× prefill throughput contribution on the prefill-bound portion. Quality risk: **none** (ordering only).

- [HIGH] **Payload structure amplifies thrash.** Every unit check embeds the **full** `candidate_md` per call (`unit_judge.py:775-776`); monolith sends full PDF text + markdown (`pdf_judge.py:640-643`). Shared `CONVERSION_CONTRACT` (~3.7k chars) is identical across call types (`00-baseline:48-49`, `unit_judge.py:70+`) but a fresh `SRC{hex}` guard suffix breaks system-prompt tail identity each call (`pdf_judge.py:638-639`, `unit_judge.py:767-768`, `pipeline/tools.py:55-62`). Correct APC layout is `[static system+contract] + [guard — small tail delta] + [shared doc in user msg]`; interleaving still evicts the **document body** KV between serial calls of the same paper. Impact: paper-affinity is necessary even after moving guard tags; tag fix alone does not solve cross-paper eviction. Quality risk: none for affinity; guard-tag relocation is a separate lever (00-baseline:50-52).

- [MED] **Mixed prefill/decode batching** is opt-in: `enable_mixed_chunk` (default `False`, `server_args.py:924-928`) allows chunked prefill batches to `mix_with_running` active decode requests (`scheduler.py:1009-1012,2942,3108-3120`), improving GPU utilization when prefills and decodes would otherwise serialize. `PrefillAdder` passes `num_mixed_decode_tokens=running_bs` when mixed chunk is on (`scheduler.py:2942`, `schedule_policy.py:451,465-475`). Impact: not directly portable to vLLM CLI; marginal for our judge workload (short decode, long prefill). Quality risk: none.

- [MED] **MoE-specific request scheduling: not present.** Expert routing is handled inside the forward pass via token dispatchers (e.g. `layers/moe/token_dispatcher/standard.py:19-31,59-68`); the scheduler has no MoE-aware ordering policy. DeepSeek-V4 hybrid SWA/Mamba KV budgeting lives in `PrefillAdder` (`schedule_policy.py:496-535,622-665,1051-1088`) — memory admission, not expert selection. Impact: MoE batch-composition variance (00-baseline:96) is a **concurrency** risk, not solved by cache-aware scheduling. Quality risk: lowering concurrency for affinity may **reduce** MoE variance (fewer simultaneous prefills).

- [LOW] **Portable client design: paper-affinity batching.** (1) Set `--concurrency 16` to match server slots (`cli.py:127`, 00-baseline:66). (2) Replace flat `gather` with a **paper-finish-first** pool: maintain a FIFO of not-started papers but when a semaphore slot frees, prefer a paper already in-flight (has completed ≥1 call this run) over a cold paper — approximates LPM without server support. (3) **Wave mode** (simpler): process papers in stable-order groups of 16; each paper runs its full serial chain while the group holds ≤16 concurrent workers; next wave starts only when all 16 complete — bounds concurrent unique prefixes to 16 and minimizes inter-call gap to ≤15 foreign requests. (4) On SGLang migration: `--schedule-policy lpm` + optional `routing-key` policy (`schedule_policy.py:160-161,381-407`) if API exposes per-request routing keys. Cache-capacity math: with 16 slots and ~8–40k-token document prefills per call, radix/APC holds O(slots) hot document roots; at 32 papers **capacity/scans ratio ≈ 16/32 = 0.5** of slot-aligned working set → systematic eviction between serial calls; waves of 16 → ratio **16/16 = 1.0** (best case for LRU retention within a wave). Quality risk: **none**; same calls, same prompts, different dispatch order.

## False-pass hypothesis

Paper-affinity could hide a latency-dependent bug (e.g. rate-limit backoff ordering) that only manifests under 32-paper pile-up. No evidence such a bug exists in tapetum-llm today; monitor retry counts (55 on baseline) after affinity change.

## False-fail hypothesis

none found — dispatch reordering does not alter prompts, schemas, or serial per-paper semantics (`00-baseline:36-42`).

## What would change my mind

A/B on alliance-pod: same 381-paper cold run with (a) current c=32 interleave vs (b) c=16 paper waves, logging vLLM prefix-cache hit rate / prefill tokens from server metrics. If hit rate and wall time are unchanged, cache thrash is not a binding lever for this fleet.
