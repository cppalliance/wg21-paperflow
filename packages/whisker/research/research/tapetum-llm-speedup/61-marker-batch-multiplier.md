# 61 - marker-Batch-Multiplier

**Verdict:** usable-with-conditions (marker/surya GPU tensor batching and VRAM-scaled vLLM flags do not transfer to our remote DeepSeek judge; the portable levers are concurrent independent HTTP requests and very narrow same-task block grouping, both with RuVerBench-quality caveats on multi-rubric packing)
**Confidence:** high

## Findings

- [CRITICAL] **`batch_multiplier` does not exist** in marker or its surya dependency (rg over `research/repos/marker` and `research/repos/surya` returns zero hits). Local batching uses named env/settings instead: `DETECTOR_BATCH_SIZE`, `OCR_ERROR_BATCH_SIZE`, `FAST_LAYOUT_BATCH_SIZE`, `SURYA_INFERENCE_PARALLEL`, plus server-side coalescing knobs (`*_SERVER_BATCH_WAIT_MS`, `*_SERVER_MAX_BATCH`). Evidence: absent symbol; surya settings at `surya/settings.py:117-191`. Impact: **0 s** from chasing a non-existent knob; tapetum should map to our `--max-num-seqs` / client concurrency, not `batch_multiplier`. Quality risk: none.

- [CRITICAL] **VLM layout/recognition “batching” = N concurrent one-image HTTP completions, not one multi-page prompt.** Layout builds one `BatchInputItem` per page and calls `manager.generate(batch)` (`surya/layout/__init__.py:58-67`). Block-mode recognition flattens all block crops across pages into a batch list but each item still becomes its own `chat.completions.create` via `ThreadPoolExecutor` (`surya/recognition/__init__.py:179-204`, `surya/inference/backends/openai_client.py:158-215`). Marker passes full page lists to surya layout in one call (`marker/builders/layout.py:136-138`). Impact: Direct analog for tapetum is **in-paper parallel unit checks** (≤5 independent POSTs), not packing N page rubrics into one prompt. With ~1510 serial unit calls today, overlapping 5-wide could shave ~60–80% off the unit-check slice (~900–1200 s of the 3003 s run if unit phase is ~40% of wall) → **~360–720 s fleet saving** if decode-bound and slots free; **0 s** if server already saturated at 16 seqs. Quality risk: MoE batch-composition variance (00-baseline); unrelated to marker’s local GPU batch fill.

- [HIGH] **VRAM-aware vLLM server sizing (surya backend, used by marker balanced/fast).** On spawn, `_gpu_settings()` scales `max_num_batched_tokens` and `max_num_seqs` linearly from a 24 GB baseline (8192 tokens, 32 seqs); e.g. B200 (180 GB) → ~64k batched tokens, 240 seqs, capped client auto-parallel at 96 (`surya/inference/backends/vllm.py:28-60,84-89,140-173`). README documents balanced sustains **2.9 pg/s** vs **~0.3 pg/s** single-stream on one B200 (`marker/README.md:469-479,524-528`). Impact: **Not portable** — we already run remote vLLM with fixed `--max-num-seqs 16`; raising it regressed +60% wall (00-baseline measured negative). Quality risk: N/A for tapetum judge path.

- [HIGH] **Detection / OCR-error / fast-layout use device-default micro-batches + shared servers.** Text detection defaults cuda batch 36, overridable via `DETECTOR_BATCH_SIZE` (`surya/detection/__init__.py:32-33,98-103`). OCR-error server defaults cuda 64 (`surya/ocr_error/__init__.py:25-26`); marker overrides caller-side to **14 cuda / 4 cpu** when unset (`marker/builders/line.py:25-29,192-197,262`). Fast layout server coalesces pages within **5 ms** wait window (`surya/settings.py:185-191`). Marker workers hold **no GPU models**; heavy work POSTs to shared servers (`marker/models.py:23-60`). Impact: **0 s** on tapetum-llm (no local torch inference on judge path). Quality risk: none.

- [HIGH] **Cross-worker concurrency budgeting (marker production pattern).** Default worker count = `min(cores-2, ceil(SURYA_INFERENCE_PARALLEL × 1.5))` (`marker/utils/batch.py:8-29`). Parent sets per-worker `SURYA_INFERENCE_PARALLEL = ceil(capacity × 1.5 / workers)` so aggregate in-flight ≈ **1.5× server capacity**, not N×capacity (`marker/scripts/convert.py:201-212`; README `marker/README.md:160-161`). Benchmark harness drives **48 workers** against one surya server (`benchmarks/inference.py:20-25,176-179`). Impact: Fleet-level analog = our **32-paper gather** already oversubscribes the pod; missing piece is **within-paper** parallel unit dispatch. Porting marker’s 1.5× oversubscribe per paper (5 checks × fleet) adds ~0–15% if 16 seq slots already full. Quality risk: queue latency/timeouts, not verdict drift from batching itself.

- [HIGH] **Remote LLM (`--use_llm`): default is one API request per block; concurrency only via thread pool.** `BaseLLMProcessor.max_concurrency = 3` (`marker/processors/llm/__init__.py:42-45`). `LLMSimpleBlockMetaProcessor` submits **one `llm_service()` future per block prompt** across all simple processors (`marker/processors/llm/llm_meta.py:44-73`). `BaseLLMComplexBlockProcessor` same pattern per block (`marker/processors/llm/__init__.py:163-172`). Gemini service increments `llm_request_count=1` per call (`marker/services/gemini.py:79-92`). Impact: Marker does **not** batch unrelated blocks into one remote call except the exceptions below. Tapetum already matches “1 rubric = 1 call”; copying marker means **parallel calls**, not prompt packing → up to **~4× unit slice** (see finding 1), **~15–25%** on 3003 s cold run under favorable slot availability. Quality risk: low for parallel-only; high for packing (RuVerBench, 05-web Q5).

- [MED] **Two intentional “multi-block in one call” LLM processors (quality-motivated grouping, not throughput-first).** (a) `LLMPageCorrectionProcessor` sends **all blocks on one page** as one JSON list + one page image per request (`marker/processors/llm/llm_page_correction.py:150-159,283-288`). (b) `LLMTableMergeProcessor` sends **two adjacent table images + both HTML tables** in one prompt to decide merge direction (`marker/processors/llm/llm_table_merge.py:314-328,55-57`). (c) `LLMTableProcessor` **splits** large tables into row chunks of `max_rows_per_batch=60`, each chunk = separate call (`marker/processors/llm/llm_table.py:23-26,143-170`) — chunking for accuracy, not call reduction. Impact: Packing 5 tapetum unit rubrics into one call could cut ~1510 → ~302 unit calls (~**−80% unit-call count**, ~**600–960 s** if linear) but RuVerBench reports **double-digit drops** batching 4–5 rubrics on long-context tasks (05-web Q5). Expected net: **high verdict-drift risk**; not recommended without A/B on 381-paper baseline. Quality risk: **HIGH** for multi-unit packing; **LOW** for table-merge-style tightly coupled pairs only.

- [LOW] **Documented throughput anchors for comparison.** olmOCR-bench on one B200: marker balanced **76.0** score @ **2.9 pg/s**, fast **66.6** @ **7.4 pg/s**, fast-no-OCR **43.6** @ **23.7 pg/s** (`marker/README.md:465-475,524-528`). olmOCR-Bench overall marker **76.1** vs our domain N/A (05-web Q2 cites marker 76.1). Impact: Marker’s speed comes from **VLM call elimination + concurrent pages**, not from multi-block LLM prompts. Tapetum cannot eliminate judge calls without router precision (70% zero-defect checks, 00-baseline). Quality risk: N/A.

## False-pass hypothesis

Adopting marker-style **multi-unit prompt packing** (like `LLMPageCorrectionProcessor`’s full-page JSON) for tapetum unit checks hides a defect on page 3 because the model attends to pages 1–2 rubric noise and returns empty defect groups for page 3, matching our 70% zero-defect rate but **missing the 16/381 papers** whose merged verdict changes (~143 calls/paper, 00-baseline) — silent quality regression consistent with RuVerBench multi-rubric degradation (05-web).

## False-fail hypothesis

Adopting marker/surya-style **client concurrency=3** default (`max_concurrency=3`) without raising tapetum fleet/in-paper parallelism under-fills DeepSeek `--max-num-seqs 16` during monolith-heavy papers, inflating queue wait and pushing marginal unit checks into `UNIT_CHECK_TIMEOUT_SECONDS=120` false failures (00-baseline implied ~20 s/call vs 120 s cap).

## What would change my mind

A 381-paper cold replay with **in-paper parallel unit checks** (marker/surya concurrent-HTTP pattern, concurrency=5, payloads unchanged) showing **zero merged-verdict drift** vs v10 serial baseline and ≥30% wall reduction on the unit-check slice would upgrade the concurrent-HTTP lever to fully **usable**; a controlled multi-unit pack (2–5 rubrics/call) showing **<1% verdict drift** would upgrade prompt-packing to **usable-with-conditions**.
