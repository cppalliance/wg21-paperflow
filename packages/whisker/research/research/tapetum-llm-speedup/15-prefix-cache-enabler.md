# 15 - Prefix-Cache-Enabler

**Verdict:** usable-with-conditions — server-side APC plus prompt reorder and a per-paper guard tag can recover hundreds of seconds on the 3003 s cold run, but prefix caching alone cannot reach the 5–10 min target without call-count levers.
**Confidence:** high

## Findings

- [CRITICAL] **Per-call random guard tag breaks identical leading tokens on every one of ~2284 calls.** Each call draws `tag = f"SRC{secrets.token_hex(4)}"` and appends `guard_instruction(tag)` to the system prompt (`unit_judge.py:767-768`, `unit_judge.py:244-245`, `pdf_judge.py:638-639`, `pdf_judge.py:387-388`). `guard_instruction` embeds the tag in the system suffix (`pipeline/tools.py:55-61`), so the static ~3.7k-char `CONVERSION_CONTRACT` prefix matches only up to the last ~40–60 tokens; every call also opens user blocks with a fresh `<<<{tag}>>>` delimiter (`pipeline/tools.py:49-52`, `unit_judge.py:774-776`). Impact: at concurrency 16 on DeepSeek-V4-Pro, unfixed APC yields **0% prefix hits** ([vLLM PR #43447](https://github.com/vllm-project/vllm/pull/43447)); even with the fix, per-call tags prevent delimiter-level identity across the 6-call paper cascade. Quality risk: none (tag is transport-only).

- [CRITICAL] **Unique unit metadata precedes the shared full document, zeroing cross-unit KV reuse.** `_check_one_unit` builds `user_msg` as Paper → Unit → Risk signal → SOURCE TEXT → CANDIDATE MARKDOWN (`unit_judge.py:769-776`). APC matches only identical *leading* token sequences ([05-web.md Q4](research/tapetum-llm-speedup/05-web.md), [vLLM APC design](https://docs.vllm.ai/en/latest/features/automatic_prefix_caching/)). The full `candidate_md` (~5k–80k+ tokens, sent on all ~1510 unit checks per `00-baseline.md:43-47`) diverges before it starts because `Unit:` / `Risk signal:` / per-unit source text differ. Impact: **5 serial unit checks per paper re-prefill the entire markdown 5×** despite serial execution (`unit_judge.py:389-416`, `00-baseline.md:36-42`). Restructure per Q4: `[static system + per-paper tag]` → `[Paper: pid]` → `[CANDIDATE MARKDOWN wrapped once]` → `[unique Unit/Risk/SOURCE last]`. Quality risk: low but unmeasured; model task text stays identical, only block order changes — needs holdout A/B before fleet deploy.

- [HIGH] **Six call types cannot share one full-document KV block today because system prompts diverge at token 0.** Monolith (`JUDGE_SYSTEM_PROMPT`, `pdf_judge.py:180-213`), metadata (`METADATA_CHECK_SYSTEM_PROMPT`, `unit_judge.py:114-127`), page escalation (`PAGE_JUDGE_SYSTEM_PROMPT`, `pdf_judge.py:215-250`), and unit check (`UNIT_CHECK_SYSTEM_PROMPT`, `unit_judge.py:129-159`) share `CONVERSION_CONTRACT` but differ in task headers and output schemas. Impact: even with per-paper tags and user reorder, **only calls sharing the same system prompt** (e.g. unit checks 2–5 within one paper, or page escalations 2–N) can share the candidate-markdown prefix; monolith + metadata + unit cannot share from the first token. Cross-type sharing would require a unified system stub plus call-specific instructions moved to the user tail — out of scope for a tag-only fix. Quality risk: high if system prompts are collapsed without rubric testing.

- [HIGH] **Page escalations repeat the same anti-pattern.** `_escalate_page` uses per-call random tag (`pdf_judge.py:387-388`) and places one page's raw text before full `tomd_md` (`pdf_judge.py:389-395`), mirroring the unit-check failure mode. Only ~16 escalations fleet-wide (`00-baseline.md:23`), so impact is small in absolute seconds but confirms the pattern is systemic. Impact: **negligible on 3003 s wall** (~16 calls); fix is free when restructuring unit checks. Quality risk: none at current volume.

- [HIGH] **DeepSeek-V4-Pro on `alliance-pod` at `--max-num-seqs 16` matches the 0%→74% APC regression testbed.** Our model, concurrency, and MoE class match [PR #43447](https://github.com/vllm-project/vllm/pull/43447) and the [official DeepSeek-V4-Pro recipe](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4-Pro) (`00-baseline.md:65-66`, `05-web.md Q1`). Without the retention fix, APC overhead can *hurt* throughput (~36.7% hash-management overhead with no shared prefixes, [05-web.md Q4 squeezebits card](research/tapetum-llm-speedup/05-web.md)). Impact: enabling APC without PR #43447 + retention env may yield **0% hits and wasted overhead**; with fix, trace replay shows **~4.5× server throughput** (44→196 tok/s) at 74.3% hit rate — upper bound when prompts are restructured to share. Quality risk: none (KV reuse is bitwise-identical prefix replay).

- [MED] **Security tradeoff: per-paper deterministic tag vs per-call random tag.** Pipeline's `StepContext` uses one `_guard_tag` per pipeline *run* (`pipeline/runner.py:117-126`); tapetum_llm uses one tag per *call* (`secrets.token_hex(4)` at every call site above). Per-call random maximizes prompt-injection isolation: a delimiter forged in `candidate_md` cannot reuse a tag seen in an earlier call on the same paper (defense layered on `escape_guard_delimiters`, `pipeline/tools.py:38-46`, and CLAUDE.md prompt-injection rules). Per-paper deterministic tag — e.g. `SRC{sha256(pid)[:8]}` — is **required** for identical system+delimiter prefixes across all 6 calls, but means all calls on one paper share one namespace; forgery attempts targeting that tag affect every wrapped block on that paper (still escaped, but a single escape bug scales to the whole cascade). Impact: per-paper tag is the right speed tradeoff if `escape_guard_delimiters` is trusted (it is today). Quality risk: none; security risk: low, conditional on escape correctness — do not drop per-call random without a security review of edge-case delimiter collisions.

- [MED] **Concrete server-side config for `alliance-pod`.** Deploy on the vLLM launch (H200 recipe baseline from [recipes.vllm.ai](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4-Pro)): keep `--max-num-seqs 16`, add `--enable-prefix-caching`, set env `VLLM_PREFIX_CACHE_RETENTION_INTERVAL=32768` ([PR #43447](https://github.com/vllm-project/vllm/pull/43447)), retain `--kv-cache-dtype fp8` if already set. Verify pod runs a vLLM build containing the DeepSeek V4 selective retention merge. Client-side: **no API changes** for server-only win; whisker changes needed for unit-check reorder + per-paper tag. Impact: server-only unlocks shared static-system caching across ~2284 calls (~925 tokens × hit rate); prior internal estimate **60–180 s** on 3003 s (`research/tapetum-llm-throughput/SYNTHESIS.md:80-81`, `tapetum_llm.md:309`). Quality risk: none.

- [LOW] **Estimated total saving on the 3003 s cold run (prefix levers only).** Decompose: (1) server APC on static system suffix only: **60–180 s** (2–6%); (2) per-paper tag (identical system+delimiters across 6 calls/paper): **+30–60 s**; (3) user reorder so ~1129 of 1510 unit checks (calls 2–5 per paper) hit cached `candidate_md` prefill — at ~60–70% prefill share of ~20 s/call (`00-baseline.md:24-28`) and ~75% of unit calls cacheable: **+500–900 s** (17–30%). **Combined prefix-cache envelope: ~600–1100 s (20–37%) → projected wall ~1900–2400 s (~32–40 min)**, still above the 5–10 min target. [PR #43447](https://github.com/vllm-project/vllm/pull/43447) throughput multiplier applies under heavy prefix overlap and concurrent load; it does not linearly translate to fleet wall when decode (~70 tok/s, `pdf_judge.py:27`) remains ~2–4 s/call. Quality risk: none for server config; low-unmeasured for reorder (see finding 2).

## False-pass hypothesis

Reorder `candidate_md` before unit-specific source text so APC hits rise: the model may overweight document-global context and under-attend to the bounded SOURCE TEXT block, missing localized qualifier omissions that the current source-first layout surfaces. A holdout paper where defects live in a single page's table footnotes could flip unit-check `pass` → silent miss while fleet wall time drops.

## False-fail hypothesis

Keeping per-call random tags for "security" while enabling APC: zero cross-call sharing persists, operators believe prefix caching is "enabled," and no wall-time improvement materializes — the fleet stays at ~3003 s with added APC hash overhead ([05-web.md Q4](research/tapetum-llm-speedup/05-web.md)), falsely suggesting the speedup study failed when the config was never cache-aligned.

## What would change my mind

A measured A/B on the 48-paper holdout (`whisker/CLAUDE.md` dev-replay / holdout strata): same `_LANE_VERSION`, same 381-paper fleet concurrency, variant = per-paper tag + unit-check user reorder + server APC/retention fix vs control, reporting verdict diff rate and wall time. If verdict diffs exceed the advisory lane's documented ~25% flip budget or wall savings are <300 s, downgrade to garbage for the reorder lever and keep server-only APC.
