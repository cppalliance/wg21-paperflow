# 71 - olmocr-Concurrency-Model

**Verdict:** usable-with-conditions — olmOCR's deep-client / shallow-server queue architecture (client semaphore ≫ vLLM `max-num-seqs`) is the portable lesson; the literal `1600` default and page-level TaskGroup fan-out do not transfer to our MoE judge at 16 slots without measured quality proof, and deeper queueing past c=32 is expected to hurt or stall, not close the 3003 s gap.
**Confidence:** high

## Findings

- [CRITICAL] **Global client semaphore defaults to 1600; every HTTP completion acquires it once.** Evidence: module init `max_concurrent_requests_limit = asyncio.BoundedSemaphore(1)` (`olmocr/pipeline.py:88`); CLI default `--max_concurrent_requests 1600` (`olmocr/pipeline.py:1202`); reassigned in `main()` to `asyncio.BoundedSemaphore(args.max_concurrent_requests)` (`olmocr/pipeline.py:1267`); held for the full POST in `try_single_page` (`olmocr/pipeline.py:181-182`). Impact: olmOCR intentionally allows up to 1600 in-flight HTTP requests regardless of worker count; this is a **client-side admission cap**, not the GPU batch size. Our equivalent today is `_DEFAULT_CONCURRENCY = 32` papers × **1 serial LLM call** = **32 max in-flight** (`cli.py:127`, `00-baseline.md:34-38`). Quality risk: none from the comparison itself.

- [CRITICAL] **Within-document and within-work-item parallelism is aggressive; workers=20 only bounds queue consumers.** Evidence: `--workers` default 20 spawns 20 async `worker()` tasks (`olmocr/pipeline.py:1201`, `1435-1437`); each worker pulls one work item then opens `asyncio.TaskGroup` over all PDF paths in that item (`olmocr/pipeline.py:697-704`); each PDF opens another TaskGroup over **all pages** `1..num_pages` concurrently (`olmocr/pipeline.py:538-541`); tarball paths add a third TaskGroup over extracted PDFs (`olmocr/pipeline.py:499-500`). Work items target ~500 pages each via `--pages_per_group` default 500 (`olmocr/pipeline.py:1198`, `1292-1293`, `1382-1386`). Impact: theoretical fan-out ≈ **20 workers × ~50 PDFs × ~10 pages ≈ 10⁴ page tasks**, all gated only by the 1600 semaphore — the architecture assumes **many independent page OCR calls** and a server that can absorb a deep waiting queue. Our tapetum chain is **6 serial calls/paper** with shared full-document prefill (`00-baseline.md:22-47`); copying page-level TaskGroups would change call semantics, not just scheduling. Quality risk: HIGH if ported verbatim (MoE batch-composition variance, `20-in-paper-parallelist.md:16-17`).

- [CRITICAL] **olmOCR does NOT set `--max-num-seqs` in its bundled vLLM launch; dense 7B + short context inherits vLLM defaults (~128 slots on v0.11.2).** Evidence: `vllm_server_task` builds `vllm serve` with `--port`, `--tensor-parallel-size` (default 1), `--data-parallel-size` (default 1), `--max-model-len` (CLI default **16384**, `olmocr/pipeline.py:1233`), `--limit-mm-per-prompt`, optional `--gpu-memory-utilization`, then **`unknown_args` passthrough only** (`olmocr/pipeline.py:792-819`) — no `--max-num-seqs` anywhere in repo grep. Model default `allenai/olmOCR-2-7B-1025-FP8` (`olmocr/pipeline.py:1191-1192`); pinned `vllm==0.11.2` (`olmocr/pyproject.toml` gpu extra). vLLM 0.11 scheduler default `DEFAULT_MAX_NUM_SEQS = 128` when unset. Contrast: our judge pod runs **MoE** `deepseek-v4-pro` at **`--max-num-seqs 16`** with **393k** context (`00-baseline.md:65-66`, `05-web.md:13-17`). Impact: olmOCR's **1600/128 ≈ 12× client overfill** targets a **dense 7B** that can actually schedule ~8–128 concurrent sequences on one GPU; our **32/16 = 2× overfill** already matches measured sweet spot (`cli.py:122-126`, 692.3 s at 381 papers). Blindly raising client depth toward 1600 on 16 MoE slots does not add decode capacity. Quality risk: MEDIUM (deeper queues inflate TTFT and MoE batch variance without more running sequences).

- [HIGH] **olmOCR monitors vLLM server queue depth and uses it for retry scheduling, proving the design is queue-aware.** Evidence: `vllm_server_task` parses vLLM log lines `Running: (\d+)` and `(?:Waiting|Pending):\s*(\d+)` into globals `last_running_req`, `vllm_queued_requests` (`olmocr/pipeline.py:853-865`); non-rotation retry path fires **parallel** remaining attempts when `vllm_queued_requests == 0` (`olmocr/pipeline.py:337-354`). Impact: they treat an **empty server waiting queue** as slack to burn extra parallel retries; a deep client queue is meant to keep `Waiting > 0` during steady-state OCR. Our client has no server-queue feedback loop; we rely on paper-level semaphore only (`cli.py:1112-1113`). Portable pattern: **metrics on `num_requests_running` / `num_requests_waiting`** (05-web.md Q3) before deepening queues. Expected saving: diagnostic only, **0 s** until paired with more server slots or fewer calls.

- [HIGH] **Effective queue depth ratio is the mechanism, not the absolute 1600.** Steady-state: client permits up to 1600 in-flight HTTP; server runs up to ~128 sequences (vLLM default); ~1400 requests sit in vLLM's FCFS waiting queue or client await. When one page decode finishes, the next prefilled request is already admitted — **continuous batching keeps the prefill/decode pipeline fed** without client idle bubbles. Our measured regime: **32 client / 16 server = 2× overfill** eliminated ~4% wall vs c=16 (`cli.py:125-126`); **server 16→32 regressed +57%** because MoE decode cost scales with concurrent expert union, not slot count alone (`00-baseline.md:82`, `research/slots-32-regression/11-moe-batch-scaling.md:8`). With in-paper parallelism (persona 20): **32 papers × W≤12 parallel calls ≈ 384 client depth** (`20-in-paper-parallelist.md:10`, `constants.py:191,223`) — **24× server overfill**, closer to olmOCR's ratio but still capped at **16 running sequences**. Impact: deeper queueing might trim **intra-paper slot idle** (~0 s on 381-paper fleet per slot-second accounting, `20-in-paper-parallelist.md:12-13`) but **cannot beat 2284 × ~20 s / 16 ≈ 2855 s** (`00-baseline.md:22-25`). Quality risk: HIGH at 384 depth (MoE flip rate ≥25%, heterogeneous batch shapes from monolith + unit full-markdown prefills, `20-in-paper-parallelist.md:16-20`).

- [MED] **Separate CPU render semaphore prevents client-side thrashing; LLM concurrency is decoupled from PDF rasterization.** Evidence: `pdf_render_max_workers_limit = asyncio.BoundedSemaphore(cpu_count - 2)` (`olmocr/pipeline.py:87`); `build_page_query` acquires it before `render_pdf_to_base64png` (`olmocr/pipeline.py:108-110`). LLM gate is independent (`olmocr/pipeline.py:181`). Impact: olmOCR separates **CPU-bound page prep** from **GPU-bound inference queueing**; our PDF prep (`extract_page_units`, `screen_pages`) runs inside the paper semaphore (`cli.py:1120`, `pdf_judge.py:662-668`) — hoisting prep before parallel LLM waves is orthogonal (~≪1% fleet, `20-in-paper-parallelist.md:22`). Quality risk: none.

- [MED] **olmOCR uses raw asyncio HTTP (`apost`) specifically to avoid httpx pool deadlocks at 100M+ request scale.** Evidence: comment at `olmocr/pipeline.py:371-374`; one connection per request with `Connection: close` (`olmocr/pipeline.py:407-410`). Impact: explains why 1600-wide concurrency is viable for them (no shared connection pool); our stack uses `AsyncOpenAI`/httpx through `pipeline` with c=32 tested, c=381 **proxy-killed 257/381** (`cli.py:130-131`). Pushing toward 200+ concurrent connections on RunPod is **infrastructure-risky** regardless of vLLM scheduler. Quality risk: operational (timeouts/errors), not verdict drift.

- [LOW] **Reported throughput (3050 output tok/s, 1288 pages in 5m07s on H100) assumes this concurrency model on dense 7B, not our judge workload.** Evidence: `05-web.md:37-40` citing olmOCR technical report; page `max_tokens=8000` (`olmocr/pipeline.py:105`) vs our unit-check cap 1536 (`00-baseline.md:27-28`). Impact: confirms olmOCR optimizes **many short-ish independent VLM decodes**; our bottleneck is **few long-context MoE prefills per paper**. No direct wall-clock transfer to 3003 s cold fleet.

## False-pass hypothesis

Adopting olmOCR-style client depth (~384 via in-paper parallel + c=32) on MoE `max-num-seqs 16`: a heterogeneous batch (monolith + five full-markdown unit checks from different papers co-scheduled) shifts expert routing enough that a borderline table defect clears on unit 3 while the serial baseline would have flagged `review` — silent advisory false-pass on a conversion the operator trusts because LLM findings demoted deterministic pass (`20-in-paper-parallelist.md:24-26`, `52-docling-parallelism.md:28`).

## False-fail hypothesis

Matching olmOCR's `1600` client cap on a 16-slot MoE pod without extending httpx/read timeouts: tail papers sit in vLLM FCFS queue **700+ s** before first token (`research/concurrency-381/10-vllm-scheduler.md:14`) while the paper still holds a concurrency slot until `APITimeoutError` — coverage marked incomplete → advisory `review` cap on a clean conversion (`20-in-paper-parallelist.md:28-30`).

## What would change my mind

A live A/B on the 381-paper cold corpus: **(A)** current c=32 serial in-paper vs **(B)** c=32 with max in-paper parallel (W≤12) vs **(C)** client depth ~200+ (e.g. c=64 or dual-wave), all on the same `--max-num-seqs 16` MoE pod, reporting fleet wall within ±5% **and** merged-verdict flip rate ≤2 pp on the 16 baseline-changed papers (`00-baseline.md:29-30`) — would upgrade deep-queue levers from "harmful/neutral" to "material." Without that, slot-second accounting and the slots-32 regression stand.
