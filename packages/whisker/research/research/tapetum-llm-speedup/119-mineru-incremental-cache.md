# 119 - mineru-Incremental-Cache

**Verdict:** usable-with-conditions — MinerU validates in-process model warmup and hybrid stage separation, but ships no document-level incremental skip and no default KV/prefix-cache server flags.
**Confidence:** high

## Findings
- [HIGH] No output-existence or content-hash skip on re-parse: every API task gets a fresh UUID output directory and always runs full inference. Evidence: `mineru/cli/fast_api.py:880-881` (`task_id = str(uuid.uuid4())`, `create_task_output_dir(task_id)`), `mineru/cli/fast_api.py:822-867` (`run_parse_job` always calls `do_parse`/`aio_do_parse`). Impact: zero wall savings on our 3003 s cold fleet (381 papers always re-judged today anyway); confirms whole-paper fingerprint skip is already ahead of MinerU, but per-unit fingerprint remains our unique lever (~potentially large if a changed markdown touches 1 page not 6 calls). Quality risk: low if fingerprint covers inputs + model version.
- [HIGH] In-process model singletons eliminate per-request cold load within a long-lived worker: VLM `ModelSingleton` keyed by `(backend, model_path, server_url)` at `mineru/backend/vlm/vlm_analyze.py:43-61,248-252`; pipeline `ModelSingleton` at `mineru/backend/pipeline/pipeline_analyze.py:33-58`; atom/hybrid singletons at `mineru/backend/pipeline/model_init.py:148-187,294-317`. Impact: saves seconds-to-minutes of init per worker session, not our ~2284-call decode-bound wall (~2855 s modeled in 00-baseline). Quality risk: none (same models, same weights).
- [HIGH] Explicit VLM warm-up at API/Gradio startup via `--enable-vlm-preload` / `MINERU_API_ENABLE_VLM_PRELOAD`: preload path `mineru/cli/vlm_preload.py:78-85` calls `ModelSingleton().get_model(...)`; wired at `mineru/cli/fast_api.py:247-253,270-273` and documented `docs/en/usage/quick_usage.md:51`. Impact: removes first-request cold-start latency in server mode; analogous to our 24/7 alliance-pod (already warm). Does not cut per-call prefill/decode. Quality risk: none.
- [MED] Intermediate `middle.json` artifact separates inference from final Markdown rendering when `client_side_output_generation=true`: server forces `return_md=false`, `return_middle_json=true` at `mineru/cli/api_request.py:226-231`; client regen from cached middle JSON at `mineru/cli/client_side_output.py:44-97`; server skips `finalize_middle_json` when client will finalize at `mineru/backend/vlm/vlm_analyze.py:513-514`, `mineru/backend/pipeline/pipeline_analyze.py:120-128`. Impact: bandwidth/CPU split within one run, not cross-run reuse — no savings on re-parsing same document. For tapetum: precedent for sidecar-first workflow, not judge-call elimination. Quality risk: MED if client-side finalize diverges from server finalize path.
- [MED] Hybrid backend decouples layout detection (pipeline small model) from VLM content recognition within processing windows, reusing layout model instance per window: `mineru/backend/hybrid/hybrid_analyze.py:663-681` (`_predict_layout_for_window` via `HybridModelSingleton`, comment at 669: "returns reusable small-model instance"). Layout and VLM run sequentially per window, not cached separately across runs. Impact: architectural precedent for scoped payloads (layout/page context before content LLM) rather than shipping full document 6× — supports our payload-scoping lever, not a direct cache. Quality risk: MED if layout stage misses region that VLM-only path would catch.
- [MED] FastAPI "caching" is task-result retention for async polling, not parse deduplication: completed tasks kept `MINERU_API_TASK_RETENTION_SECONDS` default 86400 s (`mineru/cli/fast_api.py:321-326,1184-1203`, `docs/en/usage/cli_tools.md:171-173`), then output dirs deleted. Each new upload still re-infers. Impact: zero on cold fleet throughput. Quality risk: none.
- [LOW] Model weight download cache via local path existence + `@lru_cache` on HuggingFace snapshot: `mineru/utils/models_download_utils.py:151-164,253-276`. Install-time only. Impact: irrelevant to 3003 s judge run. Quality risk: none.
- [LOW] vLLM server launcher does NOT enable prefix/KV cache by default; only injects port, gpu-memory-utilization, logits-processors: `mineru/model/vlm/vllm_server.py:44-53`. Device-specific override explicitly DISABLES prefix caching on kxpu via `--no-enable-prefix-caching`: `mineru/backend/vlm/utils.py:145,212-214`. VLM framework migrated sglang → vLLM (`docs/en/reference/changelog.md:131`); no radix-cache or `--enable-prefix-caching` defaults found anywhere in repo. LMDeploy server sets `--cache-max-entry-count 0.5` (memory fraction, not RadixAttention): `mineru/model/vlm/lmdeploy_server.py:52-53`, engine default `mineru/backend/vlm/vlm_analyze.py:181-182`. Impact: MinerU is NOT production precedent for cache-enabled document VLM at scale; our APC lever rests on vLLM docs (05-web Q1/Q4), not MinerU shipping config. Quality risk: N/A for MinerU itself.

## False-pass hypothesis
Adopting per-unit fingerprint skip (gap MinerU also lacks) could false-pass if a cosmetic markdown edit on page N shifts paragraph boundaries read by a unit check on page N+1 that still fingerprinted unchanged: we'd skip a check whose effective context changed without the fingerprint knowing.

## False-fail hypothesis
Copying MinerU's server-side `finalize_middle_json` deferral without equivalent client-side postprocess would false-fail good conversions (over-flagging title levels or table merges) if we ever split judge finalize to client — not our current architecture, but the split-stage pattern carries this risk.

## What would change my mind
A current MinerU docker/compose or vLLM launch recipe that sets `--enable-prefix-caching` (or sglang `--enable-radix-cache`) by default with measured prefix-hit rates on document batches — none exists in this repo HEAD.
