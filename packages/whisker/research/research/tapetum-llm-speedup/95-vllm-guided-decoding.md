# 95 - vllm-Guided-Decoding

**Verdict:** usable-with-conditions — enable vLLM `response_format` / xgrammar only after holdout A/B on alliance-pod (post-#41199, `--reasoning-parser deepseek_v4`, MTP smoke); reject as a primary 3003 s → 5–10 min lever because retry elimination caps at ~100 s (~3%) while per-decode bitmask overhead and verdict-drift risk can erase or exceed that gain.
**Confidence:** high (vLLM source + measured retry census); medium (alliance-pod live guided-json latency/drift without probe)

## Findings

- [CRITICAL] **xgrammar compiler caches compiled grammars across requests; our 4 judge schemas are the ideal reuse case.** `XgrammarBackend.__post_init__` constructs `xgr.GrammarCompiler(..., cache_enabled=True, cache_limit_bytes=vllm.envs.VLLM_XGRAMMAR_CACHE_MB * 1024 * 1024)` (`research/repos/vllm/vllm/v1/structured_output/backend_xgrammar.py:65-69`). Default cache budget: `VLLM_XGRAMMAR_CACHE_MB` default 512, comment "enough for roughly 1000 JSON schemas" (`research/repos/vllm/vllm/envs.py:1533-1536`). Schema identity key is `(StructuredOutputOptions.JSON, json_str)` via `get_structured_output_key()` (`research/repos/vllm/vllm/v1/structured_output/request.py:82-88`). Impact: after 4 warm compiles, ~2280/2284 calls should hit compiler cache (compile amortized ≈0); first cold fleet pass pays ≤4 async compiles, not 2284. Quality risk: none from caching itself. Wall: saves retry re-decodes (~100 s ceiling, `00-baseline.md:18,60-61`) but does not cut the ~2900 s decode/prefill mass.

- [CRITICAL] **Per-request latency: async grammar compile blocks scheduling until ready; per-token cost is CPU bitmask fill on every decode step.** New structured requests start in `WAITING_FOR_STRUCTURED_OUTPUT_GRAMMAR` (`research/repos/vllm/vllm/v1/request.py:113-114`); scheduler promotes only when `grammar` Future resolves (`research/repos/vllm/vllm/v1/core/sched/scheduler.py:2590-2598`). Compilation runs on a thread pool (`research/repos/vllm/vllm/v1/structured_output/__init__.py:166-174,76-77`); readiness polled at 100 µs (`research/repos/vllm/vllm/v1/structured_output/request.py:52-55`). Each decode step calls `grammar.fill_bitmask()` (`research/repos/vllm/vllm/v1/structured_output/__init__.py:196-204,237-279`). Impact: first-of-schema adds queue wait (typically ms–low hundreds ms for small JSON; regex path capped at `VLLM_REGEX_COMPILATION_TIMEOUT_S=5`, `envs.py:1537-1542`); warm path adds per-token CPU mask work. Red Hat cached-JSON benchmark: TPOT "only marginally higher" vs unconstrained (https://developers.redhat.com/articles/2025/06/03/structured-outputs-vllm-guiding-ai-responses). At ~20 s/call × 2284 calls, even +2% TPOT ≈ +115 s wall, potentially exceeding the ~100 s retry budget. Quality risk: low from latency alone.

- [HIGH] **Token distribution at temperature 0: masking changes the sampled token only when the unguided argmax is grammar-invalid.** Sampler pipeline applies `allowed_token_ids_mask` (grammar-derived) at step 3, before greedy sampling at step 7a (`research/repos/vllm/vllm/v1/sample/sampler.py:31-32,391-392,41-43`). Design doc: a mask that zeroes the current argmax is **non-argmax-invariant** and cannot be skipped for greedy batches (`research/repos/vllm/docs/design/logits_processors.md:160-164`). Impact: at temp 0 (our default, D5), guided and unguided outputs match whenever the model's top logit is schema-valid; they diverge only on steps where free decoding would emit invalid JSON tokens (exactly the retry-trigger steps). Quality risk: **medium** — divergences concentrate on failure-prone steps, so eliminating retries is not quality-neutral; semantic validators (`verdict_matches_defects`, etc.) still run client-side (persona 32).

- [HIGH] **DeepSeek-V4-Pro + MoE + thinking: structured output is supported but gated behind reasoning-end detection; MTP on alliance-pod is a compatibility hazard.** `deepseek_v4` reasoning parser registered (`research/repos/vllm/vllm/reasoning/__init__.py:31-32`). Default `enable_in_reasoning=False` (`research/repos/vllm/vllm/config/structured_outputs.py:41-42`); `should_fill_bitmask()` returns False until `reasoning_ended` (`research/repos/vllm/vllm/v1/structured_output/__init__.py:362-379`), deferring JSON masking until after thinking — matches xgrammar "defer until reasoning end_token_id" (`docs/features/structured_outputs.md:213-217`). DeepSeek-V4-Pro requires `enable_thinking: true` for reasoning tokens (`docs/features/reasoning_outputs.md:321`). MoE path is unaffected by grammar backend choice (mask applied post-logits in sampler); MoE dispatch uses separate env (`VLLM_MOE_SKIP_PADDING`, `envs.py:1520-1523`). **MTP + structured output + reasoning** had `reasoning_ended` never becoming True under speculative decode (https://github.com/vllm-project/vllm/issues/34650); alliance-pod ships MTP per `05-web.md:16-17`. Impact: must verify `--reasoning-parser deepseek_v4` + MTP + `response_format` on pod before fleet flip; pre-#41199 JSON-in-reasoning-channel bug (#41132, persona 32) is a hard blocker. Quality risk: **high** if reasoning-end detection fails (JSON unconstrained or empty `content` parse).

- [HIGH] **Repetition-collapse evidence exists in vLLM for grammar-constrained JSON, but workload differs from our short judge outputs.** vLLM #40080: infinite repetition "significantly more frequently when structured output (JSON schema) is enabled"; grammar mask applied before penalties, `-inf` disallowed tokens, default `repetition_penalty=1.0` (`https://github.com/vllm-project/vllm/issues/40080`). SqueezeBits benchmark: guided decoding failures "often due to output degeneration (e.g., unnatural token repetition such as `\n`, `\t` or spaces)" (https://blog.squeezebits.com/guided-decoding-performance-vllm-sglang). olmOCR avoids JSON schema enforcement at inference for repetition risk (`05-web.md:47-48`, https://arxiv.org/abs/2502.18443 §4.2). Our unit-check outputs cap at 1536 tokens with quote strings (`00-baseline.md:27-28`), much shorter than olmOCR page bodies — lower intrinsic pressure, not zero. Impact: strict `json_schema` on quote-heavy `UnitCheck`/`DefectFinding` is the highest-risk schema; syntax-only or parse-and-retry remains safer default (personas 74, 88). Quality risk: **medium** for strict schema; **low** for syntax-only `json_object`.

- [MED] **Backend selection: `auto` prefers xgrammar for our Pydantic JSON schemas; engine latches one backend for life.** `SamplingParams._validate_structured_outputs` tries xgrammar first, falls back to guidance/outlines (`research/repos/vllm/vllm/sampling_params.py:1029-1059`). `StructuredOutputManager.grammar_init` notes "We only support a single backend" per engine (`research/repos/vllm/vllm/v1/structured_output/__init__.py:124-127`). Impact: with 4 fixed schemas, xgrammar cache wins (Red Hat + SqueezeBits: xgrammar beats guidance on repeated schemas at batch ≥16). Guidance better for unique-per-request schemas (not us). Quality risk: low. Wall: xgrammar path optimal for our repetition profile.

- [MED] **Measured retry economics confirm guided decoding cannot reach 5–10 min alone.** Cold fleet: 55 retries / ~2284 calls ≈ 2.4%, ~100 s wall (`00-baseline.md:18,60-61`); persona 32/74 agree. Production tapetum uses schema-in-prompt + client parse, no `response_format` (`32-structured-output-mechanic.md:8`). Impact: zeroing retries saves ≤~100 s (~3.3%); target gap ~2400 s requires call elimination / payload / parallelism levers (`00-baseline.md:88-103`). Quality risk: flipping mechanism without holdout violates quality-stability (`00-baseline.md:77-78`).

- [LOW] **Outlines disk cache exists for outlines backend fallback, not xgrammar's primary path.** `OutlinesDiskCache` persists compiled indices across restarts (`research/repos/vllm/tests/v1/structured_output/test_outlines_cache.py:28-34,68-74`). xgrammar relies on in-process `GrammarCompiler` cache (`backend_xgrammar.py:65-69`). Impact: pod restarts re-pay ≤4 compiles; irrelevant at steady-state 24/7 alliance-pod (`00-baseline.md:65-66`).

## False-pass hypothesis

Enable strict `json_schema` on unit checks; first-attempt syntactic validity rises and retries drop, but constrained decoding on quote-string fields narrows token choices so the model emits `verdict:"pass"` with empty `defects` more often on table-boundary errors that free-form decoding occasionally surfaced via longer pre-JSON reasoning — silent pass on some of the 16/381 verdict-changing papers (`00-baseline.md:29-30`), matching olmOCR §4.2 schema-distribution warning (persona 74) and langextract's fail-soft `[]` anti-pattern (persona 88).

## False-fail hypothesis

Enable guided JSON on alliance-pod with thinking + MTP while client still reads only `delta.content`: valid JSON lands in the reasoning channel (vLLM #41132) or `reasoning_ended` never flips under MTP (#34650), `_extract_json` fails twice (`32-structured-output-mechanic.md:30`), paper tombstones as `error` despite a correct structured verdict in an unobserved field — fail-closed blow-up with zero wall-clock win.

## What would change my mind

Holdout A/B on alliance-pod (post-#41199, logged vLLM version, `--reasoning-parser deepseek_v4`, MTP smoke): `response_format json_schema` on `UnitCheck`/`PdfJudgment` achieves ≥98% first-attempt parse, ≤1 pp shift in pass/review/fail histogram vs schema-in-prompt, zero new missed defects on 48-anchor holdout, **and** measured per-call p95 latency ≤ baseline + 1% — would upgrade to **usable** for a `VllmThinkingBackend` flag flip (persona 88 routing tier 2). If histogram shifts ≥2 pp or p95 latency rises >3%, keep parse-and-retry (personas 32/74/88 tier 3–4).
