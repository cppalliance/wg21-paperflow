# 103 - vllm-MTP-Determinism

**Verdict:** usable-with-conditions — MTP is a throughput lever, not a quality-free lever; greedy rejection sampling is algorithmically lossless but vLLM explicitly disclaims bit-exact greedy equality under default kernels, and MTP adds verify-path batch-shape divergence plus the same batch-composition/MoE variance our fleet already suffers; ship only after persona-47 verdict-drift A/B, so it belongs in the MODERATE package, not CONSERVATIVE.
**Confidence:** high

## Findings

- [CRITICAL] **Greedy rejection sampling is NOT hardware-exact output preserving at temp=0; acceptance is strict argmax equality on verify logits.** At `all_greedy`, `rejection_sample` computes `target_argmax = target_logits.argmax(dim=-1)` and the Triton kernel accepts a draft iff `draft_token_id == target_argmax_id`, else emits `target_argmax_id` (`research/repos/vllm/vllm/v1/sample/rejection_sampler.py:435-469`, `:747-757`). Any 1–2 ULP logits delta between verify-step and single-token decode flips acceptance and therefore token IDs. vLLM's own lossless docs admit "variations in generated outputs with and without speculative decoding can occur" from floating-point precision and **batch size / numerical stability** (`research/repos/vllm/docs/features/speculative_decoding/README.md:211-216`). Impact: **0 s wall by itself**, but **unbounded verdict-drift risk** on structured judge JSON if a flipped token crosses a schema or reasoning boundary; blocks CONSERVATIVE adoption without A/B.

- [CRITICAL] **MTP at temperature=0 diverges from non-MTP greedy on the same prompt in eager mode; maintainers closed as expected behavior, not a bug.** [Issue #42518](https://github.com/vllm-project/vllm/issues/42518): MTP verification forward runs at **batch_size=2** (context + draft token) while non-MTP decode runs at **batch_size=1**; cuBLAS picks different GEMM algorithms → 1–2 ULP BF16 attention deltas written into KV → argmax flip after ~50–100 tokens (repro: first mismatch pos 99 on MiMo-7B, 11/11 cases). Maintainer `@benchislett` closed: use `VLLM_BATCH_INVARIANT=1` for exact reproducibility; reporter confirmed batch-invariant mode fixes token-id mismatch but **cuts MTP eager throughput ~75→23 tok/s** on their RTX 3090 repro. Impact: if our H200 pod runs eager or hits the same GEMM path, MTP could **save 100–200 s** decode (`40-server-flag-auditor.md`) while **raising ≥25% paper-level verdict-flip exposure** (`20-in-paper-parallelist.md:16`, `MODELS.md:69-70`); net EV negative without measured A/B.

- [HIGH] **Spec decode explicitly expands effective batch shape, coupling MTP to continuous-batching variance our 32×16 fleet already has.** FAQ: same request may batch differently due to "other concurrent requests, changes in batch size, or **batch expansion in speculative decoding**" → logprob drift → sampled token drift (`research/repos/vllm/docs/features/speculative_decoding/README.md:206-209`, `research/repos/vllm/docs/usage/faq.md:26-29`). Scheduler pads single-token decode steps to `1 + num_spec_tokens` to preserve CUDA graphs (`research/repos/vllm/vllm/v1/core/sched/scheduler.py:824-840`). Impact: **no extra call count**, but MTP increases batch-shape diversity under c=16 concurrent slots (`00-baseline.md:24-25`, `32 papers` client-side), compounding MoE routing sensitivity documented for DeepSeek-class MoE (`MODELS.md:69-70`, `77-78`).

- [HIGH] **MTP draft and verify paths use different kernels than plain decode (fused MTP RMSNorm, separate forward), so "same target distribution" assumes identical logits, which vLLM does not guarantee.** DeepSeek V4 MTP runs `fused_mtp_input_rmsnorm` + `mtp_shared_head_rmsnorm` before logits (`research/repos/vllm/vllm/models/deepseek_v4/nvidia/mtp.py:145-264`, `research/repos/vllm/vllm/models/deepseek_v4/common/ops/fused_mtp_input_rmsnorm.py:153-190`). Draft greedy sampling uses `logits.argmax(dim=-1)` on the MTP head (`research/repos/vllm/vllm/v1/spec_decode/llm_base_proposer.py:428-438`, `:473-474`). `MODELS.md:70-71` already flags speculative verify-step **tie-break edges** for Eagle3; MTP shares the same rejection/compare-at-argmax structure. Impact: speed lever intact; **quality-stability unproven** for tapetum until rerun on 381-paper fleet with MTP on/off at production concurrency.

- [MED] **Batch-invariant mode is the supported mitigation but trades speed for determinism and is beta without DeepSeek-V4-Pro on the tested-model list.** `VLLM_BATCH_INVARIANT=1` "deterministic results regardless of batch composition" (`research/repos/vllm/vllm/envs.py:601-603`; docs `research/repos/vllm/docs/features/batch_invariance.md:7-8`, `:116-123`). Tested models include DeepSeek-V3/R1/V3.1 and Qwen3 MoE, **not** DeepSeek-V4-Pro (`batch_invariance.md:103-105`). Tracking issue [#27433](https://github.com/vllm-project/vllm/issues/27433). Impact: enabling BI on the alliance pod may **erase most MTP decode gain** (Issue #42518 ~3× slowdown) while fixing token-id parity; needs pod-level benchmark before bundling with CONSERVATIVE flags.

- [MED] **Algorithmic losslessness is tested in CI, but upstream maintainers acknowledge batch-size token changes in the wild.** Greedy equality e2e tests cited in docs (`README.md:201-204`); Issue [#7627](https://github.com/vllm-project/vllm/issues/7627) maintainer note: "changing the batch size can introduce small changes to the sampled tokens" even with spec-decode greedy tests passing, pointing at `test_multistep_correctness.py` batch-size caveat. Impact: CI green ≠ fleet-stable for our MoE judge at c=16; supports MODERATE + A/B gate, not CONSERVATIVE drop-in.

- [LOW] **CUDA-graph mode may mask MTP-vs-non-MTP divergence on fixed batch shapes, but does not remove MoE batch-composition variance across the 381-paper fleet.** Issue #42518: `enforce_eager=False` → 100% identical token IDs in reporter's MiMo repro; our pod likely uses graphs. FAQ batch-composition caveat and MoE routing (`MODELS.md:69-70`) still apply independent of MTP path parity. Impact: MTP may be **safer than Issue #42518 suggests on graph-enabled H200**, but **does not satisfy quality-stability without fleet A/B**.

## False-pass hypothesis

Enable MTP k=1 on the alliance pod without A/B: a verify-step argmax flip on a borderline unit-check JSON field (e.g., `severity` or a quoted span boundary) removes a real defect from the merged advisory verdict because the flipped structured output still validates against schema; fusion cannot recover a finding the model never emitted (`rejection_sampler.py:756-757`, Issue #42518 pos-99 flip pattern). Operator sees faster wall clock and fewer review flags on a paper that serial non-MTP would have flagged.

## False-fail hypothesis

Disable MTP in CONSERVATIVE package despite acceptable semantic equivalence: fleet stays at 3003 s cold wall while a measured-safe MTP+k=1 configuration (CUDA graphs + unchanged verdict distribution on 381-paper replay) would have saved ~100–200 s decode (`40-server-flag-auditor.md:73`) with zero change to pass/review/fail counts; we leave speed on the table without ever running persona-47 A/B.

## What would change my mind

Persona-47 A/B on production `deepseek-v4-pro` at `--max-num-seqs 16`, client c=32, `--speculative-config '{"method":"mtp","num_speculative_tokens":1}'` vs baseline: **0 changed pass/review/fail/error counts** and **≤1% diff in merged defect groups** on the 381-paper cold fleet (or a 50-paper stratified holdout with fingerprinted reruns), with MTP acceptance metrics logged. That would promote MTP to CONSERVATIVE server flags; absent that, keep in MODERATE only.
