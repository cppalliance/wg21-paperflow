# 94 - vllm-Chunked-Prefill

**Verdict:** usable-with-conditions — chunked prefill is already default-on in V1 and is required infrastructure for 40k-token judge prefills at our pod's implicit `max-num-batched-tokens=8192`; it is not a new on/off lever (~0 s delta if left default) but co-tuning MBT to 16384 plus `long-prefill-token-threshold=8192` is a schedulable ~100–250 s gain on the 3003 s cold run with no quality risk.
**Confidence:** high

## Findings

- [CRITICAL] **V1 has no separate prefill/decode phases; chunked prefill is the mechanism that splits long prompts across scheduler steps bounded by `max_num_batched_tokens`.** Evidence: `vllm/v1/core/sched/scheduler.py:426-435` ("There's no 'decoding phase' nor 'prefill phase'"; unified `{request_id: num_tokens}` budget covers "chunked prefills, prefix caching, speculative decoding"); chunk admission uses `num_new_tokens = min(remaining, token_budget)` at `scheduler.py:822,856` and `scheduler.py:501-508` for running requests. Impact: a **40k-token** cold prefill requires **ceil(40000/MBT)** forward passes when alone — **5 steps at MBT=8192** (8192×4 + 7232), **3 steps at MBT=16384** (16384×2 + 7232). At ~17 s prefill per call (`00-baseline.md:26-27`), raising MBT 8192→16384 saves ~2 scheduler rounds ≈ **6–7 s per isolated 40k call** (~**100–250 s fleet** if prefill-bound across 2284 calls / 16 slots, conservative). Quality risk: **none** (scheduling-only).

- [CRITICAL] **Chunked prefill is default-on in V1 whenever the model supports it; our DeepSeek-V4-Pro generative path keeps it enabled unless explicitly disabled.** Evidence: `SchedulerConfig.enable_chunked_prefill: bool = True` at `vllm/config/scheduler.py:88-91`; `arg_utils.py:2488-2489` sets `enable_chunked_prefill = model_config.is_chunked_prefill_supported` when unset; `docs/usage/v1_guide.md:37-39` ("enabled by default whenever possible"); `docs/configuration/optimization.md:53` (same). `tests/test_config.py:1020` confirms generative models support chunked prefill. Impact: **0 s** from "turning on" chunked prefill on alliance-pod (already active); **crash/correctness risk** if disabled with MBT < max_model_len at 393k context (`optimization.md:69-71`, `scheduler.py:848-854`). Quality risk: **none** if unchanged.

- [HIGH] **Each scheduler step interleaves running decodes before waiting-queue prefills by draining the running queue first, then spending leftover `token_budget` on new/chunked prefills.** Evidence: running loop `scheduler.py:468-618` precedes waiting loop `scheduler.py:663+`; decodes need `num_new_tokens==1` (`scheduler.py:501-505`) and consume budget first; waiting prefills only enter when `token_budget > 0` after running queue (`scheduler.py:667`). Docs echo decode-first policy at `docs/configuration/optimization.md:53-58`. Impact: at **c=16** with mixed prefill+decode, each step spends up to **16 tokens** on decodes before prefill chunks — good for ITL, adds **1+ scheduler steps** to TTFT vs monolithic prefill. For our short-decode (~1536 cap, often less, `00-baseline.md:27-28`) long-prefill mix this is the intended tradeoff. Quality risk: **none**.

- [HIGH] **`long_prefill_token_threshold` caps per-request prefill chunk size and is the fairness knob when MBT is large and concurrency is high.** Evidence: `SchedulerConfig.long_prefill_token_threshold` default 0 (disabled) at `vllm/config/scheduler.py:82-85`; applied at `scheduler.py:506-507` (running) and `scheduler.py:842-844` (waiting). With MBT=16384 and threshold=0, the FCFS running queue lets index-0 consume the full 16384-token budget in one step (`scheduler.py:508`, `617-618`), starving co-running prefills. With threshold=8192, two 40k prefills can advance 8192 tokens each per step. Impact: at **16–32 concurrent long prompts**, threshold=8192 cuts worst-case prefill-serialization rounds roughly **2×** vs uncapped MBT=16384 (persona 40 recipe). Fleet saving overlaps MBT raise; combined **~100–250 s** on 3003 s (`40-server-flag-auditor.md:45`). Quality risk: **none**.

- [HIGH] **Our pod likely runs MBT=8192 (H200 OPENAI default), not the recipe's 16384 — chunked prefill therefore takes 5 steps per 40k prefill instead of 3.** Evidence: `arg_utils.py:2424-2428` sets `OPENAI_API_SERVER` default **8192** on ≥70 GiB non-A100 GPUs; recipe specifies **16384** (`05-web.md:15-16`); persona 40 confirms H200SXM launch omits explicit MBT (`40-server-flag-auditor.md:12,69`). Impact: **+2 scheduler forward passes** per cold 40k prefill vs recipe — ~**6–7 s × (2284 long calls / 16 slots) ≈ 100–250 s** wall if prefill-step time dominates. Quality risk: **none**.

- [MED] **Chunked prefill composes with APC (PR #7753); Q1 card cites ~+8% throughput over APC alone when both enabled.** Evidence: `05-web.md:32-33` (PR #7753); PR merged 2024-09 enabling simultaneous prefix caching + chunked prefill (block-aligned token counts divisible by block size 16). V1 scheduler integrates both in one loop (`scheduler.py:434`, prefix lookup at `scheduler.py:714-735`). Impact: once APC hits are live (separate lever, `05-web.md:5-12`), chunked prefill lets cached-prefix + uncached-suffix advance in the same step budget — incremental **~8% server throughput** on prefix-heavy loads, not a standalone 3003 s lever. Quality risk: **none** (KV replay).

- [MED] **Throughput-vs-TTFT tradeoff is explicit in docs: lower MBT → better ITL; higher MBT → better TTFT/throughput on long prefills.** Evidence: `docs/configuration/optimization.md:62-67` (2048 better ITL; >8192 recommended for throughput; MBT=max_model_len ≈ V0 policy). Our workload is **long prefill (~3k–100k), short decode** with **16 server slots / 32 client papers** (`00-baseline.md:34-35,66`). Impact: favor **higher MBT (16384)** + **threshold cap (8192)** over lowering MBT. Lowering MBT to 2048 would shrink prefill chunks but inflate scheduler steps on 40k prompts (**~20 steps at 2048**) — wrong direction for fleet wall clock. Quality risk: **none** for recommended direction.

- [LOW] **At 32 client concurrency with 16 server slots, waiting-queue depth doubles; chunked prefill does not add parallelism beyond the token budget.** Evidence: client `_DEFAULT_CONCURRENCY = 32` vs server `--max-num-seqs 16` (`00-baseline.md:34,66`); admission gate `scheduler.py:670-672` (`num_running >= max_num_running_reqs` breaks). Impact: second-tier requests see **queue wait + multi-step prefill**; per-call latency tail grows under burst but steady-state ~20 s (`00-baseline.md:24-25`) already implies queueing. Chunked prefill prevents single-request prefill monopoly blocking admission (vs disabled chunked prefill at MBT < prompt len). Quality risk: **none**; tail latency is operational, not verdict drift.

## False-pass hypothesis

Raising `max-num-batched-tokens` to 16384 without `long-prefill-token-threshold` could let one 40k prefill monopolize an entire 16384-token step in the FCFS running queue (`scheduler.py:506-508,617-618`), inflating TTFT for co-slot requests enough that client-side `UNIT_CHECK_TIMEOUT_SECONDS=120` (`00-baseline.md:53-54`) fires on unrelated papers — a **throughput optimization masquerading as success** while coverage drops via timeout tombstones, not changed verdicts.

## False-fail hypothesis

Disabling chunked prefill to "reduce scheduler overhead" would either **fail startup** (MBT=8192 < max_model_len=393216 requires chunked prefill, `optimization.md:69-71`) or force **single monolithic 40k prefill steps** that block all 15 co-slots for one forward pass — inflating fleet wall clock and causing **timeout failures on good conversions**, not false defect findings.

## What would change my mind

A `/metrics` capture from alliance-pod under a 381-paper fleet showing `max_num_batched_tokens=16384`, chunked prefill enabled, and **no reduction** in p50 `vllm:request_prefill_time_seconds` vs MBT=8192 — would mean MoE prefill kernel time dominates step count and MBT tuning is a rounding error on our pod.
