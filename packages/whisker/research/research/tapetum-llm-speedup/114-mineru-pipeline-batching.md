# 114 - mineru-Pipeline-Batching

**Verdict:** usable-with-conditions — MinerU's current (3.x) batch/parallel machinery is a conversion pipeline, not a judge harness, but its two-level batching model (64-page memory windows + in-window VLM concurrency or vLLM stepping batches) and corpus task planner are directly portable to tapetum-llm's in-paper serial bottleneck; sglang is historical only (migrated to vLLM at 2.5).
**Confidence:** high

## Findings

- [CRITICAL] **sglang is gone in current MinerU; vLLM is the shipped VLM engine.** MinerU 2.5 moved VLM inference code to `mineru-vl-utils` and explicitly switched the acceleration framework from sglang to vLLM for ecosystem compatibility (`docs/zh/reference/changelog.md:133-137`). Current public backends are `vlm-engine`, `vlm-http-client`, `hybrid-engine` (`mineru/cli/backend_options.py:4-22`); `ModelSingleton.get_model()` wires `vllm-engine`, `vllm-async-engine`, `lmdeploy-engine`, `http-client` — no sglang backend (`mineru/backend/vlm/vlm_analyze.py:118-174,222-238`). README still mentions SGLang only as a generic OpenAI-compatible server option (`README.md:287`), not as a first-class MinerU backend. **Impact:** supports our vLLM-first pod strategy; do not pivot fleet to sglang based on MinerU — their own migration is evidence against it. Historical sglang peak (>10,000 tok/s on 4090, `docs/zh/reference/changelog.md:282`) is not reproducible on current HEAD. **Quality risk:** none (infra choice only).

- [HIGH] **Multi-page PDFs use fixed 64-page processing windows, sequential across windows.** VLM and hybrid backends iterate `range(0, page_count, effective_window_size)` with default `MINERU_PROCESSING_WINDOW_SIZE=64` (`mineru/backend/vlm/vlm_analyze.py:446-482`; `mineru/utils/config_reader.py:158-169`; `mineru/cli/api_protocol.py:4`). Each window loads PIL images then calls `predictor.batch_two_step_extract(images_pil_list)` once (`vlm_analyze.py:478-482`). Pipeline multi-file mode fills windows up to 64 pages across documents before one `batch_image_analyze` (`mineru/backend/pipeline/pipeline_analyze.py:207-275`). **Impact:** memory-bound chunking, not a latency win by itself; for tapetum's text judge, analogous chunking would not cut the 3003 s cold run unless paired with parallel in-chunk calls. At ~13 pages/paper median, most WG21 papers fit one window — windowing saves RAM, not wall clock. **Quality risk:** low if page boundaries preserved (MinerU does not merge judge logic across windows).

- [HIGH] **Within a window, VLM uses two batching modes: `concurrent` (fan-out) vs `stepping` (collect-then-batch).** `mineru-vl-utils` sets `batching_mode="concurrent"` for `http-client`, `vllm-async-engine`, `lmdeploy-engine`; `"stepping"` for `transformers` and `vllm-engine` (`research/repos/mineru-vl-utils/mineru_vl_utils/mineru_client.py:666-669`). **Concurrent:** up to `max_concurrency=100` (default) pages run `aio_two_step_extract` in parallel via `asyncio.Semaphore` (`mineru_client.py:1038-1053`; wired from `vlm_analyze.py:71,231`). **Stepping:** all pages do `batch_layout_detect`, flatten all block crops, then one `_batch_predict` through vLLM with `batch_size` 4/8/16 by VRAM (`mineru_client.py:1077-1088`; `mineru/backend/vlm/utils.py:95-111`; `vllm_engine_client.py:228-237`). **Impact on 3003 s run:** closest analog is tapetum's serial 0–5 unit checks (`00-baseline.md:36-38`). Parallelizing 5 unit checks (concurrent mode, cap 5) could shrink per-paper unit phase from ~100 s to ~20 s for papers hitting MAX_UNIT_CHECKS → fleet estimate **~950–1200 s (~16–20 min)** at 16 slots (381×~40 s/16), not 5–10 min alone. Stepping mode shows vLLM `LLM.generate()` multi-prompt batching works when prompts share one engine — portable only if unit-check payloads can be flattened without rubric interference (cf. RuVerBench caution in `05-web.md:96-98`). **Quality risk:** HIGH for concurrent (MoE batch-composition variance at 16 slots, `00-baseline.md:96`); MED for stepping (batch size changes prefill/decode mix).

- [HIGH] **HTTP-client VLM config: concurrency 100, conservative API worker concurrency 3.** `ModelSingleton.get_model()` defaults `max_concurrency=100`, `max_retries=3`, `retry_backoff_factor=0.5`, `http_timeout=600` for http-client (`vlm_analyze.py:71-75,231-235`). `HttpVlmClient` posts to `{server_url}/v1/chat/completions`, default `max_concurrency=100`, httpx retry transport (`mineru-vl-utils/.../http_client.py:59-77,131-137`). Separately, corpus API throughput is capped at `MINERU_API_MAX_CONCURRENT_REQUESTS` default **3** via `asyncio.Semaphore` in `mineru-api` (`mineru/cli/api_protocol.py:3`; `mineru/cli/fast_api.py:228-234`; `docs/zh/usage/cli_tools.md:136-138`). CLI submit concurrency = `min(local_max, server_max, task_count)` (`mineru/cli/client.py:765-768,981-984`). **Impact:** MinerU separates **server slot limit (3 docs)** from **in-doc page fan-out (100)** — we already run **32 papers** at fleet level (`00-baseline.md:34`) but **0 in-paper parallelism**. Raising client paper concurrency past server capacity hurt us before (`00-baseline.md:81`); MinerU's pattern says raise in-document parallelism first, not cross-paper. Matching their 3-doc API default would *slow* us; matching their 100-request page fan-out (capped to 5 unit checks) is the portable knob. **Quality risk:** server overload if in-paper concurrency × fleet concurrency exceeds `--max-num-seqs 16`.

- [MED] **Corpus-scale task planning: pipeline bin-packs small docs; VLM/hybrid one doc per task.** `plan_pipeline_tasks()` greedily packs documents until `total_pages <= processing_window_size` (64), longest-first (`mineru/cli/client.py:609-647`). VLM/hybrid backends use one document per `PlannedTask` (`client.py:659-664`). `execute_planned_tasks()` runs a worker pool of size `concurrency` (`client.py:781-816`). `demo.py` submits multi-file batches through async task API with queue status (`demo/demo.py:116-187`). `mineru-router` sums worker `max_concurrent_requests` and load-balances (`mineru/cli/router.py:818-822,1189-1229`). **Impact:** bin-packing reduces fixed overhead for small papers; at 381 papers × ~6 calls, overhead is LLM not API — expect **<5% (~150 s)** unless we add per-call setup cost. Dual-pod sharding (`00-baseline.md:67-68`) mirrors router multi-GPU: **~2× wall** if second pod has same model → **~1500 s (~25 min)** combined with in-paper parallelism. **Quality risk:** low for bin-packing; dual-pod needs fingerprint consistency.

- [MED] **vLLM server flags MinerU ships: port 30000, dynamic GPU util, custom logits processor, param passthrough.** `mineru-vllm-server` entrypoint (`pyproject.toml:130`) defaults `--port 30000`, `--gpu-memory-utilization` from VRAM (0.5, or 0.7 if ≤8 GB on vllm≥0.11), injects `mineru_vl_utils:MinerULogitsProcessor` when enabled (`mineru/model/vlm/vllm_server.py:45-53`; `mineru/backend/vlm/utils.py:83-92,12-57`). All vLLM/LMDeploy CLI flags pass through on `mineru`, `mineru-api`, `mineru-openai-server` (`docs/zh/usage/advanced_cli_parameters.md:7-10`). Device-specific vLLM kwargs auto-applied via `MINERU_VLLM_DEVICE` (`mineru/backend/vlm/utils.py:175-235`). **Impact:** no MinerU-specific `--max-num-seqs` recommendation beyond vLLM defaults — our `--max-num-seqs 16` already matches DeepSeek recipe (`05-web.md:15-17`). Logits processor is conversion-token markup specific, not portable to judge JSON. **Quality risk:** none for passthrough; do not copy logits processor.

- [LOW] **Hybrid `effort=medium` skips full VLM layout pass — 35–220% measured speedup at −0.13 OmniDocBench accuracy.** Hybrid medium uses pipeline layout → `batch_extract_with_layout` instead of full `batch_two_step_extract` (`mineru/backend/hybrid/hybrid_analyze.py:965-986`; README changelog 3.3). **Impact:** analog to routing 70% zero-defect unit checks (`00-baseline.md:29-30`) or metadata-fail short-circuit — if router precision holds, **~700–1050 s saved** on unit-check calls (70% × 1510 × 20 s / 16 slots ≈ 1320 s upper bound; less if fewer than 5 checks fire). **Quality risk:** MED — −0.13 bench delta is acceptable for conversion, may not transfer to defect-class recall on WG21 goldens.

## False-pass hypothesis

Adopting MinerU **concurrent** mode literally for tapetum — firing 5 unit checks in parallel each carrying the **full candidate markdown** (`00-baseline.md:43-44`) — could let one page's defects bleed into another check's structured output (shared long context + concurrent decode on MoE), mimicking RuVerBench multi-rubric degradation (`05-web.md:96-98`), while still returning schema-valid empty defect lists on 70% of checks.

## False-fail hypothesis

Adopting MinerU **stepping** `batch_predict` to pack 5 unit checks into one vLLM batch without identical system-prefix structure would break APC (guard tag random suffix per call, `00-baseline.md:50-52`), increasing prefill cost and TTFT variance — looks like a slowdown regression, not a quality failure, but could timeout papers at `UNIT_CHECK_TIMEOUT_SECONDS=120` (`constants.py:197`).

## What would change my mind

A tapetum A/B on 50 held-out papers showing **in-paper parallel unit checks (concurrency 5)** with DeepSeek-V4 at `--max-num-seqs 16` yields **≥95% merged-verdict agreement** vs serial baseline — MinerU's concurrent pattern is conversion-grade, not judge-grade, until that measurement exists.
