# 108 - sglang-Structured-Output

**Verdict:** usable-with-conditions — jump-forward / compressed-FSM is real SGLang/xgrammar technology, but the current server runtime never calls it (token-by-token `accept_token` only), vLLM has no equivalent, and even if rewired the savings cap at ~2–5% cold-fleet wall because prefill dominates our ~20 s/call budget.
**Confidence:** high (runtime wiring, vLLM absence); medium (schema-token fraction and wall savings are modeled, not A/B-measured on alliance-pod)

## Findings
- [CRITICAL] Jump-forward APIs exist but are **not wired into the decode hot path**. `batch_result_processor.py:817-821` advances grammar one token at a time via `_accept_grammar_tokens` → `req.grammar.accept_token(token_id)` (`623-641`); `rg` finds exactly one `.try_jump_forward(` call site and it is an internal delegate in `reasoner_grammar_backend.py:212`, not the scheduler. Impact: **0 s today** on the 3003 s cold run; quality risk none until someone rewires it.
- [HIGH] xgrammar backend (default `--grammar-backend xgrammar`, `server_args.py:5606-5607`) exposes jump-forward via `GrammarMatcher.find_jump_forward_string()` in `XGrammarGrammar.try_jump_forward` (`xgrammar_backend.py:157-160`) and compiles JSON schemas with `grammar_compiler.compile_json_schema` (`336-338`), but nothing invokes `try_jump_forward` during generation. Impact: latent only; flipping SGLang on the pod buys bitmask-guided decoding, not jump-forward, until runtime work lands.
- [HIGH] Compressed FSM for outlines/regex lives in `outlines_jump_forward.py:62-139` (`init_state_to_jump_forward` merges singular FSM edges into jump chains; blog ref line 15-16). The outlines backend **disables** it: `jump_forward_map = None` at `outlines_backend.py:157-158`. Impact: historical 2–3× JSON decode wins (README line 55, lmsys 2024-02 blog) do not apply to default xgrammar path or current outlines JSON dispatch.
- [HIGH] vLLM has **no jump-forward / jump-ahead** implementation (`rg jump_forward|find_jump_forward` over `research/repos/vllm` → zero hits). Its v1 scheduler advances grammars token-by-token: `vllm/v1/core/sched/scheduler.py:1732` `grammar.accept_tokens(...)`. Both stacks share xgrammar bitmask masking (`StructuredOutputsConfig.backend` default `"auto"` → xgrammar, `vllm/config/structured_outputs.py:21-22`). Impact: jump-forward is SGLang-differentiated **in design**, not in our current vLLM deployment; migration alone does not unlock it.
- [MED] Schema-deterministic vs content tokens on tapetum schemas (`models.py` `UnitCheck`, `PdfJudgment`, `MetadataOutlineCheck`): modeled JSON for a **zero-defect unit check** (70% of unit calls per 00-baseline) is ~167 chars (~42 tok), ~46% punctuation/field-name/literal envelope; a **one-defect unit check** ~404 chars (~100 tok), ~50% envelope; monolith/page/metadata calls with 40–60 word `reasoning` plus optional quote lists drop envelope share to **~15–25%**. At 70 tok/s decode (00-baseline) and ~100 avg output tok/call, decode ≈1.4 s of ~20 s/call (~7% wall); skipping 35% of decode forwards saves **~0.35×1.4 s ≈ 0.5 s/call → ~70 s fleet wall (2.3%)** at 16 slots (`2284×0.5/16`). Impact: far below the 2400 s gap to 5–10 min; quality risk low if jump strings are re-tokenized (`xgrammar_backend.py:167-189`).
- [MED] SGLang grammar stack otherwise aligns with our constraints: JSON-schema dispatch (`grammar_manager.py:144-148`), bitmask in-place on logits (`xgrammar_backend.py:125-136`), default xgrammar backend, optional compact JSON (`constrained_json_disable_any_whitespace`, `server_args.py:1567-1570`). Impact: server swap is feasible for structured outputs, but parity with vLLM xgrammar does not by itself cut wall clock; MoE + full-markdown prefill remain the bottleneck (00-baseline §Architecture facts).
- [LOW] Benchmark artifacts remain under `benchmark/json_jump_forward/` and `test/manual/lang_frontend/test_jump_forward.py` (regex/json jump-forward demos), but they exercise the **frontend** regex path, not proof that the 2026 runtime server applies jump-forward on OpenAI JSON-schema requests. Impact: do not extrapolate bench numbers to alliance-pod vLLM replacement without a live A/B.

## False-pass hypothesis
Rewiring jump-forward without SGLang’s re-tokenize path (`xgrammar_backend.py:167-189`) could shift logits after injected schema strings and drop rare borderline quotes from `missing_content` / `defects`, silently clearing a real review flag while JSON still validates.

## False-fail hypothesis
Aggressive `constrained_json_disable_any_whitespace=true` (`server_args.py:1567-1570`) tightening JSON envelope tokenization could change whitespace inside long `source_quote` spans vs vLLM xgrammar, causing schema retries or truncated quotes that inflate review rate without catching new defects.

## What would change my mind
An alliance-pod A/B on 50 unit-check calls showing (1) `completion_tokens_wo_jump_forward` metric dropping ≥30% with jump-forward enabled in a SGLang build that actually calls `try_jump_forward` in `process_batch_result_decode`, and (2) zero change in merged verdict distribution vs vLLM xgrammar baseline.
