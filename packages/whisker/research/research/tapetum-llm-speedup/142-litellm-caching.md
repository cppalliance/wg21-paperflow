# 142 - litellm-Caching

**Verdict:** usable-with-conditions (+ adopt litellm's exact prompt+model SHA-256 call cache on disk beside sidecars, but strip random guard tags from the hash input or every call misses; does not shrink the first 3003 s cold run without stacking call elimination)
**Confidence:** high

## Findings

- [CRITICAL] **Cache backends: local in-memory, Redis/Redis-cluster, disk (`diskcache`), S3, GCS, Azure Blob, plus semantic variants (Redis/Valkey/Qdrant).** Evidence: `LiteLLMCacheType` enum (`litellm/types/caching.py:8-17`); constructor dispatch (`litellm/caching/caching.py:170-265`): `LOCAL` → `InMemoryCache`, `REDIS` → `RedisCache`/`RedisClusterCache`, `DISK` → `DiskCache(disk_cache_dir)`, `S3` → `S3Cache`, etc. Default disk path `.litellm_cache` when `disk_cache_dir` is None (`litellm/caching/disk_cache.py:22-25`). Redis uses `DualCache` (in-memory L1 + Redis L2) when Redis is enabled (`litellm/caching/caching_handler.py:141-147`, `litellm/caching/dual_cache.py:51-78`). Impact: for tapetum, **`DiskCache` beside `whisker/llm/<pid>.tapetum.json`** is the litellm analogue: no new infra, survives process restarts, TTL via `expire=` (`disk_cache.py:28-31`). Quality risk: **LOW** if keys are exact-match; semantic caches (`REDIS_SEMANTIC`, `QDRANT_SEMANTIC`) are **unsafe** for judge fidelity (similarity threshold, not identity).

- [CRITICAL] **Key derivation: concatenate all OpenAI-spec LLM API params present in kwargs (including `messages` / `input`), SHA-256 hex; optional Redis `namespace:` prefix.** Evidence: `get_cache_key` iterates kwargs against `ModelParamHelper._get_all_llm_api_params()` (`caching.py:347-363`, `model_param_helper.py:59-86`); `messages` is in chat-completion kwargs and is **not** in `_get_exclude_kwargs()` (only `metadata` excluded, `model_param_helper.py:171-175`); hash via `hashlib.sha256(cache_key.encode()).hexdigest()` (`caching.py:459-475`); namespace from `cache.namespace` or `metadata.redis_namespace` or global namespace (`caching.py:477-494`). `model` resolves through caching groups / `model_group` before hashing (`caching.py:395-408`). Impact: our call-level key should be **`sha256(model_contract + canonical_json(messages) + schema_sha256 + response_format/thinking)`** — mirrors litellm's "full request identity" rule. **Guard-tag normalization required:** we append `SRC{secrets.token_hex(4)}` per call (`unit_judge.py:767-768`, `pdf_judge.py:638-639`); litellm would treat each tag as a new prompt → **0% hit rate** unless we hash the prompt with a fixed sentinel replacing the random tag (same pattern litellm uses excluding `metadata` from identity). Quality risk: **MEDIUM** if guard tag is stripped from hash but left in live prompt (injection defense preserved; cache identity stable).

- [HIGH] **TTL policies: three layers — backend default, global `Cache.ttl`, per-request `cache={"ttl": N}` override; lookup-side `s-maxage` freshness window.** Evidence: `BaseCache.default_ttl = 60` (`base_cache.py:23-33`); Redis `set(..., ex=ttl)` via `get_ttl(**kwargs)` (`redis_cache.py:394-400`); in-memory default **600 s** (`in_memory_cache.py:32-34`); store wraps `{timestamp, response}` (`caching.py:656-657`); on get, `_get_cache_logic` rejects entries where `now - timestamp > max_age` (`caching.py:511-529`); per-request `cache["ttl"]` overrides default on write (`caching.py:649-654`); `DynamicCacheControl` fields (`types/caching.py:74-89`). S3 uses object `Expires` + `CacheControl` headers (`s3_cache.py:71-98`). Impact: tapetum disk cache can use **infinite TTL** (prompt-hash keys are self-invalidating) plus optional `s-maxage` for dev hygiene; no fleet-wide invalidation API needed. Quality risk: **LOW** with content-addressed keys; **MEDIUM** if TTL expires while markdown unchanged and a later model version would have judged differently (mitigate by including model contract in key, as we already do in `_compute_fingerprint`, `cli.py:526-563`).

- [HIGH] **Streaming-response caching: store complete assembled response; on hit, replay as synthetic stream.** Evidence: cache lookup runs **before** the HTTP call even when `stream=True`, with `cache_key` precomputed (`caching_handler.py:314-315`, `710-711`); on hit with `stream=True`, `_convert_cached_stream_response` wraps cached dict in `CustomStreamWrapper` (`caching_handler.py:796-802`, `912-939`); on miss, `_add_streaming_response_to_cache` assembles chunks via `_assemble_complete_response_from_streaming_chunks` then stores (`caching_handler.py:1069-1095`); optional artificial delay `CACHED_STREAMING_CHUNK_DELAY = 0.02` s per 5-char chunk (`caching.py:496-509`, `constants.py:373`). Success callbacks deferred on stream cache hit to avoid double-counting (`caching_handler.py:114-123`, `241-249`). Impact: tapetum uses non-streaming structured output today; pattern still applies if we ever stream. Quality risk: **none** for our current call path.

- [HIGH] **Per-request cache control: opt-in/out, no-store, no-cache, namespace, TTL.** Evidence: `CacheMode.default_on` vs `default_off` (`caching.py:49-51`, `880-896`); under `default_off`, requires `cache={"use-cache": True}`; `should_use_cache` gate (`caching.py:880-896`); skip read when `cache["no-cache"]` (`caching_handler.py:184-185`); skip write when `cache["no-store"]` (`caching_handler.py:1044`); all `DynamicCacheControl` keys (`types/caching.py:74-89`). Impact: map to tapetum as **`--no-llm-cache`** (force `no-cache`) on fleet runs that must re-sample, and default-on elsewhere. Quality risk: **LOW**.

- [HIGH] **Determinism: cache replay is strictly more stable than re-sampling MoE.** Evidence: litellm returns the stored structured response verbatim (`caching.py:533-543`); tapetum measured **≥25% verdict-flip** on identical reruns (`whisker/CLAUDE.md`, advisory lane section); warm fingerprint skip already treats unchanged inputs as authoritative (`00-baseline.md:19-20`). Impact: call-level cache is a **quality-positive** lever for quality-stability: zero sampling variance on hits, same structured output → same merge/fusion. This is the inverse of prefix-cache risk (MoE batch composition); cached responses remove the model from the path entirely. Quality risk: **LOW** on hits; **none** vs today's re-sample variance.

- [MED] **Win sizing vs 3003 s cold fleet run.** Call census: **2284 calls** (`00-baseline.md:22-23`); implied **~20 s/call**, **16 slots** (`00-baseline.md:24-25`). Call-level cache **does not reduce N** on a true cold run (empty cache → still 3003 s). It **does** reduce N on: (1) **`_LANE_VERSION` bump affecting only unit routing (v10-class):** monolith (381) + metadata (377) + page (16) = **774 calls** unchanged → **~774×20/16 ≈ 968 s saved → ~2035 s (~34 min)**, not 5–10 min (`19-incremental-granularity.md:10`, `18`). (2) **Single-class prompt edit:** same as persona 19's class-hash accounting (unit-only → ~1888 s wall). (3) **Retries:** 55 retries ≈ **~69 s** recoverable if same prompt (`00-baseline.md:60-61`). (4) **Dev re-run / partial re-adjudication:** proportional to unchanged calls. Overlap with persona 19: both survive prompt-only edits; **call-level cache is simpler to implement** (hash-in/hash-out, no sidecar merge/re-ground rules) but **class-hash skip is simpler operationally** (extends existing whole-paper fingerprint UX at coarser granularity). Use call-level cache **inside** each call site; use class-hash **for paper-level skip** — complementary, not either/or.

- [LOW] **Explicit invalidation is unnecessary with content-addressed keys; litellm has flush/delete but no prompt-registry.** Evidence: no inverse index; keys are one-way hashes (`caching.py:459-475`); `flush_cache` / `delete_cache_keys` exist (`disk_cache.py:81-82`, `caching.py:908-912`). Prompt or schema change → new hash → automatic miss. Impact: no TTL-based fleet invalidation ceremony; bump `schema_sha256` or prompt text and only affected calls miss. Quality risk: **none**.

## False-pass hypothesis

**Stale hit after schema tightening without key update:** a cached `UnitCheck` JSON from an older schema (missing a new required field) replays as valid structured output while a fresh call would fail validation and retry. Mitigation: include `schema_sha256` in the cache key (litellm includes response-shaping params like `response_format` via the OpenAI param set; we should hash Pydantic `model_json_schema()` explicitly, as `_compute_fingerprint` already does at paper level, `cli.py:603`).

## False-fail hypothesis

**none found** — cache replay returns the prior accepted structured verdict; it cannot invent new defects. Worst case is stale pass (false-pass above), not spurious fail. Re-grounding-only paths (persona 19) are orthogonal; call-level cache stores LLM output before post-processing.

## What would change my mind

A/B on 50 papers showing **>5% verdict flips** when replaying sidecar-cached LLM outputs vs live re-sample **with identical prompts and model contract** would prove MoE variance dominates and cache replay is unsafe; that has not been observed (current evidence is the opposite: reruns flip, cache would freeze the first good answer).
