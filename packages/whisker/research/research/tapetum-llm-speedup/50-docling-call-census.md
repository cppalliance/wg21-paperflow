# 50 - docling-LLM-Call-Census

**Verdict:** usable-with-conditions — Docling's call-bounding and batching patterns are concrete and well-instrumented, but its default path is zero-LLM extraction while tapetum is a mandatory multi-call judge fleet; only stage-gating and in-paper parallel dispatch port cleanly, not page-image vLLM batching.
**Confidence:** high

## Findings

- [CRITICAL] Default **Standard PDF pipeline makes zero LLM/VLM calls**; optional VLM enrichments are all `False` by default (`do_picture_description`, `do_code_enrichment`, `do_formula_enrichment`, `do_picture_classification`). Evidence: `pipeline_options.py:1247,1265,1788,1789`; PDF routes to `StandardPdfPipeline` (`document_converter.py:212`) whose build stages are local OCR/layout/table models (`standard_pdf_pipeline.py:590-614`), not LLM. Impact: docling achieves speed primarily by **not calling** LLMs; tapetum cannot copy this without a deterministic pre-gate. Quality risk: none for docling; for tapetum, skipping judge calls risks false-pass unless a deterministic floor covers the gap.

- [CRITICAL] **VlmPipeline call count is bounded to `ceil(pages / page_batch_size)`** batched inference calls per document (default `page_batch_size=4`). Pages are chunked in `_build_document`, each chunk invokes `VlmConvertModel.__call__`, which calls `engine.predict_batch()` once per chunk. Evidence: `settings.py:32`; `base_pipeline.py:271-272,282`; `vlm_convert_model.py:153-198`; `vllm_engine.py:254-322` (`llm.generate(llm_inputs, ...)` on the whole batch). A 20-page paper → **5 vLLM calls**, not 20. Impact: **not portable** to tapetum unit checks (different prompt per unit; RuVerBench in `05-web.md` warns against multi-rubric packing). Docling's ~4× call reduction has no direct analog in our 2284-call fleet.

- [HIGH] **VlmPipeline enrichment pipe is intentionally empty** — no picture-description or code/formula stages unless a separate pipeline enables them. Evidence: `vlm_pipeline.py:95-97`. Impact: docling separates "convert" (1 VLM stage) from "enrich" (optional, off by default). Tapetum already separates monolith/metadata/units but runs all by default; docling's pattern supports a **router short-circuit** before unit checks. Skipping 70% zero-defect unit checks (~1057/1510 per `00-baseline.md`) removes ~1057 calls → **~1321 s saved** on the 3003 s run (1057×20/16), landing ~1682 s (~28 min). Quality risk: medium — false-negative if router misses a latent defect.

- [HIGH] **Enrichment LLM calls are element-bounded and image-batched**, not per-page. After document build, `_enrich_document` iterates models serially; within each model, `chunkify(..., elements_batch_size)` groups elements. Picture description: default `batch_size=8`, skips pictures below `picture_area_threshold=0.05` page area and classification filters. Code/formula: `elements_batch_size=5`, one `predict_batch` per chunk. Evidence: `base_pipeline.py:118-127`; `pipeline_options.py:638-666`; `picture_description_base_model.py:80-99,101`; `code_formula_vlm_model.py:67,221-272`. Call formula when enrichments ON: `ceil(qualifying_pictures/8) + ceil(code_formula_elements/5)` per document, plus **zero** for standard PDF. Impact: **filter-before-call** (`picture_area_threshold`) is portable as deterministic pre-gate before expensive judge calls; batching 5 units into one prompt is **not** portable (quality). Pre-gate on deterministic pass could cut calls 30-60% per `05-web.md` cascade literature → **~900-1800 s** potential if combined with router. Quality risk: low for deterministic pre-gate, high for batching prompts.

- [HIGH] **Within-batch parallelism uses vLLM true batching (local) or ThreadPoolExecutor (API), not cross-stage parallelism.** Local vLLM: all items in a batch share one `generate()` (`vllm_engine.py:322`). API engine: `ThreadPoolExecutor(max_workers=min(concurrency, len(batch)))` fires concurrent HTTP requests (`api_openai_compatible_engine.py:202-220`). Picture API model explicitly avoids multi-image HTTP batch because "vllm won't allow more than 1" (`picture_description_api_model.py:54-68`), default API `concurrency=1` (`pipeline_options.py:749`). Impact: **portable pattern** — parallel tapetum unit checks within one paper (5 concurrent HTTP calls, distinct prompts) collapses the serial 5×20 s unit phase to ~20 s per paper. Unit checks are ~1510/2284 = 66% of calls; serial-within-paper makes them ~1510×20 s = 30200 call-seconds vs fleet-parallel 1888 s wall share. In-paper parallel recovers up to **~1510 s** on the 3003 s run (1888→378 s on unit phase), landing ~**1493 s (~25 min)**. Quality risk: medium — MoE batch-composition variance at concurrency 16 (`05-web.md`, `00-baseline.md` measured regression at seq 32).

- [MED] **Cross-document and cross-page concurrency knobs exist but default to serial.** `doc_batch_size=1`, `doc_batch_concurrency=1` with explicit warning "No benefit expected without free-threaded python" (`settings.py:30-31`); `page_batch_concurrency=1` marked "Currently unused" (`settings.py:33`); `document_converter.py:672-674` only threads when both doc batch settings >1. Threaded PDF pipeline adds stage batch sizes (`ocr/layout/table_batch_size=4`, `batch_polling_interval_seconds=0.5`, `queue_max_size=100`) for **local CV models** (`pipeline_options.py:1908-1960`, `standard_pdf_pipeline.py:567-568`). Impact: doc batch threading is **not portable** (GIL caveat); stage pipelining applies to local inference not HTTP judge. Tapetum already exceeds docling at fleet level (`_DEFAULT_CONCURRENCY=32`, `00-baseline.md`). Quality risk: none.

- [MED] **Identical prompt across pages maximizes prefix-cache reuse in VlmPipeline.** Every page in a batch gets the same `model_spec.prompt` (`vlm_convert_model.py:178`); shared generation template built once per batch (`vlm_convert_model.py:108-135`). Impact: **partially portable** — tapetum already shares `CONVERSION_CONTRACT` prefix but appends per-call random guard tag at system-prompt end (`00-baseline.md:48-52`). Moving guard to user message (unique query last, per `05-web.md` APC pattern) could lift prefix hits toward docling's 74% APC recovery on DeepSeek-V4 (`05-web.md` Q1). At 4.5× server throughput (`05-web.md`), 3003 s → **~667 s (~11 min)** if fully realized — but shared document body is re-sent per call today, limiting hit rate. Quality risk: low if guard tag placement only.

- [LOW] **Picture classification is a local image-classification engine, not an LLM call.** Evidence: `document_picture_classifier.py:24-28,95-101` uses `create_image_classification_engine`, not VLM. Impact: not applicable to tapetum; confirms docling's enrichment census must distinguish VLM stages (picture desc, code/formula, VlmPipeline convert) from CV classifiers.

## False-pass hypothesis

Parallelizing tapetum's 5 in-paper unit checks (docling's `ThreadPoolExecutor` API pattern) at fleet slot saturation increases concurrent MoE requests on DeepSeek-V4, reproducing the batch-composition variance that already broke quality-stability at `max-num-seqs=32` (`00-baseline.md:82`), silently flipping unit verdicts on papers that currently pass.

## False-fail hypothesis

Adopting docling's default-off enrichment model literally — skipping unit checks on pages where deterministic metrics look clean — would false-fail good conversions on pages where OCR/layout pass but semantic conversion errors (wrong heading level, dropped table row) only surface in the full-markdown judge context.

## What would change my mind

A tapetum A/B on 381 papers showing in-paper parallel unit checks (5 concurrent, distinct prompts, same schemas) with zero verdict drift vs the current serial chain and ≥4× wall reduction on the unit-check phase.
