# 90 - langextract-Quality-Speed

**Verdict:** usable-with-conditions — LangExtract documents every quality-vs-speed dial explicitly but publishes **no quantitative recall uplift** for multi-pass and **no production quality floor**; defaults are speed/cost-biased (`extraction_passes=1`, `max_char_buffer=1000`) with opt-in thorough profiles, which supports tunable tapetum tiers only if we ablate the 16/381 verdict-changed papers.
**Confidence:** high

## Findings

- [CRITICAL] **Google documents no production quality floor — all recall/accuracy knobs are user-tunable with speed-biased defaults.** Shipped `extract()` defaults: `extraction_passes=1`, `max_char_buffer=1000`, `batch_length=10`, `max_workers=10` (`extraction.py:53-58,64`). Benchmark suite mirrors: `default_extraction_passes: int = 1` (`benchmarks/config.py:48`). README "production" guidance is **throughput/rate-limit tiering** ("paid Gemini tier … increase throughput and avoid rate limits"), not minimum quality settings (`README.md:118`). Model choice is advisory: Flash = "recommended default … strong extraction quality"; Flash-Lite = "high-volume or cost-sensitive"; Pro = "highly complex tasks requiring deeper reasoning" (`README.md:118`). Accuracy disclaimer: "contingent upon the selected LLM, the complexity of the task, the clarity of the prompt instructions, and the nature of the prompt examples" (`README.md:45`). Internal skill doc: "Start with [extraction_passes=] 1 and increase only if recall is insufficient" (`skills/langextract-usage/SKILL.md:186-187`). Impact: our "same quality" constraint **permits** nightly/weekly profile tiers (langextract/marker pattern) because Google treats quality as operator choice, not a enforced minimum — but we still owe evidence that a reduced tier misses ≤ agreed delta on the 381-paper fleet (`00-baseline.md:29-30`, 16 verdict-changed papers). Quality risk: adopting tiers without ablation repeats marker's `use_llm=False` false-pass class.

- [CRITICAL] **`extraction_passes`: documented recall lever, default OFF, linear cost multiplier — no published recall percentages.** Docstring: "Supports sequential extraction passes to improve recall at the cost of additional API calls" (`extraction.py:80-81`); "extraction_passes=3 reprocesses tokens 3x" (`extraction.py:154-160`). Annotator: "Values > 1 reprocess tokens multiple times, potentially increasing costs with the potential for a more thorough extraction" (`annotation.py:237-241`). README/long-text example promote `extraction_passes=3` as user opt-in ("Improves recall through multiple passes", `README.md:156-157`; "Multiple extraction passes improve recall", `longer_text_example.md:154-158`). Mechanism: independent full re-chunk→infer→align per pass; merge with **first-pass-wins** on overlaps (`annotation.py:46-84`, `477-528`; `longer_text_example.md:156-158`). **No 1-pass vs 3-pass entity-count or F1 table in-repo** — only qualitative claims plus one demo output: 4,088 entities from Romeo & Juliet at `extraction_passes=3` (`longer_text_example.md:71-73,134`) with no single-pass baseline. Impact: langextract's recall knob is **cost-linear and evidence-qualitative**; inverting tapetum to default-off unit/page stages (analogous to `extraction_passes=1`) saves ~67% calls → ~948–997 s on one pod (`00-baseline.md:22-25`, persona 83/66 census), not 5–10 min without dual-pod or latency levers. Quality risk: 16/381 papers whose merged verdict changed only after unit checks (`00-baseline.md:29-30`).

- [HIGH] **`max_char_buffer`: smaller chunks = more API calls + claimed accuracy gain; two default surfaces.** `extract()` default `max_char_buffer=1000` (`extraction.py:53,109`); raw `Annotator.annotate_documents` default **200** (`annotation.py:213`). Cost doc: "Smaller max_char_buffer values increase the number of API calls" (`extraction.py:95-96`). Quality doc: README "Smaller contexts for better accuracy" (`README.md:158`); longer-text guide "chunked processing approach can improve extraction quality over a single inference pass on a large document" and "maintain extraction quality across large documents" via smaller `max_char_buffer` + parallel workers (`longer_text_example.md:164-167`). ChunkIterator respects sentence/newline/token boundaries (`chunking.py:350-379`). Impact: langextract trades **call count for scoped prefill and accuracy** — opposite of our full-markdown ×6 re-prefill (`00-baseline.md:43-47`). Raising buffer toward our `MAX_PAPER_MD_CHARS=500_000` analog cuts calls but docs warn accuracy may drop (`longer_text_example.md:164-167`). Quality risk: cross-page defects without `context_window_chars` (`extraction.py:161-164`, default None).

- [HIGH] **`max_workers` + `batch_length`: pure wall-clock parallelism, zero token/call savings.** Docstring: "max_workers improves processing speed **without additional token costs**" (`extraction.py:97-98`); effective parallelism `min(batch_length, max_workers)` (`extraction.py:122-127`); warning when `batch_length < max_workers` (`extraction.py:243-248`). Defaults: `batch_length=10`, `max_workers=10` (`extraction.py:57-58`); Gemini provider default `max_workers: int = 10` (`gemini.py:129`). Implementation: ThreadPoolExecutor when `len(batch_prompts) > 1` (`gemini.py:475-504`). README example uses `max_workers=20` "Parallel processing for speed" alongside quality knobs (`README.md:157-158`). Impact: copying max_workers to tapetum enables **in-paper parallel unit checks** (advisory lane D11-exempt, `00-baseline.md:95-96`) — wall reduction on serial 6-call papers (~120 s each, `00-baseline.md:38-39`) without eliminating calls; MoE batch-composition variance is the quality risk. No impact on 2284-call census if serial within paper stays.

- [HIGH] **Model guidance: Flash default for quality; Pro for reasoning depth; no mandated Pro for production.** README: "`gemini-3.5-flash` is the recommended default, offering strong extraction quality for LangExtract's schema-constrained workflows" (`README.md:118`); Pro only for "highly complex tasks requiring deeper reasoning"; Flash-Lite for volume/cost (`README.md:118`). Skill doc: "`gemini-2.5-flash` recommended for most tasks; `gemini-2.5-pro` for complex reasoning" (`skills/langextract-usage/SKILL.md:189-190`). Quick-start uses Flash only (`README.md:109`). Impact: external precedent for a **cheap default judge + escalate-to-deep** cascade (`05-web.md` Q5 LLMTrace/SAJA) without declaring Flash insufficient for production — aligns with persona 24 cascade designer. Quality risk: our DeepSeek-V4 monolith may carry defects Flash-tier nightly misses; needs measured agreement on 381-paper subset.

- [MED] **Comparison table: langextract dials vs tapetum lane dials.**

  | Concern | langextract (default → thorough opt-in) | tapetum_llm (fleet default → exhaustive opt-in) |
  | --- | --- | --- |
  | Recall / coverage multiplier | `extraction_passes=1` → `=3` (linear API cost, first-pass-wins merge; `extraction.py:154-160`, `annotation.py:46-84`) | Fixed ~6-call cascade → `--exhaustive-units` / `--all-pages` (no cap; `constants.py:223`, `cli.py:301-312`) |
  | Scoped check budget | ~`len(doc)/max_char_buffer` chunks/pass (1000 default, 200 Annotator; `extraction.py:53`, `annotation.py:213`) | `MAX_UNIT_CHECKS=5` + `MAX_PAGE_ESCALATIONS=5` (`constants.py:191,223`) |
  | Payload per call | One chunk + optional prior-source tail (`context_window_chars`; `extraction.py:161-164`) | Full candidate markdown + one page/unit source (`00-baseline.md:43-47`) |
  | Parallelism | In-document `max_workers`×`batch_length` (`gemini.py:475-504`) | Cross-paper 32, serial within paper (`00-baseline.md:34-42`) |
  | Quality-speed default posture | Quality multipliers **OFF** at API defaults | Quality multipliers **ON** (full cascade every cold run) |
  | Production "floor" | None documented — operator tunes | Fidelity rules forbid cutting caps without equivalence proof (`00-baseline.md:84-85`) |

  Impact: structural isomorphism to marker persona 66 — external systems default fast, we default thorough; langextract gives vocabulary (`extraction_passes`, buffer size, worker count) for tier naming but not call-count parity (80+ chunk calls/doc vs our 6). Quality risk: lowering our caps without tier fingerprinting poisons incremental cache (`cli.py:112-113`, coverage_mode).

- [LOW] **Alignment/resolver dials are quality-precision knobs with fixed defaults, not speed levers.** `resolver_params` documents fuzzy threshold 0.75, density 1/3, etc. (`extraction.py:139-145`); post-LLM align adds zero API calls (`annotation.py:404-429`). Impact: irrelevant to 3003 s LLM wall; portable for grounding precision only. Quality risk: lowering fuzzy gates increases false-pass on spans (`resolver.py:57-58` per prior audit).

## False-pass hypothesis

Adopt langextract-style defaults literally on tapetum — fleet `extraction_passes=1` analog (monolith + metadata only, no unit checks): a table-cell transposition or secno-heading drift that monolith/metadata miss but a scoped unit check would catch ships with advisory pass until a manual `--exhaustive-units` re-run, mirroring the 16/381 verdict-changed long tail (`00-baseline.md:29-30`) while langextract's own demo never compares pass-1 vs pass-3 entity yield (`longer_text_example.md:134`).

## False-fail hypothesis

Weekly `--all-pages` full cascade on papers whose sidecar already has `coverage_mode=all_pages` (superset skip, `tapetum_llm.md:320`) wastes serial wall on unchanged markdown; advisory review noise without new defects — not a gate false-fail, but violates operator expectation if tier schedule is misconfigured.

## What would change my mind

A langextract-style ablation published in-repo: Romeo-scale or WG21-scale fixture with **paired** runs at `extraction_passes={1,2,3}` reporting entity-count delta and grounded-entity precision, OR our 381-paper tapetum tier test (monolith+metadata vs full cascade) with verdict-delta ≤ 2% at ≥ review severity — either would quantify the recall knob Google leaves qualitative.
