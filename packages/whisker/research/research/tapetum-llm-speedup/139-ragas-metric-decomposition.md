# 139 - ragas-Metric-Decomposition

**Verdict:** usable-with-conditions — ragas's extract-then-batch-verify pattern (2 calls, list-schema NLI) is the right model for a *verification* sub-step, but it does not map 1:1 onto our unit checks, which combine scoped discovery with verification and resend full markdown per call; porting only the list-verification half is a medium wall lever with medium quality risk, not a 6× lever alone.
**Confidence:** high

## Findings

- [CRITICAL] **Faithfulness = exactly 2 LLM calls per sample: statement extraction, then ONE batched NLI over all statements.** Call 1: `StatementGeneratorPrompt.generate` on `{question, answer}` → `StatementGeneratorOutput.statements: List[str]` (`_faithfulness.py:166-180`, schemas `:25-31`). Call 2: `NLIStatementPrompt.generate` on `{context: joined(retrieved_contexts), statements}` → `NLIStatementOutput.statements: List[StatementFaithfulnessAnswer {statement, reason, verdict: 0|1}]` (`_faithfulness.py:152-164`, `:58-65`). Score = faithful count / N (`_faithfulness.py:182-194`). v2 collections mirror the same 2-step pipeline (`collections/faithfulness/metric.py:116-128`, `139-146`). Prompt assembly: static instruction + embedded JSON Schema + 1–2 few-shot examples + input JSON (`prompt/pydantic_prompt.py:89-134`); measured static prefix ~3–4 k chars for faithfulness, NLI input grows ~O(N) with statement count only, not N separate round-trips.

- [CRITICAL] **Context recall = 1 LLM call with list output (not N classification calls).** Single `ContextRecallClassificationPrompt.generate` on `{question, context, answer}` → `ContextRecallClassifications.classifications: List[{statement, reason, attributed: 0|1}]` (`_context_recall.py:131-156`, schemas `:35-42`). v2: one `llm.agenerate(..., ContextRecallOutput)` (`collections/context_recall/metric.py:112-119`, `util.py:36-41`). Legacy `generate_multiple` without `n=` defaults to n=1 ensemble hook, not per-sentence calls (`prompt/pydantic_prompt.py:177-186`, `_context_recall.py:137-145`). Impact: ragas batches sentence-level attribution in one structured list; our serial unit loop (`unit_judge.py:389-416`) is the anti-pattern they avoid for homogeneous yes/no judgments.

- [HIGH] **Context precision = K calls where K = len(retrieved_contexts) — ragas does NOT batch across chunks.** Serial loop: one `ContextPrecisionPrompt.generate` per context chunk → single `Verification {reason, verdict: 0|1}` (`_context_precision.py:148-160`, `:34-37`). v2 identical per-context loop (`collections/context_precision/metric.py:104-112`). Average-precision score computed downstream (`_context_precision.py:113-132`). Impact: ragas only batches *within* a call (many statements / many questions); heterogeneous contexts stay separate calls. Our page-escalation loop (`pdf_judge.py:753`) matches this pattern, not faithfulness batching.

- [HIGH] **Answer relevancy = 3 identical LLM calls (strictness default), not 1 batched multi-question call.** `question_generation.generate_multiple(..., n=self.strictness)` with `strictness=3` (`_answer_relevance.py:94`, `:142-144`) → each returns `{question, noncommittal: 0|1}` (`_answer_relevance.py:26-28`). For LangChain backends this duplicates the same prompt 3× (`prompt/pydantic_prompt.py:247-252`); embeddings aggregate cosine similarity across the 3 generated questions (`_answer_relevance.py:96-127`). Impact: ragas "multi-call" here is variance reduction, not throughput batching — do not confuse with list-schema verification.

- [HIGH] **Factual correctness reuses faithfulness NLI batching: 2–4 calls depending on mode.** Per direction: `decompose_claims` (1 call → `ClaimDecompositionOutput.claims: List[str]`, `_factual_correctness.py:225-234`) then `verify_claims` with batched `NLIStatementInput` (`_factual_correctness.py:236-250`, reuses `_faithfulness.py:NLIStatementPrompt`). F1 mode runs both directions via `asyncio.gather` (`_factual_correctness.py:265-280`) = 4 calls total; precision mode skips reverse direction = 2 calls. Impact: ragas's portable primitive is "decompose once, verify many in one list call," not parallel per-claim loops.

- [HIGH] **Answer correctness = 3 LLM calls with one batched TP/FP/FN classifier.** Two `StatementGeneratorPrompt` calls (response + reference) (`_answer_correctness.py:226-234`), then one `CorrectnessClassifier.generate` on `{question, answer: List[str], ground_truth: List[str]}` → `{TP, FP, FN: List[{statement, reason}]}` (`_answer_correctness.py:239-251`, `:40-48`). Summarization = 3 sequential calls with two list outputs: keyphrases → questions list → answers list batched in one call (`_summarization.py:174-238`, `:29-34`, `:105-109`). Impact: even ragas's heaviest multi-step metrics cap list outputs at one generation per step; none pack unrelated rubrics into one prompt.

- [MED] **Our unit check is discovery+verification in one call; ragas splits them.** `_check_one_unit` sends `UNIT_CHECK_SYSTEM_PROMPT` (~5.5 k chars incl. `CONVERSION_CONTRACT`, `unit_judge.py:129-159`) + full `candidate_md` + one page `source_text` per call (`unit_judge.py:756-777`), output `UnitCheck {defects: List[DefectFinding] max 5, verdict, confidence}` (`models.py:298-314`). Census: ~1510 unit calls serial per paper (`00-baseline.md:22-23`, `unit_judge.py:389`). Ragas faithfulness never sends the full answer twice for verification — context once, all statements once (`_faithfulness.py:157-159`). Impact: biggest tapetum waste is 6× full-markdown prefill (`00-baseline.md:43-44`), not fixable by list-schema alone; batching verification without scoping candidate_md still prefills the whole doc.

- [MED] **List-schema verification batching is plausibly distinct from RuVerBench multi-rubric packing.** RuVerBench drops double digits when packing 4–5 *different rubrics* per call on long agentic tasks (`05-web.md:96-98`). Ragas batches *homogeneous* binary NLI items sharing one context and one instruction (`_faithfulness.py:73-74`, `NLIStatementOutput`). Portable sub-pattern for tapetum: after monolith/page-screen emits short defect hypotheses, one `{context_i, claims[]}` verify call per page (or per paper if ≤5 claims) mirroring `NLIStatementPrompt`. Impact: on papers with findings, could collapse 2–5 unit calls into 1 verify call (~600–900 calls saved → ~750–1125 s fleet at 20 s/call and 16 slots, upper bound if all 1510 unit calls replaced — unrealistic without discovery rework). Quality risk: **medium** — Batch Prompting shows accuracy falls as per-item context grows (`05-web.md:63-64`); WG21 page sources are longer than RAG chunks ragas targets.

## False-pass hypothesis

Replacing 5 serial unit checks with one ragas-style batched verify call over monolith-extracted claims, without per-page source text in the prompt: a localized table cell swap visible only when page-7 source is paired with candidate markdown gets dropped because the batched prompt omits that page's source block or the model attends to higher-salience claims first — silent pass on a defect today's scoped `_check_one_unit` catches.

## False-fail hypothesis

Batching verify-only calls while keeping monolith discovery: the monolith emits a false `constexpr`-count claim for page 3; the batched verifier returns `verdict=0` for all 5 bundled statements because shared candidate_md context is ambiguous, demoting a clean paper to `review` where serial unit checks (with explicit page source) returned zero defect groups (70% baseline, `00-baseline.md:29-30`).

## What would change my mind

A stratified A/B on 50 papers with non-zero unit findings: (A) current serial `UnitCheck` vs (B) monolith extract + single `NLIStatementPrompt`-shaped batched verify per paper with per-claim page context included — showing identical merged verdict on all 16/381 verdict-changed papers (`00-baseline.md:29-30`) and zero new false-fails on the golden holdout.
