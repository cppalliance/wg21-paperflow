# 70 - olmocr-Work-Queue

**Verdict:** usable-with-conditions (+ olmOCR's lock/done-flag work queue is portable for distributed resume, but its within-item page flood does not improve our slot utilization because we are already 16/16 slot-saturated at c=32 and total slot-seconds is invariant under in-paper parallel bursts per persona 20)
**Confidence:** high

## Findings

- [CRITICAL] **Work items are ~500-page bundles of PDF paths, not single documents.** Evidence: `WorkItem` holds `hash` + `work_paths: List[str]` (`work_queue.py:30-35`); `populate_queue` chunks new paths into groups of `items_per_group` (`work_queue.py:127-151`); default `--pages_per_group 500` for self-hosted vLLM, 50 for remote `--api_key` (`pipeline.py:1314-1315`); `items_per_group = max(1, int(pages_per_group / avg_pages_per_pdf))` after sampling up to 100 PDFs (`pipeline.py:1379-1408`). Impact: olmOCR's scheduling grain is **~500 pages ≈ tens of PDFs**, not one page; our analogue is **one paper ≈ 6 calls**, two orders of magnitude smaller. Quality risk: none from mapping alone.

- [CRITICAL] **Lock-based coordination: filesystem locks + done flags, stale-lock recovery at 1800 s.** Evidence: dirs `worker_locks/` and `done_flags/` (`work_queue.py:26-27`); lock path `worker_{hash}.lock` (`work_queue.py:305-307`); done path `done_{hash}.flag` (`work_queue.py:309-311`); `is_worker_lock_taken` returns False when lock mtime age exceeds `worker_lock_timeout_secs` default **1800** (`work_queue.py:323-337`, `174`); comment "Create lock (overwrites if stale)" on successful claim (`work_queue.py:210-212`); `mark_done` writes done flag then deletes lock (`work_queue.py:221-230`). `get_work` loop skips completed (local cache + backend, refresh after 3 stale hits at `work_queue.py:178-203`) and locked items (`work_queue.py:205-208`). Impact: pattern is for **multi-worker S3 resume**, not GPU fill; portable if we shard 381 papers across pods with crash recovery. Expected wall saving on single-pod cold run: **0 s**. Quality risk: none from locks; duplicate work on lock failure is explicitly tolerated (`work_queue.py:350-351`).

- [CRITICAL] **Per-worker loop: get work → submit ALL paths/pages concurrently → TaskGroup drain → mark_done → next.** Evidence: `worker()` infinite loop calls `get_work()` (`pipeline.py:698-705`); wraps every path in `asyncio.TaskGroup` — PDF via `process_pdf`, tarball via `process_tarball` (`pipeline.py:711-718`); logs `Finished TaskGroup` only after all tasks complete (`pipeline.py:721`); then `mark_done(work_item)` (`pipeline.py:802`). Within each PDF, second TaskGroup fires **all pages 1..N concurrently** (`pipeline.py:548-551`); collects `[task.result() for task in page_tasks]` before document assembly (`pipeline.py:553-554`). Impact: olmOCR's "drain before next item" is **structural await on TaskGroup**, not a pending-count poll (contrast retry-only use of `vllm_queued_requests == 0` at `pipeline.py:345-346`). Our paper adjudication already drains before sidecar write (`cli.py:1120-1238`). Quality risk: none from keeping drain semantics.

- [CRITICAL] **Slot utilization: work-item burst does not beat our cross-paper serial chain on the 3003 s fleet.** Evidence: olmOCR bounds HTTP with `max_concurrent_requests_limit = BoundedSemaphore(1600)` default (`pipeline.py:88`, `1224`, `1289`, acquired per page POST at `pipeline.py:184`); **20 workers** each hold one work item until TaskGroup exit (`pipeline.py:1223`, `1457-1458`). Our fleet: **32 papers** in flight, **1 LLM call at a time per paper** (`00-baseline.md:34-42`, `pdf_judge.py:753`, `unit_judge.py:389`); server **16 slots** (`00-baseline.md:24-25`). Steady-state: we already emit **≤32 concurrent HTTP requests** for **16 decode slots** → **~100% slot utilization** when corpus is large (c=16→c=32 A/B saved only **4.2%**, `28-semaphore-topologist.md:10`). Persona 20 dependency analysis: after CPU prep, up to **W=12** calls per paper have **no prompt dependencies** (`20-in-paper-parallelist.md:8-9`), but **total slot-seconds = 2284 × ~20 s = 45,680 regardless of serial vs parallel scheduling** (`20-in-paper-parallelist.md:12-13`); fleet wall model **2284 × 20 / 16 ≈ 2855 s** closes on measured **3003 s** (`00-baseline.md:22-25`). Work-item-style grouping (burst all 6 calls after deterministic phase): projected fleet saving **~0 s (±30–90 s tail, 1–3%)** (`20-in-paper-parallelist.md:14-15`), not the 25× gap to 5–10 min. Quality risk: **HIGH** MoE batch-composition variance from heterogeneous simultaneous prompts (`20-in-paper-parallelist.md:16-17`, `MODELS.md:69-70`).

- [HIGH] **Why olmOCR's pattern works for them but not our slot math: homogeneous page calls + localhost + deep server queue.** Evidence: each page sends static YAML prompt + **unique page image** (`pipeline.py:133-146`); no shared multi-kilobyte document prefix resent per call (contrast our full `candidate_md` ×6, `00-baseline.md:43-47`). Internal server `http://localhost:{port}/v1` (`pipeline.py:1432-1434`); no RunPod ~100 s proxy TTFT ceiling (`77-olmocr-queue-drain.md:22`, `28-semaphore-topologist.md:12-13`). olmOCR throughput (1288 pages in 5m07s, 3050 tok/s on H100, `05-web.md:37-39`) comes from **page-level parallelism on dense 7B FP8**, not from work-item grouping reducing call count. Impact: copying the **coordination shell** (locks, done flags, ~N-page grouping for resume) helps multi-pod sharding; copying the **within-item flood** without call elimination does not move the 3003 s needle. Quality risk: **HIGH** if 32×12=384 burst deep-queues HTTP through RunPod proxy → 524 tombstones (`77-olmocr-queue-drain.md:26-27`).

- [HIGH] **Granularity mismatch: olmOCR groups for blast radius and spend control, we would group for paper-depth only.** Evidence: remote API lowers `pages_per_group` to 50 because "not to overwhelm such servers / not to waste money if a group doesn't finish right away" (`pipeline.py:1312-1315`); tarballs always `items_per_group=1` (`pipeline.py:1410-1412`). Atomic completion requires all pages valid or whole PDF aborts (`pipeline.py:543-544`, `559-563`). Our paper already has atomic sidecar + fingerprint skip (`00-baseline.md:57-58`); grouping 6 calls into one burst changes **per-paper wall** (~120 s → ~20–30 s critical path, `20-in-paper-parallelist.md:10-11`) but **not slot-seconds**. Quantified per-paper win: **~4–6×** single-paper latency; fleet win: **~0×** (`20-in-paper-parallelist.md:10-13`). Quality risk: parallel unit checks under slot contention can timeout → `coverage_complete=false` advisory review cap (`20-in-paper-parallelist.md:30-31`).

- [MED] **olmOCR separates CPU render sem from HTTP sem; our CPU sits inside paper sem and blocks cross-paper dispatch.** Evidence: `pdf_render_max_workers_limit` from CPU count, acquired in `build_page_query` (`pipeline.py:87`, `109-111`); HTTP sem separate (`pipeline.py:184`). Our `screen_pages` / `ground_spans` run synchronously on asyncio loop between serial LLM awaits (`28-semaphore-topologist.md:16-17`, `pdf_judge.py:628-636`). Impact: olmOCR-style "prep outside burst" aligns with persona 20's shared CPU prep phase (`20-in-paper-parallelist.md:8`); offloading CPU to threads saves **≤1–2% fleet wall (~30–60 s)**, orthogonal to work-item grouping (`28-semaphore-topologist.md:16-17`). Quality risk: none from CPU offload alone.

- [LOW] **Completion markers enable incremental resume at work-item grain; we resume at whole-paper fingerprint only.** Evidence: `get_completed_hashes` scans `done_*.flag` files (`work_queue.py:297-303`, `407-416`); `initialize_queue` subtracts done from index and shuffles remainder (`work_queue.py:161-165`). Our skip is per-paper SHA-256 fingerprint (`00-baseline.md:57-58`); changed markdown reruns entire 6-call cascade. Impact: per-call or per-unit fingerprints (separate lever) could save calls on edit; work-item locks do not. Quality risk: per-unit skip needs fail-closed coverage proof (`00-baseline.md:102-103`).

## False-pass hypothesis

Burst all 12 independent calls per paper under c=32 while MoE runs without batch-invariant kernels: monolith draw under a fat heterogeneous batch routes to "pass" expert composition where serial rerun would demote to review; fusion cannot promote to deterministic pass but operator treats advisory `suggested_verdict` as verified (`20-in-paper-parallelist.md:26-27`, ≥25% flip baseline). Work-item grouping increases simultaneous prompt-shape diversity versus today's one-call-at-a-time per paper.

## False-fail hypothesis

Adopting olmOCR's 20-worker / one-item-at-a-time ratio by lowering tapetum `--concurrency` from 32 to 20: measured c=16→32 gain is only 4.2% (`28-semaphore-topologist.md:10`); cutting to 20 loses ~2% fill with zero quality benefit — pure infrastructure slowdown, not a conversion false-fail (`77-olmocr-queue-drain.md:30-31`).

## What would change my mind

A measured A/B on the live 381-paper cold fleet: **(A)** current serial in-paper + c=32 vs **(B)** paper-as-work-item burst (all prep-independent calls parallel after deterministic phase) + c=32, same 2284 calls and 16 slots, reporting fleet wall **>10% reduction** AND merged-verdict / defect-group recall within the MoE drift band (≤2 pp on the 16 papers whose merged verdict changed, `00-baseline.md:29-30`, `20-in-paper-parallelist.md:34-35`) — would upgrade work-item-style grouping from "~0 s fleet utility" to "material slot-utilization lever."
