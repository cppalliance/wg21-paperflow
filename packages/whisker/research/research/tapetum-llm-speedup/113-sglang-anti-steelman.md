# 113 - sglang-Anti-Steelman

**Verdict:** garbage — sglang pod migration cannot reach the 5–10 min cold-fleet target, inherits active radix-cache correctness churn on DeepSeek-V4-Pro, and its incremental prefix win over a correctly tuned vLLM APC stack (~0–120 s) is dwarfed by ~100–150 min full revalidation and shared-pod operational risk.
**Confidence:** high

## Findings

- [CRITICAL] **Shared-pod swap is another team's infra on a 24/7 vLLM endpoint we do not control.** `alliance-pod` is a shared RunPod vLLM instance billed per uptime-hour (`SERVICES.toml:64-69`, `00-baseline.md:65-66`); replacing it with sglang requires a maintenance window, container rebuild, and cold KV on a endpoint other workloads may share. Concurrent non-tapetum traffic already perturbs MoE batch composition (`MODELS.md:77-78`, `102-vllm-anti-steelman.md:20`). Impact: migration is not a flag flip — it is a fleet-wide outage plus revalidation budget before any wall-clock claim. Quality risk: undetected verdict drift if validation is skipped.

- [CRITICAL] **Python API path is GIL-bound under the concurrency regime sglang itself documents as problematic.** Primary serving surface is FastAPI/Uvicorn over `TokenizerManager` (`research/repos/sglang/python/sglang/srt/entrypoints/http_server.py:17-18`, `:46-51`, `:155`, `:2497-2534`). Benchmark issue [#21061](https://github.com/sgl-project/sglang/issues/21061) at 150 concurrent requests: sglang throughput **<50% of vLLM**, host CPU capped at **~127%** (single-core GIL), maintainer cites Python router GIL contention; experimental mitigation is C++ radix tree via `SGLANG_EXPERIMENTAL_HIRADIX_CACHE=1`. RFC [#22558](https://github.com/sgl-project/sglang/issues/22558) states HTTP requests acquire the GIL for parsing, tokenization, and response serialization — "under high concurrency these become the bottleneck — not the GPU." Our fleet runs **32 client papers × 16 server slots** (`00-baseline.md:34-35`, `:66`); not 150-way flood, but the same Python orchestration layer serializes under burst. Impact: expected saving **≤120 s** on 3003 s from prefix scheduling (`106-sglang-radixattention.md:12-14`) is at risk of being eaten by API-layer contention when cross-paper bursts align; quality risk none, operational risk HIGH.

- [CRITICAL] **Radix-cache bugfix velocity is high; a judge fleet inherits every stale-hit / OOB class.** Release notes (v0.5.10–v0.5.12.post1) list **≥18 cache-correctness fixes** in six months, including: DSV4 HiCache + `SGLANG_OPT_CACHE_SWA_TRANSLATION=1` returns **stale translation indices after cache rebuild → OOB writes / wrong outputs** ([#25889](https://github.com/sgl-project/sglang/releases)); DSV4 EAGLE/MTP disagg decode crashes at ~2000 req from **stale sliding-window mappings** ([#25805](https://github.com/sgl-project/sglang/releases)); UnifiedTree **tombstone replay**, **cascade_evict leaf**, **partial match on evicted+backuped nodes** ([#24972](https://github.com/sgl-project/sglang/releases), [#25068](https://github.com/sgl-project/sglang/releases), [#24943](https://github.com/sgl-project/sglang/releases)); streaming/chunked **KV cache leaks** ([#20070](https://github.com/sgl-project/sglang/releases), [#20476](https://github.com/sgl-project/sglang/releases)); Spec-V2 **stale-state** ([#23456](https://github.com/sgl-project/sglang/releases)). DeepSeek-V4 SWA radix matching is tombstone-aware with non-trivial invariants (`swa_radix_cache.py:888-918`). Disaggregation code assumes **"CPython GIL guarantees ordering"** between scatter flags and events (`staging_handler.py:226-228`) — a correctness contract that free-threaded Python explicitly breaks ([#22889](https://github.com/sgl-project/sglang/issues/22889)). Impact: silent wrong KV on shared `CONVERSION_CONTRACT` + `candidate_md` prefixes could change structured defect groups while wall time improves — **quality-stability violation** on the advisory lane. Expected wall saving if cache were perfect: **500–900 s** (`15-prefix-cache-enabler.md`); actual net depends on hit rate AFTER client reorder, not engine brand alone.

- [HIGH] **DeepSeek-V4-Pro on sglang is younger and noisier than vLLM's official recipe on the same hardware class.** vLLM ships a verified H200 recipe (TP+EP, `--max-num-seqs 16`, FP8 KV, MTP) at [recipes.vllm.ai/deepseek-ai/DeepSeek-V4-Pro](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4-Pro) plus merged PR [#43447](https://github.com/vllm-project/vllm/pull/43447) for SWA+APC retention (`05-web.md:6-17`). sglang has a cookbook ([DeepSeek-V4 docs](https://docs.sglang.io/cookbook/autoregressive/DeepSeek/DeepSeek-V4)) and model registration (`deepseek_v4.py:98`, `:627`), but **v0.5.12.post1** was a stability patch "primarily for DeepSeek V4" fixing garbled single-token decode on B200/B300 ([#25733](https://github.com/sgl-project/sglang/releases)), stale SWA cache ([#25805](https://github.com/sgl-project/sglang/releases)), and wrong HiCache indices ([#25889](https://github.com/sgl-project/sglang/releases)). ROCm sparse prefill is disabled by default because it "returns incorrect output" (`deepseek_v4_hook.py:27-37`). olmOCR **migrated sglang → vLLM** at v0.1.75 for production OCR serving (`05-web.md:46-47`). Impact: we would be early adopters on a moving DSV4 cache stack; vLLM APC determinism concerns are documented separately (`104-vllm-apc-determinism.md`) but on a stack already wired to `VllmThinkingBackend`. Quality risk: **HIGH** until persona-47 equivalence passes; engineering cost **2–5 days** parity bake-off minimum (`106-sglang-radixattention.md:20`).

- [HIGH] **Counterfactual: vLLM APC + prompt reorder captures most of sglang's prefix win; residual sglang edge is small on our call pattern.** Q4 cards: with **unique prompts**, sglang vs vLLM gap **collapses**; with **shared prefixes**, sglang leads up to **6.4×** prefix-heavy vs vLLM baseline, but vLLM APC on the correct layout ([static system] → [shared document] → [unique query LAST], `05-web.md:69-77`) yields **74.3% hits**, **4.5× server tok/s**, **−78% TTFT** at c=16 (PR #43447 + gingerlabs card, `05-web.md:6-12`, `:69-73`). Without shared prefixes, APC adds **~36.7% overhead** (squeezebits, `05-web.md:81-82`) — applies to BOTH engines until guard-tag reorder lands (`00-baseline.md:48-52`). sglang's incremental mechanisms beyond block-APC — page-aligned radix split (`radix_cache.py:398`, `:535-537`), default-OFF LPM scheduling (`server_args.py:776-791`, `schedule_policy.py:147-151`) — buy **~0 s** on our serial 6-call chains because call N+1 is submitted only after call N completes (`00-baseline.md:36-42`, `106-sglang-radixattention.md:14-15`). Impact: after client reorder + vLLM retention env, incremental sglang migration saving is **~0–120 s** on 3003 s (`106-sglang-radixattention.md:12`), not the **1500–2400 s** still needed for ≤600 s target (`102-vllm-anti-steelman.md:12-13`). Quality risk: none from arithmetic; false economy if migration skips cheaper client levers first.

- [HIGH] **Engine swap triggers full persona-47 revalidation, not server-only exemption.** Model/engine change is explicitly **NOT exempt** from the 381-paper equivalence gate (`47-quality-equivalence.md:20`): requires **A1 + A2 + B1 ≈ 150 min** (3 × 50 min cold fleet) or accepted shortcut **A1 + B1 ≈ 100 min** with weekly A/A baseline (`47-quality-equivalence.md:16-17`). Adoption rule: `flip_AB ≤ flip_AA + margin` where identical reruns already flip **≥25%** of papers on the Alliance pod (`47-quality-equivalence.md:10-11`, `packages/whisker/src/whisker/CLAUDE.md:556-558`). Also requires dev-replay recall on 9 golden PRs and holdout manifest if evidence-touching (`47-quality-equivalence.md:12-14`). Impact: one failed bake-off wastes **~100 min** and blocks attribution; bundling sglang with client levers confounds results (`47-quality-equivalence.md:16`). Quality risk: treating MoE noise as regression blocks migration; ignoring noise ships real cache-corruption regressions.

- [MED] **HiCache / UnifiedRadixTree adds complexity we do not need for a single-pod judge fleet.** Defaults now enable hierarchical cache for hybrid/SWA models (`releases` v0.5.11 HiCache for hybrid by default); DeepSeek-V4 paths include HiSparse, Mooncake offload, UnifiedTree (`releases` HiCache section). Our pod is one H200-class instance, 16 slots, no PD disaggregation. Impact: more surface area for bugs like #25889 without throughput upside on serial per-paper submission. Quality risk: MEDIUM on DSV4 SWA+HiCache combos; disable paths exist (`disable_radix_cache`, `server_args.py:880-882`) but defeat the migration rationale.

## False-pass hypothesis

Deploy sglang RadixAttention on shared `CONVERSION_CONTRACT` prefixes before per-paper `extra_key` isolation is wired: `match_prefix` namespaces by `RadixKey.extra_key` (`radix_cache.py:358-367`), but if two papers share leading tokens and the client omits distinct salts, a stale or cross-paper KV hit returns a clean structured `UnitCheck` while the candidate markdown differs — wall time drops, defect groups shrink, fleet flip gate may stay inside the ≥25% MoE noise band (`47-quality-equivalence.md:10-11`), and localized omissions lose their only page-scoped quotes.

## False-fail hypothesis

Reject sglang after a pod swap that changes only the server while prompts remain guard-tag-broken: prefix hit rate stays ~0% on both stacks (`106-sglang-radixattention.md:16`), wall remains ~3000 s, and operators conclude "RadixAttention is garbage" when the measured failure mode is **cache-misaligned prompts** — the same false-fail class documented for vLLM APC (`102-vllm-anti-steelman.md:28-30`) — forfeiting a potential 0–120 s incremental win that only appears after client reorder anyway.

## What would change my mind

Stay on vLLM through client prompt reorder + PR #43447 retention + bounded APC A/B (`104-vllm-apc-determinism.md:27`). Re-open sglang only if, on the **same H200 pod and identical structured outputs**, a 20-paper × 6-call replay with guard-tag fixed shows sglang `--schedule-policy lpm` beats vLLM APC by **>15% aggregate prefill wall** (`106-sglang-radixattention.md:34`) **and** persona-47 `flip_AB ≤ flip_AA + margin` on a 381-paper cold run — then verdict upgrades to usable-with-conditions for a isolated second pod, not a shared-pod cutover.
