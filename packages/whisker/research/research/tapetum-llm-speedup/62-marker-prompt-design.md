# 62 - marker-Prompt-Design

**Verdict:** usable-with-conditions (marker's prompt/schema discipline is real and cheap, but it optimizes block-level extraction/correction, not document-level verification; portable only where we preserve fail-closed coverage semantics)
**Confidence:** high

## Findings

- [CRITICAL] Marker scopes every LLM call to one block (cropped image + local HTML), never the full document; we send the entire `candidate_md` on every unit check. Evidence: `unit_judge.py:769-776` (full markdown in user_msg) vs `llm_equation.py:92-108` (one equation block + crop), `llm_table.py:166-170` (batch row crop + partial HTML), `llm_form.py:77-92` (single form block). Impact: ~1510 unit checks replay the full candidate prefill each time (00-baseline: ~6.0 calls/paper, serial chain). Scoping the candidate to the unit region (plus a fixed heading index) could cut prefill tokens ~5-6× on unit calls; at ~20 s implied per-call latency and decode-bound 70 tok/s (00-baseline), expect **~400-700 s** wall savings on the 3003 s cold run if prefill is ~30-40% of latency. Quality risk: low if grounding post-process stays global; missing cross-unit defects in the same call is already the unit-check contract.

- [HIGH] Marker output schemas are tiny (1-4 top-level fields) and task-native (corrected HTML/markdown, merge booleans); pass paths emit a fixed short string (`"No corrections needed."`) inside one field. Evidence: `HandwritingSchema` 1 field `marker/processors/llm/llm_handwriting.py:84-85`; `ImageSchema` 1 field `llm_image_description.py:87-88`; `EquationSchema` 2 fields `llm_equation.py:141-143`; `FormSchema` 2 fields `llm_form.py:120-122`; `MergeSchema` 5 bounded literals `llm_table_merge.py:453-458`. Our `UnitCheck` carries `reasoning` (40 words), `unit_id`, `verdict`, `confidence`, plus up to five `DefectFinding` objects with seven fields each including quotes (`models.py:231-320`, `unit_judge.py:156-158`). Impact: 70% of unit checks return zero defect groups (1057/1510, 00-baseline) but still decode the full schema. A pass-only micro-schema (~10-20 output tokens: verdict + confidence) on clean units could save **~100-200 s** fleet wall (1057 passes × ~100-150 excess decode tokens ÷ 70 tok/s ÷ 16 slots). Quality risk: medium unless pass-path is gated by deterministic pre-checks; a false pass on the cheap path is the main hazard.

- [HIGH] Marker does not set `max_output_tokens` by default (`None`); output length is bounded by task (block HTML size) and post-hoc rejection, not a global cap. Evidence: `BaseService.max_output_tokens = None` `marker/services/__init__.py:18-20`; applied only when set `gemini.py:69-70`; Claude service uses `max_claude_tokens=8192` `claude.py:22-24,79`. We cap judge output at 1536 (`cli.py:1029-1034`). Impact: marker is **not** cheaper because of tighter `max_tokens`; our 1536 cap is already conservative. Lowering it further is not a marker lesson. Quality risk: n/a.

- [HIGH] Marker eliminates LLM calls upstream with deterministic gates before any prompt is built. Evidence: skip tables >175 rows `llm_table.py:127-133`; skip small equations `llm_equation.py:80-88`; skip text blocks with existing lines `llm_handwriting.py:44-47`; table-merge pairs require geometry heuristics first `llm_table_merge.py:177-257`; inline-math redo off by default `llm_mathblock.py:17-23,79-81`; image-description LLM disabled when `extract_images=True` `llm_image_description.py:43-47`. Our analog is the source router + 70% zero-defect unit checks (00-baseline), but we still **invoke** the LLM on every selected unit. Impact: a deterministic pre-gate that skips the LLM when router confidence is low could eliminate ~700-1000 calls (pattern from 05-web SAJA/LLMTrace cascades: 80-90% cost cut cited); at 20 s/call that is **~900-1400 s** wall if quality holds. Quality risk: high without holdout proof; this is the largest lever and the easiest to false-pass.

- [MED] Marker runs independent block LLM calls with `ThreadPoolExecutor(max_workers=3)` across simple processors and complex processors (`llm/__init__.py:42-45`, `llm_meta.py:44-49`, `llm/__init__.py:163-172`). We run unit checks in a serial loop (`unit_judge.py:389-416`). Impact: parallelizing up to 3 unit checks per paper could shrink per-paper unit-phase serial time ~40-60% when slots are free; fleet wall improvement **~300-600 s** on 3003 s (1510 unit calls, 16 slots), with contention if many papers each spawn 3 calls. Quality risk: medium (MoE batch-composition variance, 00-baseline constraint note on D11 exemption).

- [MED] Marker validates LLM output lightly: structured JSON via provider schema, max 3 attempts (`max_retries=2`, `services/__init__.py:14-16`), retries only rate limits + JSON decode on Gemini (`gemini.py:94-125`), then returns `{}` and **keeps the pre-LLM block** on any failure (`gemini.py:131`, `openai.py:128`, `ollama.py:71`). Processors apply deterministic sanity checks (length ratios, HTML parse, balanced `<math>` tags): `llm_equation.py:118-136`, `llm_form.py:101-114`, `llm_table.py:239-276`. No pydantic cross-field validators on LLM schemas. We use pydantic validators (`models.py:315-320`), post-hoc grounding, and fail-closed coverage: failed/missing unit checks cap verdict at `review` via `coverage_complete` (`unit_judge.py:419-423,460-477`). Impact: marker's silent `{}` fallback is **not portable** to verification (would suppress findings); our retry budget (55 retries ~100 s total, 00-baseline) is already cheap. Quality risk: adopting marker fallback would false-pass on LLM outage.

- [LOW] Marker system prompts are long and instructional (table prompt ~45 lines `llm_table.py:43-88`, page correction ~100 lines `llm_page_correction.py:37-136`) but **static per processor** with no per-call random suffix, so prefix caching could hit across blocks of the same type. We embed ~3.7k-char `CONVERSION_CONTRACT` plus a fresh random `guard_instruction` tag every call (`unit_judge.py:70,767-768`, 00-baseline). Impact: moving the guard tag to the user message tail (05-web APC pattern) could improve prefix-cache hit rate on monolith/metadata/unit system prompts; **~200-400 s** wall if DeepSeek V4 APC fix applies (05-web: 0%→74% hits, ~4.5× throughput under load). Quality risk: low if injection defense preserved.

## False-pass hypothesis

Adopt marker's `{}` parse-failure fallback on unit checks: a timeout or malformed JSON on a page with token-preserving table corruption would leave `failed_unit_ids` empty if miswired, or more likely cap at `review` via incomplete coverage; if mis-implemented as "keep prior pass," a corrupted page could clear. Marker explicitly accepts stale extraction on failure (`llm_equation.py:118-120: keep original block`).

## False-fail hypothesis

Adopt marker's output length ratio gates verbatim on unit-check quotes: `len(corrected_html) < len(block_html) * 0.33` (`llm_form.py:112-114`) applied to candidate evidence would reject legitimately shorter sanitized markdown (entity cleanup, TOC removal), forcing `review` on clean papers.

## What would change my mind

A holdout run showing a two-stage unit gate (marker-style `"no_corrections"` micro-call then full `UnitCheck` only on flag) matches current merged verdicts on the 48-anchor holdout (whisker CLAUDE.md §9) with ≥95% agreement and zero silent demotions from `fail` to `pass`.
