# 88 - langextract-Schema-Discipline

**Verdict:** usable-with-conditions — Google’s library is strong precedent for provider-conditional structured output (native schema when the API supports it, fenced parse fallback otherwise), but it has no schema-noncompliance re-prompt loop and defaults to fail-soft chunk drops, so adopt the routing pattern, not the failure semantics.
**Confidence:** high

## Findings

- [CRITICAL] **Two-path routing: constraint decoding when the provider advertises a schema class, fenced parse otherwise.** `factory._create_model_with_schema()` builds a provider schema from examples (`schema_class.from_examples(examples)`) or user `output_schema` (`from_schema_dict`) when `use_schema_constraints=True` and the provider returns a schema class (`factory.py:270-283`). If a schema is applied and `requires_raw_output=True`, `BaseLanguageModel.requires_fence_output` returns False (constraint path); with no schema or `use_schema_constraints=False`, fences default True (parse path) (`base_model.py:136-151`, `factory_schema_test.py:146-167`, `169-189`). `extract()` wires resolver fences from `language_model.requires_fence_output` via `FormatHandler.from_resolver_params(..., base_use_fences=language_model.requires_fence_output)` (`extraction.py:342-348`). Impact: mirror this for tapetum — vLLM/OpenAI-compat with `json_schema` guided decoding → no fences; syntax-only or unknown backends → fenced prompt + parse. Quality risk: low if we keep our D6/D10 validation-retry on top; latency: could trim part of the ~55 retries / ~100 s wall (00-baseline) by reducing malformed JSON, but langextract itself does not quantify this.

- [CRITICAL] **Gemini: controlled generation via `response_mime_type` + schema field choice.** Example-derived schemas emit OpenAPI-style `response_schema`; user `output_schema` uses native JSON Schema via `response_json_schema` (`providers/schemas/gemini.py:63-75`, `195-204`). `GeminiLanguageModel._process_single_prompt()` merges `gemini_schema.to_provider_config()` into the genai `config` before `generate_content` (`gemini.py:363-366`, `368-370`). `requires_raw_output=True` disables fences (`providers/schemas/gemini.py:86-89`). Impact: for any dev/validation Gemini lane, use native schema + raw JSON parse (no ``` fences). Not our production pod path; no cold-run savings unless we add a Gemini judge tier.

- [HIGH] **OpenAI: strict `json_schema` when schema active, `json_object` syntax-only fallback.** With `openai_schema` set, `_build_chat_completions_params()` sets `response_format` to `OpenAISchema.response_format` (`type: json_schema`, `strict: True` by default) (`providers/schemas/openai.py:178-188`, `239-260`; `openai.py:208-211`). Without a schema but JSON format, it falls back to `{'type': 'json_object'}` (`openai.py:223-224`). OpenAI JSON mode also forces `requires_fence_output=False` (`openai.py:97-104`). Impact: our vLLM OpenAI-compatible endpoints that expose structured outputs should follow the OpenAI branch (guided `json_schema`, fences off). Endpoints with only `json_object` map to langextract’s Ollama tier: syntax guarantee, resolver still validates shape.

- [HIGH] **Ollama / self-hosted: syntax-only `format=json`, no field-level schema.** `OllamaLanguageModel.get_schema_class()` returns `FormatModeSchema`, which ignores examples and only sets `{"format": "json"}` (`ollama.py:172-178`, `core/schema.py:118-144`; `provider_schema_test.py:44-51`, `111-145`). Payload sends `format: "json"` on `/api/generate` (`ollama.py:643-644`; `provider_schema_test.py:170-170`). `apply_output_schema()` raises — user schemas unsupported (`provider_schema_test.py:679-685`; `docs/examples/output_schema.md:13-14`). GPT-OSS uses a chat adapter with a system instruction forbidding fences/prose (`ollama.py:111-116`, `476-538`). Impact: **recommended production strategy for alliance-pod vLLM (DeepSeek V4)**: enable vLLM structured output at JSON-syntax or grammar level if available; do **not** assume OpenAI-strict field schemas unless verified on that model; keep fenced-parse fallback + our existing `VllmThinkingBackend` parse retry (langextract lacks this). Quality risk on MoE: olmOCR (05-web Q2) reports repetition collapse with guided JSON — langextract does not discuss repetition explicitly; treat strict guided decoding on DeepSeek as A/B before fleet rollout. Latency: syntax-only guided decoding is lower risk than full strict schema; potential savings bounded by retry share (~4% wall).

- [HIGH] **Resolver is always parse-based post-decode; constraints do not skip it.** After every `infer()`, `annotation.py` calls `resolver.resolve()` then `resolver.align()` (`annotation.py:404-428`). `resolve()` uses `format_handler.parse_output(input_text, strict=constraint.strict)` then `extract_ordered_extractions()` for LangExtract envelope typing (`resolver.py:301-321`, `437-536`). `FormatHandler` strips fences when `use_fences=True`, tolerates top-level lists, and on non-strict parse failure strips `<think>` before retrying JSON load (reasoning-model path) (`format_handler.py:151-245`, `261-276`, `278-333`). Impact: even with guided decoding, keep resolver-equivalent Pydantic validation in tapetum; thinking-token suppression aligns with `think=False` default on Ollama (`ollama.py:279-280`) and format_handler thinking strip — supports output-token reduction lever (00-baseline decode-bound ~20 s/call) without dropping validation.

- [MED] **No schema or parse-failure re-prompt; only HTTP retries on Gemini.** Parse/schema errors: log + `return []` when `suppress_parse_errors=True` (default forced in `extract()`: `extraction.py:365`) (`resolver.py:309-321`). Empty model output raises `InferenceOutputError` (`annotation.py:399-402`). Gemini retries transient HTTP/API errors only (`gemini.py:351-391`, `45-49`); OpenAI/Ollama infer paths have no output-validation retry loop. Impact: **do not copy** langextract’s silence — keep tapetum fail-closed + D10 `ModelRetry` on schema violations; langextract’s chunk `[]` drop is a false-pass vector for advisory judging. Latency: their design trades away re-prompt cost (~20 s × failed chunks) for silent continuation; we should keep retries narrow (truncation/BPE) per measured 55-retry budget.

- [MED] **Explicit tradeoffs documented in code/comments.** Fence vs constraint: `AbstractResolver` docstring — fences for models without constrained decoding; set `fence_output=False` when schema handles structure (`resolver.py:100-108`). `output_schema` rejects `fence_output=True` (`extraction.py:212-213`; `output_schema.py:63-64`). Gemini/OpenAI warn that `fence_output=True` with schema “may cause parsing issues” (`providers/schemas/gemini.py:98-105`, `providers/schemas/openai.py:216-223`). OpenAI strict vs experimental: docs say use `strict=False` only for schema features outside OpenAI’s strict subset (`docs/examples/output_schema.md:153-155`). YAML on Ollama forces fences back on (`factory_schema_test.py:335-373`). Impact: for tapetum personas 32/74 — **capability matrix**: (1) Gemini/Vertex → full schema, no fence; (2) OpenAI or vLLM with verified `json_schema` → strict schema, no fence; (3) vLLM/Ollama JSON mode only → no fence, parse + retry; (4) no API constraint → fenced few-shot + parse; (5) never combine user schema with fences. vLLM is not in core langextract (community plugin only: `COMMUNITY_PROVIDERS.md:17`); treat Ollama path as the in-repo self-hosted precedent.

- [LOW] **`use_schema_constraints=False` is the deliberate parse-only escape hatch.** Disabling skips `response_schema` / example schema generation and restores `requires_fence_output=True` (`extract_schema_integration_test.py:189-228`; `factory_schema_test.py:169-189`). README still claims “controlled generation” as default product path (`README.md:40`). Impact: use only for models/backends where guided JSON provably hurts quality (olmOCR repetition precedent); expect slightly higher parse-retry rate, not a 50 min → 5 min lever by itself.

## False-pass hypothesis

A vLLM unit-check call returns truncated but HTTP-200 JSON that parses to `verdict: pass` with empty defects; langextract-equivalent behavior with `suppress_parse_errors=True` would log “Skipping chunk: parse error” and treat the unit as having zero findings (`resolver.py:309-312`, `extraction.py:365`), letting downstream aggregation pass the paper — same class as 70% zero-defect unit checks (00-baseline) when combined with no coverage gate.

## False-fail hypothesis

Turning on OpenAI-strict `json_schema` guided decoding on DeepSeek V4 MoE for all unit checks causes repetition collapse or schema reject loops (olmOCR 05-web precedent; langextract does not retry schema failures), inflating per-call latency beyond the current ~20 s and increasing timeout tombstones (`constants.py:197`) without improving detection.

## What would change my mind

A/B on alliance-pod: strict vLLM `json_schema` vs syntax-only `json_object` vs fenced-parse on 50 papers measuring (a) schema/parse retry count, (b) verdict drift vs current fleet, (c) p95 decode tokens — showing strict guided decoding cuts retries by >50% with zero verdict changes would upgrade vLLM to the OpenAI/Gemini tier; showing repetition or drift would confirm Ollama-tier syntax-only + tapetum retry.
