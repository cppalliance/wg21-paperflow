# 64 - marker-LLMScorer-Bench

**Verdict:** usable-with-conditions — marker's `LLMScorer` is the closest published per-page image-vs-markdown LLM judge prior art (prompt shape, structured rubric, Gemini vision), but it is an offline eval lane with serial execution, no throughput engineering, heuristic-only CI gates, and single-page samples at ~2.1k scale, not a blueprint for a 381-paper / ~6-call-per-paper fleet finishing in 5–10 min.
**Confidence:** high

## Findings

- [CRITICAL] LLM judge granularity is one Gemini call per **single-page benchmark row**, not per multi-page document. Each HF sample is already a one-page PDF (`benchmarks/overall/methods/marker.py:15`), and `LLMScorer.__call__` renders only `doc[0]` before judging (`benchmarks/overall/scorers/llm.py:101-105`). Full published run is **2,138 rows** (`datalab-to/marker_benchmark`, HuggingFace dataset card), i.e. 2,138 page-judge calls if `--scores llm`, versus our **381 papers × ~6 calls ≈ 2,284 calls** with multi-page unit coverage. Impact: marker never runs comparable multi-page verification QA; their design does not bound or optimize a 381-doc cold fleet. Quality risk if we copied their scope: N/A (under-coverage, not over-speed).

- [CRITICAL] Scoring loop is fully **serial** with no in-sample or cross-sample LLM parallelism. `get_method_scores` iterates rows with `tqdm`, then methods, then score types in nested loops (`benchmarks/overall/overall.py:33-65`). `LLMScorer` has no async, thread pool, or batch API. Impact: at our ~20 s/call (00-baseline), 2,138 serial judge calls alone would be **~12 h wall**; marker accepts that for offline benchmarking. Adopting serial execution would **add ~0 s savings** and would forfeit our existing 32-paper client concurrency. Quality risk: low if we parallelize in-paper unit checks carefully (MoE variance per 05-web Q5).

- [HIGH] LLM scorer is **opt-in and failure-tolerant**, not on the critical path. CLI default is `--scores heuristic` (`benchmarks/overall/overall.py:93`); README instructs `--scores heuristic,llm` only when explicitly benchmarking (`README.md:535-543`). LLM failures are caught, printed, and **skipped** (`benchmarks/overall/overall.py:60-63`); results table tolerates missing LLM keys (`benchmarks/overall/display/table.py:59-62`). CI runs **`--max_rows 5` with heuristic verify only** (`.github/workflows/benchmarks.yml:30-31`; `benchmarks/verify_scores.py:10-13` gates marker heuristic ≥90, never LLM). Impact: marker optimizes for **fast deterministic CI** and treats LLM judge as optional reporting; copying this split would not reach 5–10 min with same finding quality because our lane is verification-critical, not supplementary. Quality risk: high if we skip-fail LLM errors like marker.

- [HIGH] **No LLM latency or cost accounting** in the harness. `average_times` records only conversion-method wall (`benchmarks/overall/methods/marker.py:33-39`, aggregated at `benchmarks/overall/overall.py:53`); README "Avg Time" column (marker **2.84 s**) is conversion on H100, not Gemini judge time (`README.md:472-477`). LLM scorer has no timing, token, or spend fields. Cost controls are minimal: empty markdown short-circuit to score 1 (`benchmarks/overall/scorers/llm.py:109-116`); on Vertex `APIError`, sleep **120 s** and retry up to depth 2 (`benchmarks/overall/scorers/llm.py:155-160`); 60 s HTTP timeout (`benchmarks/overall/scorers/llm.py:138`). Impact: marker authors do not publish or optimize judge wall-clock; we cannot infer a 5–10 min target from their numbers. Portable lever: add per-call timing (we already have sidecars); not portable: "accept slow offline judge."

- [HIGH] Judge **payload and model** differ materially from tapetum-llm. Model: **`gemini-2.0-flash-001`** via Vertex, `temperature: 0`, JSON schema response (`benchmarks/overall/scorers/llm.py:144-151`). Prompt embeds the **full method markdown** plus a **96 dpi page raster** (`benchmarks/overall/scorers/llm.py:15-85`, `:102`, `:128-129`). Output schema: 3 string descriptions + 8 integer subscores 0–5 keyed `overall`, `text`, `formatting`, `section_headers`, `tables`, `forms`, `equations`, `lists`, `images` (`benchmarks/overall/scorers/llm.py:87-91`, `:117-134`). No defect quotes, no fail-closed verdict enum, no per-unit routing. Impact: rubric is holistic scoring, not our structured defect extraction; naively swapping prompts would change finding classes. Quality risk: high if we shrink to 0–5 scores without quote-backed defects.

- [MED] **Scorer validation is heuristic-first; LLM judge is not meta-validated in-repo.** Published README table juxtaposes heuristic (0–100) and LLM (0–5) columns (`README.md:472-495`) but provides no correlation study, human adjudication set, or CI gate on LLM scores. Separate `benchmarks/overall/elo.py` runs pairwise image-vs-two-markdown comparisons with the same Gemini model (`elo.py:125-155`) but also serial, and on rate limit **returns None** (drop) rather than retry-with-backoff (`elo.py:156-158`). Impact: marker treats LLM judge as qualitative leaderboard signal; we need quality-stability and fail-closed semantics. Portable: dual-lane heuristic + LLM reporting; not portable: LLM-as-optional-nice-to-have.

- [LOW] Production `--use_llm` extraction uses **`max_concurrency=3`** thread pools for block processors (`marker/processors/llm/__init__.py:42-45`, `marker/processors/llm/llm_meta.py:44-49`), unrelated to `LLMScorer`. Benchmark conversion optionally passes `--use_llm` into `MarkerMethod` (`benchmarks/overall/overall.py:96`, `benchmarks/overall/methods/marker.py:19`) — that is extraction LLM, not the judge. Impact: do not conflate marker's extraction concurrency with judge throughput; neither path targets our advisory verification lane.

## False-pass hypothesis

If we adopted marker's **skip-on-LLM-failure** pattern (`benchmarks/overall/overall.py:60-63`) to hit 5–10 min, papers where Gemini rate-limits or schema validation fails would silently receive no LLM judge score and could pass on heuristic/metadata alone, dropping defect classes that only the vision judge catches (tables, forms, layout drift visible in raster but not in text diff).

## False-fail hypothesis

If we copied marker's **empty-markdown score=1** short-circuit (`benchmarks/overall/scorers/llm.py:109-116`) into a fail-closed verification lane, a blank candidate from a crashed conversion would get a passing numeric score instead of a hard fail, wrongly clearing papers that lost entire pages.

## What would change my mind

A marker-maintained benchmark log or CI job running `--scores heuristic,llm` on the full 2,138-row set with **published total LLM-judge wall time, parallelism settings, and p50/p95 per-call latency**, showing they routinely complete LLM judging at ≥200 calls/min with quality gates — none exists in the clone today (only conversion timing in README and 5-row heuristic CI).
