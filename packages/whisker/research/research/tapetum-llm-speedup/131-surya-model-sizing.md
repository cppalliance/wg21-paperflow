# 131 - surya-Model-Sizing

**Verdict:** usable-with-conditions — Surya is the strongest in-repo precedent for task-decomposed tiny specialists vs one general model, but our metadata/outline lane is mis-tiered: it should be a deterministic comparator (Surya's DistilBERT/OCR-error tier, not its 650M VLM tier), eliminating 377 MoE calls (~471 s) with lower quality risk than persona 23's dense-judge swap.
**Confidence:** high (surya clone @ `packages/whisker/research/repos/surya`, README/settings/loader read; tapetum metadata prompt + router read)

## Findings

- [CRITICAL] **Surya's model-sizing philosophy: one shared 650M VLM for generative layout/OCR/table, plus separate sub-100M torch classifiers for narrow non-generative tasks.** Evidence: README headline "650M param OCR model" with "smaller models for line-level text detection and ocr error detection" (`README.md:23-31`); usage doc "Text detection and OCR errors are separate models" while "layout, OCR, and table recognition through a single VLM" (`README.md:110-113`); training section: shared ~650M Qwen3.5-style VLM for layout/OCR/table prompts, "Text-line detection is a separate small torch model — a modified EfficientViT segformer" (`README.md:469-474`); checkpoints `DETECTOR_MODEL_CHECKPOINT` (`settings.py:110`) and `OCR_ERROR_MODEL_CHECKPOINT` (`settings.py:119`); OCR-error is DistilBERT 6-layer/768-dim/512-pos (`ocr_error/model/config.py:24-38`, ~66M params per `research/vlm-pdf-qa/26-surya-ocr-error-analyst.md:17`); detection loads EfficientViT semantic segmentation (`detection/loader.py:8-46`). Impact: validates persona 23/76 debate — **specialize by task shape**, not by "use any smaller LLM." Our metadata/outline check outputs booleans + bounded lists (`models.py:262-295`), not generative HTML; surya would never route that through the 650M VLM. **Quality risk: LOW** if we match surya's tiering (deterministic or ~66M classifier), **MEDIUM** if we only swap DeepSeek→Qwen3-32B (persona 23) without changing call class.

- [CRITICAL] **`run_metadata_outline_check` is a structured diff masquerading as an LLM call — 377-call elimination (~16.5% of fleet) needs no generative model.** Evidence: mandatory second call after monolith (`pdf_judge.py:675-688`, `adjudicate.py:501-508`); payload is bounded source metadata + outline + candidate front matter + ATX headings only (`unit_judge.py:231-256`), not full markdown; schema is five mechanical fields + verdict (`models.py:262-295`); prompt asks only "Compare… Judge field values, missing sections, and heading-level drift" with TOC/chrome ignore rules (`unit_judge.py:114-127`); census **377 metadata/outline calls** of 2284 (`00-baseline.md:22-23`, `10-call-graph-accountant.md:45`). HTML lane **already** compares source vs candidate outline deterministically in `route_html_units` (level + title key, TOC skip via `_is_sanctioned_toc_title`, `source_router.py:163-164`, `:286-312`); `extract_heading_outline_normalized` + `normalize_heading_text` are deterministic (`html_outline.py:119-147`). Whisker core already parses YAML front-matter keys (`gates.py:34-75`). Impact: replace LLM with `compare_metadata_outline()` reusing router/html_outline/gates patterns → save **377 × ~20 s / 16 slots ≈ 471 s (~15.7%)** on 3003 s cold run (`00-baseline.md:24-25`); per-paper serial chain drops one ~20 s stage (`00-baseline.md:36-38`). **Quality risk: LOW–MEDIUM** — requires holdout parity vs current LLM on fusion fold (`pdf_judge.py:711-714`, `adjudicate.py:371-378`); PDF source outline is noisier than HTML (font-size heading candidates at `pdf_judge.py:669-673`) so deterministic path must reuse `normalize_heading_text` + sanctioned-TOC filter (`unit_judge.py:119-120`, test at `test_unit_judge.py:452-472`).

- [HIGH] **Documented surya throughput is per-model-class and concurrency-tuned, not one headline number.** Evidence: README claims **5 pages/s on RTX 5090** (`README.md:26`); throughput table: concurrency **128 → 5.35 pages/s, 12,884 tok/s**, p50 **18,915 ms**, avg **2,410 tok/page** at 96 DPI full-page OCR (`README.md:441-452`); Apple Silicon llama.cpp **8 parallel → 0.108 pages/s, 254 tok/s** (`README.md:454-460`); VLM tuning via `--max-num-seqs`, `SURYA_INFERENCE_PARALLEL=8`, DPI 192→96 tradeoff (`README.md:169-173`, `settings.py:15-16,58`); detection-only path: torch CPU batch **8** default (`detection/__init__.py:24`), image-adaptive thresholds (`detection/heatmap.py:13-23` per redteam); OCR-error: CPU batch **8**, argmax in `inference_mode` (`ocr_error/__init__.py:16-48`). Impact: surya proves **specialist components run at very different duty cycles** — 650M VLM is decode-bound at page granularity; 66M DistilBERT is batch-CPU-cheap. Analog for tapetum: metadata comparator should be **microseconds**, not another 20 s MoE slot. **Quality risk: N/A** (throughput observation only).

- [HIGH] **olmOCR-bench size frontier supports "small specialized beats large general" — same axis as personas 23/76, opposite of our metadata LLM choice.** Evidence: README benchmark table: **Surya OCR 2 0.65B → 83.3** vs Chandra 5.3B/9.0B, olmOCR 8.3B, Infinity-Parser 35.1B (`README.md:389-398`); "Pareto-optimal on the size-vs-score frontier, and best in class under 3B params" (`README.md:387-388`). Persona 76 cites olmocr 7B dense FP8 at 3050 tok/s beating GPT-4o teacher; persona 23 routes metadata to dense 32B. Impact: for **unit checks** (generative defect finding), fine-tuned 7B–32B dense offload is surya/olmocr-class; for **metadata/outline** (boolean diff), surya's OCR-error tier (or pure Python) is the closer analog — **do not spend MoE or 32B tokens on it**. Replacing metadata LLM + persona-23 dense offload is **orthogonal levers** (~471 s + ~250 s). **Quality risk: unit offload HIGH without persona 47 A/B; metadata deterministic LOW if parity-tested.**

- [MED] **What the metadata LLM still does that deterministic code must explicitly encode (not "impossible without LLM").** Evidence: prompt rules — ignore TOC entries, page numbers, running headers/footers (`unit_judge.py:119-120`); "cosmetic source formatting is not a defect" (`unit_judge.py:118`); map PDF title-block lines to YAML front matter (`unit_judge.py:73-75`, `pdf_judge.py:200-201`); heading drift format `h2:Abstract -> ###:Abstract` (`models.py:271-274`). Deterministic port: (1) parse candidate YAML (`gates.py:60-75` extended with `date`/`document` regex against `P\d{4}R\d+`), (2) run HTML-style outline diff for HTML papers (`source_router.py:286-312`), (3) for PDF, normalize font-size heading candidates through `normalize_heading_text` + `_is_sanctioned_toc_title`, (4) emit same `MetadataOutlineCheck` without `run_judge_task` (`unit_judge.py:257-266`). Residual uncertainty band: date format variants and PDF page-1 metadata noise → default **`review`**, not LLM (`05-web.md:93-96` deterministic floor + cascade). Impact: **~471 s** wall + removes guard-tag prefix break on this call class (`00-baseline.md:48-52`). **Quality risk: MEDIUM** on PDF papers with split title-block extraction (`pdf_judge.py:674` = entire page-1 text layer).

- [MED] **Persona 17 metadata short-circuit stacks with elimination, not substitutes it.** Evidence: 232/378 sidecars metadata non-pass still ran 1047 unit checks (`17-metadata-short-circuit.md:8`); metadata LLM runs **before** unit loop with no early exit on fail (`pdf_judge.py:677-688` then `:870+`). Eliminating the LLM call saves **all 377** metadata calls; short-circuit saves **up to 1047** unit calls when metadata verdict already caps fusion. Combined upper bound **~1800 s** (`17-metadata-short-circuit.md:8` + this finding) — still needs monolith/unit levers for 5–10 min. **Quality risk: short-circuit MEDIUM on inspect completeness; elimination LOW on verdict if deterministic parity holds.**

- [LOW] **Surya ships no in-repo LLM-judge / conversion-verification harness — quality numbers are external olmOCR-bench** (`README.md:378-408`, `research/llm-readability/repo-scan/surya.md:16-19`). Impact: surya teaches **architecture and sizing**, not judge-prompt patterns. **Quality risk: N/A.**

## False-pass hypothesis

Deterministic metadata comparator uses strict string equality on `date:` after normalization and marks **review** on `2024-01-15` vs `January 15, 2024` while today's LLM returns `date_matches=True` with verdict **pass** — paper stays pass, but a genuinely wrong year (`2023` vs `2024`) that fuzzy-matches after aggressive normalization could slip through if regex is too loose. Mitigation: separate **identity fields** (document PID, title token set) as hard fail; date as review-only unless exact ISO match.

## False-fail hypothesis

PDF lane feeds noisy `page_units[0].text` and font-size `heading_candidates` (`pdf_judge.py:669-674`) into deterministic outline diff without LLM lenience: benign prose lines on page 1 register as `missing_sections`, metadata **fail** fires (`pdf_judge.py:711-712`), fusion hard-caps (`fusion.py:187-189`) — false advisory fail on clean conversions that the LLM currently passes. Mitigation: reuse router's normalized-title matching (`source_router.py:35-41`, `:236-255`) and cap PDF missing-section at **review** unless document PID mismatch.

## What would change my mind

Holdout replay (48-paper holdout + dev-replay 9, `47-quality-equivalence.md:12-14`) showing a deterministic `compare_metadata_outline()` disagrees with v10 LLM `metadata_outline_check` on **>5% of papers** **and** changes fused advisory verdict on **any** paper — would keep the LLM call (or a surya-style ~66M classifier fine-tuned on sidecar labels) instead of pure diff.
