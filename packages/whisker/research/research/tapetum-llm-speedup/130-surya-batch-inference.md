# 130 - surya-Batch-Inference

**Verdict:** usable-with-conditions — Surya splits inference into two tiers: true server-side continuous batching for tiny torch models, and for its 650M VLM the same pattern we already use (N concurrent OpenAI HTTP calls sized to vLLM `max_num_seqs`). The CV `_Batcher` machinery and VRAM auto-scaling formula do not transfer to our MoE judge fleet; the one portable scheduling idea is flatten-and-flood independent units into one concurrent pool.
**Confidence:** high (VLM + batch_service source read end-to-end); medium on fleet wall quantification (extrapolated from 00-baseline slot math, not surya-measured on judge workloads)

## Findings

- [CRITICAL] **Surya VLM "batch inference" is not an application batch API — it is `ThreadPoolExecutor` + sync `OpenAI.chat.completions.create`, one HTTP request per item.** Evidence: `chat_completions_batch()` maps each `BatchInputItem` through `_generate_one()` with `client.chat.completions.create(**kwargs)` (`inference/backends/openai_client.py:70-115,158-215`); `max_workers` defaults to `min(64, len(batch))` unless overridden (`:173-174`); `VllmBackend.generate()` passes `max_workers=self._client_parallel()` (`inference/backends/vllm.py:223-232`); `LlamaCppBackend.generate()` same with `SURYA_INFERENCE_PARALLEL or DEFAULT_PARALLEL=8` (`inference/backends/llamacpp.py:205-214`). Module docstring: "Both servers expose `/v1/chat/completions`… single point of HTTP contact" (`openai_client.py:1-5`). Impact: **negative result for "purpose-built batch consumer"** — surya's high-throughput VLM consumer is functionally equivalent to our `AsyncOpenAI` + paper semaphore (`00-baseline.md:34-35`, `judge_task.py:63-66`). No vLLM offline engine, no multi-prompt packing, no Ray Data. **Quality risk: N/A** (architecture observation). Expected fleet saving from mimicking surya VLM client alone: **~0 s on 3003 s cold run**.

- [CRITICAL] **Independent work units are flattened into one concurrent pool before `generate()` — the one scheduling pattern worth copying.** Evidence: block-mode recognition builds "a flat batch across all pages for max concurrency" (`recognition/__init__.py:179-204`), one `manager.generate(batch)` for all non-skipped blocks; layout/table_rec build per-image `BatchInputItem` lists then single `manager.generate(batch)` (`layout/__init__.py:58-67`, `table_rec/__init__.py:75-84`); full-page OCR batches all pending pages per regen round (`recognition/__init__.py:336-347`). Client concurrency capped at `min(_max_num_seqs, MAX_AUTO_PARALLEL=96)` with comment that B200 layout throughput knee is ~96 concurrent (`inference/backends/vllm.py:84-104`). Impact: analog for tapetum is a **call-level** pool (all pending unit checks / escalations across papers), not today's one-call-at-a-time per paper (`00-baseline.md:36-38`). Upper bound unchanged (**2284 calls**, `00-baseline.md:22-23`); benefit is **slot-fill during heterogeneous cascade phases**, not call elimination. Rough bound: if fleet tail leaves slots idle >10% of wall, flattening could recover **~300 s (~10%)**; persona 20 argues steady-state is already slot-saturated at c=32 vs 16 seqs → **~0–300 s**, quality risk from MoE batch-composition variance (**HIGH** without batch-invariant rerun, `20-in-paper-parallelist.md:16-17`).

- [HIGH] **VRAM-based vLLM sizing exists but conflicts with our measured MoE judge ceiling.** Evidence: `_gpu_settings()` scales from 24 GB baseline (`BASELINE_MAX_BATCHED_TOKENS=8192`, `BASELINE_MAX_NUM_SEQS=32`) by VRAM ratio with log2 floor for tokens and 8-wide rounding for seqs (`inference/backends/vllm.py:28-60`); GPU table through `b300:270` … `t4:16` (`:33-48`); docker spawn passes computed `--max-num-seqs`, `--max-num-batched-tokens`, `--enable-prefix-caching`, optional MTP (`:140-189`). On **H200 (141 GB)** the formula yields ~**32768** batched tokens and ~**184** seqs (ratio 5.875×). Our pod runs **`max-num-seqs 16`** and measured **16→32 = +60% wall** (`00-baseline.md:65-67,82-83`). Impact: surya's auto-scale is tuned for **dense 650M VLM page OCR**, not DeepSeek MoE judge; blindly applying H200 formula to alliance-pod is **anti-lever**. Portable pieces only: **`--enable-prefix-caching`** + MTP already in surya spawn (`vllm.py:176-189`), aligned with 05-web Q1 (~4.5× throughput under prefix-heavy load when APC works). **Quality risk: LOW** for server flags if GSM8K-style accuracy holds (05-web cites ~95.6%); **HIGH** for raising `max-num-seqs` on MoE judge.

- [HIGH] **True continuous batching is a separate tier for torch CV models only; surya does not use it for layout/OCR VLM.** Evidence: generic `_Batcher` coalesces queued jobs for `batch_wait_ms` (default **5 ms**) up to `max_batch` (`common/batch_service/server.py:63-100`, `config.py:27-28`); `service_config_from_settings()` reads `<PREFIX>_SERVER_BATCH_WAIT_MS` / `_MAX_BATCH` (`config.py:31-54`); used by detection (`detection/server.py:1-60`), fast layout (`fast_layout/server.py:1-101`), ocr-error (`ocr_error/server.py:1-34`); test proves concurrent submits merge into one `detect()` forward (`tests/test_fast_layout_server.py:41-76`). VLM path never imports `BatchEngine` — only `openai_client.chat_completions_batch`. Impact: **not portable** to tapetum LLM judge (different modality, no shared weights, prompts are megabyte-scale text not PIL tensors). **Quality risk: N/A**.

- [MED] **Per-model batch sizes (detection / recognition / layout) are device-defaulted torch micro-batches, not LLM batching.** Evidence: `DetectionPredictor.default_batch_sizes = {"cpu": 8, "mps": 8, "cuda": 36}` with split-aware packing in `batch_detection()` (`detection/__init__.py:32-33,98-124`); `OCRErrorPredictor.default_batch_sizes = {"cpu": 8, "mps": 8, "cuda": 64}` (`ocr_error/__init__.py:25-26,62-97`); fast layout `RfDetrTorch.detect(..., batch_size=8)` chunks forwards (`common/rfdetr_torch.py:137-151`); server ceilings default **`DETECTOR_BATCH_SIZE or 8`**, **`FAST_LAYOUT_BATCH_SIZE or 8`**, **`OCR_ERROR_BATCH_SIZE or 8`** via settings (`settings.py:117-118,134,138,154,189-191`; `detection/config.py:17`, `fast_layout/config.py:17`). Detection postprocess parallelized at `DETECTOR_MIN_PARALLEL_THRESH=3` with CPU worker pool (`detection/__init__.py:69-82`, `settings.py:122-123`). Impact: teaches **specialist micro-batch defaults by device**, irrelevant to MoE decode-bound judge calls. **Quality risk: N/A**.

- [MED] **llama.cpp backend shows KV-budget-aware slot sizing — conservative parallel vs vLLM.** Evidence: `DEFAULT_PARALLEL=8`; total ctx `max(16384, parallel × CTX_PER_SLOT=12288)` (`inference/backends/llamacpp.py:70-128`, `settings.py:63-71`); warns when per-slot ctx below recommended 12k (`llamacpp.py:129-135`). Impact: documents that **wider client parallel without KV headroom truncates outputs** — caution if we ever shard judge to llama-class servers. **Quality risk: MEDIUM** (silent truncation → false pass) if copied without ctx math.

- [LOW] **No cross-request prompt batching or offline inference mode anywhere in surya.** Evidence: `SuryaInferenceManager.generate()` delegates straight to backend (`inference/__init__.py:101-102`); vLLM docker uses online OpenAI server only (`inference/backends/vllm.py:146-198`); no `LLMEngine`/Ray references in repo. Impact: 05-web Q3 offline ~2× claim **not validated here**; surya offers no counterexample to our HTTP-online architecture. **Quality risk: N/A**.

## False-pass hypothesis

Adopting surya's H200 `_gpu_settings()` and raising alliance-pod to **~184 max-num-seqs** to "match surya throughput": MoE expert routing destabilizes under wide heterogeneous judge batches (`00-baseline.md:82-83`, `20-in-paper-parallelist.md:16`), producing confident passes on borderline unit checks that serial c=16 reruns flag — advisory verdict drift without deterministic gate change.

## False-fail hypothesis

Flattening all unit checks fleet-wide into one 16-wide burst per completion wave: several checks on large papers hit `UNIT_CHECK_TIMEOUT_SECONDS=120` under contention (`constants.py:197`, `20-in-paper-parallelist.md:30-31`), mark `coverage_complete=false`, cap fused verdict at review on clean conversions that serial per-paper scheduling completes in time.

## What would change my mind

A surya-style benchmark on **our** judge model: run 381-paper fleet with (A) current AsyncOpenAI c=32 serial-in-paper vs (B) surya-identical sync `ThreadPoolExecutor` + call-level flatten pool sized to `min(max_num_seqs, 96)`, reporting **≥15% wall reduction** at **≤2 pp** merged-verdict drift — would upgrade the flatten-and-flood pattern from conditional to fleet-critical.
