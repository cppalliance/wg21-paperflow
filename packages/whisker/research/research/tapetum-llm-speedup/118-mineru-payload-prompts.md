# 118 - mineru-Payload-Prompts

**Verdict:** usable-with-conditions — MinerU's two-step per-page VLM (fixed 1036² layout + bbox-cropped content calls, ~20-char task prompts, no document text) is the strongest scoped-payload reference in the swarm, but it is a generation pipeline with regex-parsed layout tokens and truncation-tolerant decode; porting to tapetum verification requires persona-13 hybrid (section window + full-doc presence oracle), not raw MinerU copy.
**Confidence:** high

## Findings

- [CRITICAL] **Two-step call graph per page: exactly 1 layout VLM call + M content VLM calls (M = eligible detected blocks).** Evidence: `two_step_extract` runs `layout_detect` then `prepare_for_extract` + `batch_predict` on block crops (`research/repos/mineru-vl-utils/mineru_vl_utils/mineru_client.py:953-972`); production entry `doc_analyze` invokes `predictor.batch_two_step_extract` per processing window (`research/repos/mineru/mineru/backend/vlm/vlm_analyze.py:479-482`). Step 1 returns bbox-typed blocks via regex on model output (`mineru_client.py:238-269`, pattern `mineru_client.py:26-31`); step 2 sends one image+prompt per non-skipped block (`mineru_client.py:328-363`). Skips always remove `list`, `equation_block`, `image_block`; `image`/`chart` skipped when `image_analysis=False` (`mineru_client.py:313-316,328-330`). MinerU wires `image_analysis=True` and `enable_cross_page_table_merge=True` at client init (`vlm_analyze.py:236-238`). Impact: a dense WG21 page with ~15 text/table/equation blocks pays **~16 VLM calls/page**, but **zero full-document prefill**; contrast our **~6 calls/paper** each embedding P50 **34 336-char** candidate md (`00-baseline.md:43-47`, `13-payload-scoper.md:12`). Quality risk: N/A for MinerU generation; for tapetum, block-scoped verification without presence oracle false-passes cross-page joins (`13-payload-scoper.md:26-27`).

- [CRITICAL] **Page image resolution: 200 DPI full-page raster; layout fixed 1036×1036; content = bbox crop + optional pad/rotate, no tiling.** Evidence: `DEFAULT_PDF_IMAGE_DPI = 200` (`research/repos/mineru/mineru/utils/pdf_image_tools.py:35`); pages loaded via `load_images_from_pdf_doc` at default DPI (`pdf_image_tools.py:50-65`, `vlm_analyze.py:464-468`); layout step resizes entire page to `layout_image_size=(1036, 1036)` default (`mineru_client.py:505,231-233`); content step crops normalized bbox to pixels (`mineru_client.py:339-341`), rotates 90/180/270 (`352-353`), then `resize_by_need` enforces `min_image_edge=28`, pads extreme aspect ratios up to `max_image_edge_ratio=50` (`mineru_client.py:506-507,214-228`). No multi-tile/page split in repo. Impact: prefill is **O(page_image + Σ block_crops)**, bounded per page by layout block count, not O(document_tokens × calls). Our unit checks re-prefill **~9259 user tok/call** at P50 (`13-payload-scoper.md:14`). Quality risk: none for MinerU; cropping irrelevant to our text-judge task unless we adopt image lanes.

- [CRITICAL] **Prompt templates are tiny, static, task-typed; system prompt is generic; no custom prompts on `MinerUClient` public API.** Evidence: `DEFAULT_PROMPTS` — `"\nLayout Detection:"` (18 chars), `"\nText Recognition:"`, `"\nTable Recognition:"`, etc. (`mineru_client.py:58-66`); `DEFAULT_SYSTEM_PROMPT = "You are a helpful assistant."` (`mineru_vl_utils/vlm_client/base_client.py:11-12`); chat template builds `[image(s), text_prompt]` with image-before-text default (`base_client.py:125-129`, `vllm_engine_client.py:107-131`). Custom prompts not exposed on `two_step_extract` (GitHub Discussion #3906, cited in persona research). Impact: **~7–540 prompt tokens** vs our **~3.7k-char `CONVERSION_CONTRACT`** embedded per call (`00-baseline.md:48-49`); MinerU's speed win is **scoped pixels + micro-prompts**, not shorter boilerplate alone. Quality risk: low for prompt size; task semantics differ (OCR vs verification).

- [HIGH] **Output format: layout = custom delimiter tokens + normalized 0–1000 bbox coords; content = free text/HTML/LaTeX per block type — not guided JSON.** Evidence: layout regex expects `<|box_start|>…<|ref_end|>` with optional `<|rotate_*|>` and `txt_contd_tgt` merge flag (`mineru_client.py:26-31,238-264`); bbox normalized to [0,1] (`mineru_client.py:108-117`, `structs.py:141-144`); table → HTML, equation → LaTeX, text → plain (`README.md` in mineru-vl-utils:39-43). Post-hoc Python assembly into middle JSON (`vlm_analyze.py:492-499`, `model_output_to_middle_json.py`). Contrast: we use Pydantic structured output (D6) with **1536 tok** unit cap (`00-baseline.md:27-28`); olmOCR deliberately avoids guided JSON at inference (`74-olmocr-no-guided-json.md`). Impact: MinerU trades schema enforcement for **logits-processor + regex parse + post_process** (`mineru_client.py:365-379`). Quality risk: **HIGH** if we dropped Pydantic for free-text judge output; **LOW** if we only borrow input scoping.

- [HIGH] **Output length: default `max_new_tokens=None` → full `model_max_length`; truncation allowed, not fail-closed.** Evidence: vLLM client sets `"max_tokens": sp.max_new_tokens if sp.max_new_tokens is not None else self.model_max_length` (`vllm_engine_client.py:143-144`); `MinerUClient` passes `allow_truncated_content=True` (`mineru_client.py:625`); finish_reason `"length"` logs warning instead of error when allowed (`vllm_engine_client.py:169-173`). Sampling pins decode: `temperature=0.0`, `top_p=0.01`, `top_k=1`, `no_repeat_ngram_size=100` (`mineru_client.py:37-44,68-76`); vLLM server ships `MinerULogitsProcessor` for n-gram ban (`research/repos/mineru/mineru/model/vlm/vllm_server.py:52-53`). Impact: MinerU accepts **variable-length block output up to model context** with repetition control, not bounded judge reasoning; our decode cap + 40–60 word reasoning budget (`00-baseline.md:27-28`) is tighter. Quality risk: truncation-tolerant generation incompatible with tapetum fail-closed verification semantics.

- [HIGH] **Call bounding: per-page M is content-driven (no fixed cap); fleet batches pages in windows of 64 with stepping/concurrent modes.** Evidence: `get_processing_window_size(default=64)` via `MINERU_PROCESSING_WINDOW_SIZE` (`config_reader.py:158-169`); `doc_analyze` loops windows and calls `batch_two_step_extract` on each (`vlm_analyze.py:446-482`); `batch_two_step_extract` chooses `concurrent` (http/vllm-async, `max_concurrency=100` default, `vlm_analyze.py:71`) vs `stepping` (transformers/vllm-engine: batch all layouts then flatten all block extractions, `mineru_client.py:1069-1107,1171-1194`). Optional cross-page table merge adds **sparse text-only** calls (no image) when boundary heuristics match (`cross_page_table.py:259-291,370-372`; enabled `vlm_analyze.py:238`). Separate optional **title-level LLM** (text-only, document title dict) via `llm_aided.py` — not VLM (`llm_aided.py:71-111,178-182`). Impact: 20-page doc ≈ **20 layout + Σ M_i content** calls (often **200–400+** on block-heavy pages), still **no document markdown in any prompt**; our **2284 calls / 381 papers = 6.0/paper** with **full-md × ~6 prefill** (`00-baseline.md:22-23,43-47`). Quality risk: MinerU's high call count works because each call is tiny; copying call count without shrinking payloads does not help us.

- [MED] **Portable hybrid for tapetum (MinerU + persona 13/75/54 pattern):** (1) keep monolith/metadata on bounded slices where already scoped (`unit_judge.py:220-256` metadata pattern); (2) unit checks: one page source packet + H2 window ± neighbor + compact presence index, not full md (`13-payload-scoper.md:18-19`); (3) unchanged post-hoc `ground_spans` / `classify_candidate_evidence` on full on-disk md (`86-langextract-payload-scoping.md:16`); (4) prefix-cache reorder (stable per-paper guard tag, shared candidate block last) may match MinerU's identical micro-prompt reuse (`00-baseline.md:48-52`, `05-web.md:69-73`). - [LOW] **MinerU pipeline mode (non-VLM) uses local layout/OCR models — zero VLM calls.** Evidence: `enum_class.py:101` references `pp_doclayout_v2`; hybrid backend exists alongside VLM path. Impact: same "speed by not calling LLM" pattern as Docling default (`50-docling-call-census.md:8`). Quality risk: none for payload analysis.

## False-pass hypothesis

Adopt MinerU-style section/bbox-scoped unit payloads without a full-document presence index: a cross-page join tail under an earlier heading is outside the scoped window; the LLM returns pass with zero defect groups; post-hoc grounding never runs — same silent-miss class as persona 13/54/60 (`unit_judge.py:137-139`, `13-payload-scoper.md:26-27`). MinerU avoids this for **generation** because each block call only emits that block's text; we **verify** assembled markdown holistically.

## False-fail hypothesis

Keep full-doc post-hoc grounding but add MinerU-style micro-prompts + mechanical presence index: model flags a join fragment; index shows normalized phrase exists document-wide; ANYWHERE rule caps severity; `classify_candidate_evidence` refutes missing quotes against full md — verdict unchanged, prefill drops. MinerU's `txt_contd_tgt` merge flag (`mineru_client.py:127-128,262-264`) is layout-only; it does not substitute for our cross-page candidate presence check.

## What would change my mind

Holdout replay showing unit checks rewritten with MinerU-scoped source windows (page packet + ≤8K candidate slice) + compact full-doc presence index + unchanged post-hoc grounding achieves **≥25% cold-fleet wall reduction** with **≤1% fused-verdict diff** vs full-md control (persona 47 protocol) — that would elevate MinerU-style scoping from "necessary complement to APC" to "primary lever toward 5–10 min."
