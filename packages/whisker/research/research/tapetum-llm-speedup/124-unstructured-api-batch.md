# 124 - unstructured-API-Batch

**Verdict:** usable-with-conditions (ingest/batch pipeline lives in the separate `unstructured-ingest` repo, removed from the `unstructured` clone at `research/repos/unstructured/CHANGELOG.md:1288`; patterns are per-document-per-step, not per in-paper LLM call, so they improve restartability and warm/incremental runs more than the 3003 s cold fleet wall)
**Confidence:** high

## Findings

- [CRITICAL] **Clean-kill resume is filesystem idempotency per pipeline step, not a mid-run snapshot.** Each step writes hashed artifacts under `{work_dir}/{step_id}/` and skips when output already exists: `should_partition` (`research/repos/unstructured-ingest/unstructured_ingest/pipeline/steps/partition.py:34-37,55-57`), same pattern for chunk (`chunk.py:34-37,55-57`) and embed (`embed.py:34-37,53-55`). Download skips when local file exists unless `re_download` or remote `date_modified` is newer (`download.py:48-64,90-91`). Index persists `FileData` JSON per doc (`index.py:42-48`). **Impact:** on restart after a kill at ~40 min (~80% of 381 papers finished), tapetum today skips only papers whose sidecar fingerprint matches (`cli.py:1175-1202`, warm 375/381 in 00-baseline); in-flight papers redo all ~6 serial calls (~120 s/paper). Unstructured-style step cache would skip completed steps for in-flight papers (e.g. partition done, unit checks pending saves ~3 calls × 20 s × ~76 papers ≈ **285 s** restart wall, **0 s** on a true cold 3003 s run). **Quality risk:** low if step hashes include full config (partition hashes `PartitionerConfig` at `partition.py:71-77`); stale cache if hash omits a changed field.

- [HIGH] **Cross-document parallelism is process-pool or asyncio-gather, chosen per step.** `PipelineStep.__call__` picks async when `context.async_supported and process.is_async()`, else `mp.Pool` when `num_processes > 1`, else serial (`interfaces.py:118-130,77-104`). Default `num_processes=2` (`processor.py:25-27`). Test harnesses scale to `os.cpu_count()` (`test_unstructured_ingest/src/pdf-fast-reprocess.sh:14,35`). **Impact:** unstructured parallelizes *documents* across CPU/API workers; tapetum already runs 32 papers concurrently (`00-baseline` `cli.py:1096`) but serializes ~6 calls inside each paper. Porting only the mp/async dispatch pattern without in-paper parallel unit checks does not move the 3003 s needle. **Quality risk:** MoE batch-composition variance if we copy in-paper parallel without serial control (00-baseline open lever #3).

- [HIGH] **API-rate limiting uses `max_connections` + `asyncio.Semaphore`, not global sleep.** `ProcessorConfig.max_connections` builds a semaphore in `model_post_init` (`processor.py:28-29,74-76`); download/partition/chunk/embed acquire it before async API work (`download.py:101-103`, `partition.py:61-63`). GitHub connector adds typed `RateLimitError`, honors `Retry-After` capped at 300 s, tenacity exponential backoff with max 10 attempts (`github.py:49-51,127-131,284-305,339-342`). **Impact:** bounded concurrent API calls reduce 429-driven retry storms; our fleet already caps server slots at 16 (`00-baseline` SERVICES.toml). A `max_connections` semaphore on in-paper async unit checks (if we parallelize them) could shave retry wall (~55 retries ≈ 100 s in 00-baseline) without raising slot count. **Quality risk:** low for throttling alone; capping wait at 300 s can fail a doc that needs longer primary-window reset (`github.py:49-51`).

- [MED] **Hosted partition API path has client-side retry/backoff but ingest does not retry 429 on partition.** Main-repo `partition_via_api` exposes backoff defaults: 3000 ms initial, 720000 ms max interval, 1800000 s max elapsed (`research/repos/unstructured/unstructured/partition/api.py:17-21,140-228`). Ingest `call_api_async` has no retry wrapper (`unstructured_api.py:82-108`); integration tests document that `wrap_error` maps 429 to `UserError`, so throttles fail fast (`test/integration/utils.py:19-22`). **Impact:** portable retry config for our `judge_task` HTTP layer could recover transient 5xx/timeout (~4% retry wall in 00-baseline) but not 429 unless we classify it as retriable. **Quality risk:** retrying user/input errors would mask fail-closed semantics (utils.py:51-52).

- [MED] **Batch HTTP upload for multi-doc partition exists in main repo only.** `partition_multiple_via_api` posts all files in one `requests.post` (`partition/api.py:232-243,298-303`). Ingest pipeline processes one doc per partition call with per-doc cache skip. **Impact:** multi-unit prompt packing is a different shape (RuVerBench double-digit drops in 05-web.md Q5); this batch API pattern is not a safe direct port for multi-unit judge calls. **Quality risk:** high if copied to multi-unit judge prompts.

- [MED] **Embedding providers batch API payloads by token/count limits.** VoyageAI `MAX_BATCH_SIZE=1000` with token-budget batching (`research/repos/unstructured/unstructured/embed/voyageai.py:35-36,88-128`); MixedbreadAI `BATCH_SIZE=128` (`mixedbreadai.py:13,116-122`). **Impact:** irrelevant to judge decode-bound workload (1536-token unit outputs, 00-baseline); no cold-run savings. **Quality risk:** none for judge path.

- [LOW] **Metrics evaluation uses `ProcessPoolExecutor` defaulting to `MAX_PROCESSES` or CPU count** (`research/repos/unstructured/unstructured/metrics/evaluate.py:161-171,173-190`). Failures omitted, not retried. **Impact:** offline QA parallelism only. **Quality risk:** none.

## False-pass hypothesis

A killed run resumes from a stale partition `.ndjson` when `PartitionerConfig` changed but the 12-char SHA256 prefix collision or a field excluded from `serialize_base_model_json` leaves the old artifact valid (`partition.py:39-43,71-77`), skipping re-partition and silently serving outdated element structure on downstream chunk/embed/upload steps that also skip on file existence.

## False-fail hypothesis

Download step sets `file_data.reprocess = True` when remote `date_modified` is newer than local mtime (`download.py:54-62`), forcing full re-partition even if markdown-equivalent content unchanged; analogously, a tapetum step-cache keyed only on source mtime could re-run all judge calls after a no-op mailing refresh, wasting wall on a restart without changing findings.

## What would change my mind

A measured restart experiment on unstructured-ingest: kill mid-corpus after partition completes for N docs, rerun with same `work_dir`, and show (a) zero re-partition API calls for those N docs in logs, and (b) byte-identical final upload vs an uninterrupted run — proving step-cache skip is safe under their hash scheme; if instead any doc shows drift, downgrade checkpoint finding to MED.
