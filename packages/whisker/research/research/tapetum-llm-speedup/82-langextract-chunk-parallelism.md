# 82 - langextract-Chunk-Parallelism

**Verdict:** usable-with-conditions (+ langextract's in-document chunk parallelism is a direct template for parallelizing our unit-check wave, but it shortens per-paper depth only; it does not cut the 381-paper cold fleet wall because call count and 16 vLLM slots stay binding, and blind max_workers=10-style fan-out on a MoE pod adds batch-composition quality risk)
**Confidence:** high

## Findings

- [CRITICAL] Langextract splits each document into sentence-aware `TextChunk`s capped by `max_char_buffer` (default **1000** chars), then groups chunks into inference batches of `batch_length` (default **10**). Chunking walks sentences via `ChunkIterator` / `SentenceIterator`, breaking oversized sentences at newlines and token boundaries (`chunking.py:343-506`, `chunking.py:265-279`). The public API defaults are `batch_length=10`, `max_workers=10`, `max_char_buffer=1000` (`extraction.py:53-58`, `extraction.py:122-127`). Impact: a long doc with ~50 chunks runs **5 sequential batch rounds** at defaults, not one giant parallel wave; per-document wall ≈ `ceil(n_chunks / batch_length) × ~call_latency`, not `n_chunks × call_latency`. Quality risk: smaller `max_char_buffer` increases chunk count and call volume (explicit cost warning at `extraction.py:95-96`).

- [CRITICAL] Parallelism is **client-side HTTP thread pooling**, not async GPU batching. After prompts are built sequentially for each batch, `Annotator._annotate_documents_single_pass` calls `language_model.infer(batch_prompts=prompts)` once per batch (`annotation.py:366-392`). Gemini and OpenAI providers fan out with `concurrent.futures.ThreadPoolExecutor(max_workers=min(self.max_workers, len(batch_prompts)))` when `len(batch_prompts) > 1` (`gemini.py:475-504`, `openai.py:355-385`). Results are reassembled in **prompt index order** via a preallocated list (`gemini.py:487-504`), so completion order from `as_completed` does not affect merge order. Ollama processes `batch_prompts` **sequentially** in a for-loop (`ollama.py:291-310`); SKILL.md documents provider-dependent parallelism (`skills/langextract-usage/SKILL.md:125-128`). Impact: the pattern ports to our vLLM HTTP judge only if we implement the same thread-pool (or asyncio.gather) fan-out around independent calls; it is not automatic for all backends.

- [CRITICAL] Effective in-batch parallelism is **`min(batch_length, max_workers, len(batch_prompts))`**. `extract()` warns when `batch_length < max_workers` because only `batch_length` workers can run (`extraction.py:243-248`, `extraction.py:125-127`). README's Romeo example sets `max_workers=20` without raising `batch_length`, which would trigger that warning unless `batch_length >= 20` (`README.md:151-158`). Default **10** aligns batch size with thread count so one batch fully parallelizes without extra token cost (`extraction.py:97-98`: "max_workers improves processing speed without additional token costs"). Impact: mapping to tapetum unit checks means `batch_length=max_workers=MAX_UNIT_CHECKS` (5) for one parallel wave; defaults of 10 are irrelevant numerically but show the design intent (match batch to workers). Quality risk: none from batching mechanics alone.

- [HIGH] Chunk results merge **deterministically by document traversal order**, not by parallel completion time. Batches are processed in chunk-stream order (`annotation.py:351`, `annotation.py:366-440`); within each batch, outputs are zipped to chunks in list order (`annotation.py:396-432`). Extractions append to `per_doc[document_id]` as each chunk resolves (`annotation.py:431-432`). Completed documents emit in input order via `doc_order` / `_emit_docs_iter` (`annotation.py:307-346`, `annotation.py:440-445`). Multi-pass recall uses first-pass-wins overlap merge on char intervals (`annotation.py:46-84`, `extraction.py:154-158`). Default `suppress_parse_errors=True` lets one bad chunk fail locally (`extraction.py:136-138`, `annotation.py:365`). Impact: parallel unit checks can merge by sorted `unit_id` the same way; verdict fold stays serial (`pdf_judge.py:927-932`). Quality risk: parallel prompts lose langextract's optional sequential `context_window_chars` carry-over unless prompts are built in order before fan-out (`prompting.py:179-276`, `annotation.py:370-375`); our unit checks are scoped per page and do not need cross-unit context.

- [HIGH] Langextract parallelizes **within** a document (and can **across** documents in the same batch). `_document_chunk_iterator` yields chunks from a document stream; `make_batches_of_textchunk` can mix chunks from different `document_id`s in one batch (`annotation.py:118-160`, `annotation.py:224-227`, `chunking.py:265-279`). This is the opposite of our tapetum shape today: **32 papers concurrent, but serial inside each paper** (monolith → metadata → serial page escalations `pdf_judge.py:753` → serial unit loop `unit_judge.py:389-423`, `00-baseline.md:36-42`). Impact: adopting langextract's pattern for unit checks only removes up to **4× ~20 s ≈ 80 s** from the median paper's **~120 s** serial LLM depth (5 unit checks after shared prep), bringing unit phase from ~100 s to ~20 s if slots are free; monolith+metadata+escalations remain unless persona-20's full parallel wave is also taken. Fleet cold run: **~0 s** saving because total calls stay ~2284 and slot-seconds stay ~45,680 (`00-baseline.md:22-25`, `20-in-paper-parallelist.md:12-13`). Quality risk: MoE batch-composition variance worsens when one paper suddenly occupies W≤12 concurrent heterogeneous prefills (`20-in-paper-parallelist.md:16-17`, `MODELS.md:69-70`).

- [MED] Langextract's default `max_workers=10` targets **cloud API throughput**, not a fixed GPU slot count. Docstring: "Supported by Gemini models" (`extraction.py:125-127`); implementation is per-request HTTP threads with provider-side rate-limit retries (`gemini.py:351-391`). There is no global semaphore tied to server `max-num-seqs`. README scales to `max_workers=20` for a 147k-char novel (`README.md:151-158`). Impact: on our **16-slot** self-hosted pod with **32** cross-paper workers already overfilling slots (`cli.py:125`, `00-baseline.md:34-35`), naively copying `max_workers=10` **per paper** could demand 32×5=160 concurrent decodes during unit-heavy phases, inflating ITL/timeouts (`20-in-paper-parallelist.md:30-31`) without increasing fleet throughput. Portable rule: cap in-paper fan-out to `min(MAX_UNIT_CHECKS, free_slots)` or reduce cross-paper concurrency when in-paper parallel is enabled. Quality risk: timeout-driven false review caps (`unit_judge.py:419-423`).

- [MED] Payload scoping differs: langextract sends **one chunk's text** per call (plus optional previous-chunk tail via `context_window_chars`), while each tapetum unit check sends the **full `candidate_md`** plus one page's source (`unit_judge.py:769-776`, `00-baseline.md:43-47`). Parallelizing five unit checks therefore launches **five full-document prefills simultaneously**, amplifying KV pressure and breaking prefix-cache identity (random guard tag per call at `unit_judge.py:767-768`). Impact: per-paper latency win is **sublinear** in W under MoE at c=16 (`05-web.md` Q1/Q4, `20-in-paper-parallelist.md:20-21`); fleet tail may **worsen slightly**. Quality risk: prefix-cache miss + MoE routing variance compound.

- [LOW] `extraction_passes>1` multiplies total calls for recall and is explicitly anti-speed (`extraction.py:154-160`); default is 1. Langextract separates "parallel for speed" (same tokens, concurrent HTTP) from "passes for recall" (reprocess tokens). Impact: not applicable to tapetum unless we add redundant judge passes. Quality risk: N/A.

## False-pass hypothesis

Fleet run with in-paper `asyncio.gather` on five unit checks per paper while keeping `_DEFAULT_CONCURRENCY=32`: under slot starvation, several checks return empty or truncated JSON, retries succeed on attempt 2 (`00-baseline.md:60-61`), but the first attempt's partial reasoning biases which defect groups survive merge; a paper with a real table swap gets advisory pass because the one timed-out high-signal unit never ran and `coverage_complete` logic treats cap-skip differently from fail (`unit_judge.py:419-423`, `pdf_judge.py:895-902`). Langextract avoids this class for parse failures via `suppress_parse_errors` per chunk (`extraction.py:136-138`), but we gate on coverage completeness.

## False-fail hypothesis

Parallel unit checks on a clean paper where four of five return zero defects and one returns a hallucinated `candidate_not_found` quote: serial execution might have hit the zero-defect majority first and short-circuited operator attention; parallel merge still aggregates all results, and `verify_unit_evidence` demotes ungrounded quotes, but concurrent full-markdown prefills on MoE increase routing variance so the hallucination appears only under parallel batch composition (`20-in-paper-parallelist.md:26-27`). Advisory review cap triggers on a paper serial reruns would pass.

## What would change my mind

Measured tapetum A/B on 381 papers: serial in-paper vs langextract-style unit wave (`batch_length=max_workers=5`) with **cross-paper concurrency reduced** so peak in-flight ≤16, showing (1) fleet wall within ±2% of 3003 s, (2) p95 single-paper wall drop ≥3× on papers with 5 unit checks, and (3) merged-verdict / defect-group distribution within the existing MoE drift band (`20-in-paper-parallelist.md:34-35`), would upgrade fleet utility from "~0 s" to "worth shipping for tail UX."
