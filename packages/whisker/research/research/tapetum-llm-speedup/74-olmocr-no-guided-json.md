# 74 - olmocr-No-Guided-JSON

**Verdict:** usable-with-conditions — olmOCR's production default (YAML front matter + parse-and-retry, guided decoding off) is strong counter-evidence against flipping tapetum to guided JSON on DeepSeek MoE; repetition collapse they document is VLM/long-output/schema-mismatch specific, not a universal MoE law, but we lack their temperature ramp (D5) and already run a lower retry rate.
**Confidence:** high (olmocr source + paper §4.2 verified in clone); medium (transfer to our text-only judge schemas without live guided-json probe)

## Findings

- [CRITICAL] **Production inference deliberately avoids guided JSON schema enforcement; parse failure triggers retry, not constrained decode.** Paper §4.2 "Retries": "we do not enforce a specific JSON schema during inference on our fine-tuned model" because OSS schema-forcing tools are "unreliable" and "enforcing a schema which is even slightly off from what the model expects can cause generations to go out-of-domain or collapse into repetitions"; on parse failure they "simply retry generating from the same input sequence" ([arxiv:2502.18443](https://arxiv.org/abs/2502.18443) §4.2, mirrored in `05-web.md:47-48`). Code path: default `guided_decoding=False` in tests (`tests/test_pipeline.py:199`); production sends plain `chat/completions` with prompt-only structure (`pipeline.py:133-146,177`), YAML parse via `FrontMatterParser` (`pipeline.py:210-212`, `train/front_matter.py:37-53`). Impact: olmOCR treats server-side schema enforcement as a **quality risk**, not a speed win; aligns with our schema-in-prompt path (`model_backends.py:285-316`). Quality risk if we adopt guided JSON without holdout: same "schema slightly off → repetition" failure mode paper describes.

- [HIGH] **Optional `--guided_decoding` exists but uses vLLM `guided_regex` for YAML header only, not JSON schema; default remains off.** Opt-in flag: `parser.add_argument("--guided_decoding", action="store_true", help="Enable guided decoding for model YAML type outputs")` (`pipeline.py:1231`). When set, request adds regex mask for YAML front-matter fields, not `response_format` / `json_schema` (`pipeline.py:179-182`). Benchmark harness enables it (`scripts/run_benchmark_guided_decoding.sh:92,160`) but README documents it as optional (`README.md:465`). Impact: olmOCR did **not** reject all constrained decoding — they reject **JSON schema forcing on long VLM page output** while keeping regex guidance for eval. Our judge JSON is closer to their small header than to 8000-token page bodies, but we still use nested Pydantic schemas with free-text quote fields. Quality risk: low if regex-only; **HIGH** if full `json_schema` on MoE thinking models without #41199 fix.

- [HIGH] **Output format migrated JSON → YAML front matter specifically to cut repetition loops and retries.** v2 paper: "We switched to YAML, which reduced the retry rate dramatically… With JSON, we also found more incidences of repetition loops" ([arxiv:2510.19817](https://arxiv.org/abs/2510.19817) §YAML). Prompt requests "markdown, with a front matter section on top" (`prompts/prompts.py:164-170`); `PageResponse` dataclass validates parsed fields (`prompts/prompts.py:66-92`). Separate `openai_response_format_schema()` with strict JSON schema exists only for **OpenAI teacher labeling**, not vLLM serve (`prompts/prompts.py:95-142`, used in `data/buildsilver.py:59` with comment "use structured outputs" for batch GPT-4o silver data — `buildsilver.py:35-36`). Impact: format choice matters as much as guided vs unguided; JSON-shaped structured output + long free-text fields is the high-risk combo. Our unit-check JSON is shorter but still embeds quote strings. Quality risk: guided JSON on quote-heavy schemas may recreate olmOCR's JSON repetition class.

- [HIGH] **Measured structured-output failure / retry economics: ~12% page-level retries without guided JSON; we are ~2.4%.** Paper Table 6: "We measured a 12% retry rate for olmOCR" on production throughput/cost accounting ([arxiv:2502.18443](https://arxiv.org/abs/2502.18443) Table 6 text). Pipeline retry machinery: up to `--max_page_retries 8` (`pipeline.py:1221`), temperature ramp `0.1→1.0` "helps overcome repetition issues" (`pipeline.py:84-85,164-177`), invalid if `finish_reason != "stop"` or over context (`pipeline.py:202-206`), parallel retry burst when queue empty (`pipeline.py:343-363`), document discard if fallback rate > 0.004 (`pipeline.py:559-562`). Final stats log page failure rate and per-attempt histogram (`pipeline.py:1492-1510`). Tapetum cold fleet: **55 retries / ~2284 calls ≈ 2.4%**, ~100 s wall (`00-baseline.md:18,60-61`). Impact: olmOCR pays **5× our retry rate** already **without** guided JSON; guided JSON is not their latency silver bullet. Wall savings from eliminating our retries ≤ ~100 s (~3% of 3003 s) per persona 32 — not a 5–10 min lever either way.

- [MED] **Repetition collapse is documented as a VLM page-generation pathology, mitigated by temperature escalation we cannot port.** Paper §4.2 "Decoding": "most common failure… endless repetitions of the same token, line, or paragraph… caught when output exceeds maximum context length, or does not validate against our JSON schema"; mitigation is τ=0.1→0.8 plus retries ([arxiv:2502.18443](https://arxiv.org/abs/2502.18443) §4.2). Code ties repetition to non-`stop` finish and parse/validation failure (`pipeline.py:205-206,228-230`). Gemini bench runners explicitly label non-STOP finish as "repetition failure" (`bench/runners/run_gemini.py:118,150`). Impact: risk is **modality + output length + decoding constraints**, not "MoE" alone. Our text-only judge calls cap at 1536 tokens (`00-baseline.md:27-28`) with no page raster — lower intrinsic repetition pressure. Quality risk: adopting guided JSON on DeepSeek-V4 thinking without temperature ramp removes olmOCR's second repetition escape hatch; D5 forbids that ramp (`00-baseline.md:86`, `73-olmocr-retry-economics.md:10`).

- [MED] **No vLLM GitHub issue references in the olmocr clone; their vLLM integration is operational, not issue-tracker-driven.** `rg` over `research/repos/olmocr` finds vLLM install/docs links only (`pipeline.py:924`, README migration note `README.md:44`), no `github.com/vllm-project/vllm/issues/` citations. Server spawn passes through CLI args to `vllm serve` (`pipeline.py:807-858`). Separate vLLM thinking + structured-output hazards for **our** stack live in vLLM #41132 / #41199 and pipeline #28219 (`32-structured-output-mechanic.md:20`), not olmOCR evidence. Impact: olmOCR cannot validate vLLM guided-json fixes for DeepSeek MoE; any adoption requires our own holdout probe, not olmOCR precedent.

- [LOW] **Silver-data pipeline contradicts production: OpenAI structured JSON for labeling, free generation for serve.** `buildsilver.py:35-36`: "use structured outputs… Even if the last 10 queries… returned exactly what you wanted… that doesn't mean this will hold across 1000's of queries" with `response_format: openai_response_format_schema()` (`buildsilver.py:59`). Production vLLM path never sets `response_format`. Impact: olmOCR separates **teacher batch reliability** (guided JSON OK on GPT-4o) from **fine-tuned VLM serve reliability** (guided JSON avoided). Analogous split for us: constrained decode might help one-off eval, not proven for 2284-call fleet on alliance-pod.

## False-pass hypothesis

Enable vLLM `response_format json_schema` on unit checks; first-attempt syntactic validity rises so retry rate drops, but constrained decoding narrows the token manifold and the model emits `verdict:"pass"` with empty `defects` more often on table-boundary errors that free-form decoding occasionally caught via longer pre-JSON reasoning — silent false-pass on the 16/381 verdict-changing papers (`00-baseline.md:29-30`), matching olmOCR's warning that schema enforcement changes generation distribution when the schema does not exactly match training-time behavior ([arxiv:2502.18443](https://arxiv.org/abs/2502.18443) §4.2).

## False-fail hypothesis

Adopt guided JSON on alliance-pod while client still reads only `delta.content` and thinking is enabled: valid JSON lands in the reasoning channel (vLLM #41132), `_extract_json` fails twice (`model_backends.py:362-410`), paper tombstones as `error` despite a correct structured verdict in an unobserved field — fail-closed blow-up unrelated to olmOCR but blocking the speed win persona 32 expects.

## What would change my mind

Holdout A/B on alliance-pod (post-#41199, reasoning parser verified): guided `json_schema` on `UnitCheck`/`PdfJudgment` achieves ≥98% first-attempt parse, ≤1 pp shift in pass/review/fail histogram vs current schema-in-prompt, **and** zero new missed defects on 48-anchor holdout — would downgrade olmOCR counter-evidence to "VLM-specific" and permit a flagged backend toggle; absent that, olmOCR supports **keep parse-and-retry** as default.

## Recommendation (for persona 32)

**Keep parse-and-retry (schema-in-prompt + client validate + bounded retry).** Do not adopt server-side guided JSON as the tapetum fleet default based on olmOCR:

1. They explicitly avoid JSON schema enforcement at inference because OSS guided tools caused repetition collapse when schemas drift from fine-tune ([arxiv:2502.18443](https://arxiv.org/abs/2502.18443) §4.2).
2. Their optional `guided_regex` targets a tiny YAML header, not nested judge JSON with quote fields (`pipeline.py:179-182`).
3. They already run ~12% page retries without guided JSON — worse than our ~2.4% — so guided decode is not prerequisite for production OCR quality.
4. Repetition mitigation relies on temperature ramp (`pipeline.py:84-85`), which we cannot use (D5).
5. Workload mismatch: 1 VLM call/page up to 8000 tokens vs our ~6 serial text judge calls capped at 1536 tokens (`00-baseline.md:22-28`, `81-olmocr-anti-steelman.md:8`).

olmOCR does **not** prove DeepSeek MoE + guided JSON will repetition-collapse; it proves **VLM + long structured markdown + schema mismatch + JSON syntax** is dangerous. That is cautionary, not dispositive. Treat guided JSON as holdout-gated experiment only (persona 32 conditions), not a fleet speed lever.
