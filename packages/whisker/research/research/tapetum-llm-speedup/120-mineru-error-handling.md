# 120 - mineru-Error-Handling

**Verdict:** usable-with-conditions (MinerU is an extraction pipeline with deliberate fail-open partials; batch/task isolation and timeout layering are portable, but its per-page and document abort semantics must not be copied into our fail-closed judge lane without a quality proof)
**Confidence:** high

## Findings

- [CRITICAL] MinerU's corpus batch model isolates failures at the **task** boundary, not the page boundary. CLI workers catch per-task exceptions, append `TaskFailure`, and continue (`client.py:794-816`); only after all tasks finish does the CLI raise with a failure summary (`client.py:1016-1023`). VLM/hybrid backends plan **one document per task** (`client.py:661-664`), so one bad PDF in a 1000-file folder fails that task only; the other 999 keep running. Impact: confirms our paper-level firewall pattern is industry-normal; no cold-run saving unless we were failing the whole fleet on first error (we are not: `cli.py:1373-1399`). Quality risk: none for isolation itself.

- [HIGH] **Intra-task multi-file batches are atomic.** A single API task can upload multiple files; `load_parse_inputs` raises on the first unreadable file and aborts the whole task (`fast_api.py:812-818`). VLM processing loops documents sequentially with no per-doc try/except (`common.py:448-464`); the first exception stops later files in the same task. Pipeline mode can pack multiple docs into one processing window (`pipeline_analyze.py:232-262`), so one bad page batch can abort siblings in that window. Impact: irrelevant to our 381-paper judge fleet (one paper per worker), but explains why MinerU defaults VLM to one-doc tasks for robustness. Quality risk: N/A for tapetum.

- [HIGH] **Per-page VLM failure is fail-fast, not fail-open.** `doc_analyze` / `aio_doc_analyze` process pages in windows of up to `MINERU_PROCESSING_WINDOW_SIZE` (default 64, `config_reader.py:158-169`). Each window calls `predictor.batch_two_step_extract` with no inner try/except (`vlm_analyze.py:478-482`, `578-581`); any VLM error aborts the entire document. No olmOCR-style `max_page_error_rate` threshold exists anywhere in the repo (searched). Impact: MinerU does **not** validate the cross-repo "extractors tolerate page loss" pattern at VLM depth; only **pre-inference** PDF repair is fail-open. Quality risk: copying page-level fail-open into our `--all-pages` unit lane would violate fail-closed coverage (`pdf_judge.py:584-586`, `985-993`).

- [HIGH] **Pre-inference PDF repair fails open; post-inference output assembly fails open.** Broken PDFium pages are skipped with warnings (`common.py:212-247`); render timeouts raise but recycle the executor (`pdf_image_tools.py:313-318`, `343-347`). Optional steps degrade silently: layout/span viz skipped on exception (`common.py:288-298`), LLM title leveling retries 3x then returns `None` (`llm_aided.py:169-218`), visualization jobs skipped (`client.py:436-443`). Result ZIP/JSON builders skip files whose parse dir is missing instead of failing the response (`fast_api.py:453-460`, `515-516`). Impact: saves wall on optional/auxiliary work only. Porting to tapetum: could apply to **non-gating** ideal verifier or debug paths only; applying to monolith/metadata/unit checks would create false-pass holes. Estimated cold-run saving if we fail-open optional ideal calls on transport error: low single-digit % (ideal inventory is small); quality risk **high** on core judge steps.

- [MED] **VLM backend retry/timeout structure (http-client only).** `ModelSingleton.get_model` sets `http_timeout=600`, `max_retries=3`, `retry_backoff_factor=0.5`, `max_concurrency=100` for the http-client backend (`vlm_analyze.py:71-75`, `232-235`). Local vLLM/lmdeploy/transformers paths have no application-level retry loop around inference. API layer: task wait default 3600s (`api_client.py:89-97`), result download 600s (`api_client.py:100-109`), PDF render default 300s via `MINERU_PDF_RENDER_TIMEOUT` (`os_env_config.py:10-12`), status poll retries on read timeout until deadline (`api_client.py:949-957`). Impact: our lane already has per-call timeouts (`constants.py:197,241`) and paper budgets (`cli.py:137-161`); MinerU adds no novel retry lever for DeepSeek judge calls beyond "bounded poll retry." Quality risk: lowering our 120s unit timeout to fail faster would increase error tombstones (`cli.py:747-760`) without quality gain.

- [MED] **Server concurrency vs client concurrency are decoupled.** FastAPI limits in-flight parse jobs with `_request_semaphore` sized from `MINERU_API_MAX_CONCURRENT_REQUESTS` (default 3, `fast_api.py:95-98`, `228-234`). Failed async tasks set `TASK_FAILED`, store `task.error`, signal waiters (`fast_api.py:1149-1154`); dispatcher crash sets `last_worker_error` and marks API unhealthy (`fast_api.py:1109-1113`, `1070-1084`). Impact: mirrors our client/server slot split (32 papers vs 16 server seqs in baseline); no new speed lever. Quality risk: none.

- [HIGH] **We already match MinerU's best batch pattern but lack their early-abort on doomed papers.** Our per-paper firewall catches exceptions, writes error tombstones (preventing stale passes), and continues the fleet (`cli.py:1118`, `1373-1387`, `747-760`). Warm incremental skip (64.8s vs 3003s cold in baseline) has no MinerU analogue. **Gap:** after `metadata_check.verdict == "fail"` we still run page escalations and unit checks (`pdf_judge.py:711-714`, then `753+`, `858+`); there is no metadata-fail short-circuit despite baseline listing it as an open lever (`00-baseline.md:90-91`). Impact: on metadata-fail papers, skipping remaining ~0-5 escalations + ~1-5 unit checks could save **~240-720s per affected paper** at ~20s/call (baseline implied latency), fleet-wide saving depends on fail rate (not measured in baseline). Quality risk: **medium** if metadata false-fails; must cap at `review`/`fail` without implying coverage_complete.

## False-pass hypothesis

Adopting MinerU's `build_result_dict` "skip missing outputs" semantics for tapetum sidecars would let a paper timeout mid-cascade leave no tombstone while earlier partial LLM findings look complete; fusion could treat incomplete coverage as pass. Concrete case: monolith succeeds, metadata passes, first unit check times out; MinerU-style assembly would omit failed units from the ZIP; our fail-closed lane must tombstone or mark `coverage_complete=false` (`fusion.py:192`, `pdf_judge.py:985-993`).

## False-fail hypothesis

Adopting MinerU's CLI "raise after batch with failure list" exit semantics without distinguishing operational error vs advisory `fail` would mark the whole fleet run as exit 1 even when every completed paper has a valid advisory verdict. Concrete case: 1/381 papers hits `asyncio.TimeoutError` at paper budget; we correctly tombstone and count `error` (`cli.py:1405-1406`, `1434`); treating that like MinerU's `click.ClickException` at end is fine for ops but must not downgrade the other 380 sidecars.

## What would change my mind

A fleet histogram from our 381-paper cold run: count of papers with `metadata_outline_check.verdict=="fail"` (or transport `PdfLaneError` before unit phase) multiplied by mean remaining LLM calls actually executed, showing >=5% of total 2284-call budget wasted on post-metadata work. Without that number, metadata short-circuit remains speculative.
