# 133 - deepeval-Judge-Design

**Verdict:** usable-with-conditions — deepeval documents strong within-metric batching and sub-step parallelism, but no framework-level "extract once, judge many" across rubrics; SAJA-style 1-call restructuring is not validated here.
**Confidence:** high

## Findings

- [CRITICAL] **GEval = 2 LLM calls by default (step synthesis + scored evaluation); 1 call if `evaluation_steps` pre-supplied.** Evidence: `a_measure` always calls `_a_generate_evaluation_steps` then `_a_evaluate` (`research/repos/deepeval/deepeval/metrics/g_eval/g_eval.py:201-207`); step generation skipped when `self.evaluation_steps` already set (`g_eval.py:229-231`). Output schema: `Steps.steps: List[str]` then `ReasonScore {reason, score}` (`g_eval/schema.py:5-17`). Impact: pre-caching rubric steps on our monolith/metadata prompts could drop 1 call/paper (~20 s serial wall, ~381 s fleet if universal); quality risk low if steps are frozen and versioned like deepeval's `pull()` path (`g_eval.py:458-502`).

- [CRITICAL] **Faithfulness = 3–4 calls, NOT N per claim: extract truths + claims (parallel), batch-verify all claims in one verdict call, optional reason call.** Evidence: `asyncio.gather` on truths/claims (`faithfulness.py:172-175`); single `_a_generate_verdicts` with all claims (`faithfulness.py:249-270`); optional `_a_generate_reason` (`faithfulness.py:191-218`, `include_reason=True` default at `:62-67`). Schemas: `Truths`, `Claims`, `Verdicts` with `FaithfulnessVerdict {verdict: yes|no|idk}` (`faithfulness/schema.py:5-23`). Impact: our 5 serial unit checks (~1510 calls fleet) could become 1 batched defect-group call per paper if we adopt faithfulness-style batching — up to ~4× call reduction on flagged papers (~1200 calls saved, ~750 s at 20 s/call serial, ~300 s fleet at 16 slots); quality risk HIGH for long-context multi-page packing (RuVerBench in `05-web.md` Q5: double-digit drops).

- [HIGH] **Summarization metric = 6–7 calls within ONE metric (worst case in repo).** Evidence: parallel truths+claims (`summarization.py:168-171`); coverage path = question generation + 2 answer batches (`summarization.py:380-408`, default `n=5` at `:46`); alignment verdicts (`summarization.py:436-447`); reason (`summarization.py:202-245`). Reuses `Truths`/`Claims` schemas from faithfulness (`summarization.py:33-34`). Impact: deepeval does NOT collapse multi-axis evaluation into one call even when axes share inputs; a 1-call tapetum cascade would be MORE aggressive than their heaviest metric. Quality risk: none from copying deepeval — they already spend 6+ calls.

- [HIGH] **No cross-metric extraction amortization: each metric re-extracts independently; metrics run in parallel but do not share state.** Evidence: `copy_metrics` clones fresh metric instances per test case (`metrics/utils.py:86-106`, `evaluate/execute/e2e.py:404-406`); `measure_metrics_with_indicator` runs all metrics via `asyncio.gather` with no shared extraction cache (`metrics/indicator.py:226-238`); Faithfulness and Summarization both call `_a_generate_truths`/`_a_generate_claims` separately with no cross-metric hook. Impact: running our monolith + metadata + units as separate "metrics" without app-level memo would DUPLICATE document prefill like our current 6× markdown resend (`00-baseline.md:43-44`); zero wall savings unless we build explicit shared extraction ourselves.

- [HIGH] **Within-metric parallelism via `asyncio.gather` on independent sub-calls (not serial like our per-paper cascade).** Evidence: Faithfulness truths+claims (`faithfulness.py:172-175`); Summarization truths+claims then coverage+alignment (`summarization.py:168-178`); ContextualRelevancy one call per retrieval chunk gathered in parallel (`contextual_relevancy.py:172-178`). Cross-test-case parallelism: `AsyncConfig.max_concurrent=20` semaphore (`evaluate/configs.py:8-11`, `evaluate/execute/e2e.py:348-352`). Impact: in-paper parallel unit checks (advisory lane exempt D11) mirrors deepeval's gather pattern — could cut per-paper serial wall from ~120 s toward ~40 s on 6-call papers if MoE batch variance acceptable (`00-baseline.md:35-42`); quality-stability risk from MoE composition noted in baseline.

- [MED] **Hallucination / AnswerRelevancy / ContextualRecall use 2–3 calls with batched intermediate extraction in the verdict prompt (not per-item loops).** Evidence: Hallucination single `_a_generate_verdicts` over full output (`hallucination.py:131-134`, `202-218`); AnswerRelevancy statements then batched verdicts (`answer_relevancy.py:137-142`, `208-228`); ContextualRecall one verdict call for all sentences (`contextual_recall.py:262-291`). Exception: ContextualRelevancy scales as **N+1** calls for N retrieval chunks (`contextual_relevancy.py:172-178`). Impact: prefer batched verdict pattern over per-page serial loops; avoid ContextualRelevancy-style N-chunk scaling for our page units.

- [MED] **No framework token budget: output size bounded only by provider defaults + Pydantic schema shape; pass `generation_kwargs` per model.** Evidence: `GPTModel.generate` passes `**self.generation_kwargs` with no `max_tokens` constant (`models/llms/openai_model.py:168-169`, `198-202`); structured output via `generate_with_schema_and_extract` (`metrics/utils.py:495-555`). Schemas are compact (string lists, yes/no/idk verdicts, float scores). Impact: deepeval achieves speed via small structured outputs, not explicit caps — our 1536-token unit cap (`00-baseline.md:27-28`) is already tighter; further decode reduction portable if schemas stay small.

- [LOW] **Call-reduction knobs: `include_reason=False` (-1 call/metric), `evaluation_steps` pre-set (-1 GEval call), per-metric disk cache (`CacheConfig.use_cache=False` default), DAG `TaskNode` for custom extract→judge pipelines.** Evidence: reason skip (`faithfulness.py:192-193`); step skip (`g_eval.py:229-231`); cache (`evaluate/configs.py:38-41`, `metrics/indicator.py:211-224`); DAG TaskNode output feeds children via `_resolve_text` (`metrics/dag/nodes.py:173-196`, `graph.py:89-105`). Impact: cache helps warm reruns only (cf. our 64.8 s warm run, `00-baseline.md:19-20`); DAG is opt-in composition, not default fleet behavior.

## False-pass hypothesis

Batching all 5 unit checks into one faithfulness-style verdict call on a 13-page WG21 paper: a table-row swap on page 7 and a heading demotion on page 11 could both land in one prompt, and the judge returns only the higher-salience defect — matching RuVerBench multi-rubric degradation (`05-web.md:96-98`) and deepeval's own lack of multi-metric packing.

## False-fail hypothesis

Replacing per-page unit checks with one comprehensive extraction call whose structured output feeds deterministic metadata/outline scoring: a page-local code-block fence error visible only when source page text is paired with candidate (our current unit payload) may be absent from a document-level extraction schema, causing a silent pass where today's scoped checks fail-closed.

## What would change my mind

An A/B on our 381-paper fleet (or 37-pass + 43-fail stratified sample) showing a 1-call structured extraction + deterministic downstream verdicts matches the v10 6-call cascade on verdict-changed papers (16/381 baseline, `00-baseline.md:29-30`) with zero new false-fails on the golden holdout set.
