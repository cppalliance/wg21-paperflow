# 111 - sglang-Hierarchical-Cache

**Verdict:** usable-with-conditions — SGLang HiCache/HiRadix is production-grade tiered prefix retention (L1 GPU → L2 host → L3 storage) and matches our 381×~40k-token scan-pollution problem, but on `alliance-pod` (vLLM + DeepSeek-V4-Pro) the portable win is vLLM MooncakeStoreConnector or `--kv-offloading-size` + APC/retention fixes, not a sglang stack swap; hierarchical tiering alone cannot reach the 5–10 min target without guard-tag and prompt-layout fixes first.
**Confidence:** medium

## Findings

- [CRITICAL] **HiCache is a shipped three-tier radix extension, not an experimental flag.** L1 = GPU device pool (RadixAttention tree), L2 = host pool sized by `--hicache-ratio` (default 2.0× device) or `--hicache-size` GiB override, L3 = optional storage backends (`file`, `mooncake`, `hf3fs`, `nixl`, …). Config lives in `server_args.py:2502-2575`; tree wiring selects `HiRadixCache` for plain MHA/MLA (`registry.py:117-129`) or `UnifiedRadixCache.init_hicache()` for DSA/hybrid SWA models including DeepSeek V4 (`registry.py:117-121`, `unified_radix_cache.py:502-568`, `unified_cache_components/README.md:69-70`). DeepSeek V4 Flash has dedicated CI with `--enable-hierarchical-cache --hicache-ratio 4 --hicache-write-policy write_through` (`test_unified_radix_cache_kl_dsv4.py:73-87`). Impact: architecture fits our “keep all paper prefixes warm across 6 interleaved calls” story; quality risk **none** (KV replay, validated by KL tests at threshold 0.005, `test_unified_radix_cache_kl_dsv4.py:42`).

- [CRITICAL] **Default is OFF; DeepSeek V4 requires Unified Radix Tree.** `--enable-hierarchical-cache` defaults `False` (`server_args.py:2502-2504`). DSV4/hybrid path requires `SGLANG_ENABLE_UNIFIED_RADIX_TREE=1` (tests set it at `test_unified_radix_cache_kl_dsv4.py:102`; MiMo raises if unset at `server_args.py:5073-5078`). Mutually exclusive with `--disable-radix-cache` (`server_args.py:7200-7204`). Impact: enabling on a sglang pod is a deliberate launch change plus env var, not a runtime toggle; quality risk **none**, ops risk **medium** (misconfig fails at startup).

- [HIGH] **GPU eviction demotes to L2 instead of dropping; reload is async H→D per layer.** On GPU pressure, `HiRadixCache.evict()` demotes backuped leaves to host under `write_through` (`hiradix_cache.py:1115-1155`, `_evict_backuped` at `1204-1208`); `write_backup()` copies D→H via `HiCacheController.write()` (`hiradix_cache.py:833-863`, `cache_controller.py:743-758`). On prefix hit against an evicted node, `load_back()` walks the evicted chain, skips if `< load_back_threshold` (10 tokens, `hiradix_cache.py:201`, `unified_radix_cache.py:555`), else issues per-layer `load_to_device_per_layer()` on a dedicated load stream with layer-compute overlap (`cache_controller.py:782-835`, design note in `unified_cache_components/README.md:69`). Prometheus histogram buckets for `sglang:load_back_duration_seconds` span **1 ms–1 s** (`metrics_collector.py:1902-1940`), implying sub-second reload vs multi-second full prefill. MiMo regression forces L2 eviction then verifies `cached_tokens_details.host > 0` and KL-accurate logprobs after load-back (`test_unified_radix_cache_kl_mimo.py:127-144`). Impact: under 32-paper client concurrency (`00-baseline.md:34-35`), prefixes evicted from ~1–3M-token GPU L1 can survive on L2 and avoid ~5–15 s full-document prefills on calls 2–6; estimated **400–800 s** wall on the 3003 s cold run if prompt identity is fixed and L2 sized to hold the hot set. Quality risk **low** (KL-gated in CI; production drift unmeasured on our judge prompts).

- [HIGH] **Capacity math for 381 papers: L2 alone is insufficient; L3 or large `--hicache-size` needed.** Default `--hicache-ratio 2.0` gives 2× GPU token capacity on host (`server_args.py:2505-2509`). DSV4 tests use ratio 4 with `--max-total-tokens 20000` (`test_unified_radix_cache_kl_dsv4.py:74-85`). Fleet: 381 × ~40k ≈ **15 M document tokens** (`00-baseline.md:23-24`, user mandate); GPU L1 holds ~1–3 M under load (persona 92 estimate). At ratio 4 on a ~2 M GPU pool, L2 ≈ 8 M tokens — covers ~200 full papers, not all 381 simultaneously. L3 file backend test uses `--hicache-storage-backend file` with `SGLANG_HICACHE_FILE_BACKEND_STORAGE_DIR` (`test_unified_radix_cache_kl_dsv4.py:153-175`); Mooncake L3 PR benchmark used **600 GB L2 + 800 GB L3** (`sglang PR #19320`). Impact: to keep **all** paper prefixes warm across interleaved scheduling, plan **≥300 GB host** (`--hicache-size`) or L3 mooncake/file tier; otherwise cold papers still recompute. Quality risk **none**; cost risk **medium** (host RAM/disk on RunPod).

- [HIGH] **Write policy and I/O knobs trade backup bandwidth vs retention.** Default `--hicache-write-policy write_through` backs up to host immediately (`server_args.py:2515-2522`, `hiradix_cache.py:198-200`); alternatives `write_through_selective` (hit-count gated) and `write_back` (on eviction only; `_evict_write_back` marked for deprecation at `hiradix_cache.py:1157-1159`). I/O backend `kernel` (default) vs `direct` with layout auto-normalization (`server_args.py:2523-2544`, `_handle_hicache` at `6719-6777`). DSV4 uses `page_first_direct` + `direct` or `page_first` + `kernel` (`test_unified_radix_cache_kl_dsv4.py:39-40, 117-118). Impact: `write_through` maximizes L2 hit rate for our “same doc 6×” pattern at cost of PCIe write bandwidth during first prefill; selective/write_back reduce I/O but increase recompute risk under churn. Quality risk **none**.

- [MED] **Published benchmarks: large TTFT/throughput wins on multi-turn prefix-heavy loads, not our exact judge schema.** LMSYS HiCache blog reports up to **6× throughput** and **80% TTFT reduction** on long-context / multi-turn benchmarks (`05-web.md` Q4, lmsys.org blog 2025-09-10). SGLang PR #19320 multi-round L2+L3: cache hit 26%→55%, avg TTFT 3.49 s→2.34 s; community patch on saturated host: TTFT avg **1.20 s→0.44 s** (−63.5%). Repo ships `benchmark/hicache/bench_long_context.py` and `bench_multiturn.py` for reproduction (`benchmark/hicache/bench_long_context.py:1-100`). Impact: transfer+reload beats recompute when prefixes reuse; does **not** translate linearly to 3003 s until guard-tag and user-block reorder land (persona 15). Quality risk **none** for benchmarks; **unmeasured** for tapetum judge outputs.

- [MED] **vLLM equivalents on our existing pod — no sglang migration required for tiering.** vLLM APC is **GPU-only LRU** (`92-vllm-apc-internals.md`); extended by PR #43447 retention for DSV4 SWA (`05-web.md` Q1). **CPU tier:** `--kv-offloading-size <GiB>` activates native `OffloadingConnector` or `SimpleCPUOffloadConnector` (`cache.py:180-189`, `vllm.py:863-881`). **LMCache:** `--kv-offloading-backend lmcache` → `LMCacheMPConnector` (`vllm.py:882-888`, `docs/deployment/integrations/production-stack.md:7`). **Distributed L3:** `MooncakeStoreConnector` explicitly supports “CPU/disk offloading” and “prefix caching across instances” (`docs/features/mooncake_store_connector_usage.md:3-6, 75-80`) — same Mooncake backend SGLang HiCache L3 lists (`server_args.py:2545-2558`). SGLang also exposes `--enable-lmcache` as an alternative hierarchical path (`server_args.py:2793-2797`). Impact: for `alliance-pod`, **MooncakeStoreConnector + APC + PR #43447 retention + guard fix** is the lowest-friction hierarchical stack; sglang HiCache is justified only if we are already moving inference to sglang for other reasons. Quality risk **low** if KV replay is bitwise-identical (APC/offload design); **high** if we migrate judge stack without holdout A/B.

- [LOW] **HiCache does not fix tapetum prefix-identity bugs.** Per-call random `SRC{hex}` guard tags break leading-token identity across all ~2284 calls (`15-prefix-cache-enabler.md`, `unit_judge.py:767-768`); unit-check user layout puts unique metadata before shared `candidate_md` (`15-prefix-cache-enabler.md` finding 2). HiCache/RadixAttention only helps when token prefixes **match** — same constraint as vLLM APC (`92-vllm-apc-internals.md:8`). Impact: enabling hierarchical cache with unfixed prompts yields **near-zero cross-call hits** and added I/O overhead (APC hash overhead ~37% at 0% hits, `05-web.md` Q4). Quality risk **none** for HiCache itself; **false-pass** risk if operators believe cache is “on.”

## False-pass hypothesis

Enable `--enable-hierarchical-cache` with `write_through` on a sglang judge pod without moving the guard tag to per-paper scope: L2 retains KV for random per-call system suffixes, operators see rising `sglang:hicache_host_used_tokens` (`metrics_collector.py:632-639`) and believe prefixes are shared, but calls 2–6 still diverge at the guard tail so document KV is not reused — wall time stays ~3003 s while host RAM fills with useless per-call entries, masking the real prompt-layout fix.

## False-fail hypothesis

Reject HiCache because “we run vLLM”: vLLM `MooncakeStoreConnector` + `--enable-prefix-caching` + `VLLM_PREFIX_CACHE_RETENTION_INTERVAL=32768` on DeepSeek-V4-Pro (`05-web.md` Q1, `mooncake_store_connector_usage.md:75-80`) provides the same L1→CPU→disk tiering without sglang; a holdout run that only benchmarks sglang migration latency would falsely conclude hierarchical tiering is unusable when the portable vLLM path was never tried.

## What would change my mind

A 10-paper canary on `alliance-pod` with MooncakeStoreConnector (or sglang HiCache if testing migration): guard moved to per-paper scope + unit user reorder per persona 15, logging `vllm:prefix_cache_hits/queries` or `sglang:load_back_tokens_total` + `sglang:load_back_duration_seconds` through all 6 serial calls per paper at concurrency 32. If call 2+ shows **>50% host/L2 hits** on the shared document block and wall drops **≥600 s** with zero verdict diffs on the 48-paper holdout, upgrade to **usable**; if hits stay <10% after prompt fix, downgrade hierarchical tiering to **garbage** for this fleet.
