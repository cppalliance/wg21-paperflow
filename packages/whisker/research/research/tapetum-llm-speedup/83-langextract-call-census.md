# 83 - langextract-Call-Census

**Verdict:** usable-with-conditions — langextract's call formula is explicit and tiered (1 pass + scoped chunks by default; recall and parallelism are opt-in multipliers), but its chunk-per-call model inverts our economics on long WG21 papers (~80–400 calls vs our fixed 6) even before multi-pass; the portable lesson is default-off quality multipliers, not copying its chunking budget.
**Confidence:** high

## Findings

- [CRITICAL] **Exact LLM API call formula per document:**

  ```
  LLM_API_calls = extraction_passes × C(doc)
  ```

  where `C(doc)` = number of `TextChunk`s yielded by `ChunkIterator` for that document's tokenized text under `max_char_buffer` (sentence/newline/token-aware, not a simple char division). Evidence: one `infer(batch_prompts=...)` per batch of chunks (`annotation.py:366-392`); inside `GeminiLanguageModel.infer`, each prompt in `batch_prompts` invokes one `_process_single_prompt` → one `generate_content` (`gemini.py:476-508`, `368-370`); multi-pass replays the full single-pass pipeline `extraction_passes` times (`annotation.py:477-491`). Multi-document: `C_total = Σ C(doc_i)` over `_document_chunk_iterator` (`annotation.py:118-160`, `348-351`). Orchestration-only: `infer_invocations = extraction_passes × ceil(C_total / batch_length)` (`chunking.py:265-279`). Impact: an 80k-char WG21 paper at `max_char_buffer=1000` (shipped `extract()` default, `extraction.py:53`) yields roughly 80–150 chunks → **80–150 API calls at default `extraction_passes=1`**, vs our **6 fixed calls/paper** (`00-baseline.md:22-23`) but with **chunk-scoped payloads** instead of full markdown ×6. Quality risk: raising `max_char_buffer` toward our single-shot budget trades call count for extraction recall (README recommends smaller buffers, `README.md:158`, `longer_text_example.md:164-167`).

- [CRITICAL] **`batch_length` groups chunks per `infer()` call; it does NOT reduce billed API calls.** `make_batches_of_textchunk` batches up to `batch_length` chunks (`chunking.py:265-279`); each chunk still gets an individual `generate_content` inside parallel or sequential branches (`gemini.py:476-508`). Docstring: "`max_workers` improves processing speed **without additional token costs**" (`extraction.py:97-98`); effective parallelism = `min(batch_length, max_workers, len(batch_prompts))` (`extraction.py:122-127`, `gemini.py:477-478`). Shipped defaults: `batch_length=10`, `max_workers=10` (`extraction.py:57-58`). Impact: langextract parallelizes **within** a document by default; our lane parallelizes **across** papers but stays serial within one paper (`00-baseline.md:36-42`). Porting `batch_length` without in-paper parallel unit checks saves zero calls; only wall-clock if we adopt concurrent distinct-prompt dispatch (MoE variance risk per `00-baseline.md:95-96`, persona 66 marker cap of 3). Quality risk: medium for in-paper parallel on shared MoE pod.

- [HIGH] **`extraction_passes>1` is documented as a linear cost multiplier for recall, default OFF.** Defaults: `extraction_passes=1` (`extraction.py:64`, `annotation.py:216`). Tradeoff text: "Supports sequential extraction passes to **improve recall at the cost of additional API calls**" (`extraction.py:80-81`); "`extraction_passes=3` **reprocesses tokens 3×**" (`extraction.py:154-160`); Annotator docstring: "Values > 1 reprocess tokens multiple times, **potentially increasing costs** with the potential for a **more thorough extraction**" (`annotation.py:237-241`); README/longer-text example promote `extraction_passes=3` as user opt-in ("Improves recall through multiple passes", `README.md:156-157`; "Multiple extraction passes improve recall", `longer_text_example.md:154-158`). Mechanism: each pass is an independent full re-chunk → infer → align cycle on identical source; results merged with **first-pass-wins** for overlaps, non-overlapping entities from later passes appended (`annotation.py:46-84`, `477-528`; `longer_text_example.md:158-159`). **No prior extractions fed back into prompts** — not a verification loop (`annotation.py:482-491`; prior census `12a-langextract-callsites.md`). Impact: langextract users pay 1× by default and opt into 2–3× for recall; our lane runs the full 6-call cascade by default (monolith + metadata + up to 5 unit checks + page escalations, `00-baseline.md:22-23,56-57`) — structurally identical to marker persona 66's finding that **quality multipliers default OFF externally and ON for us** (`66-marker-quality-speed-flags.md:8-9`). Inverting tapetum to nightly monolith+metadata (~2 calls) + weekly `--thorough` (6 calls) mirrors langextract's `extraction_passes=1` + opt-in `=3` pattern and persona 66's `--use_llm` tiering; estimated **−67% calls** on nightly (1510 unit + 16 page calls removed, `66-marker-quality-speed-flags.md:8`, `00-baseline.md:22-23`). Quality risk: the 16/381 papers whose verdict changed only after unit checks (`00-baseline.md:29-30`).

- [HIGH] **Post-LLM alignment adds zero LLM calls.** After each chunk inference, `resolver.resolve` + `resolver.align` run deterministically (`annotation.py:404-429`; `WordAligner` at `resolver.py:789+`). Prompt pre-flight validation also uses deterministic `WordAligner` (`prompt_validation.py:130-168`). Impact: langextract's total model spend is **purely extraction_passes × chunks**; our 6-call judge chain has no second-pass merge — each call is an independent verdict stage. Quality risk: none from skipping alignment (we already use deterministic grounding in whisker).

- [MED] **Two default surfaces: shipped `extract()` vs raw `Annotator`.** `extract()` defaults: `max_char_buffer=1000`, `batch_length=10`, `max_workers=10`, `extraction_passes=1` (`extraction.py:53-58,64`). `Annotator.annotate_documents` defaults if called directly: `max_char_buffer=200`, `batch_length=1`, `extraction_passes=1` (`annotation.py:213-216`). Doc warns smaller `max_char_buffer` "increase[s] the number of API calls" (`extraction.py:95-96`). At Annotator default 200-char buffer, an 80k-char paper → ~400 calls/pass (`06-performance-scalability.md:7-8`, `annotation.py:609-611` debug estimate `len(text)//max_char_buffer+...` — approximate only; true count is sentence-aware, `chunking.py:343-506`). Impact: integrators hitting Annotator directly pay **~67× our call budget** vs **~13–25×** via `extract()`. Quality risk: conflating the two defaults when benchmarking external repos.

- [MED] **Chunk payload scope vs our full-document re-prefill.** Each LLM call sends one chunk's `chunk_text` plus optional `context_window_chars` trailing prior-chunk **source** tail (`annotation.py:304-305`, `360-375`; `prompting.py:179-276`) — not prior model extractions. Contrast: tapetum unit checks send **full candidate markdown** every call (`00-baseline.md:43-47`). Impact: langextract trades **call count** for **scoped prefill**; a 80k paper at 1000-char chunks ≈ 80 calls × ~1k chars vs our 6 × ~80k chars ≈ **480k char-prefill-equivalent**. Prefix-cache leverage favors langextract's repeated small prompts with shared system/few-shot prefix; our random guard tag at system-prompt end breaks APC (`00-baseline.md:48-52`). Quality risk: low for payload scoping if page-local defects still reachable; cross-page defects need `context_window_chars` or larger buffers.

- [LOW] **Gemini Batch API is a separate call-economics path.** Batch mode triggers when `len(batch_prompts) >= batch.threshold` (default 50, `gemini.py:424-425`; sub-threshold falls back to realtime, `gemini.py:466-472`). Impact: batch reduces **cost/latency** for large chunk counts, not call semantics; 80-chunk doc stays realtime. Quality risk: batch job all-or-nothing failure (`06-performance-scalability.md:25-26`).

## False-pass hypothesis

Adopting langextract-style defaults literally — `extraction_passes=1` nightly without a weekly full cascade — drops the unit-check and page-escalation stages that changed 16/381 merged verdicts (`00-baseline.md:29-30`), mirroring marker's `use_llm=False` false-pass class (`66-marker-quality-speed-flags.md:24-26`): table-cell transpositions or single-page wording swaps that monolith/metadata miss ship undetected until a manual re-run.

## False-fail hypothesis

Raising tapetum `max_char_buffer` toward langextract's chunk-scoped pattern by **batching multiple unit checks into one prompt** (analogous to `batch_length>1` grouping) would reproduce RuVerBench double-digit rubric-accuracy drops on long-context tasks (`05-web.md` Q5) — advisory false alarms on good conversions, not a gate false-fail, but still a quality-stability violation.

## What would change my mind

A measured tapetum ablation mirroring langextract's tiering: nightly `extraction_passes=1` analog (monolith+metadata only) vs weekly `extraction_passes=3` analog (full 6-call cascade) on the 381-paper fleet, reporting (a) wall time, (b) verdict-delta count vs full cascade, (c) defects found only in the "pass 2–3" tier — if (c) ≤ 2% of papers at ≥ review severity, the inversion is free; if ≥ 10%, keep full cascade default.
