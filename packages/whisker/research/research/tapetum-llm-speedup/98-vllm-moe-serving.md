# 98 - vllm-MoE-Serving

**Verdict:** usable-with-conditions — vLLM's MoE+EP stack explains why `--max-num-seqs 16` is the hard decode ceiling on alliance-pod; raising slots or relying on server knobs alone cannot reach the 5–10 min target without call-volume cuts or a second pod.
**Confidence:** high

## Findings

- [CRITICAL] **MoE decode cost is driven by the union of distinct experts activated in one forward pass, not by dense-style batch amortization.** Each token routes to `config.num_experts_per_tok` experts (`vllm/models/deepseek_v4/nvidia/model.py:538,711`); on EP8 each GPU holds `n_local_physical_experts = n_physical_experts // ep_size` local shards (`model.py:621-625`). The modular-kernel dispatch buffer scales with concurrent tokens: `max_num_tokens = num_dispatchers() * max_num_tokens_per_rank()` (`docs/design/fused_moe_modular_kernel.md:158-160`). More simultaneous decode tokens widen the per-step expert union, increasing HBM weight traffic per output token. Impact: the measured 692.3 s → 1090.2 s (+57%) when `--max-num-seqs` rose 16→32 (`research/slots-32-regression/SYNTHESIS.md:7-13`) is the expected MoE superlinear penalty, not a scheduler bug. Quality risk: none from keeping 16 slots; raising slots slows every call uniformly.

- [CRITICAL] **The pod's effective concurrency ceiling is ~16 simultaneous decodes; client c=32 only back-fills the queue.** Isolation test: server cap 32 with client c=16 still took 763.7 s vs 692.3 s at server cap 16 (`SYNTHESIS.md:14-15,23-25`). vLLM admits at most `max_num_seqs` running sequences (`vllm/v1/utils.py:727`); with 16 slots and 32 client papers, ~16 decode while 16 wait at zero GPU cost. At 32 slots all 32 compete every MoE step for the same `max_num_batched_tokens` budget (`vllm/v1/utils.py:728`, `docs/configuration/optimization.md:41-42`). Impact: no single-server flag safely raises effective slots above 16 on this H200×8 EP8 MoE stack; dual-pod sharding (`SERVICES.toml:47-74`, two live `deepseek-v4-pro` instances) is the only hardware-free parallelism multiplier. Quality risk: dual-pod adds routing/fingerprint complexity, not model variance.

- [HIGH] **Why 16→32 regressed +57%: mechanism is expert-activation spread + fixed token budget, not KV preemption.** KV preemption was ruled out (`num_preemptions_total 0`, `SYNTHESIS.md:28-31`). Primary mechanism: 32 decode tokens/step vs 16 (`docs/configuration/optimization.md:53-58` — V1 batches all pending decodes before prefills) loads ~2× the local expert union per MoE layer × ~58 layers. Secondary: `max_num_batched_tokens` stayed at 8192 while slots doubled (`docs/configuration/optimization.md:62-67`), so 32 sequences share the same per-step token pool, increasing prefill-decode mixing (`research/slots-32-regression/13-prefill-interference.md:83-89`). Impact: co-raising `--max-num-batched-tokens` to 16384–32768 might shave prefill interference but cannot cancel expert-union HBM growth; measured ratio 1.57× matches MoE decode superlinearity, not a pure 2× stall model. Quality risk: low for reverting to 16; retuning 32 without A/B is high risk of unchanged or worse wall time.

- [HIGH] **Expert parallelism forces per-layer all2all dispatch/combine whose volume scales with concurrent tokens.** EP size is `TP × DP` (`docs/serving/expert_parallel_deployment.md:34-38`); MoE layers shard across all EP ranks (`expert_parallel_deployment.md:50-52`). Backend selection (`--all2all-backend`: default `allgather_reducescatter`, decode-tuned `deepep_low_latency` with batched activation format — `docs/design/moe_kernel_features.md:19,37`, `expert_parallel_deployment.md:17-25`) controls dispatch layout; `deepep_high_throughput` / `deepep_low_latency` are tuned for disaggregated P/D and "may show poor performance for mixed workloads" (`expert_parallel_deployment.md:209-210`). DeepSeek V4 MegaMoE hard-requires EP (`vllm/models/deepseek_v4/nvidia/model.py:527-531`). Impact: doubling in-flight decodes doubles all2all traffic alongside expert-weight reads; `--enable-dbo` overlaps comm with compute (`expert_parallel_deployment.md:210`, `docs/design/dbo.md:32-40`) but does not remove union growth. Quality risk: backend swaps can change numerics at margin; test before production.

- [HIGH] **DeepSeek-V4-Pro serving path in this clone: MLA attention + MegaMoE/DeepGEMM + optional EPLB.** MLA: `DeepseekV4Attention` with platform sparse-MLA backends (`vllm/models/deepseek_v4/attention.py:102-111`); FP8 decode uses `deep_gemm_fp8_o_proj` (`vllm/models/deepseek_v4/nvidia/flashinfer_sparse.py:175-189`). MoE: `deep_gemm.fp8_fp4_mega_moe` after `prepare_megamoe_inputs` quantizes activations and repacks routing for DeepGEMM (`model.py:481-505`, `vllm/models/deepseek_v4/nvidia/ops/prepare_megamoe.py:1-7`). EPLB hooks map logical→physical experts and record per-forward load (`model.py:460-479,386-398`; interface contract `vllm/model_executor/models/interfaces.py:894-925`). Impact: decode is memory-bandwidth-bound on MLA KV + MoE expert reads; kernel path is already the optimized DeepGEMM MegaMoE stack — little headroom from backend swaps alone. Quality risk: `compressor.py:368` documents non-deterministic output if PDL races are enabled; unrelated to slot count but relevant to quality-stability.

- [MED] **`--enable-eplb` balances skewed expert load across EP ranks, not batch-width growth.** EPLB collects load every forward and periodically rebalances (`docs/serving/expert_parallel_deployment.md:136-142,148-156`); redundant experts cost ~2.4 GB/expert on DeepSeekV3 (`expert_parallel_deployment.md:186-187`) and compete with KV at `--gpu-memory-utilization 0.95` + 393k context. DSv4 wires `enable_eplb` and `num_redundant_experts` into both FusedMoE and MegaMoE init (`model.py:689-690,615-616`). Impact: EPLB can reduce straggler EP ranks when routing is skewed (mixed prompt types in our fleet), but it does **not** shrink the per-step expert union at fixed concurrency — unlikely to justify 32 slots or save >5–10% wall on a balanced judge workload. Quality risk: periodic expert remapping introduces transient numeric drift during rebalance windows; use `--eplb-config '{"use_async":true}'` default (`expert_parallel_deployment.md:154`) to limit latency spikes.

- [MED] **Batch-composition determinism: MoE outputs vary with concurrent batch mix; `VLLM_BATCH_INVARIANT=1` is the server-side variance reducer.** vLLM documents batch invariance as "deterministic results regardless of batch composition" (`vllm/envs.py:601-603`, `docs/features/batch_invariance.md:7-8`); tested on DeepSeek-V3/R1 (`batch_invariance.md:103-104`) but "may impact performance" (`batch_invariance.md:122-123`). Default MoE paths use batched all2all layouts (`moe_kernel_features.md:37`) where token order and padding change grouped GEMM shapes. Our guard-tag suffix breaks prefix identity (`00-baseline.md:50-52`), so APC gains are partial; batch mix still shifts MoE grouping. Impact: parallel in-paper unit checks (client-side lever) carry verdict-flip risk; server-side `VLLM_BATCH_INVARIANT=1` + pinned concurrency (16 server / ≤32 client queue) reduces drift at ~5–15% throughput cost (doc warning). Quality risk: **lowering variance without batch invariance** → false-pass on verdict stability; **enabling batch invariance without pinning concurrency** → slower but more stable.

- [LOW] **Server-side throughput levers that do NOT raise slot count but can cut the 3003 s wall (orthogonal to concurrency ceiling).** (a) Prefix-cache retention fix for DSv4 sliding-window APC (`05-web.md:5-12`, PR #43447) — same 16 slots, higher effective tok/s on repeated ~3.7k system prefix. (b) MTP speculative decoding (`05-web.md:16-17`, `expert_parallel_deployment.md` disagg section) — more output tok/s per slot. (c) `--max-num-seqs 16` + client c=32 remains optimal (`SYNTHESIS.md:50-53`). Impact: these can contribute to the 5–10 min target via per-call latency and call elimination (other personas), not by breaking the 16-slot MoE decode ceiling. Quality risk: MTP acceptance rate must stay high on short judge outputs (1536 cap, `00-baseline.md:27-28`).

## False-pass hypothesis

Raising `--max-num-seqs` to 32 (or enabling in-paper parallel unit checks) changes MoE batch composition and expert-grouping numerics; a defect that passes at concurrency-16 mix may fail at concurrency-32 mix (or vice versa) without any change to the candidate markdown — silent verdict drift, the known quality-stability failure mode (`00-baseline.md:77-78`, `batch_invariance.md:7-8`).

## False-fail hypothesis

Enabling `VLLM_BATCH_INVARIANT=1` with fixed server cap 16 could stabilize borderline unit-check calls that previously flipped on batch mix, causing a paper to pass where an earlier fleet run flagged review — same markdown, stricter reproducibility, potentially fewer false fails at the cost of slower decode (`batch_invariance.md:122-123`).

## What would change my mind

An A/B on the 381-paper corpus showing `--max-num-seqs 32` with full MoE co-tune (`--max-num-batched-tokens 32768`, `--all2all-backend deepep_low_latency`, optional `--enable-dbo`) beats the proven **692.3 s** baseline (`SYNTHESIS.md:50-53`) by ≥10% **and** verdict fingerprints match the 16-slot run — or vLLM ships MoE-aware batch scheduling that caps expert union per step (tracking issue class for `batch_invariance.md:127-132` / expert-affinity batching mentioned in `SYNTHESIS.md:57-58`).
