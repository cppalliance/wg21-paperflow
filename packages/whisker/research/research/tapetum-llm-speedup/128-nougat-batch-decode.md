# 128 - nougat-Batch-Decode

**Verdict:** usable-with-conditions — Nougat's decode-time repetition abort is the portable idea (early-exit on degenerate generation), but our 55-retry budget is only ~100 s (~3%) of the 3003 s cold run and GPU page batching does not map to serial HTTP judge calls per paper.
**Confidence:** high

## Findings

- [CRITICAL] **Page batching is a PyTorch DataLoader tensor batch, not cross-request HTTP parallelism.** Default batch size is a VRAM heuristic: `total_memory_MB / 1000 * 0.3`, falling back to 1 on CPU (`nougat/utils/device.py:11-25`). CLI `--batchsize` / env `NOUGAT_BATCHSIZE` override (`predict.py:31-35`, `app.py:28`); `batchsize <= 0` forces 1 (`predict.py:129-131`, `app.py:57-58`). Pages are rasterized, collated via `LazyDataset.ignore_none_collate` (`nougat/utils/dataset.py:102-119`), and fed to `DataLoader(..., batch_size=args.batchsize, shuffle=False)` (`predict.py:156-161`). Each batch invokes one `model.inference(image_tensors=sample)` (`predict.py:167-169`), which runs a single batched `decoder.model.generate(...)` over the encoder outputs (`nougat/model.py:591-609`). Impact: amortizes GPU kernel launch across N pages; on tapetum, unit checks are already one HTTP request each with no shared decoder state, so this pattern does not cut our ~2284-call census. Quality risk: none (orthogonal architecture).

- [CRITICAL] **Decode-time repetition abort via `StoppingCriteriaScores` (the famous failure mode guard).** When `early_stopping=True` (default; disabled by `--no-skipping`, `predict.py:74-77,168`), generation attaches `StoppingCriteriaList([StoppingCriteriaScores()])` (`nougat/model.py:606-608`). The criterion tracks per-step max logit variance (`RunningVarTorch`, L=15) and variance-of-variance over a 200-token window; when `varvar < 0.015` it schedules a stop index per batch element and sets `stopped[b]` once the index is reached (`nougat/model.py:442-474`). This aborts autoregressive decode before `max_length` on repetition collapse. Impact: saves wasted decode seconds on stuck pages (Nougat's core speed+quality trade for VLM OCR). Portable analogue for tapetum: streaming early-abort when output is degenerate. We have `stream = true` on alliance pods (`SERVICES.toml:57,74`) but `VllmThinkingBackend` accumulates the full stream before parse (`model_backends.py:306-328`) with no mid-decode cancel. Quality risk: threshold miscalibration false-truncates valid repetitive WG21 boilerplate (Nougat README documents CPU false positives).

- [HIGH] **Second-pass repetition detection on stacked logits after generate (not just stopping criteria).** `inference()` stacks `decoder_output.scores`, takes vocab-max logit per step, computes 15-token sliding variance then 10-window var-of-var; consecutive low-var windows (`varvar < 0.045`, diff < 2) set truncation index `idx` with `minlen=120`, pads tail tokens (`nougat/model.py:614-647`). EOS-before-end clears the flag (`629-633`); `idx/N > 0.9` clears (`639-641`); `small_var[0] < 30` marks out-of-domain not repetition (`642-643`). CLI maps `repeats[j] > 0` → `[MISSING_PAGE_FAIL:n]` page sentinel, no retry loop (`predict.py:181-185`). Impact: confirms abort is decode-time + post-decode, never a regeneration retry (contrast olmOCR 12% retry, `05-web.md:41`). For tapetum: requires per-token logprobs/scores from vLLM; not exposed on judge path today. Quality risk: same false-truncate class as stopping criteria.

- [HIGH] **Multi-page processing within one PDF is serial through the DataLoader, not worker-parallel.** The main loop is `for i, (sample, is_last_page) in enumerate(tqdm(dataloader))` (`predict.py:166-207`): batches are processed sequentially on one GPU. Multiple PDFs use `ConcatDataset(datasets)` in one loader but still one batch at a time (`predict.py:133-161`). Parallelism appears only in offline dataset tooling (`create_index.py:117` ProcessPool) and optional postprocess pool via `NOUGAT_MULTIPROCESSING` (`postprocessing.py:503-507`), not in inference. Impact: nougat's wall-clock win from batching is GPU utilization within a batch, not asyncio page fan-out like olmOCR's `--workers 20` / 1600 concurrent requests (`05-web.md:41-42`). Our in-paper serial chain (`00-baseline.md:36-38`) is closer to nougat's inference loop than to olmOCR's page concurrency; nougat does not justify cross-paper HTTP parallelism we already have at 32. Quality risk: N/A.

- [MED] **Our BPE-corruption retry class burns full decodes despite streaming enabled.** Measured: 55 retries ≈ 100 s fleet wall (~3.4% of 3003 s, `00-baseline.md:18,60-61`). Backend: `max_attempts = min(2, request_limit)` serial loop (`model_backends.py:300-302`); on `"Raw JSON parse failed"` it appends the failed assistant turn plus nudge and re-issues a complete HTTP completion (`model_backends.py:394-405`), paying ~20 s mean decode again (`00-baseline.md:24-25`). BPE cleanup runs only after the stream completes (`_clean_bpe` at `model_backends.py:95-106`, applied post-accumulation at `352-362`). Judge output cap is 1536 tokens (`cli.py:1034`). So yes: retries that fail parse/validation on attempt 1 typically consumed the full streamed completion (up to cap) before retry. Impact: each of ~55 retries ≈ one wasted full decode on slot 1/16, not overlapped; total bounded at ~100 s, not minutes (`25-retry-economist.md:8-10`). Quality risk: none if retry output matches attempt-2 success.

- [MED] **Streaming JSON-prefix abort could shave per-retry latency but cannot reach the 5–10 min target alone.** With `stream=true`, we could cancel when (a) no `{` appears after N tokens, (b) `\u0120`/`\u010a` BPE markers appear in the buffer, or (c) tail matches `truncate_repetitions` logic (`postprocessing.py:102-165`) before max tokens. Nougat's stopping criteria show decode-time abort saves seconds-to-minutes per stuck autoregressive page; our retries are mostly short JSON malformation where attempt 2 succeeds (`cli.py:218-221`), not 1536-token repetition loops. Even zeroing all 55 retries saves ≤100 s (~3.3%). Incremental `json.loads` on partial buffers risks false abort on thinking blocks or schema preamble. Quality risk: LOW if abort triggers retry only (same 2-attempt budget); MED if abort misclassifies slow-valid JSON as garbage.

- [LOW] **Batch size auto-tuning is hardware-local, not fleet-scheduler logic.** `default_batch_size()` scales with GPU VRAM (`device.py:13-15`); MPS hardcodes 4 (`18-20`). No dynamic batching across documents or queue-depth feedback (contrast olmOCR queue-aware parallel retries, `05-web.md:72`). Impact: irrelevant to tapetum's vLLM `--max-num-seqs 16` slot cap (`00-baseline.md:66-67`). Quality risk: none.

## False-pass hypothesis

Adding streaming abort that treats any repetitive substring in judge `reasoning` as degenerate (nougat-style varvar without source grounding) could cancel a valid unit-check call mid-decode and retry into a shorter, schema-valid response that omits a real table-cell swap — advisory pass with fewer defect groups, the token-preserving corruption class tapetum exists to catch (`00-baseline.md:29-30`).

## False-fail hypothesis

Streaming abort on malformed JSON prefix fires during a long `<think>` block before the JSON object opens (`model_backends.py:352-362`), cancels attempt 1 at ~5 s, attempt 2 still fails BPE cleanup, and the unit check hits `coverage_complete=False` → verdict capped at `review` for a clean conversion — same false-fail shape as timeout under slot starvation, but triggered by an over-eager abort heuristic.

## What would change my mind

Per-call debug tagging of all 55 retries (`cli.py:223-226`) showing ≥70% attempt-1 streams exceed 800 tokens before first parse failure OR show tail repetition detectable within the first 200 streamed tokens — would justify implementing streaming cancel in `VllmThinkingBackend` as a primary lever worth ≥300 s on the cold run; otherwise it stays a ≤100 s rounding-error optimization.
