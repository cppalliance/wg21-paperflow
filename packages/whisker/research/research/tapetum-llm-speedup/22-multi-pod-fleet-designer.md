# 22 - Multi-Pod-Fleet-Designer

**Verdict:** usable-with-conditions — port only health-gated multi-pod assignment and per-pod concurrency caps into `cli.py` (persona 21's deterministic shard); a full LiteLLM-style latency router adds nondeterminism and mid-chain failover risk without meaningful extra wall savings on a nightly homogeneous batch.
**Confidence:** high

## Findings

- [CRITICAL] **LiteLLM's router optimizes per-request deployment pick; tapetum-llm's bottleneck is per-paper slot saturation, not client pick latency.** LiteLLM `get_available_deployment` selects among healthy deployments per call via `simple-shuffle` / `least-busy` / `latency-based-routing` (`litellm/router.py:11046-11159`, `litellm/types/router.py:84-89`). Our fleet wall is bounded by ~2284 serial-ish calls at ~20 s each divided by 16 server slots per pod (`00-baseline.md:22-25`). Persona 21's `index % len(live_pods)` on the sorted PID list already yields ~50/50 paper split and **~3003 s → ~1600 s** (`21-dual-pod-sharder.md:8`). Dynamic latency routing might rebalance a few long-chain papers but cannot beat parity sharding by more than a few percent on 381 independent papers. Impact: **~0-120 s** marginal vs persona 21; **quality risk: MED** (routing state becomes runtime-dependent). Not a path to 5-10 min alone.

- [CRITICAL] **Mid-call cross-pod retry (LiteLLM default) conflicts with tapetum fail-closed serial chains.** LiteLLM `async_function_with_retries` re-invokes `make_call` after failure, and each retry can land on a different deployment via `_async_get_healthy_deployments` + routing strategy (`litellm/router.py:6486-6570`). Our PDF lane runs monolith → metadata → serial page escalations → serial unit checks (`00-baseline.md:36-38`, `pdf_judge.py:586`). Fidelity policy: any failure → `PdfLaneError`, no partial sidecar (`pdf_judge.py:586`). CLI writes `status="error"` tombstones, never pass (`cli.py:747-771`, `cli.py:1373-1387`). Switching pods mid-chain breaks prefix-cache locality (`05-web.md:69-77`) and adds a second MoE batch-composition axis beyond the documented ≥25% advisory flip rate (`21-dual-pod-sharder.md:16`). Minimal in-house rule: **pin all calls for one paper to one pod**; if the pod fails after backend retries, fail the paper (tombstone) or **restart the whole paper** on an alternate pod — never reroute call 4 of 6 to a different endpoint. Impact: avoids silent partial coverage; **0 s** speedup from safe failover vs tombstone + warm retry.

- [HIGH] **What is worth porting from LiteLLM: pre-batch health filter + cooldown exclusion, not the 11k-line Router.** LiteLLM filters deployments through health-check state, then cooldown list, then strategy (`litellm/router.py:11091-11104`; cooldown triggers on 429/401/408/404 and failure-rate thresholds, `litellm/router_utils/cooldown_handlers.py:40-89`, `151-168`). We already have a single-endpoint probe on the effective `fast` slot only (`cli.py:910-951`). Persona 21 extends this to every shard pod and falls back to `live_pods` subset (`21-dual-pod-sharder.md:12-13`; prior `h200x8` 404 while `alliance-pod` 200). A ~40-line whisker-local equivalent: probe each `--shard-pods` name, drop dead endpoints, abort if zero live — no `litellm` import, no proxy. Impact: prevents ~50% false `error` tombstones when one proxy is half-dead; **quality risk: none**.

- [HIGH] **Per-deployment concurrency cap is the one routing primitive LiteLLM has that persona 21 omits.** LiteLLM `least-busy` tracks in-flight requests per deployment id in a cache and picks the lowest (`litellm/router_strategy/least_busy.py:24-46`, `110-130`). Our client uses one global `asyncio.Semaphore(concurrency)` at `_DEFAULT_CONCURRENCY = 32` (`cli.py:127`, `cli.py:1112`) against pods with `--max-num-seqs 16` each (`00-baseline.md:66`). With two live pods, 32 in-flight papers can still pile 20+ onto one pod if completion order skews. Minimal fix: **per-pod semaphores capped at 16** (or `--max-num-seqs`), plus deterministic paper→pod map — composes with persona 21, stays in `cli.py`, satisfies model-sovereignty (direct `AgentBackend` to `SERVICES.toml` endpoints, `services.py:97-102`). Impact: **~100-300 s** extra savings vs naive global-32 split under skew; **quality risk: LOW** (same models, fixed assignment).

- [HIGH] **Heterogeneous endpoints belong in a cascade lever, not a fleet router.** LiteLLM `fallbacks` / `context_window_fallbacks` switch **model groups** after retry exhaustion (`litellm/types/router.py:79-81`, `litellm/router.py:6356-6391`). Our inventory lists different weights on `b200-r1`, `b300-qwen36-27b`, etc. (`SERVICES.toml:76-138`, `00-baseline.md:69-71`). `resolve_pipeline_models` binds slot → service → `model` string (`adjudicate.py:753-768`); `_effective_model_contract` fingerprints `model` + `base_url` per selected service (`cli.py:526-563`, `87-97`). Routing unit checks to Qwen3-32B via a latency router would change verdicts and invalidate all sidecars — the cascade lever in `00-baseline.md:100-101`, not fleet sharding. Impact: **N/A for 3003 s target** unless explicitly accepting verdict drift; **quality risk: HIGH** if smuggled in as "speedup."

- [MED] **LiteLLM `simple-shuffle` uses `random.choice` / `random.choices`; that violates our quality-stability goal for incremental reruns.** Evidence: `litellm/router_strategy/simple_shuffle.py:59-68`. Persona 21's stable `index % N` keeps per-paper pod fixed across reruns so warm fingerprint skip stays valid (`21-dual-pod-sharder.md:10-14`, `00-baseline.md:19-20`). Random per-call routing would change MoE neighbor batches on every rerun even with unchanged markdown — strictly worse than today's single-pod variance. Impact: **negative** for determinism; **MED-HIGH** triage noise.

- [MED] **Fingerprint contract already supports multi-pod mode if the shard SET is encoded, not the runtime pick.** `_compute_fingerprint` stores `model` as JSON from `_effective_model_contract`, which iterates `sorted(set(slots.values()))` (`cli.py:543-554`, `566-619`). Extending to `sorted(set(slots.values()) | set(shard_pods))` (persona 21) preserves warm skip after a cold dual-pod run without baking latency-router state. LiteLLM has no equivalent artifact — it is a stateful proxy. Impact: warm rerun stays **~65 s** (`00-baseline.md:19-20`); **quality risk: none** for skip semantics.

- [LOW] **LiteLLM retry budgets (`num_retries`, per-exception `RetryPolicy`) duplicate what `AgentBackend.run` already provides.** Router defaults `num_retries` from config or OpenAI default (`litellm/router.py:559-564`, `6461-6520`); our lane documents backend retry on BPE/truncation/transient errors (`judge_task.py:27-29`, `00-baseline.md:60-61`, 55 retries ≈ 100 s). Adding a second retry layer at routing would inflate tail latency without addressing the 2284-call census. Impact: **≤4%** wall (`00-baseline.md:60-61`); **quality risk: LOW** if redundant, **MED** if cross-pod.

## False-pass hypothesis

**Latency-router "load balancing" hides a sick pod.** LiteLLM can bypass cooldown when all deployments are cooling (`litellm/router.py:11105-11109`). If we copied that escape hatch, a degraded pod still serves ~half of papers under `simple-shuffle`, returning fast low-confidence passes on zero-defect unit checks (`00-baseline.md:29-30`) while the healthy pod would have flagged defects — fleet wall drops, advisory recall drops, fusion stays green.

## False-fail hypothesis

**Mid-chain cross-pod retry after a 429 cooldown** (`litellm/router_utils/cooldown_handlers.py:69-71`): monolith succeeds on pod A, unit check 3 fails transiently and retries on pod B with cold prefix cache. The recomposed verdict differs from a single-pod run; operator interprets as conversion regression, re-runs `--force`, and burns another **~120 s × N papers** chasing MoE noise (`21-dual-pod-sharder.md:16`).

## What would change my mind

A 381-paper A/B with (A) persona 21 deterministic shard and (B) a whisker-local least-busy router (per-pod in-flight counters, no cross-pod mid-chain retry) showing wall **≥5% below** persona 21 **and** borderline verdict-flip rate **≤1.1×** single-pod baseline (`21-dual-pod-sharder.md:31-32`) would upgrade the dynamic piece to **usable**. Without that measurement, ship persona 21 + per-pod semaphores only.
