# 67 - marker-Concurrency-Config

**Verdict:** usable-with-conditions — Marker's corpus-scale batch architecture and B200 throughput claims are well-instrumented for PDF **extraction**, but published numbers exclude `--use_llm`, use B200 not H100/A100, and measure a different workload than tapetum's 2284-call verification fleet; useful for grounding "others are faster" only after separating convert-from-PDF from judge-markdown.
**Confidence:** high

## Findings

- [CRITICAL] Batch conversion entrypoint is `marker` → `convert.py:1-4` → `marker/scripts/convert.py:convert_cli`. It lists a folder, optionally shards with `--num_chunks` / `--chunk_idx` (`marker/scripts/convert.py:115-127,159-164`), caps with `--max_files`, resumes with `--skip_existing`, and runs `torch.multiprocessing.Pool` with `spawn` + `imap_unordered` over `(pdf, kwargs)` tasks (`marker/scripts/convert.py:174-237`). Each worker converts one whole PDF serially (`process_single_pdf`, `marker/scripts/convert.py:62-110`). There is no separate `marker chunk convert` CLI; "chunk" means either output format `chunks` (`marker/config/parser.py:152-153`) or multi-node file-list sharding (`README.md:169`, `marker/scripts/convert.py:159-164`). Impact: our 381-paper fleet is file-parallel like marker's pool, not page-parallel inside a PDF; marker's published pg/s assumes many single-page bench PDFs in flight (`benchmarks/inference.py:107-108`). Quality risk: n/a (architecture comparison only).

- [CRITICAL] Parent process owns **one shared surya VLM inference server**; worker processes are thin CPU clients. Parent spawns `SuryaInferenceManager` and sets `SURYA_INFERENCE_URL` (`marker/scripts/convert.py:189-196`, `marker/models.py:23-36`). GPU VRAM stays on the server; when `total_processes > 1` and CUDA is available, worker-local models are forced to CPU (`marker/scripts/convert.py:214-218`). Multi-GPU: `VLLM_GPUS=0,1,2,3 marker /folder ...` (`README.md:108-109,169`). Aggregate VLM client concurrency is budgeted to ~**1.5× server capacity** split across workers unless the user sets `SURYA_INFERENCE_PARALLEL` (`marker/scripts/convert.py:201-212`). Impact: marker saturates one GPU server with many CPU workers; tapetum saturates one LLM pod with 32 asyncio papers × serial 6-call chains (`00-baseline.md:34-42`). Different bottlenecks. Quality risk: n/a.

- [HIGH] Default worker count is auto-derived, not fixed. `get_worker_count()` sizes the pool to `min(physical_cores - 2, ceil(SURYA_INFERENCE_PARALLEL × 1.5))` when server parallel is known, else `physical_cores - 2` (`marker/utils/batch.py:8-29`). README says `--workers` can be raised for throughput at higher CPU cost (`README.md:160-161`). Benchmark harness uses **48 workers (balanced)** and **32 workers (fast)** against a pre-started surya server (`benchmarks/README.md:62-71`). Impact: headline throughput requires tuned worker count + server; naive single-worker would match README's ~0.3 pg/s single-stream note (`README.md:479`). Quality risk: n/a.

- [HIGH] Published sustained throughput on **one B200** (not H100/A100 in repo): balanced **2.9 pg/s** (341 ms/page effective), fast **7.4 pg/s** (134 ms), fast `--disable_ocr` **23.7 pg/s** (42 ms) over olmocr-bench's 1,403 pages (`README.md:465-475,522-528`). Reproduced by `benchmarks/inference.py` printing `throughput {N} pages/s` at chosen `--workers` (`benchmarks/inference.py:257-263`, `benchmarks/README.md:78-80`). Competitive table: docling **2.1 pg/s**, MinerU pipeline **0.54 pg/s** on same host (`README.md:470-472`). Impact: at **~5000 pages** (381 WG21 papers), **without `--use_llm`**: balanced ≈ **5000/2.9 ≈ 1724 s (~29 min)**, fast ≈ **5000/7.4 ≈ 676 s (~11 min)**, fast no-OCR ≈ **5000/23.7 ≈ 211 s (~3.5 min)** — all on B200-class hardware at benchmark concurrency. Tapetum cold verification is **3003 s (~50 min)** on already-converted markdown (`00-baseline.md:17-18`). Marker extraction without LLM is **faster wall-clock than tapetum verification**, but it is **not doing the same job**. Quality risk: comparing marker convert time to tapetum judge time implies false equivalence.

- [HIGH] **`--use_llm` has no published throughput or slowdown factor.** README throughput table and bar charts include only balanced/fast/fast-no-OCR (`README.md:465-475,522-528`). `--use_llm` is documented as hybrid accuracy mode (Gemini default, external APIs) (`README.md:53,136,384-392`). Benchmark harness labels `--use-llm` as "accurate mode" and prints throughput at runtime, but ships **no pre-measured pg/s** (`benchmarks/README.md:73-75`, `benchmarks/inference.py:191-194,257-263`). LLM processors default `max_concurrency=3` and fan out block/page work via `ThreadPoolExecutor` (`marker/processors/llm/__init__.py:42-45,163-172`; same pattern `llm_meta.py:44`, `llm_page_correction.py:283`). Ten LLM processor classes sit in the default pipeline but gate on `use_llm` and block type (`marker/converters/pdf.py:97-106,156-157`). Impact: **WITH `--use_llm`**, wall time is **≥ baseline conversion time** plus **O(matching_blocks) external LLM calls** at ≤3 concurrent per processor stage; for ~5000 pages on born-digital WG21 papers (tables, headers, few forms) expect **multiples of the no-LLM estimate**, bounded below only by "no matching blocks." Cannot derive a defensible minutes number from repo sources alone. Quality risk: LOW for honesty; HIGH if we assume marker+LLM ≈ marker balanced pg/s.

- [MED] Distributed corpus runs shard the **file list**, not pages inside a PDF. `--num_chunks N --chunk_idx i` splits `ceil(len(files)/N)` paths per node; each node spawns its own inference server (`README.md:169`, `marker/scripts/convert.py:159-164,189-196`). Commercial README claims managed batch at **1B+ pages/week** with infra they operate (`README.md:37-38`) — no file:line duty cycle. Impact: dual-pod sharding (`00-baseline.md:67-68`) mirrors marker multi-node pattern; linear speedup requires independent servers per shard. Quality risk: n/a.

- [MED] `--disable_multiprocessing` and worker recycling: batch path forces `disable_multiprocessing=True` and `pdftext_workers=1` per worker to avoid nested ProcessPool deadlocks (`marker/scripts/convert.py:78-83,170-171`); pool uses `maxtasksperchild=200` (`marker/scripts/convert.py:141-144,234`). `--disable_ocr` skips server entirely and sizes pool by CPU cores only (`marker/scripts/convert.py:182-187`, `marker/utils/batch.py:16-17`). Impact: CPU-only text-layer path (23.7 pg/s) is irrelevant to tapetum (markdown already exists) but shows marker's fastest lane avoids all VLM/LLM. Quality risk: n/a.

- [LOW] FastAPI `marker_server` deliberately **does not expose** `--use_llm` or `--disable_ocr` (`README.md:436-437`). Corpus `--use_llm` runs require CLI/Python API. Impact: no hidden fast path via HTTP server for hybrid mode. Quality risk: n/a.

## False-pass hypothesis

Equating marker balanced **2.9 pg/s (~29 min / 5000 pages)** to tapetum's **50 min / 381 papers** and concluding "we are slower at the same task": tapetum re-sends full candidate markdown up to ~6× per paper for defect adjudication (`00-baseline.md:43-45,22-23`); marker without `--use_llm` only extracts PDF→markdown and would still need a separate verification pass to match tapetum finding quality.

## False-fail hypothesis

Adopting marker's **1.5× server-capacity worker budget** (`marker/scripts/convert.py:201-208`) for tapetum's DeepSeek MoE judge pod without equivalence testing: oversubscribing `max-num-seqs` already regressed wall +60% at 32 slots (`00-baseline.md:82`) and could flip unit verdicts while appearing "faster."

## What would change my mind

A published `benchmarks/inference.py --use-llm` run on olmocr-bench (or WG21 sample) printing sustained pg/s on B200/H200 with `--workers` documented, showing `--use_llm` slowdown factor vs balanced baseline — would allow a numeric WITH-LLM estimate for the 5000-page corpus.
