# 76 - olmocr-Dense-Model-Choice

**Verdict:** usable-with-conditions — olmocr proves task-specialized dense 7B + FP8 beats its GPT-4o teacher on a narrow OCR task at ~17× lower $/M pages; the same strategy is the correct long-term lever for tapetum unit checks (CLAUDE.md "future fine-tunes"), but it is a 6–12 week program, not a near-term path to the 5–10 min cold fleet target (expect ~850–1200 s savings once deployed, per persona 23's proportional model).
**Confidence:** medium

## Findings

- [CRITICAL] **olmocr's economics rest on a fine-tuned dense 7B beating its GPT-4o teacher, not on raw Qwen scale.** v1 distills GPT-4o labels on 260k pages (`olmOCR-mix-0225`); fine-tuned `olmOCR-7B-0225-preview` on olmOCR-Bench **significantly outperforms GPT-4o (anchored 69.9±1.1) and the unfine-tuned Qwen 2.5 VL 7B base** ([arxiv:2502.18443](https://arxiv.org/abs/2502.18443) §3, Table 4). v2 ships `olmOCR-2-7B-1025` at **82.4±1.1** vs GPT-4o **68.9±1.1** and base Qwen 2.5 VL 7B **65.5±1.2** ([arxiv:2510.19817](https://arxiv.org/abs/2510.19817) benchmark table). Base model lineage: `Qwen/Qwen2.5-VL-7B-Instruct` in every shipped SFT config (`research/repos/olmocr/olmocr/train/configs/v0.4.0/qwen25_vl_olmocrv4_rotation_1epoch_mix_1025.yaml:8-9`; `prepare_checkpoint.py:62-64`). Impact: validates "narrow task + teacher distillation + specialization > general frontier model" for our unit-check lane; quality risk if we swap models without re-distillation (persona 47 full protocol).

- [CRITICAL] **Throughput: 3050 output tok/s on H100, 1288 pages in 5m07s, $176–178/M pages — concurrency + dense FP8, not a bigger model.** Measured on 1288 benchmark pages: H100 **3050 output tok/s**, runtime **5m07s**, cost **$178/M pages**; L40S 906 tok/s at $176/M ([arxiv:2502.18443](https://arxiv.org/abs/2502.18443) Table 6, Appendix B). Pipeline defaults maximize in-flight pages: `--workers 20`, `--max_concurrent_requests 1600`, `--pages_per_group 500` (`pipeline.py:1223-1224`, `1314-1315`); within one PDF **all pages launch concurrently** via `asyncio.TaskGroup` (`pipeline.py:548-551`); global semaphore caps server requests (`pipeline.py:88`, `184`). Default inference model **`allenai/olmOCR-2-7B-1025-FP8`** (`pipeline.py:1212-1214`); vLLM launched with `--max-model-len 16384`, `--tensor-parallel-size 1` (`pipeline.py:807-825`, `1255`). Impact: our bottleneck is **~1510 serial unit checks × ~20 s** on MoE (`00-baseline.md:22-25`, `36-38`); a dense fine-tuned judge on a dedicated pod could cut unit-check wall **~850–1200 s** (persona 23) if decode scales like olmocr's dense-vs-frontier gap; **still ~1800 s short** of 300–600 s target without call elimination / parallelism. Quality risk: none from throughput alone; risk enters only on model swap without equivalence gate.

- [HIGH] **FP8 is a first-class deployment choice, not an afterthought.** Shipped HF weights are FP8-suffixed (`README.md:40-42`: v0.2.1 "default FP8, needs much fewer retries"; v0.4.0 `olmOCR-2-7B-1025-FP8`). Quantization recipe: `FP8_DYNAMIC` on all `Linear` layers, excluding `lm_head` and `model.visual.*` (`research/repos/olmocr/olmocr/train/quantization_configs/qwen2_5vl_w8a8_fp8.yaml:1-6`). External vLLM recipe: `vllm serve allenai/olmOCR-2-7B-1025-FP8 --max-model-len 16384` (`README.md:329-330`). Impact: FP8 halves weight memory → higher batch concurrency on same GPU; pairs with our existing `b300-qwen3-235b` FP8 pod pattern (`00-baseline.md:69-70`). For a future unit-check fine-tune, deploy FP8 on `h200-qwen3-32b` or a new 7B–14B dense slot. Quality risk: olmocr reports **no benchmark regression** from FP8 default vs BF16 path in README release notes; our gate still requires persona 47 A/B, not release-note trust.

- [HIGH] **Smaller-vs-larger on their task: specialization beats scale; general VLMs lose to fine-tuned 7B.** Documented comparisons on olmOCR-Bench: base Qwen 2 VL 7B **31.5±0.9** → Qwen 2.5 VL 7B **65.5±1.2** → GPT-4o **68.9±1.1** → olmOCR 2 **82.4±1.1** ([arxiv:2510.19817](https://arxiv.org/abs/2510.19817)). README benchmark table shows **Nanonets-OCR2-3B at 69.5±1.1** (smaller specialist) vs **Marker 76.1** / **Mistral OCR API 72.0** (`README.md:119-129`). olmocr experiments with **Qwen3-VL-30B-A3B MoE + LoRA** exist (`qwen3_moe_vl_mini_olmocrv5_annotatefirstrow.yaml:8-24`) but **production stays 7B dense** — economics favor one-GPU FP8 7B at 3050 tok/s over a 30B MoE serving path. Impact: for tapetum unit checks (text-only, structured `UnitCheck`, `models.py:298-313`), target **7B–14B dense** (Qwen3-8B, Phi-4-14B class per SLMJury `05-web.md:88-90`), not MoE V4-pro or 235B. Quality risk: SLMJury quick-verdict gains **lose up to 23% on general tasks** (`05-web.md:90`); our schema is richer than 10-token verdicts — distillation must preserve defect_groups, not collapse to pass/fail.

- [HIGH] **Training recipe is reproducible: GPT teacher labels → SFT → (optional) RLVR with binary unit tests → FP8 serve.** v1: GPT-4o batch labels with document-anchoring, 8×H100, lr 1e-6, ~10k steps, 16 node-hours per run, 365 node-hours total experiments ([arxiv:2502.18443](https://arxiv.org/abs/2502.18443) §2.3). v2 current trainer: `Qwen/Qwen2.5-VL-7B-Instruct`, bf16, flash-attn, **effective batch 32** (batch 1 × grad accum 32), lr **2e-5**, 1 epoch, collator max **8192** tokens, image dim **1288** (`qwen25_vl_olmocrv4_rotation_1epoch_mix_1025.yaml:38`, `74-85`, `105`). GRPO phase: 8×H100, **28 completions/document**, reward = olmOCR-Bench test-case pass fraction ([arxiv:2510.19817](https://arxiv.org/abs/2510.19817) §RL). Inference robustness: **no guided JSON at serve** (repetition collapse); temperature ramp + up to 8 retries (`pipeline.py:85`, `1221`; [arxiv:2502.18443](https://arxiv.org/abs/2502.18443) App. D.2). Impact: maps directly to our fine-tune path below. Quality risk: olmocr's 12% retry rate ([arxiv:2502.18443](https://arxiv.org/abs/2502.18443) Table 6) is acceptable for OCR batch; judge lane must stay fail-closed — retries OK, silent false-clear not OK.

- [MED] **Proposed whisker unit-check fine-tune path (distill DeepSeek-V4-pro → dense specialist on our pods).** (1) **Corpus:** export ~1510 unit-check calls/cold run (`00-baseline.md:22-23`) plus historical sidecars under `whisker/llm/*.tapetum.json` (fingerprints at `cli.py:565+`); input = `UNIT_CHECK_SYSTEM_PROMPT` + guard tag + one page source + full `candidate_md` (`unit_judge.py:769-776`); label = teacher `UnitCheck` JSON. Include **70% zero-defect** examples (`00-baseline.md:29`) so the student learns pass calibration, not only fail patterns. (2) **Base model:** open-weight dense on existing pods — `h200-qwen3-32b`, `b200x2-gemma4`, or train/export a **Qwen3-8B** text instruct (unit checks are text-only; no VLM needed, simpler than olmocr). (3) **SFT:** structured output training mirroring olmocr's masked-loss-on-response pattern (`train.py` + Pydantic `UnitCheck` schema); 1–2 epochs, bf16, flash-attn; **~8–24 GPU-hours** on one H200/B200 (vs olmocr's 16 node-hours for 260k-page VLM). (4) **Optional RLVR:** use dev-replay 29 labeled defect groups + holdout 48 anchors (`47-quality-equivalence.md:12-14`) as binary rewards (olmocr v2 pattern) — **2–4 weeks** extra. (5) **Deploy:** FP8 quantize (`qwen2_5vl_w8a8_fp8.yaml` pattern adapted for text-only), vLLM on dedicated pod; route unit + metadata calls off `alliance-pod` (1887/2284 calls, persona 23). (6) **Cost/effort:** **~2–3 engineer-weeks** data export + SFT + pod wiring; **~6–12 weeks** if RLVR + full validation cadence. Dollar cost dominated by **3× ~50 min `--force` fleet runs** (~150 min) for persona 47 gate (`47-quality-equivalence.md:16-17`), not training GPU. Impact: **~850–1200 s** cold-run savings at 2–2.5× decode (`23-small-judge-evaluator.md:18`); **does not reach 5–10 min alone**. Quality gate: persona 47 **full protocol** — `flip_AB <= flip_AA + margin` on 381-paper equivalence vector, dev-replay recall ≥ baseline − 0.05, holdout anchor recall if evidence-touching (`47-quality-equivalence.md:8-14`); `_LANE_VERSION` bump mandatory (`cli.py:99-117`).

- [LOW] **olmocr throughput techniques partially portable without fine-tuning.** Prefix-heavy shared prompts (`CONVERSION_CONTRACT` ~820 tok static, guard tag only 52 tok at tail — persona 15), cross-paper concurrency (olmocr 1600 vs our 32 papers × serial-in-paper), and FP8 KV on MoE (`39-kv-quant-scout.md`) are independent levers. olmocr's page-level `TaskGroup` parallelism (`pipeline.py:548-551`) parallels our **forbidden-without-gate** in-paper parallel unit checks (`20-in-paper-parallelist.md`; D11 exempt but MoE variance risk). Impact: copy **concurrency + FP8 serve + teacher distillation** doctrine; do not copy OCR pipeline verbatim (vision input, 8000 max output tokens/page vs our 1536 cap `00-baseline.md:27-28`).

## False-pass hypothesis

Fine-tuned dense unit-check model overfits the teacher's **70% zero-defect rate** (`00-baseline.md:29`) and returns empty `defects` on a localized omission (P0957R8-style `candidate_not_found`) where DeepSeek-V4-pro would flag it — fleet flip rate stays inside MoE A/A noise (≥25%, `47-quality-equivalence.md:10`) while dev-replay `page_content_omission` recall drops below the −0.05 floor.

## False-fail hypothesis

Student model mis-reads sanctioned `:::wording-remove` / `<del>` blocks (`unit_judge.py:93-102`, `CONVERSION_CONTRACT`) and emits structure defects on clean wording papers — false review inflation identical to persona 23's Gemma/Qwen swap fear, wasting human inspect time without improving recall.

## What would change my mind

A completed pilot: SFT on ≥3000 sidecar-exported unit-check pairs (current 1510 + history), deployed FP8 on `h200-qwen3-32b`, passing persona 47's **381-paper equivalence gate** (`flip_AB <= flip_AA + margin`) **and** dev-replay recall parity, with measured unit-check latency **≥2×** faster than MoE V4-pro on the same prompts — demonstrating olmocr-class "specialist beats teacher" on our narrow task, not just on OCR.
