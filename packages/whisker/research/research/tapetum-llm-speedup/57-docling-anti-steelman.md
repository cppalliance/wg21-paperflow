# 57 - docling-Anti-Steelman

**Verdict:** garbage (+ Docling's published "fast" numbers measure PDF *extraction* on 258M VLMs or zero-LLM CNN pipelines; it has zero post-conversion LLM verification call sites, so it cannot anchor a 3003 s → 5-10 min *judge* speedup at whisker fidelity.)
**Confidence:** high

## Findings

- [CRITICAL] Docling performs **no LLM verification** of an already-produced conversion against source. Every generative site takes source inputs (page image, crop, audio) and *produces* text/structure; none compares rendered markdown to the PDF. Evidence: inventory of 29 production generative sites, all classified extraction/refinement (`docling/models/stages/vlm_convert/vlm_convert_model.py:137-210`, `all-pages-llm-coverage/v2/11a-docling-callsites.md:94-96`). Repo-wide search for element QA returned zero matches (`11a-docling-callsites.md:88-90`). Impact: **0 s** judge wall-clock saving by copying Docling; quality risk if synthesis treats "fast conversion" as "fast verification."

- [CRITICAL] Docling regression QA is **deterministic golden replay**, not an LLM judge fleet. `verify_conversion_result_v2` gates on `ConversionStatus.SUCCESS`, page-cell counts, full `DoclingDocument` JSON walk, markdown, and doctags (`tests/verify_utils.py:357-439`); table cells use per-grid `verify_text` plus role flags (`136-172`). No LLM participates. Impact: Docling proves deterministic tripwires are cheap; our 2284-call census (`00-baseline.md:22-23`) is advisory LLM verification by design. Porting Docling eval closes deterministic gaps, not the 3003 s cold run.

- [CRITICAL] Docling's headline throughput is **not LLM-judge latency**. Published GPU table: Standard pipeline (layout+TableFormer, **no generative LLM**) at **7.9 pages/s** on RTX 5090; VLM GraniteDocling extraction at **3.8 pages/s** on the same hardware (`docs/usage/gpu.md:158-160`). Default `DocumentConverter()` uses `StandardPdfPipeline`, not VLM (`document_converter.py:87`, README quickstart `:94-99`). Impact: citing Docling "shows it can be done fast" without naming pipeline conflates **zero-LLM CNN extraction** (~0.13 s/page) with our **MoE DeepSeek V4 judge** (~20 s/call, `00-baseline.md:24-25`). False comparison.

- [HIGH] On a **comparable generative-per-page task** (VLM extraction, not verification), Docling is faster per LLM-touched page because the task is cheaper, not because judge architecture is better. VlmPipeline: **1 VLM call per page**, same static prompt `"Convert this page to docling."` (`vlm_convert_model.py:178`, `vlm_model_specs.py:24`), batched via `engine.predict_batch` (`vlm_convert_model.py:196-198`, `vllm_engine.py:322`). Model: **258M** GraniteDocling with `max_new_tokens=8192` (`vlm_model_specs.py:23-36`). Corpus estimate: 381 papers × ~13 pages ≈ **4953 pages**. At Docling's published **3.8 pages/s** (RTX 5090, `gpu.md:160`): **~1303 s** wall for extraction-only. At **2.4 pages/s** (L40S, `gpu.md:160`): **~2063 s**. Our fleet: **2284 calls / 3003 s** ≈ **1.31 s/call amortized** across 16 server slots (`00-baseline.md:17-25`), but **~6 serial calls/paper** (~120 s serial paper wall, `00-baseline.md:38-39`) on DeepSeek V4 MoE with up to 1536-token unit outputs (`00-baseline.md:27-28`). Normalized per generative page touch: Docling ≈ **0.26-0.42 s/page** server throughput vs our **~0.46 LLM calls/page** average (2284/4953) at **~20 s each** serial. Docling wins by **258M extract-one-page**, not by solving evidence-grounded verification.

- [HIGH] Docling is **weaker at fleet-level concurrency** than our tapetum-llm setup and does not exploit a 24/7 remote judge pod by default. Cross-document parallelism: `ThreadPoolExecutor` only when `doc_batch_concurrency > 1` AND `doc_batch_size > 1`; defaults are both **1** with comment "Experimental! No benefit expected without free-threaded python" (`settings.py:30-33`, `document_converter.py:672-683`). Within-document page batches run **serially** through `PaginatedPipeline._build_document` (`base_pipeline.py:271-282`). Standard PDF uses **thread-per-stage** worker pools, not asyncio (`standard_pdf_pipeline.py:216-255`, `700-733`). Picture enrichment uses `ThreadPoolExecutor` with blocking HTTP (`picture_description_api_model.py:67-68`). Impact: Docling optimizes single-machine GPU batching; our `_DEFAULT_CONCURRENCY = 32` asyncio paper fleet (`00-baseline.md:34-35`) is already ahead at cross-paper scale. Docling's VLM recipe assumes **local** `vllm serve` on bare metal (`gpu.md:73-82`); no dual-pod sharding, no warm 24/7 MoE pod economics.

- [HIGH] Docling **refuses fail-closed** semantics we require. Timeout mid-document sets `ConversionStatus.PARTIAL_SUCCESS` and breaks (`base_pipeline.py:302-319`, `standard_pdf_pipeline.py:850-863`). Errors downgrade to `PARTIAL_SUCCESS` when any `conv_res.errors` remain (`base_pipeline.py:80-83`). Agent heuristic `docling-evaluate.py` triages density/duplication and suggests `--pipeline vlm` retries; it is not golden recall and emits `"heuristic_only": True` (`docling-evaluate.py:128-157`). Impact: Docling's speed comes partly from **best-effort emit**; whisker fail-closed coverage (`00-baseline.md:79-80`) forbids trading away the 1510 unit-check calls that docling never makes.

- [MED] Docling implements **none** of our swarm's proposed judge-speed levers beyond generic page batching. No vLLM prefix/APC configuration: `_VLLM_ENGINE_KEYS` lists `kv_cache_dtype` but no `enable_prefix_caching` (`vllm_engine.py:67-87`); repo-wide `rg prefix|APC` over `*.py` returns zero matches. `use_kv_cache=True` in VLM options is per-request transformer KV reuse, not cross-request shared-document prefix caching (`pipeline_options_vlm_model.py:304-314`). No call-elimination router, no zero-defect short-circuit, no per-unit fingerprint skip (only whole-pipeline instance cache, `document_converter.py:696-723`), no dual-pod sharding, no guard-tag prefix fix, no metadata-fail short-circuit, no multi-criterion judge packing. Impact: **0 s** direct saving from "do what Docling does"; at best **page_batch_size** tuning (`settings.py:32`, default 4) mirrors our in-paper batching opportunity, not their CI path.

- [LOW] Docling's VLM server recipe runs **`--max-num-seqs 512`** (`gpu.md:78`) vs our measured **`--max-num-seqs 16`** on DeepSeek V4 (`00-baseline.md:66-67`, `82-83`). That gap reflects **258M dense Docling model vs MoE judge**, not a portable knob: raising our slots to 32 regressed +60% wall (`00-baseline.md:82`). Impact: cargo-culting Docling vLLM flags without model-class context would violate measured constraints.

## False-pass hypothesis

Synthesis adopts Docling's **3.8 pages/s VLM throughput** (`gpu.md:160`) and cuts `MAX_UNIT_CHECKS` or unit-check payload, assuming GraniteDocling-speed proves headroom. Docling never validates wrapped table cells (`SF`→`S`) or bikeshed secno outline equivalence; its CI catches those only where committed goldens exist (`verify_table_v2`, `verify_utils.py:136-172`). Whisker deterministic lane already passed PR #286 while LLM missed recall (`00-baseline.md` class-5 gaps in `r04-docling.md`). Faster by skipping checks = silent defect pass.

## False-fail hypothesis

Adding Docling-style **exact grid `verify_text`** without fuzzy mode (`verify_utils.py:153-157`, NED threshold at `:110-112`) rejects candidates with benign whitespace deltas that pass human golden review. That is a deterministic false-fail path, orthogonal to LLM speed but likely if synthesis copies Docling QA wholesale to "match their speed."

## What would change my mind

A measured run on our 381-paper corpus where Docling's **VlmPipeline + GraniteDocling 258M** (or any Docling generative path) performs **post-tomd LLM verification** with evidence-grounded per-page defect quotes, fail-closed coverage, and two-sided provenance, hitting **≤600 s** wall at ≥95% agreement with current tapetum-llm verdicts on a 50-paper stratified holdout. No such code path exists today (`11a-docling-callsites.md:94-96`).
