# 116 - mineru-Concurrency-Scaling

**Verdict:** usable-with-conditions — MinerU's portable wins are **page-window batching with cross-document interleaving** (pipeline) and **LPT client bin-packing**; VLM/hybrid paths stay **per-document serial windows**, and their default API concurrency (3) is far below our c=32 overfill, so only the window + scheduling shapes transfer, not the absolute depth.
**Confidence:** high

Repo: `research/repos/mineru` at SHA `79d6d8d79fb8f3ddba5cc34c07a16f0ec36f56c7`.

## Findings

- [CRITICAL] **Primary GPU unit of concurrency is the processing window (default 64 pages), not the document.** Evidence: `get_processing_window_size(default=64)` at `config_reader.py:158-169`, `DEFAULT_PROCESSING_WINDOW_SIZE=64` at `api_protocol.py:4-5`; pipeline fills each window by round-robin taking pages from open documents until capacity exhausted (`pipeline_analyze.py:225-262`), then runs one `batch_image_analyze` on the flat page list (`pipeline_analyze.py:271-275`); VLM/hybrid slice **one document** into windows and call `batch_two_step_extract` / `batch_extract_with_layout` per window (`vlm_analyze.py:446-482`, `hybrid_analyze.py:924-986`). Impact: for tapetum, the analogue is a **16-slot "call window"** that mixes pages/units from multiple papers per vLLM batch, not one paper holding a slot through 6 serial calls (`00-baseline.md:36-38`). A naive port (parallel in-paper unit checks only) fills 16 slots from one paper's homogeneous prefills; MinerU's cross-doc fill keeps GPU batch composition mixed. Expected saving if we interleave cross-paper unit checks in windows of 16: **~100-400 s (3-13%)** on 3003 s by trimming tail idle when long papers finish alone; quality risk **MEDIUM-HIGH** (MoE batch-composition variance, `71-olmocr-concurrency-model.md:26`).

- [CRITICAL] **Pipeline backend interleaves pages across documents inside each window; VLM/hybrid do not.** Evidence: multi-file loop walks `doc_contexts` in input order, `take_count = min(batch_capacity, page_count - page_start)` per doc (`pipeline_analyze.py:232-262`); log line `doc_slices=doc0:1-32,doc1:1-20,...` (`pipeline_analyze.py:264-267`); VLM `doc_analyze` has no `pdf_bytes_list`, only sequential windows within one PDF (`vlm_analyze.py:440-482`); hybrid identical window loop per document (`hybrid_analyze.py:914-958`). Client mirrors this: `plan_pipeline_tasks` bin-packs multiple small PDFs into one HTTP task (`client.py:609-651`); VLM/hybrid `plan_tasks` emits **one task per document** (`client.py:661-664`). Impact: head-of-line blocking from a 500-page PDF is **partially absorbed** in pipeline mode (other docs' pages ride in the same window) but **fully serial** for VLM. Our fleet is closer to VLM semantics today (one paper = one serial cascade). Cross-paper page/call interleaving is the missing tail fix; estimated **~60-200 s** if ~10% of papers are 2× median call cost and would otherwise finish last. Quality risk: **none** for scheduling-only interleaving.

- [HIGH] **Within-window inference is model-batch by modality, not one call per page.** Evidence: `BatchAnalyze.__call__` runs layout on all window pages with `batch_size=min(8, batch_ratio * LAYOUT_BASE_BATCH_SIZE)` (`batch_analyze.py:426-429`, `LAYOUT_BASE_BATCH_SIZE=1` at `batch_analyze.py:38`); formula MFR batches crops across pages at `batch_ratio * MFR_BASE_BATCH_SIZE` (`batch_analyze.py:445-449`, `MFR_BASE_BATCH_SIZE=16` at `batch_analyze.py:39`); `batch_ratio` scales with VRAM 1→16 (`pipeline_analyze.py:353-363`, hybrid `get_batch_ratio` at `hybrid_analyze.py:865-876`). VLM window calls `predictor.batch_two_step_extract(images=images_pil_list)` — external `mineru_vl_utils` batches inside the client (`vlm_analyze.py:479-482`, `max_concurrency=100` default for http-client at `vlm_analyze.py:71`). Impact: they batch **homogeneous modality work** (all layout, then all formula crops) inside a page window; our analogue is batching **same-rubric unit checks** across papers, not packing monolith+unit in one prompt. Expected saving from modality-homogeneous waves: **~0-80 s** unless call count drops; quality risk **HIGH** for multi-rubric packing (`05-web.md:96-98`, RuVerBench).

- [HIGH] **Three-tier queue: client asyncio workers → API task queue + semaphore → optional multi-server router.** Evidence: client `execute_planned_tasks` uses `asyncio.Queue` + `concurrency = min(max_concurrent_requests, task_count)` workers (`client.py:765-816`); API `AsyncTaskManager._dispatcher_loop` spawns a processor per submitted task immediately (`fast_api.py:1096-1106`) but `_process_task` acquires `_request_semaphore` before GPU work (`fast_api.py:1142-1144`); semaphore default **`DEFAULT_MAX_CONCURRENT_REQUESTS=3`** (`api_protocol.py:3`, `fast_api.py:228-234`, env `MINERU_API_MAX_CONCURRENT_REQUESTS` at `config_reader.py:172-192`). Router `WorkerPool.acquire_submission_server` picks lowest `score = (queued+processing+pending)/max_concurrent_requests` (`router.py:521-524`, `763-785`); aggregates `max_concurrent_requests` and `min(processing_window_size)` across healthy servers (`router.py:818-824`). Impact: MinerU **decouples task admission from GPU execution** (dispatcher fires freely, semaphore gates); default **3 concurrent GPU jobs** vs our **32 in-flight papers × 1 serial call**. Portable pattern: **match client overfill to server slots × small factor** (we already at 2×); raising task admission without slots does not help. Router score routing is directly portable for **dual-pod sharding** (`00-baseline.md:67-68`): **~1500 s (50%)** wall if compute-bound and second pod adds 16 slots; quality risk **none** for routing-only.

- [HIGH] **Explicit size-based scheduling at client task planning (LPT + bin-packing), not inside the GPU window.** Evidence: `plan_pipeline_tasks` sorts documents by `(-effective_pages, order)` (`client.py:614-617`); documents with `effective_pages > processing_window_size` get **isolated single-doc tasks** (`client.py:620-627`); smaller docs packed into bins with `total_pages + doc <= window_size`, choosing bin with **minimum current fill** (`client.py:630-639`). No sort-by-size inside `pipeline_analyze.py` window fill (doc order from `doc_contexts` append order at `pipeline_analyze.py:173-197`). Impact: isolating huge PDFs prevents one API task from monopolizing a mixed window; LPT reduces **client-task** tail. Direct tapetum analogue aligns with persona 29 LJF by predicted call count: **~60-180 s (2-6%)** on 3003 s (`29-tail-latency-scheduler.md:12-13`). Quality risk **none**.

- [MED] **CPU prep parallelized separately from GPU inference.** Evidence: PDF rasterization uses persistent `ProcessPoolExecutor` capped at `MAX_PDF_RENDER_PROCESSES=3` (`pdf_image_tools.py:37-38`, `145-152`); spawn throttled 100 ms between worker submits (`pdf_image_tools.py:190-206`); async path via `asyncio.to_thread` (`pdf_image_tools.py:360`); pipeline postprocess output uses `ThreadPoolExecutor(max_workers=1)` while inference streams (`common.py:402-419`); title LLM-aided uses `ThreadPoolExecutor` up to `MAX_TITLE_GROUP_WORKERS=4` (`llm_aided.py:17`, `327-337`). Impact: MinerU never blocks GPU on PDF render; our `screen_pages`/grounding runs inside the paper worker (`00-baseline.md:36-38`). Hoisting deterministic prep before parallel LLM waves saves **≪1%** fleet wall (`71-olmocr-concurrency-model.md:18`). Quality risk **none**.

- [MED] **Distributed mode = HTTP router across MinerU API instances, not Ray/k8s model parallelism.** Evidence: `WorkerPool._build_servers` registers multiple `upstream_urls` plus optional per-GPU local workers from `parse_local_gpus` (`router.py:560-589`); `submit_router_task` retries across healthy servers (`router.py:1175-1229`); each worker exposes standard health with queue stats (`router.py:653-668`, `807-829`). No in-repo Ray, Celery, or cross-node page shard beyond this proxy layer. VLM http-client backend talks to external OpenAI-compatible server (`vlm_analyze.py:71-75`, `222-238`). Impact: **multi-pod tapetum** maps 1:1 to router pattern; no hidden cluster scheduler to copy. Quality risk **none** for infra.

- [LOW] **MLX backend forces serial predictor lock; http-client allows high async concurrency.** Evidence: `_maybe_enable_serial_execution` adds `threading.Lock` for MLX only (`vlm_analyze.py:379-387`); `predictor_execution_guard` serializes MLX windows (`vlm_analyze.py:390-397`); http-client `max_concurrency=100` passed to `MinerUClient` (`vlm_analyze.py:71`, `231`). Impact: when GPU is remote (vLLM serve), MinerU assumes **many concurrent HTTP VLM requests**; when local MLX, **fully serial**. Our judge is always remote vLLM — MinerU's local-serial path is not our regime.

## False-pass hypothesis

Adopting pipeline-style **cross-paper call windows** without rubric isolation: a batch schedules monolith + unit-check calls from different papers in the same MoE forward pass; expert routing variance shifts a borderline table defect to zero-defect on unit 3 while the serial baseline flagged `review` — silent advisory false-pass (`71-olmocr-concurrency-model.md:26`, `20-in-paper-parallelist.md:24-26`).

## False-fail hypothesis

Copying MinerU API **semaphore=3** literally on a 16-slot MoE pod while keeping c=32 client depth: most papers sit in vLLM FCFS queue **>120 s** (`UNIT_CHECK_TIMEOUT_SECONDS=120`, `constants.py:197`) before first token, tripping fail-closed timeouts on clean conversions (`71-olmocr-concurrency-model.md:30`, `research/concurrency-381/12-runpod-proxy.md:29-31`).

## What would change my mind

Sidecar timestamp analysis on the 3003 s cold run showing **≥30% of wall time** occurs with **<8 concurrent sidecar writes** while **>100 papers** remain unfinished — proving cross-paper interleaving (not call elimination) is the dominant gap — would upgrade processing-window dispatch from "tail trim" to "primary lever" alongside dual-pod sharding.
