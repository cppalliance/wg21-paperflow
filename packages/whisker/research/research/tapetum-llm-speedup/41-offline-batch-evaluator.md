# 41 - Offline-Batch-Evaluator

**Verdict:** usable-with-conditions — two-phase prompt materialization is architecturally viable for the PDF-heavy fleet, but neither giant HTTP batch nor vLLM offline `run_batch` beats the proven server-16/client-32 overfill pairing on wall clock; expect **≤~4% (~120 s) savings** on the 3003 s cold run unless infra adds slots (dual-pod) or cuts call count.
**Confidence:** high

## Findings

- [CRITICAL] **`vllm run-batch` boots a separate offline engine; it cannot target a running `vllm serve` pod.** Evidence: `vllm/entrypoints/openai/run_batch.py:823-833` calls `build_async_engine_client(..., usage_context=UsageContext.OPENAI_BATCH_RUNNER)` inside `main()`, not an HTTP client to an existing server; `run_batch.py:267-270` adds `AsyncEngineArgs` CLI flags (same engine bootstrap as serve). GitHub [#8567](https://github.com/vllm-project/vllm/issues/8567): maintainer @DarkLight1337 confirms `/v1/batches` returns 404 on the online server and `run_batch` "starts a new model instance." Impact: our 24/7 RunPod pod (API-key only, no shell) **cannot** use offline batch without a CTO infra flip (stop serve, run `vllm run-batch`, or dual-process GPU contention). Quality risk: none; operational/deployment only.

- [CRITICAL] **No OpenAI Batch/Files REST API on stock vLLM HTTP server.** Evidence: [vLLM stable docs](https://docs.vllm.ai/en/stable/examples/features/openai_batch/): "batch inference using the OpenAI batch **file format**, **not** the complete Batch (REST) API"; GitHub [#8631](https://github.com/vllm-project/vllm/issues/8631) closed `not_planned`. `run_batch.py:779-818` submits all JSONL lines via `asyncio.gather` against the **local** engine, not `/v1/batches` poll semantics. Impact: "submit 2284 prompts as one async batch job and poll" is unavailable on `alliance-pod`; only concurrent `/v1/chat/completions` or host-side `run-batch` CLI. Quality risk: none.

- [CRITICAL] **Measured slot utilization is already near ceiling; batch submission cannot 2× throughput on the running server.** Evidence: `00-baseline.md:24-25` (2284 calls × ~20 s / 16 slots ≈ 2855 s closes the 3003 s wall); `research/slots-32-regression/SYNTHESIS.md:10-11,50-53` (server=16: client c=16 → **722.4 s**, c=32 → **692.3 s**, **-4.2%**); `28-semaphore-topologist.md:10` (c=32 overfill is the empirical ceiling for "more in-flight fixes idle slots"). Q3 swfte card (`05-web.md:53-55`: offline ~90% vs HTTP ~35% utilization) does **not** apply here: we are already at ~96% of the c=16 baseline, not 35%. Impact: flooding 2284 requests at once vs c=32 paper overfill saves **≤~120 s (~4%)** on 3003 s, with **worse** tail latency and RunPod proxy 524 risk (`research/concurrency-381/12-runpod-proxy.md:29-31`). Quality risk: LOW for throughput; HIGH for operational errors masquerading as coverage gaps.

- [HIGH] **Two-phase prompt generation is ~95% feasible for PDF papers, but HTML tier-2 blocks a single giant batch.** Evidence: deterministic pre-LLM phases — `pdf_judge.py:636` (`screen_pages`), `pdf_judge.py:851` (`route_pdf_units` on `page_units + raw_tomd_md`, no monolith output), `source_router.py:167-220`; page-escalation prompts known from screen flags (`pdf_judge.py:736-758`). Non-precomputable: HTML tier-2 depends on tier-1 LLM output + `_escalation_signals(tier1, paper_md)` after grounding (`adjudicate.py:256-299`); ~16 fleet page escalations (`00-baseline.md:23`). Impact: Phase 1 can emit ~**2200+** of ~2284 prompts for PDF-heavy fleet; HTML tier-2 requires **wave 2** after tier-1 results (~5–10% of calls). Wall saving from materialization alone: **0 s** (same calls, same slots). Quality risk: none if assembly preserves grounding order.

- [HIGH] **Grounding interleaving is reorderable, not eliminable; batch mode changes when CPU runs, not what runs.** Evidence: monolith grounding after LLM (`pdf_judge.py:690-697`); per-page escalation grounding inside serial loop (`pdf_judge.py:753-796`); tier-1 grounding before tier-2 gate (`adjudicate.py:271-274`). A batch architecture must add **Phase 3 assembly**: LLM outputs → same `ground_spans` / `classify_candidate_evidence` / `_escalation_signals` → conditional wave-2 prompts. Impact: no call-count reduction; sync CPU (`screen_pages`, grounding) stays ~0.1–10% per paper (`28-semaphore-topologist.md:14-16`). Quality risk: **MEDIUM** if assembly skips grounding before tier-2/units (would change verdicts).

- [HIGH] **Fail-fast per paper is lost unless batch is split into dependency waves.** Evidence: `pdf_judge.py:556-586` (`PdfLaneError` on any failure, no partial results); `pdf_judge.py:659-688` (monolith failure stops metadata/units); `cli.py:767-779` (error tombstone on exception). Single giant batch submits monolith+metadata+units for all 381 papers regardless of upstream failure → wasted GPU on downstream calls for papers that would have aborted (~6 error papers on cold run, `00-baseline.md:18`). Wave design (monolith wave → filter → metadata wave → …) preserves fail-fast but **matches today's cross-paper slot filling** under c=32. Impact: wave batch without call elimination saves **≤~4%**; unfiltered giant batch wastes **~1–3%** GPU on dead chains plus loses fail-closed semantics. Quality risk: **HIGH** for unfiltered batch (partial sidecars).

- [MED] **`run_batch` concurrent submission uses the same continuous-batching scheduler as HTTP serve.** Evidence: `run_batch.py:779` ("Submit all requests in the file to the engine concurrently"); `run_batch.py:818` (`asyncio.gather(*response_futures)`). Offline vs HTTP delta is IPC/serialization, not GPU scheduling ([vLLM #7956](https://github.com/vllm-project/vllm/issues/7956): maintainer notes `LLM` faster than API server because request data skips process boundary; measured ~3× on Llama2-70B AWQ, not MoE V4-pro at 16 slots). `research/concurrency-381/20-batch-alternatives.md:18` attributes **<1%** of ~30 s/call to HTTP setup on our decode-bound workload. Impact: even full offline flip saves **~30–60 s (~1–2%)** on 3003 s, not the Q3 ~2× figure (that compares underutilized HTTP batches to saturated offline engine). Quality risk: none.

- [LOW] **Native online `POST /v1/chat/completions/batch` is sync, no-stream, and unverified on alliance-pod.** Evidence: [vLLM 0.24 batched chat docs](https://docs.vllm.ai/en/v0.24.0/examples/generate/batched_chat_completions_online/) ("Streaming is not supported"); `packages/whisker/research/llm-batching/05b-web-batch-endpoint.md:43-49`. Tapetum streams every call (`00-baseline.md:68`). Impact: transport convenience only; same 16-slot cap; requires non-streaming code path. Quality risk: LOW if responses identical; MEDIUM if streaming/thinking parsing differs.

## False-pass hypothesis

Unfiltered Phase-2 giant batch: paper A's monolith times out or returns malformed JSON, but metadata and five unit-check prompts already ran in parallel on the GPU. Assembly treats missing monolith as empty evidence, metadata returns pass, zero-defect unit checks (70% baseline rate, `00-baseline.md:29`) merge to advisory pass — operator sees a completed sidecar while the monolith chain never executed, silently weakening coverage on a paper that fail-fast would have tombstoned (`pdf_judge.py:659`, `cli.py:767-779`).

## False-fail hypothesis

Wave-2 tier-2 batch submitted for all HTML papers whose tier-1 happened to land in the ambiguous confidence band during a high-concurrency MoE batch composition (`MODELS.md:69-70`): batch-non-invariant routing fires `SIGNAL_CONFIDENCE_AMBIGUOUS` (`adjudicate.py:276-277`) on papers that serial tier-1 at c=32 would have passed cleanly, triggering unnecessary tier-2 calls that demote pass→review (`adjudicate.py:355-356`) — false advisory review, not false deterministic fail.

## What would change my mind

Pod-side A/B on the 381-paper cold corpus: (A) current c=32 HTTP overfill vs (B) host-side `vllm run-batch` on the **same** `--max-num-seqs 16` config with wave-matched prompt count, reporting ≥**20%** wall reduction at ≤**2%** per-PID verdict flip rate — would upgrade offline batch to primary lever. Without that, dual-pod sharding (`00-baseline.md:67-68`, second live `h200x8-deepseek-v4-pro`) remains the only batch-adjacent path that actually adds decode slots.
