# 52 - docling-Parallelism

**Verdict:** usable-with-conditions — Docling's high-impact patterns are GPU page-pipeline overlap and remote document fan-out; our tapetum bottleneck is serial LLM call volume per paper, so only the "concurrent independent HTTP inferences + ordered reassembly" pattern transfers cleanly, and it does not by itself close the 3003 s → 5–10 min gap without call elimination or extra pods.
**Confidence:** high

## Findings

- [CRITICAL] Document-level parallelism is opt-in and defaults to serial. `BatchConcurrencySettings` sets `doc_batch_size=1`, `doc_batch_concurrency=1` with an explicit warning that thread parallelism is experimental and "No benefit expected without free-threaded python" (`settings.py:30-31`). `DocumentConverter._convert` only spins a `ThreadPoolExecutor` when both `doc_batch_concurrency > 1` and `doc_batch_size > 1`, using `pool.map` over document batches (`document_converter.py:663-683`). Impact: docling locally does **not** beat our 32-paper asyncio fan-out; no fleet saving from copying doc-level threads. Quality risk: none (we already parallelize more aggressively).

- [HIGH] Remote/batch API uses asyncio bounded workers, not threads. `DEFAULT_MAX_CONCURRENCY = 8` (`client.py:122`); `_run_bounded` launches `worker_count = min(len(items), max_in_flight)` asyncio tasks with an index lock (`_scheduler.py:40-73`); `convert_all` passes `ordered=True` and re-yields results in source order via an index buffer (`client.py:2180-2183`, `_async_client.py:527-531`). Impact: validates our cross-paper asyncio semaphore design; dual-pod sharding (second 16-slot instance per 00-baseline) is the docling-analog lever — **~2× fleet wall** if fully utilized (3003 s → ~1500 s), still short of 5–10 min alone. Quality risk: low if same model on both pods.

- [HIGH] Within a document, legacy/base pipeline pages are **not** concurrent — only batched serially. `page_batch_concurrency: int = 1  # Currently unused` (`settings.py:33`); `base_pipeline._build_document` chunks pages by `page_batch_size` (default 4) and runs each batch through all models in a serial `for model in self.build_pipe` loop (`base_pipeline.py:271-247`). Impact: docling explicitly rejected page-level thread concurrency for the non-threaded path; our "serial within paper" matches their conservative default, not a gap they solved with page threads. Quality risk: n/a.

- [CRITICAL] `StandardPdfPipeline` achieves in-document speed via **stage-level pipelining**, not parallel LLM-style independent calls. Five `ThreadedPipelineStage`s each run one `threading.Thread` worker (`standard_pdf_pipeline.py:216-255,682-733`); a separate producer `threading.Thread` feeds pages into preprocess while OCR/layout/table/assemble drain bounded `ThreadedQueue`s (`standard_pdf_pipeline.py:764-844,149-214`). Default stage batch sizes: `ocr_batch_size=4`, `layout_batch_size=4`, `table_batch_size=4` (`pipeline_options.py:1908-1937`). Impact: overlap works because page *N* can be in layout while page *N+4* is in OCR — our tapetum chain is monolith → metadata → escalations → unit checks with hard dependencies, so **stage overlap transfers poorly**; expect **<5% fleet saving** unless we redesign into independent page-scoped judges. Quality risk: HIGH if we parallelize dependent cascade steps.

- [HIGH] Model-level speed is **accelerator batching**, not request fan-out. Layout runs `layout_predictor.predict_batch(valid_page_images)` over a page group (`layout_model.py:178-184`); VLM convert calls `engine.predict_batch(engine_inputs)` (`vlm_convert_model.py:196-198`). `num_threads` configures CPU/GPU intra-op threads per model (`accelerator_options.py:32-43`), not cross-call concurrency. Impact: analogous to multi-unit prompt packing; 05-web RuVerBench warns double-digit accuracy loss on batched rubrics — **not recommended** for tapetum without equivalence proof. Potential decode saving 0% if quality bar holds.

- [MED] Remote/API VLM paths use `ThreadPoolExecutor` for concurrent HTTP within a page batch, with **order preserved at collection**. `api_openai_compatible_engine.predict_batch` submits futures then `outputs = [future.result() for future in futures]` in submission order (`api_openai_compatible_engine.py:212-220`); `api_vlm_model` uses `executor.map` similarly (`api_vlm_model.py:185-186`). Impact: **directly portable** to parallel tapetum unit checks (independent after metadata routing): per-paper wall drops from ~5×20 s = 100 s to ~20 s on the unit-check tail (~60–80 s saved on a 6-call paper, ~33–50% per-paper latency), but **fleet wall unchanged** (~2284 calls × ~20 s / 16 slots ≈ 2855 s per 00-baseline) because slot-seconds are identical. Quality risk: MEDIUM — MoE batch-composition variance when one paper occupies multiple slots simultaneously.

- [MED] Order determinism under parallelism: pages may **complete out of order** during threaded processing (`standard_pdf_pipeline.py:875` appends to `proc.pages` as drained), but final output is reassembled by `page_no` keyed map then filtered to original `conv_res.pages` order (`standard_pdf_pipeline.py:947-951`). Nemotron OCR uses a `pending` deque "kept in input order so they can be yielded in the same order" (`nemotron_ocr_model.py:333-352`). Remote `ordered=True` buffers by submission index (`_async_client.py:527-531`). Impact: any tapetum parallel unit-check lever **must** attach findings by stable unit/page id and merge in deterministic order — copy this pattern, not raw completion order. Quality risk: HIGH without keyed reassembly (wrong-page findings).

## False-pass hypothesis

Parallelizing up to 5 unit checks per paper without docling-style keyed reassembly (`page_no` on every `ThreadedItem`, merge via `page_map` at `standard_pdf_pipeline.py:947-951`): faster completion order could merge OCR-style findings onto the wrong page/unit, silently dropping a real defect on page 3 while clearing page 7.

## False-fail hypothesis

Fanning 5 concurrent unit-check HTTP calls from one paper under MoE `max-num-seqs 16` (`00-baseline:26-27`) shifts batch composition enough that a borderline formatting defect flips from `review` to `pass`, wrongly accepting a bad conversion — docling's API path accepts this variance for OCR text but does not prove judge-grade stability.

## What would change my mind

A measured tapetum A/B: parallel unit checks (docling `api_openai_compatible_engine.py:212-220` pattern) vs serial on 381 papers with fingerprint-stable verdicts and ≤1 changed merged verdict, plus fleet wall within 5% of serial — would upgrade to **usable** for in-paper parallelism.
