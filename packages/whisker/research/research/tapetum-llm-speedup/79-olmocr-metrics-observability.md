# 79 - olmocr-Metrics-Observability

**Verdict:** usable-with-conditions — olmOCR's run-time observability (aggregate tokens/s, retry histogram, vLLM queue-depth polling, worker state tables) is the right fleet-level template, but it persists token counts per page in Dolma metadata, not per-call wall latency; our tapetum sidecars record verdicts only, so we must add whisker-local `call_timings` + a fleet `run_manifest.json` before any 3003→5–10 min optimization claim is measurable.
**Confidence:** high

## Findings

- [CRITICAL] **olmOCR measures aggregate token throughput, not per-page or per-call wall time.** `MetricsKeeper` accumulates counters and prints lifetime + 5-minute-window **tokens/sec** rates (`olmocr/metrics.py:48-70`). Each successful HTTP response increments `server_input_tokens` / `server_output_tokens` from OpenAI `usage` (`olmocr/pipeline.py:195-196`). A background `metrics_reporter` task logs queue size + the table every 10 s (`olmocr/pipeline.py:983-990`). **No `time.monotonic()` per page or per HTTP call exists in `pipeline.py`.** Impact: olmOCR optimizes for corpus yield (3050 output tok/s in their report, `05-web.md:38-40`); we cannot back-solve our **3003 s** cold run (`00-baseline.md:17`) into monolith vs unit-check seconds from their model — and we currently cannot from ours either.

- [CRITICAL] **Our sidecars persist verdicts, not timings; fleet footer is wall-clock + retry count only.** `PdfJudgeResult.to_sidecar_dict()` emits schema v8 verdict/coverage fields with no `duration`, `usage`, or `call_timings` keys (`packages/whisker/src/whisker/tapetum_llm/pdf_judge.py:447-553`). Batch mode logs one progress bar and a footer `{pass/review/fail/error/skipped} ({retries} model retries) in {elapsed}s` (`packages/whisker/src/whisker/tapetum_llm/cli.py:1063-1087`, `1413-1424`). Prior audit: 204 sidecars parsed, zero timing keys (`packages/whisker/research/llm-batching/17-latency-decomposer.md:8`). Impact: every persona lever (prefix cache, call elimination, dual-pod) lacks a before/after per-call-class denominator on the **2284-call / 381-paper** census (`00-baseline.md:22-24`).

- [HIGH] **olmOCR tracks retry outcome histograms and page failure rate, not just a total retry count.** On success: `metrics.add_metrics(completed_pages=1, finished_on_attempt_{N}=1)` for attempt 0..`max_page_retries` (default 8), plus `finished_on_parallel_retry` when queue-empty parallel burst fires (`olmocr/pipeline.py:303-358`). On exhaustion: `failed_pages=1` (`olmocr/pipeline.py:330`, `373`). Final summary logs page failure rate and cumulative attempt distribution (`olmocr/pipeline.py:1493-1510`). **Our equivalent:** `_RetryCountFilter` swallows known BPE-retry log lines and rolls a single integer into the footer (`packages/whisker/src/whisker/tapetum_llm/cli.py:230-241`, `1414`); the 55 retries (~100 s, `00-baseline.md:60-61`) are not attributed to monolith / metadata / unit-check / page-escalation classes.

- [HIGH] **olmOCR observes vLLM queue depth and uses it for retry policy; we do not.** Global `vllm_queued_requests` is updated by parsing vLLM stderr `Running: N` and `Waiting|Pending: M` (`olmocr/pipeline.py:82`, `854-880`). When `vllm_queued_requests == 0`, remaining page retries fire in parallel (`olmocr/pipeline.py:345-358`). **Our equivalent:** CLI warns when `--concurrency` exceeds tested ceiling 32 and explicitly states queueing and per-request latency are "unmeasured" (`packages/whisker/src/whisker/tapetum_llm/cli.py:1100-1106`). Impact: on a **16-slot MoE pod** (`00-baseline.md:65-66`), we cannot split the implied **~20 s/call** (`00-baseline.md:24-25`) into queue-wait vs decode without either server metrics or client-side timestamps bracketing the HTTP POST.

- [HIGH] **olmOCR persists per-page token counts in output metadata; we persist none.** `PageResult` carries `input_tokens` / `output_tokens` per page (`olmocr/pipeline.py:95-101`). Dolma document metadata sums `total-input-tokens` / `total-output-tokens` and counts `total-fallback-pages` (`olmocr/pipeline.py:628-630`). Worker completion also rolls finished token totals into `MetricsKeeper` (`olmocr/pipeline.py:797-799`). **Our equivalent:** judge calls go through `run_judge_task` → `AgentBackend.run` with labels like `pdf-judge-{pid}`, `metadata-outline-{pid}`, `unit-check-{pid}-{unit_id}` (`packages/whisker/src/whisker/tapetum_llm/pdf_judge.py:650-655`, `packages/whisker/src/whisker/tapetum_llm/unit_judge.py:258-263`, `780-782`) but return structured output only — `VllmThinkingBackend` reads `usage` from the HTTP response (`packages/pipeline/src/pipeline/model_backends.py:330-340`) and does not surface it to whisker. Impact: decode-bound optimization (output-token caps, `00-baseline.md:92-93`) cannot be validated per call class without plumbing usage out of the backend or re-parsing debug transcripts.

- [MED] **olmOCR worker utilization is log-only state counts, not persisted utilization metrics.** `WorkerTracker.track_work(worker_id, item, "started"|"finished"|"errored")` per page task (`olmocr/pipeline.py:293-374`); `get_status_table()` rendered in the 10 s reporter (`olmocr/metrics.py:118-168`, `olmocr/pipeline.py:988-989`). **Our equivalent:** paper-level `asyncio.Semaphore(concurrency)` with up to 32 papers in flight (`packages/whisker/src/whisker/tapetum_llm/cli.py:1097-1112`, `1369`) but serial calls within each paper (`00-baseline.md:36-42`); no worker-state table. Impact: dual-pod / LJF scheduling levers need per-paper `paper_wall_ms` and in-paper phase breakdown to prove slot utilization improved.

- [MED] **olmOCR post-run `print_stats` is an offline S3 aggregator; no wandb.** `print_stats` scans completed JSONL outputs for docs/pages/input_tokens/output_tokens/fallback_pages/long-context splits and projects totals (`olmocr/pipeline.py:1105-1136+`). Console reporting is logger-only (`olmocr/pipeline.py:1476-1520`); no `wandb` import in `pipeline.py` or `metrics.py` (source search on `main` branch). **Our equivalent:** `report-merged.md/json` recomputes fusion verdicts from sidecars (`packages/whisker/src/whisker/tapetum_llm/cli.py:798-838`) — verdict counts, not timing aggregates.

- [LOW] **Minimal whisker instrumentation design (no new deps, whisker-only, CLAUDE.md-safe).** (1) Extend `run_judge_task` (`packages/whisker/src/whisker/tapetum_llm/judge_task.py:52-74`) with optional `timings: list[dict]` sink: record `{label, call_class, wall_ms, t_start_iso}` around `agent.run` using `time.monotonic()` — same pattern as `readback._ask_pod` (`packages/whisker/src/whisker/tapetum_llm/readback.py:281-310`). Derive `call_class` from label prefix (`monolith`, `metadata_outline`, `unit_check`, `page_escalation`, `ideal_verify`). (2) Append `call_timings[]` + `paper_wall_ms` + phase markers from existing `_set_progress` (`packages/whisker/src/whisker/tapetum_llm/pdf_judge.py:128-131`, `601-996`) into `to_sidecar_dict()` — **exclude `call_timings` from fingerprint hash** (`packages/whisker/src/whisker/tapetum_llm/cli.py:625+`) so observability never invalidates incremental skip. (3) After batch `asyncio.gather`, write `whisker/llm/run-manifest.json`: `{run_id, wall_s, concurrency, papers_evaluated, calls_by_class, sum_wall_ms_by_class, retries, skipped}` aggregated from sidecars. (4) Phase 2 (needs pipeline approval): return `{prompt_tokens, completion_tokens, finish_reason}` from `ModelBackend.run` so `decode_ms ≈ wall_ms - prompt_tokens/4000*1000` when queue-wait is negligible. Impact: makes every future lever report Δwall by class on the **3003 s** baseline with **quality-stability** checks unchanged (`00-baseline.md:77-78`); estimated implementation **<80 LOC** in whisker, zero runtime cost beyond monotonic reads.

## False-pass hypothesis

Logging only `wall_ms` without `prompt_tokens`/`completion_tokens` would mark a BPE-corruption retry path (attempt 1 fails fast, attempt 2 succeeds, `00-baseline.md:60-61`) as two "fast" calls and hide that the first attempt wasted a server slot — falsely crediting a concurrency increase that actually increased retry churn.

## False-fail hypothesis

Including `call_timings` in the sidecar fingerprint would change timing arrays on every rerun (network jitter) and force full re-judge of all 381 papers, appearing as a regression in incremental skip rate even when verdicts are identical — a false "optimization broke caching" signal.

## What would change my mind

Finding per-call `duration_ms` or HTTP timing fields in olmOCR's persisted Dolma/JSONL output (not just log-scraped `MetricsKeeper` counters) — current `PageResult` and metadata carry tokens and fallback flags only (`olmocr/pipeline.py:95-103`, `628-630`), so olmOCR does not solve per-call latency persistence either; a whisker-only sink remains mandatory.
