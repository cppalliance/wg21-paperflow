# 122 - unstructured-Partition-Parallelism

**Verdict:** usable-with-conditions (+ unstructured's open-source `partition_*` pipeline has zero in-document multiprocessing; the only portable artifacts are deterministic page-keyed reassembly primitives, not a parallelism lever that moves the 3003 s cold fleet run)
**Confidence:** high

## Findings

- [CRITICAL] The `partition/` tree has **no ProcessPool, ThreadPool, asyncio.gather, or executor.map**. A full sweep of `unstructured/partition/**/*.py` and `scripts/` finds no worker-pool dispatch in the partition pipeline; the only `ProcessPoolExecutor` in the library lives in the **metrics batch evaluator**, not partition (`metrics/evaluate.py:171`, `metrics/evaluate.py:184`). Impact: **~0 s** on the 3003 s cold run from copying unstructured partition parallelism (there is none). Quality risk: n/a.

- [CRITICAL] **Unit of work inside `partition_pdf` is the page, processed serially.** Fast path: `_process_pdfminer_pages` iterates `open_pdfminer_pages_generator(...)` in a single `for` loop with `starting_page_number` offset (`pdf.py:495-497`, `pdf.py:491`). OCR-only path: `convert_pdf_to_images(...)` yields pages one-by-one and each page is OCR'd in a serial `for page_number, image in enumerate(...)` loop (`pdf.py:1167-1179`). Hi-res OCR supplement: serial `for i, image_path in enumerate(image_paths)` (`ocr.py:185-199`). Impact: unstructured confirms our current tapetum shape (serial within document) is industry-default for deterministic doc pipelines; in-paper parallel unit checks would be **our** innovation, not theirs. Per-paper depth saving only if we parallelize (~4× ~20 s ≈ **60–80 s** on median 6-call papers per `00-baseline.md:36-42`), fleet wall unchanged (~2284 calls / 16 slots). Quality risk: MEDIUM if we parallelize without their reassembly discipline.

- [HIGH] **`convert_pdf_to_images` page "chunking" is memory streaming, not parallel dispatch.** Default `chunk_size=10` renders pages 1–10, then 11–20, etc., via `pdf2image` `first_page`/`last_page`, yielding images sequentially (`pdf_image_utils.py:396-429`). Comment at `pdf_image_utils.py:402` explicitly describes small page batches for conversion, not worker fan-out. Impact: **0 s** fleet saving; do not confuse with olmOCR-style concurrent page submission (`05-web.md` Q2). Quality risk: n/a.

- [HIGH] **External PDF fragment parallelism is a caller-side contract via `starting_page_number`, not an in-repo scheduler.** `partition_pdf(..., starting_page_number=1)` and `partition(...)` document that the first page of the input gets that metadata page number, "especially useful when partitioning a document that is part of a larger document" (`pdf.py:143`, `auto.py:135-138`). Each worker would partition a page-range slice with distinct `starting_page_number`, then merge element lists. Impact: pattern is portable for **page-scoped judge shards** (split source PDF, run unit checks on page subsets) but tapetum already scopes checks by page while sending full markdown; sharding the PDF does not cut the ~6× full-markdown prefill (`00-baseline.md:43-47`). Fleet saving **~0 s** without payload scoping. Quality risk: LOW for merge if page metadata honored.

- [HIGH] **Deterministic reassembly under hypothetical parallel fragments uses page number + within-page sequence, not completion order.** (1) Per-page element sort: `_partition_pdf_with_pdfparser` runs `sort_page_elements(..., SORT_MODE_BASIC)` first "for deterministic order across python versions", then optional XY-cut (`pdf.py:1118-1125`, `sorting.py:99-187`). (2) Cross-page concat preserves page-list order (`pdf.py:1118-1125`). (3) Layout merge zips inferred and extracted pages by index (`pdfminer_processing.py:782-784`), then sorts merged regions (`pdfminer_processing.py:809`). (4) Hash IDs incorporate `page_number` and per-page sequence counter so parallel fragments produce stable element IDs (`metadata.py:287-305`, `elements.py:789-800`). (5) Analysis dump reassembly: `sorted(extracted_pages, key=lambda x: x["number"])` (`layout_dump.py:166-180`). Impact: **required** if tapetum enables in-paper parallel unit checks (persona-20): attach findings by `(page_number, unit_id)`, merge in sorted page order. Quality risk: HIGH without this (wrong-page findings silently dropped).

- [MED] **Document-level parallelism exists only outside partition: metrics eval and ingest CLI, both keyed on whole files.** Metrics: `ProcessPoolExecutor(max_workers=int(os.environ.get("MAX_PROCESSES", os.cpu_count())))` + `executor.map(...)` over document paths (`metrics/evaluate.py:163-165`, `metrics/evaluate.py:184`); `executor.map` preserves submission order. Ingest test harness: `--num-processes "$max_processes"` where `max_processes=${MAX_PROCESSES:=$(python3 -c "import os; print(os.cpu_count())")}` (`test_unstructured_ingest/src/against-api.sh:16`, `test_unstructured_ingest/src/against-api.sh:41`). Impact: we already exceed this with `_DEFAULT_CONCURRENCY = 32` cross-paper asyncio (`cli.py:125`, `00-baseline.md:34-35`); copying unstructured ingest defaults adds **~0 s** and risks oversubscribing the 16-slot MoE pod. Quality risk: timeout-driven false review if combined with in-paper fan-out.

- [MED] **Whisper STT path documents the GIL ceiling and recommends process workers for true audio parallelism, but does not implement them.** Docstring: "For true parallelism, use process-based concurrency (e.g. ``multiprocessing`` or separate worker processes)" (`whisper_stt.py:22-23`). Impact: confirms unstructured defers CPU-bound parallelism to the **caller**; same applies to tapetum advisory HTTP fan-out. Quality risk: n/a.

- [LOW] **`pdf_hi_res_max_pages` is a serial guardrail, not a batching knob.** Raises when page count exceeds limit before hi-res inference (`pdf.py:604-614`, `pdf.py:847-848`). Impact: analogous to our `MAX_UNIT_CHECKS=5` cap; no speedup lever. Quality risk: n/a.

## False-pass hypothesis

Adopting unstructured's **document-level** `ProcessPoolExecutor` pattern (`metrics/evaluate.py:184`) on top of existing 32-paper asyncio without reducing cross-paper concurrency: peak in-flight requests exceed 16 vLLM slots, several unit checks time out and return empty defect groups, merge treats cap-skip as coverage-complete, and a paper with a real table swap gets advisory pass (`unit_judge.py:419-423`, `00-baseline.md:26-27`).

## False-fail hypothesis

Parallel in-paper unit checks merged in asyncio completion order instead of unstructured's page-keyed sort (`pdf.py:1118-1125`, `layout_dump.py:180`): a hallucinated finding from a fast-completing check on page 7 attaches before a zero-defect result on page 3, operator attention bias triggers review on a clean paper that serial execution would pass.

## What would change my mind

A version of unstructured (or unstructured-ingest source in `research/repos/`) shipping an in-process page-level ProcessPool inside `partition_pdf` or `_partition_pdf_or_image_with_ocr`, with measured speedup and fingerprint-stable element output vs serial, would flip partition parallelism from "absent" to "directly portable."
