# 105 - vLLM-Dense-Judge-Throughput

**Verdict:** usable-with-conditions — heterogeneous offload (1510 scoped unit checks → `h200-qwen3-32b`, 758 monolith+metadata → MoE @16 slots) is architecturally valid and model-sovereign, but vLLM clone data show MoE remains the fleet bottleneck (~620–710 s) unless paired with AGGRESSIVE call cuts + prompt reorder; dense `max-num-seqs 64` is KV-feasible only with FP8 KV and ~10–12k scoped inputs, not at full 131k per request.
**Confidence:** medium

## Findings

- [CRITICAL] **vLLM clone has no H200 serve benchmark for Qwen3-32B @131k; MoE @16 is anchored externally.** Clone evidence: `Qwen/Qwen3-32B` is listed as supported (`research/repos/vllm/docs/models/hardware_supported_models/xpu.md:23`); `--max-model-len 131072` is documented for Qwen context extension (`research/repos/vllm/docs/features/context_extension.md:26-28`); `h200-qwen3-32b` declares `max_context_window = 131072` (`SERVICES.toml:129-134`). **No** `docs/benchmarks/` or CI card quotes Qwen3-32B output tok/s on H200. MoE anchors (not in clone): DeepSeek-V4-Pro recipe defaults `--max-num-seqs 16`, `--max-num-batched-tokens 16384`, `--kv-cache-dtype fp8` ([recipes.vllm.ai/deepseek-ai/DeepSeek-V4-Pro](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4-Pro), `05-web.md:13-17`); PR #43447 trace replay at **concurrency 16**: server output **44→196 tok/s**, per-user decode **6→19 tok/s**, ITL p50 **155→54 ms** ([PR #43447](https://github.com/vllm-project/vllm/pull/43447), `05-web.md:8-11`). Baseline measured MoE solo decode **~70 tok/s** (`packages/whisker/src/whisker/tapetum_llm/pdf_judge.py:27-28`), **~20 s/call** at **16 slots** (`00-baseline.md:24-25`). Impact: dense-vs-MoE ratio must be inferred from class + external Qwen3-32B prefix benchmark, not clone serve tables. Quality risk: none for arithmetic; **HIGH** if dense swap ships without A/B (below).

- [CRITICAL] **Quality gate: different judge on unit checks = new lane semantics; forbidden without full-fleet revalidation.** Census: **1510** unit checks vs **758** MoE-resident calls (381 monolith + 377 metadata/outline, `00-baseline.md:22-23`). Only **16/381** papers had LLM findings change merged verdict (`00-baseline.md:29-30`); SLMJury quick-verdict models lose **up to 23%** on general tasks (`05-web.md:88-90`). Required before `_LANE_VERSION` bump (`cli.py:99-117`): **381/381** fused verdict parity + matching `defect_groups` / `evidence_dispositions` on all verdict-changing papers; MoE fallback for **8/381** oversize unit payloads (`23-small-judge-evaluator.md:10`). Measured MoE A/A flip **≥25%** (`packages/whisker/src/whisker/CLAUDE.md` advisory section). Impact: **6–10 weeks** validation (`48-combined-lever-modeler.md:238-243`); shipping dense judge silently breaks "same quality" claim. Quality risk: **CRITICAL**.

- [HIGH] **KV math caps realistic dense slots at ~32–48 (not 64+) for 10–15k scoped unit checks unless FP8 KV + shorter scope.** Assumptions: Qwen3-32B dense, **1×H200** (141 GiB), `--max-model-len 131072` (`SERVICES.toml:133-134`); scoped payload **10–15k tokens** after client payload scoping (not yet landed; today unit checks send **full** `candidate_md`, `unit_judge.py:769-776`, `00-baseline.md:43-44`); output **~250 tok** typical (70% zero-defect, `00-baseline.md:29`), cap **1536** (`cli.py:1030-1034`). KV estimate (GQA): **~256 KiB/token** BF16 (64 layers × 8 KV heads × 128 dim × 2 × 2 bytes). At **12k tokens/req**: **~3.1 GiB/seq**; **~70 GiB** post-weight headroom → **~22 concurrent seqs** BF16 KV. `--kv-cache-dtype fp8` halves KV (`05-web.md:23-27`, vLLM FP8 KV blog cited in `40-server-flag-auditor.md:51`) → **~44 seqs**. vLLM warns that exceeding KV budget triggers preemption/recompute (`research/repos/vllm/docs/configuration/optimization.md:29-35`). **`--max-num-seqs 64`** is feasible only with **FP8 KV + ~8–10k** effective scoped length (or accepts preemption). vLLM `parallelism_scaling.md:15-18` reports startup `Maximum concurrency for N tokens per request` from KV size; operator must read pod boot log for ground truth. Impact: plan **S=32–48** for dense pod, not Docling-style **512** (`57-docling-anti-steelman.md:22`). Quality risk: preemption adds latency variance, not verdict drift.

- [HIGH] **Dense throughput class: higher `max-num-seqs` is the lever MoE cannot use; external Qwen3-32B anchor ~1.5–3.5× MoE loaded decode.** MoE: raising `--max-num-seqs` **16→32** measured **+57–60% wall** on our pod (`00-baseline.md:82-83`, `research/slots-32-regression/SYNTHESIS.md:8-14`); vLLM docs note `max-num-seqs` impacts output-token performance (`research/repos/vllm/docs/getting_started/installation/cpu.md:307-307`). Dense 32B on one GPU: vLLM recommends **`max_num_batched_tokens > 8192`** for smaller models on large GPUs (`research/repos/vllm/docs/configuration/optimization.md:66-66`). External (not clone): Qwen3-32B prefix-heavy benchmark **427→1513 tok/s** aggregate output with APC (**+254%**, ~50% hit rate) ([Jarvis Labs blog](https://jarvislabs.ai/blog/vllm-optimization-techniques), `05-web.md:70-73`, `05c-web-prefix-guided.md:31`); APC **does not reduce decode time** (`research/repos/vllm/docs/features/automatic_prefix_caching.md:25-25`). Loaded MoE per-user decode **19 tok/s** at c=16 post-APC (`05-web.md:10-10`) vs solo **70 tok/s** (`pdf_judge.py:27-28`) → **3.7×** continuous-batch penalty. Conservative dense unit-check **L=8–12 s** at **S=32–48** (2× baseline **20 s** at S=16, consistent with `00-baseline.md:69-71`, persona 23 proportional model). Impact: dense pod wall **315–566 s** for **1510** scoped checks (table below). Quality risk: same as CRITICAL gate.

- [HIGH] **Two-pod heterogeneous fleet wall = max(dense, MoE); MoE monolith+metadata dominates at ~620–710 s without call elimination.** Model: `wall_pod = Σ(L_i × N_i) / S` (same slot formula as `00-baseline.md:25`, `48-combined-lever-modeler.md:19-31`). **MoE pod** (758 calls, **S=16**, no unit-check queue contention): assume **L_mono=18–20 s**, **L_meta=8–10 s** (metadata payload bounded, `unit_judge.py:241-256`) → **T_moe = (381×19 + 377×9)/16 ≈ 664 s** (range **617–712 s** if L_mono=18–22). **Dense pod** (1510 unit checks, scoped 10–15k):

| S_dense | L_unit (assumed) | T_dense = 1510×L/S |
|--------:|-----------------:|-------------------:|
| 32 | 12 s | **566 s** |
| 48 | 10 s | **315 s** |
| 64 | 8 s | **189 s** (needs FP8 KV + ~8k scope) |

**Fleet wall (parallel pods):** `max(T_dense, T_moe) ≈ **620–710 s** (10–12 min)** — **MoE-bound**, not sum. Baseline single-pod **3003 s** (`00-baseline.md:17-18`). Savings vs baseline from offload alone: **~2300 s** (~38 min), but **misses 5–10 min target** (`00-baseline.md:3-4`). AGGRESSIVE router (−190 calls → **473** unit checks, `48-combined-lever-modeler.md:200-202`) drops dense term to **~99–178 s**, leaving **MoE still limiting at ~620 s**. Impact: dense offload is **necessary but insufficient** for ≤600 s; needs router + prefix reorder + verdict-first stack (`48-combined-lever-modeler.md:191-254`). Quality risk: router FN (`11-combo-safe-router`) independent of dense gate.

- [MED] **Payload scoping is a prerequisite for both S≥32 and the 10–15k token assumption.** Today p50 markdown **~8500 tok** but p95 **~134k chars** (~50k tok) breaks 131k pods (`23-small-judge-evaluator.md:10`); scoping to page packet + headings (not full `candidate_md`) is assumed by AGGRESSIVE arithmetic but **not implemented** (`00-baseline.md:94`, `unit_judge.py:769-776`). Without scoping: dense pod reverts toward **L≈20 s**, **S≤16** (KV-saturated) → **T_dense ≈ 1888 s**, worse than MoE isolation benefit. Impact: scoping lands → dense row of table; scoping absent → offload **negative EV**. Quality risk: truncated evidence → false-clear (persona 72).

- [MED] **MoE pod still benefits from recipe flags (MBT/APC/MTP) on the 758-call queue; dense pod needs separate tuning.** MoE recipe: `--max-num-seqs 16` fixed (`40-server-flag-auditor.md:50-50`, `00-baseline.md:82-83`); server-only envelope **~300–550 s** on full **2284**-call fleet (`40-server-flag-auditor.md:81-81`). On **758** calls only: proportional **~100–180 s** if applied, but monolith prefills remain APC-poor until client reorder (`102-vllm-anti-steelman.md:8-10`). Dense pod launch (proposed delta): `--max-model-len 131072`, `--max-num-seqs 48`, `--max-num-batched-tokens 16384`, `--kv-cache-dtype fp8`, `--enable-prefix-caching` (unit checks share ~3.7k system prefix per call type after guard-tag fix, `00-baseline.md:48-52`), `--long-prefill-token-threshold 8192` (`research/repos/vllm/docs/configuration/optimization.md:62-66`). Impact: **+100–250 s** incremental on MoE leg; dense leg gains from APC on repeated system+scoped-doc prefix within a paper. Quality risk: APC + non-batch-invariant MoE (`MODELS.md:69-70`) — scheduling only on MoE; dense swap is semantic.

- [LOW] **Clone benchmark tooling confirms measurement method, not our model points.** `vllm bench serve` reports **Output token throughput (tok/s)** (`research/repos/vllm/docs/benchmarking/cli.md:96-98`); dashboard compares **Output Tput @ Both (tok/s)** vs concurrency (`research/repos/vllm/docs/benchmarking/dashboard.md:67-97`); `benchmark_long_document_qa_throughput.py` defaults **20k-token documents** (`research/repos/vllm/benchmarks/benchmark_long_document_qa_throughput.py:7-20`) — workload shape unlike unit checks. Recommended validation: `vllm bench serve` on `h200-qwen3-32b` with **input 12k / output 256**, **max-concurrency sweep 16–64**, and same on `alliance-pod` at **16**. Impact: replaces inferred **L** with measured **L** (±15% fleet uncertainty). Quality risk: none.

## False-pass hypothesis

Deploy `h200-qwen3-32b` at `--max-num-seqs 64` without FP8 KV or payload scoping: KV preemption storm (`optimization.md:33-34`) inflates unit-check latency to **≥20 s**, dense pod wall **≥470 s** with **no** MoE queue relief, while operators attribute success to "dense 2×" from Jarvis prefix-heavy numbers (`05-web.md:70-73`) that do not match short JSON decode — fleet stays **>15 min** but dashboards show "64 slots provisioned."

## False-fail hypothesis

Reject dense offload because clone lacks Qwen3-32B cards: measured MoE **19 tok/s** loaded decode (`05-web.md:10`) vs inferred dense **35–50 tok/s** at **S=48** still saves **~700–1100 s** on the **1510**-call leg even when MoE-bound; abandoning the second pod leaves **1510×20/16 ≈ 1888 s** of unit-check work competing with monolith on one MoE queue — **worse** wall than heterogeneous **max()** layout.

## What would change my mind

Instrumented cold run with dual routing: (1) `vllm bench serve` sweeps on **`h200-qwen3-32b`** and **`alliance-pod`** at production prompt shapes (12k/256 and 40k/900); (2) fleet run with **1510** unit checks → dense, **758** → MoE, logging per-call `{pod, cached_tokens, latency}`; (3) persona-47 **381/381** verdict parity. If measured **L_unit ≤10 s** at **S=48** with stable KV (no preemption warnings) **and** **T_moe ≤550 s**, upgrade confidence to **high** and treat dense offload as sufficient for AGGRESSIVE **MoE ≤600 s** when combined with router call cuts.
