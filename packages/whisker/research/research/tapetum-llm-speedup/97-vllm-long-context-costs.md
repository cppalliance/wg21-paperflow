# 97 - vLLM Long-Context Costs

**Verdict:** usable-with-conditions — vLLM reserves one shared paged KV block pool (not per-sequence tensors); our 16-slot cap is a MoE scheduler/recipe choice, not KV exhaustion at median ~10–40k prompts; lowering `--max-model-len` to 131k fits the paper corpus and frees APC block headroom but saves ~0 s fleet wall unless combined with prefix-cache prompt reorder (persona 15).
**Confidence:** high

## Findings

- [CRITICAL] **Startup RESERVES a single shared block pool; runtime ALLOCATES blocks on demand from that pool.** Evidence: pool sizing `num_blocks = available_memory // block_stride` after `profile_run` activation peak (`kv_cache_utils.py:1309-1337`, `_get_kv_cache_config_packed`); blocks are not pre-bound to sequences — `get_num_blocks_to_allocate` computes `cdiv(num_tokens, block_size)` minus already-held blocks (`single_type_kv_cache_manager.py:135-191`); design doc: one memory pool split into equal pages, managers allocate different counts per layer type (`docs/design/hybrid_kv_cache_manager.md:43-47`). Impact: **0 s** from "KV reservation waste" at median prompts — unused pool blocks sit idle, not pinned per slot. Quality risk: none.

- [CRITICAL] **Startup admission uses worst-case `max_model_len`; runtime uses actual token count (+ watermark for waiting queue).** Evidence: startup `check_enough_kv_cache_memory` requires pool ≥ one request at `max_model_len` (`kv_cache_utils.py:854-878`); logged `Maximum concurrency for {max_model_len} tokens per request: X` = `num_blocks / sum(cdiv(max_memory_usage_bytes, page_size))` (`kv_cache_utils.py:937-959`, `2151-2163`); `FullAttentionSpec.max_memory_usage_bytes` = `cdiv(max_model_len, block_size) * page_size_bytes` (`kv_cache_interface.py:258-263`); runtime `allocate_slots` calls `get_num_blocks_to_allocate(request, num_tokens=actual)` with optional `full_sequence_must_fit` gate (`kv_cache_manager.py:468-520`); watermark `int(watermark * num_blocks)` applied only to WAITING/PREEMPTED admissions when other reqs already scheduled (`kv_cache_manager.py:168-171`, `459-466`, `482`). Impact: **393216 `max_model_len` inflates startup sizing and activation profiling**, shrinking the block pool vs a 131k cap, but does **not** make each median request hold 393k blocks. Quality risk: none from understanding; lowering cap risks rejecting outliers above new cap.

- [CRITICAL] **DeepSeek V4 MLA compresses KV to 584 B/token (fp8_ds_mla), not standard MHA 2×heads×dim.** Evidence: `MLAAttentionSpec.real_page_size_bytes` for `deepseek_v4` + `fp8_ds_mla`: `storage_block_size * 584` where 584 = 448B NoPE + 128B RoPE + 8B scale (`kv_cache_interface.py:397-403`); `DeepseekV4FlashMLABackend.get_kv_cache_shape` returns `(num_blocks, block_size, 584)` (`sparse_mla.py:96-106`); Triton insert kernel documents per-token layout 448 fp8 + 128 bf16 + 8 scales = 576B data + alignment (`cache_utils.py:57-63`); `SlidingWindowMLASpec` uses same 584B/token for compressor-state cache (`kv_cache_interface.py:628-633`); hybrid layer mix: `MLAAttentionSpec` for compressed main KV (`attention.py:606-625`), `SlidingWindowMLASpec` for compressor with `sliding_window = (1+overlap)*compress_ratio` and tiny block_size 4 or 8 (`compressor.py:170-200`). Impact: V4 KV is **~8× smaller than V3.2 MLA** at long context (cross-check `research/slots-32-regression/10-kv-preemption.md:19-35`); classic "656 B/token × 61 layers" math **overstates** our pod pressure. Quality risk: none.

- [HIGH] **Median prompt (~10k tok candidate md, ~40k tok full monolith call) costs ~157 logical blocks per full-attention group, ~0.2–0.5 GiB/seq total — not 393k blocks.** Evidence: P50 candidate **34336 chars ≈ 8584 tok** (`13-payload-scoper.md:12`); monolith adds full PDF text → ~40k tok plausible for largest routine call (`02-prompt-token-auditor.md:16`); runtime blocks for full-attention MLA: `cdiv(num_tokens, 256)` with kernel block_size 256 (`sparse_mla.py:52-54`, `single_type_kv_cache_manager.py:169`); at 40k tokens → **157 blocks** per 256-token group; SWA/compressor groups capped by `max_admission_blocks_per_request` = `cdiv(min(sliding_window-1+max_in_flight_tokens, max_model_len), block_size)+1` (`kv_cache_interface.py:567-588`, `single_type_kv_cache_manager.py:1807-1816`) — for C128 compressor `sliding_window=128`, block_size=8 → **≤18 blocks** regardless of 40k prompt length. Analytic V4 total at 40k native tokens ≈ **0.22 GiB/seq** (scale from `10-kv-preemption.md:27-37` at 100k → 0.47 GiB). Impact: 16 concurrent median requests ≈ **3.5 GiB peak KV** vs **~120–200 GiB pool** (`10-kv-preemption.md:14-17`) — **30–50× headroom**. Quality risk: none.

- [HIGH] **`--max-num-seqs 16` is configured (recipe + MoE stability), not memory-bound — raising slots without co-tune regressed wall +57%.** Evidence: scheduler hard cap `max_num_running_reqs = scheduler_config.max_num_seqs` (`scheduler.py:109`); official recipe default 16 (`05-web.md:15-16`); vLLM MoE community guidance 4–8, our 16 already aggressive (`00-baseline.md:82-83`, `10-kv-preemption.md:74-75`); measured 16→32 slots: **692→1090 s (+57%)** with KV usage still **<40%** (`00-baseline.md:82-83`, `10-kv-preemption.md:70-72`); `max_num_seqs` is scheduler batch cap, **not** a KV reservation multiplier (`10-kv-preemption.md:58`, `kv_cache_utils.py:937-959`). Impact: **Do not raise slots for KV headroom** — expect MoE decode slowdown, not throughput gain. Quality risk: **HIGH** (MoE batch-composition variance, `MODELS.md:77-78`).

- [HIGH] **Lowering `--max-model-len` 393216 → 131072 fits every routine paper and frees KV pool + APC blocks; alone saves ~0 s on 3003 s cold run.** Evidence: corpus P50 **8584 tok**, P90 **~35k tok**, P95 **~55k tok**, max outlier **~1.2M tok** chars (`13-payload-scoper.md:12`) — 131k covers **>99%** of fleet; 131k is **33%** of 393k so `FullAttentionSpec.max_memory_usage_bytes` drops ~3× in startup concurrency formula (`kv_cache_interface.py:258-263`, `kv_cache_utils.py:937-959`); lower activation peak at profile increases `available_memory` for block pool (`kv_cache_utils.py:1309-1321`, `10-kv-preemption.md:54-60`); FP8 APC blocks compete for same pool — halved per-request worst-case reservation ≈ **2–3× more prefix blocks** storable (`39-kv-quant-scout.md:16`, persona 15). Impact: **0–50 s** server-only unless APC hit rate rises; **600–1100 s** only with client prompt reorder + retention (`15-prefix-cache-enabler.md`, `05-web.md:6-12`). Quality risk: **LOW** at 131k for fleet; **HIGH** if operators need >131k outlier papers without fallback pod.

- [MED] **SWA/compressor layers recycle blocks; only full-attention MLA groups grow linearly with prompt length.** Evidence: `SlidingWindowManager` sets `max_admission_blocks_per_request` from spec method — single source of truth for startup pool sizer and runtime gate (`single_type_kv_cache_manager.py:1801-1816`, `kv_cache_interface.py:572-576`); `remove_skipped_blocks` frees tokens outside sliding window before each allocate (`kv_cache_manager.py:491-504`, `kv_cache_interface.py:575-576`); DeepSeek V4 layers with `compress_ratio<=1` use separate SWA cache, not main MLA table (`attention.py:606-610`). Impact: long-prompt KV cost dominated by **~30 c4a + 31 c128a full-attention groups**, not 128-token SWA. Quality risk: none.

- [LOW] **Default watermark=0.0 means no extra block headroom unless operator sets `--watermark`.** Evidence: `KVCacheManager.__init__` default `watermark: float = 0.0` → `watermark_blocks = int(watermark * num_blocks)` (`kv_cache_manager.py:132`, `168-171`); applied only when admitting WAITING/PREEMPTED with other reqs scheduled (`kv_cache_manager.py:459-466`). Impact: admission is exact block count, not conservative padding, at default. Quality risk: none.

## False-pass hypothesis

Operator raises `--max-num-seqs` to 24–32 believing vLLM startup log shows KV headroom for 40k-token judge prompts: MoE expert-union decode cost dominates (+57% measured at 32), wall time rises, verdict drift from batch non-invariance increases, while KV utilization stays under 15% — falsely attributing slowness to "need more KV tuning" instead of MoE batch cap.

## False-fail hypothesis

Operator drops `--max-model-len` to 65536 to maximize APC pool: P90 papers (~35k tok candidate + PDF source in monolith) approach cap during chunked prefill + decode growth, requests fail `full_sequence_must_fit` admission (`kv_cache_manager.py:468-484`) or truncate, and rare long papers error — falsely concluding "our papers need 393k" when P95 fits 131k and only tail outliers need a separate long-context route.

## What would change my mind

Live pod capture during 381-paper fleet showing **`vllm:kv_cache_usage_perc` sustained >70%** OR startup line **`Maximum concurrency for 393,216 tokens per request: X` with X < 16**, plus rising `total_cumulative_preemption_cnt` in logs (`kv_cache_manager.py:459-466`, `10-kv-preemption.md:78-82`) — that would flip "configured not memory-bound" and make slot reduction or `max_model_len` cut a primary wall-clock lever.
