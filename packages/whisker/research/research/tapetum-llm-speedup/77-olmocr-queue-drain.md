# 77 - olmocr-Queue-Drain-Pattern

**Verdict:** usable-with-conditions — olmOCR's work-item TaskGroup drain confirms our paper-level completion gate is the right isolation unit, but their 1600-deep server queue and within-item page flood are not portable through RunPod's ~100 s proxy with 16 MoE slots.
**Confidence:** high

## Findings

- [CRITICAL] **Drain-before-next-item is enforced by nested `asyncio.TaskGroup` await, not by polling pending count.** Evidence: `worker()` takes one `WorkItem`, wraps every path in a TaskGroup (`olmocr/pipeline.py:697-707`), logs `Finished TaskGroup` only after all PDF/tarball tasks complete (`707`), then `mark_done` and loops (`788`, `687`). Within each PDF, `process_single_pdf` submits all pages in a second TaskGroup and blocks on `[task.result() for task in page_tasks]` (`538-544`). Impact: **0 s direct saving** from copying the pattern (we already drain per paper before sidecar write, `cli.py:1120-1238`); validates that cross-paper prefetch beyond completion is unnecessary. Quality risk: none from keeping drain semantics.

- [CRITICAL] **`vllm_queued_requests == 0` is a retry accelerator, not the main queue-drain gate.** Evidence: global `vllm_queued_requests` parsed from vLLM stderr `Waiting|Pending: (\d+)` (`861-865`); used only when non-rotation retries remain: `if remaining_attempts and vllm_queued_requests == 0:` fires parallel retry tasks (`337-357`). Main concurrency bound is `max_concurrent_requests_limit = BoundedSemaphore(args.max_concurrent_requests)` default **1600** (`88`, `1202`, `1267`), acquired per HTTP POST in `try_single_page` (`181`). Impact: misreading the pending check as olmOCR's primary scheduler would suggest we should poll server queue before next paper — **wrong**; our paper sem already provides the analogue. Quality risk: none.

- [HIGH] **Work items are ~500 pages (50 on remote API), bounding blast radius and memory per drain cycle.** Evidence: `--pages_per_group` default 500, lowered to 50 when `--api_key` set because "not to overwhelm such servers / not to waste money if a group doesn't finish" (`1290-1293`, `1198`); `items_per_group = max(1, int(pages_per_group / avg_pages_per_pdf))` (`1382-1386`). `--workers 20` each hold one work item until TaskGroup exit (`684-791`, `1435-1437`). Impact: olmOCR keeps the **server** queue deep (up to 1600 HTTP) but **cross-item** queue shallow (20 workers × one item). Our analogue is **381 papers × 6 serial calls** with client cap 32 — we keep the **client/proxy** queue shallow instead. Porting olmOCR's 1600 cap without TCP/direct bypass projects **524 tail on RunPod** (`research/concurrency-381/12-runpod-proxy.md:9-13`, `27-http-client-tuner.md:16`). Quality risk: HIGH if deep queue causes proxy drops → error tombstones, partial coverage.

- [HIGH] **Why drain: failure isolation and atomic document assembly, not prefix-cache locality.** Evidence: TaskGroup on pages — "if there is an exception propagated to this point in any page, it will abort the PDF itself" (`543-544`); `max_page_error_rate` discards whole document if fallback pages exceed 0.4% (`549-553`); `build_dolma_document` requires all `page_results` (`590-639`). Page prompts share static YAML template text (`137`) but each carries a **unique page image** — no shared long document prefix like our `candidate_md` resends. Impact: olmOCR's drain rationale does **not** support flooding our unit-check calls for APC; our prefix-cache lever is guard-tag placement + payload scoping (`00-baseline.md:48-49`), not work-item batching. Quality risk: none from this insight alone.

- [HIGH] **olmOCR avoids httpx pooling entirely; connection-per-request with `Connection: close`.** Evidence: custom `apost()` using raw `asyncio.open_connection`, comment that httpx/aiohttp deadlock at "100M+ requests" scale (`371-374`, `407`, `463-468`). Impact: explains why they tolerate 1600 "concurrent requests" without pool-cap drama — each page opens/closes a socket. Our OpenAI SDK path creates fresh `AsyncOpenAI` per call (`27-http-client-tuner.md:10`); **TLS churn ≈0.3–1% wall**, not the 50 min gap. Quality risk: none.

- [MED] **Memory bounds: PDF render semaphores separate from HTTP semaphores.** Evidence: `pdf_render_max_workers_limit` from CPU count (`87`), acquired in `build_page_query` (`109`); HTTP sem in `try_single_page` (`181`). Worker holds temp PDF paths and all in-flight page tasks until TaskGroup exit (`508-562`, `697-707`). Impact: our paper-level sem bounds `(md + pdf_text + page_units) × 32` (`28-semaphore-topologist.md:20`); olmOCR-style within-paper parallel unit checks would multiply held strings by up to 5× — manageable at 32 papers, catastrophic at 381-at-once. Quality risk: LOW at 32, HIGH at unbounded prefetch.

- [MED] **Recommended optimal in-flight depth for tapetum on alliance-pod: keep 32 paper-level, hard-cap 32 simultaneous HTTP, do not adopt 1600.** Evidence: server `--max-num-seqs 16` (`00-baseline.md:66`); measured c=16→c=32 saves only **4.2%** (`28-semaphore-topologist.md:10`, `cli.py:127`); c=381 → **257/381 proxy errors** (`cli.py:130-131`, `12-runpod-proxy.md:37`). Steady-state: 32 papers × 1 serial call = **32 HTTP connections**, ~16 running + ~16 vLLM-queued ≈ **~20 s max queue wait** (one slot-time), under **~100 s** proxy TTFT ceiling. Split-semaphore variant (`28-semaphore-topologist.md:22`): **`call_sem=16`** (match server slots) + **`paper_sem=32`** (CPU overlap) — same ~4% class, lower tail 524 risk. **Concrete number: 32** fleet in-flight HTTP maximum; **16** if adding in-paper parallel unit checks without raising paper count (5×5=25 would exceed proxy-safe queue). Impact: raising beyond 32 saves **≤~30 s (~1%)** on 3003 s with **HIGH** 524 risk; lowering to 16 loses ~4% fill. Quality risk: LOW at 32; HIGH above 32 on HTTP proxy.

- [LOW] **olmOCR co-locates client and vLLM (localhost or Beaker bare metal); no Cloudflare hop.** Evidence: internal server `args.server = f"http://localhost:{args.port}/v1"` (`1410-1412`); Beaker job with 125GB RAM (`1072`). Impact: their deep-queue pattern assumes **no RunPod-style origin-response timeout** — directly explains the architecture split vs our shallow client queue. Quality risk: n/a.

## False-pass hypothesis

Adopting olmOCR's within-paper page flood for unit checks (5 parallel calls × 32 papers = up to 160 in-flight HTTP): tail requests sit >100 s in vLLM queue without SSE bytes, RunPod proxy returns 524, papers land in error tombstones with no sidecar — fleet wall time improves while **advisory coverage silently drops** on failed PIDs, masquerading as a speed win.

## False-fail hypothesis

Tightening paper concurrency from 32 to 16 to mimic olmOCR's "one work item per worker" ratio: measured +4.2% wall regression on prior A/B (`28-semaphore-topologist.md:10`) with no quality benefit — pure infrastructure slowdown, not a conversion false-fail.

## What would change my mind

A tapetum cold run at **paper_sem=32 + in-paper parallel unit checks capped by `call_sem=16`** on alliance-pod with per-request TTFT logs showing **zero 524s** and **>10% wall reduction** vs serial unit checks — would upgrade in-paper parallelism from "proxy-risky" to "olmOCR-analogue worth shipping."
