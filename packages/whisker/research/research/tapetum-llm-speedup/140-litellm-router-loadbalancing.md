# 140 - litellm-Router-LoadBalancing

**Verdict:** usable-with-conditions — ship persona 21 deterministic paper sharding as the default (reproducible assignment, serial-chain pod pinning, warm-fingerprint stability); add whisker-local least-busy **paper-start** assignment as an opt-in only when `alliance-pod` carries heavy external load, because a fixed 50/50 split wastes ~952 s (~33% wall) when one pod is half-occupied externally.
**Confidence:** high (LiteLLM strategy mechanics from source); medium (952 s utilization gap is modeled from 00-baseline slot math, not a measured 381-paper A/B)

## Findings

- [CRITICAL] **LiteLLM routes per-request, not per-document; tapetum must pin all calls in one paper to one pod.** `get_available_deployment` picks a deployment on every call after health/cooldown filters, then dispatches by strategy (`litellm/router.py:11046-11168`, `1151-1194`). Our lane runs monolith → metadata → serial page escalations → serial unit checks (`00-baseline.md:36-38`). Mid-chain cross-pod picks (LiteLLM default retry path) break prefix-cache locality (`05-web.md:69-77`) and add a second MoE batch-composition axis. Minimal rule: assign pod once at paper start; never reroute call 4 of 6. Impact: **0 s** from unsafe failover; **quality risk: MED-HIGH** if per-call least-busy is copied verbatim.

- [CRITICAL] **Deterministic 50/50 sharding loses most dual-pod benefit when alliance-pod is 50% externally occupied.** Persona 21 assigns `live_pods[index % len(live_pods)]` on sorted PIDs (~190/191 papers per pod, `21-dual-pod-sharder.md:8-10`). Baseline slot model: ~2284 calls × ~20 s / slots (`00-baseline.md:22-25`). Scenario: Pod A (`alliance-pod`) has 8/16 slots taken by other tenants; Pod B (`h200x8-deepseek-v4-pro`) has 16 free. Deterministic split: Pod A shard wall = (2284/2)×20/8 ≈ **2855 s**; Pod B ≈ **1428 s**; fleet wall = **max ≈ 2855 s** (near the 3003 s single-pod baseline). Capacity-optimal routing (8+16=24 free slots): 2284×20/24 ≈ **1903 s**. **Utilization loss vs optimal least-busy: +952 s (+50%)**; vs unconstrained dual-pod (~1600 s): **+1255 s, recovering only ~5% of the ~1.9× speedup**. Impact: deterministic sharding on a shared pod is a determinism tax, not a free 2×.

- [HIGH] **`least-busy` tracks in-flight requests per deployment id and picks the minimum.** On each API call, `log_pre_api_call` increments `{model_group}_request_count[id]`; success/failure decrements (`litellm/router_strategy/least_busy.py:24-46`, `160-188`). Selection walks all deployment ids and picks lowest count, ties broken by first-seen order (`least_busy.py:174-184`). External tenants on alliance-pod inflate the counter continuously, so new tapetum papers skew toward the idle pod without client-side knowledge of foreign load. Impact: modeled **2855 s → 1903 s** (~952 s saved) under the 50%-external-load scenario; **quality risk: MED** (paper→pod assignment becomes runtime-dependent across cold runs).

- [HIGH] **`simple-shuffle` is uniformly random (or rpm/tpm-weighted), not utilization-aware.** Default strategy uses `random.choices` / `random.choice` over healthy deployments (`litellm/router_strategy/simple_shuffle.py:59-68`). No in-flight or latency signal. For tapetum this violates quality-stability on reruns (MoE neighbor batches change every call) and ignores alliance-pod contention entirely. Impact: **negative** for determinism; **MED-HIGH** triage noise; **0 s** predictable savings vs persona 21.

- [HIGH] **`latency-based-routing` picks lowest rolling per-token latency within a buffer band, still random among ties.** Maintains a sliding window of latencies per deployment (`litellm/router_strategy/lowest_latency.py:358-493`); sorts candidates, applies `lowest_latency_buffer`, then `random.choice` among valid (`lowest_latency.py:477-489`). Penalizes timeouts with 1000 s synthetic latency (`lowest_latency.py:204-208`). Useful for sick-pod avoidance, not for steady-state shared-pod slot contention (external load raises latency gradually, not instantaneously). Impact: **~0-120 s** marginal vs persona 21 on homogeneous batch (`22-multi-pod-fleet-designer.md:8`); **quality risk: MED** (runtime-dependent).

- [HIGH] **`usage-based-routing` routes by lowest TPM/RPM in the current minute bucket.** Tracks per-deployment token and request counts keyed by `{model_group}:tpm:{minute}` / `:rpm:` (`litellm/router_strategy/lowest_tpm_rpm.py:52-70`, `149-179`). v2 variant (`usage-based-routing-v2`, `litellm/types/router.py:758-764`) uses global router cache keys. Both are **per-call** and minute-granular; they do not preserve paper affinity. Impact: similar contention relief to least-busy but slower to react than in-flight counters; **quality risk: MED**.

- [MED] **Health-check and cooldown pipeline: filter before strategy, with fail-open escape hatches.** Sync path: health-check filter → cooldown filter → strategy (`litellm/router.py:11091-11104`). Cooldown triggers on 429/401/408/404 and high failure-rate (`litellm/router_utils/cooldown_handlers.py:68-89`, `151-174`). When all deployments are in cooldown and `enable_health_check_routing` is on, cooldown is bypassed (`litellm/router.py:11105-11109`). Health filter also bypasses when every candidate is unhealthy (`litellm/router.py:11405-11407`). Worth porting pre-batch probe + dead-endpoint drop into `cli.py` (`21-dual-pod-sharder.md:12-13`); **not** worth importing the 11k-line Router. Impact: prevents ~50% false error tombstones when one proxy is half-dead; **quality risk: LOW** for probe-only port, **HIGH** if cooldown-bypass escape hatch is copied.

- [LOW] **Supported strategies enum (for reference).** Router constructor accepts `simple-shuffle`, `least-busy`, `usage-based-routing`, `latency-based-routing`, `cost-based-routing`, `usage-based-routing-v2` (`litellm/router.py:335-343`; typed subset at `litellm/types/router.py:84-89`; enum at `758-764`). Strategy dispatch in `_select_deployment_sync` (`litellm/router.py:1172-1194`).

## False-pass hypothesis

**Deterministic shard onto a contended alliance-pod while h200x8 sits idle.** ~190 papers queue behind 8 free slots (~2855 s wall) while the sibling pod finishes in ~1428 s. Fusion and pass/fail counts look normal; operators attribute slowness to "MoE variance" and skip the dedicated pod. A least-busy paper-start mode would have shifted ~67% of work to h200x8 (capacity-proportional), cutting ~952 s without changing model weights.

## False-fail hypothesis

**Per-call least-busy with LiteLLM-style mid-chain retry after 429 cooldown** (`litellm/router_utils/cooldown_handlers.py:69-71`, `litellm/router.py:6486-6570`): monolith succeeds on pod A, unit check 3 retries on pod B with cold prefix cache. Verdict differs from single-pod baseline; operator re-runs `--force`, burning another ~120 s × N papers chasing MoE noise (`21-dual-pod-sharder.md:16`).

## What would change my mind

A 381-paper cold A/B: (A) persona 21 deterministic shard, (B) whisker-local least-busy at **paper start only** (pin all 6 calls, no cross-pod mid-chain retry), with alliance-pod artificially loaded to 8/16 external slots, showing wall **≥5% below** (A) **and** borderline verdict-flip rate **≤1.1×** single-pod baseline (`21-dual-pod-sharder.md:31-32`) would upgrade least-busy to **usable** default for shared-pod nightly runs.
