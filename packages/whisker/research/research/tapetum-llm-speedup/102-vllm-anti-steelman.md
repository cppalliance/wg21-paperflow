# 102 - vLLM-Anti-Steelman

**Verdict:** usable-with-conditions — official DeepSeek-V4-Pro recipe flags are real but save at most ~10–18% wall server-only (~43 min floor); several knobs are net-negative on today's prompt layout, and reaching 5–10 min requires client prompt reorder and call-count levers first, not pod euphoria.
**Confidence:** high

## Findings

- [CRITICAL] **APC enabled before prompt reorder is a net loss, not a free lunch.** vLLM APC matches only identical *leading* token sequences ([automatic_prefix_caching.md:5-6](research/repos/vllm/docs/features/automatic_prefix_caching.md)); our unit checks place unique `Unit:` / `Risk signal:` / per-unit SOURCE before shared `candidate_md` (`unit_judge.py:769-776`), and every call draws a fresh `SRC{secrets.token_hex(4)}` guard tag appended to the system suffix (`unit_judge.py:767-768`, `pipeline/tools.py:55-61`). Cross-call document KV reuse is therefore ~0% today. SqueezeBits measured vLLM APC at concurrency 16 on a random (no shared prefix) dataset: **−36.7% throughput, +25% TPOT** ([squeezebits APC blog](https://blog.squeezebits.com/vllm-vs-tensorrtllm-12-automatic-prefix-caching-38189); card at `05-web.md:81-82`). Impact: flipping `--enable-prefix-caching` without client reorder risks **+300–1000 s** on the 2855 s compute term (throughput ratio 1/0.633) vs the **60–180 s** server-only win persona 15/40 assume. Quality risk: none (KV replay is bitwise when hits occur); operational risk: operators mark "APC deployed" while wall stays ~3003 s.

- [CRITICAL] **Client prompt reorder must land before APC pays; server-first is backwards.** Correct APC shape is `[static system + per-paper tag] → [Paper: pid] → [CANDIDATE MARKDOWN once] → [unique Unit/Risk/SOURCE last]` ([05-web.md:69-77](research/tapetum-llm-speedup/05-web.md), `15-prefix-cache-enabler.md:10-11`). Per-paper HMAC tag (not bare hash) unlocks identical system+delimiter prefixes across all ~6 calls on one paper (`45-guard-tag-cryptanalyst.md:10-11`, `pipeline/runner.py:117-126`). PR #43447's **74.3% hit / 4.5× server tok/s** numbers ([05-web.md:6-12](research/tapetum-llm-speedup/05-web.md)) assume that layout under concurrent replay; they do **not** apply to current tapetum prompts. Impact: persona 15's **500–900 s** unit-reorder envelope is **client-side**; persona 40's server bundle without reorder caps at **~300–550 s** (`40-server-flag-auditor.md:81`). Quality risk: reorder needs holdout A/B (`47-quality-equivalence.md:18-20`); server flags alone do not.

- [CRITICAL] **Honest server-only wall ceiling: ~2450–2700 s (~41–45 min), not 5–10 min.** Wall model from persona 48: `wall = (N×L)/S + T + C`; baseline check **2284×20/16 + 148 = 3003 s** (`48-combined-lever-modeler.md:19-31`, `00-baseline.md:24-25`). Server-only deltas (no N cut, S=16): MBT 16384 **100–250 s**, APC static-system **60–180 s**, MTP k=1 **100–200 s**, CUDA graphs **50–120 s** (`40-server-flag-auditor.md:69-81`), overlap-discounted **~300–550 s** total → **2450–2700 s**. Persona 48 CONSERVATIVE **685–856 s** explicitly stacks **dual-pod S:16→32** + **client prefix reorder −600 s** (`48-combined-lever-modeler.md:93-126`), not server flags alone. Persona 15's **1900–2400 s** envelope likewise requires reorder + per-paper tag (`15-prefix-cache-enabler.md:22`). Impact: any plan claiming recipe flags reach ≤600 s without client/call-count levers is arithmetic fiction. Quality risk: low for scheduling-only flags; MTP/FP8 already accepted variance.

- [HIGH] **`--max-num-seqs` above 16 is a measured +57–60% regression on our MoE pod; recipe "raise concurrency" advice is poison.** Measured matrix: server 16 + client 32 = **692.3 s** (692 s era corpus); server 32 + client 32 = **1090–1465 s** (+57%+) (`research/slots-32-regression/SYNTHESIS.md:8-14`, `00-baseline.md:82-83`). MoE decode loads the **union** of activated experts per step, not amortized dense batching (`research/slots-32-regression/11-moe-batch-scaling.md:8-12`); vLLM #17598 shows TPOT rises with `max-num-seqs` even on dense models ([issue #17598](https://github.com/vllm-project/vllm/issues/17598)). Community H200 DeepSeek guidance caps **4–8** (`05-web.md` via `05a-web-concurrency-knee.md`); our pod already runs **16** (`00-baseline.md:66`, `SERVICES.toml:64-69`). Impact: adopting recipe defaults of 32–64 would add **~900–1300 s** vs optimal 16-slot config on comparable workloads, not save time. Quality risk: MoE batch-composition variance (`MODELS.md:69-70`).

- [HIGH] **MTP speculative decoding has thin ROI on short structured judge outputs; k=2 can hurt.** Official recipe ships `num_speculative_tokens=2` ([recipes.vllm.ai DeepSeek-V4-Pro](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4-Pro), `05-web.md:16-17`); GB300 blog: k=1 >80% acceptance at c≤256 but **MTP drops when OSL is very short (64 tokens)** because draft overhead is not amortized ([blog.vllm.ai GB300](https://blog.vllm.ai/2026/02/13/gb300-deepseek.html), `05-web.md:20-22`). Tapetum unit checks cap at 1536 tokens but prompt caps reasoning at 40–60 words and **70% return zero defect groups** (`00-baseline.md:27-30`) — effective OSL clusters on the short end. Per-call time is decode-tagged (~70 tok/s, `pdf_judge.py:27`) but **prefill-heavy** (~17 s of ~20 s on large docs, `40-server-flag-auditor.md:73`). Impact: persona 40's **100–200 s** MTP line is optimistic; k=2 on zero-defect JSON may **increase** TPOT and trigger schema retries. Quality risk: algorithmically lossless ([spec decode docs](https://docs.vllm.ai/en/stable/features/speculative_decoding/)) but MoE non-invariance persists.

- [HIGH] **Raising `--max-num-batched-tokens` trades prefill throughput for decode ITL under our mixed load.** vLLM optimization docs: smaller MBT = **better ITL** (fewer prefills slowing decodes); higher MBT = **better TTFT** ([optimization.md:62-66](research/repos/vllm/docs/configuration/optimization.md)). Our implicit v0.24 H200 default is **8192**; recipe targets **16384** (`40-server-flag-auditor.md:45`, `05-web.md:15-16`). At S=16 with 32 client papers in flight (`cli.py:125`, `00-baseline.md:34-35`), long judge prefills (3k–100k tokens resent per call, `00-baseline.md:43-47`) batched aggressively can **inflate decode latency** for slots already in generation — the slots-32 regression attributed part of instability to MBT not co-raised (`research/slots-32-regression/SYNTHESIS.md:40-43`). Impact: MBT 16384 is still worth A/B, but **100–250 s** savings is not free; pair with `--long-prefill-token-threshold 8192`, not MBT alone. Quality risk: none (scheduling only).

- [HIGH] **Shared-pod operational risk: restarts and version bumps invalidate cheap validation and perturb other tenants.** `alliance-pod` is a 24/7 RunPod endpoint shared infrastructure (`00-baseline.md:65-66`, `SERVICES.toml:64-69`); template changes require pod restart (model reload, KV cold, queue flush). Persona 47: MoE hosted inference is **not batch-invariant** — identical reruns already flip **≥25%** of verdicts (`packages/whisker/src/whisker/CLAUDE.md:556-558`, `47-quality-equivalence.md:10-11`); a vLLM version bump (e.g. container `v0.24.0` vs PR #43447 merge, `40-server-flag-auditor.md:10`) can shift outputs enough to require **A1+A2+B1 ≈ 150 min** full-fleet equivalence (`47-quality-equivalence.md:16-17`). Concurrent non-tapetum traffic on the same pod changes batch composition per request (`MODELS.md:77-78`). Impact: each flag bundle needs a maintenance window + revalidation budget; "flip flags tonight" ignores **~100–150 min** gate tax per non-exempt change. Quality risk: treating server tuning as zero-validation ships undetected verdict drift.

- [MED] **PR #43447 throughput multipliers do not linearly translate to fleet wall.** Trace replay: 0%→74.3% prefix hits, server output **44→196 tok/s** at c=16 ([PR #43447](https://github.com/vllm-project/vllm/pull/43447), `05-web.md:6-12`). Our fleet wall is bounded by **2284 serial-stage calls** and slot model **N×L/S** (`00-baseline.md:22-25`); APC docs explicitly state APC **does not reduce decode time** ([automatic_prefix_caching.md:25](research/repos/vllm/docs/features/automatic_prefix_caching.md)). Even if 5/6 calls per paper shared 70% prefill after reorder: savings ≈ `1510 unit calls × 0.83 shareable × 0.70 prefill fraction × 0.74 hit × 14 s / 16 slots ≈ 570 s` upper bound — still **>2400 s** wall at S=16 without dual-pod or call elimination. Impact: persona 15/48 prefix lines are real but **insufficient alone** for ≤600 s target. Quality risk: none for APC itself.

## False-pass hypothesis

Deploy full DeepSeek-V4-Pro recipe (APC + MTP k=2 + MBT 16384) during a fleet cold run without client reorder: `/metrics` prefix hit rate stays ~0%, wall drops **≤200 s** from MBT/graphs while operators attribute success to "74% APC," and the speedup program under-invests in prompt reorder and metadata short-circuit — leaving **~2700 s** cold runs while believing server tuning is "done."

## False-fail hypothesis

Enable APC on current prompts, observe **+5–10% wall** from hash overhead (squeezebits regime), revert all recipe flags including beneficial retention env and MBT co-tune — falsely concluding vLLM server tuning is "garbage" when the failure mode was **cache-misaligned prompts**, not APC itself.

## What would change my mind

Instrumented 381-paper cold run with per-call `{cached_tokens, prompt_tokens, call_type}` logging: **variant A** = current prompts + APC/retention; **variant B** = per-paper HMAC tag + unit user reorder + same server flags. If B shows **≥40% prefix hit rate on unit checks** and wall **≥500 s below A** while `flip_AB ≤ flip_AA + margin` (`47-quality-equivalence.md:10-11`), downgrade APC-first skepticism to "server+client bundle is primary lever."
