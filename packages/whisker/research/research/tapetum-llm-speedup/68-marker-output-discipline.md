# 68 - marker-Output-Discipline

**Verdict:** usable-with-conditions — marker's hybrid LLM path has *weaker* output-token discipline than tapetum (often no cap, full HTML rewrites), yet still feels fast because call count and in-document parallelism dominate; copying their output style would slow us, not speed us.
**Confidence:** high

## Findings

- [CRITICAL] **Default marker services set no output ceiling; Claude is the only backend with a hard per-call cap.** `BaseService.max_output_tokens = None` (`marker/services/__init__.py:18-20`). Gemini/Vertex honor it only when configured (`marker/services/gemini.py:69-70`). OpenAI, Azure, and OpenRouter call `chat.completions.parse` with **no `max_tokens` argument** (`marker/services/openai.py:93-102`, `azure_openai.py:82`, `openrouter.py:107-114`). Claude alone sets `max_tokens=self.max_claude_tokens` default **8192** (`marker/services/claude.py:22-24`, `79`). Impact: marker allows multi-kilobyte structured JSON per call; our fleet already caps judge at **1536** (`cli.py:1034`) and text lane at **1024/2048** (`adjudicate.py:88-91`). Quality risk: none for us if we *tighten* caps; loosening toward marker would inflate decode on our MoE pod (~70 tok/s, `00-baseline.md:26-27`).

- [CRITICAL] **Marker's expected LLM outputs are block-sized rewrites, not verdict JSON — often 10–100× our P50 per call.** Table processor schema returns `comparison`, `corrected_html`, `analysis`, `score` (`marker/processors/llm/llm_table.py:361-365`); prompts require echoing the **full table HTML** in both input and output (`llm_table.py:44-46`, `85-87`). Form/equation/mathblock processors emit entire `corrected_html` or `corrected_equation` strings (`llm_form.py:122`, `llm_equation.py:143`, `llm_mathblock.py:186+`). Page correction returns a `blocks` list with per-block `html` fields (`llm_page_correction.py:296-305`). Contrast our schemas: `PdfJudgment` is four bounded fields with 60-word reasoning and ≤5 short quotes (`pdf_judge.py:252-269`); fleet P50 **283 / 112 / 77** tok per monolith/metadata/unit call (`14-output-token-surgeon.md:8`). Impact: a single marker table hit can decode **500–3000+** output tokens vs our **~80–300** typical judge call — marker decodes *more* per invocation. Quality risk: N/A for comparison; proves output shrink is not marker's speed secret.

- [HIGH] **No streaming or server-side early termination — "no corrections" is parsed after full decode.** Ollama explicitly sets `"stream": False` (`marker/services/ollama.py:49`). Gemini uses blocking `generate_content` (`gemini.py:79-86`); OpenAI/Claude use blocking `parse` (`openai.py:93`, `claude.py:77`). Processors discard work client-side via string checks: `"no corrections needed"` (`llm_table.py:204-205`, `246-247`), `"no_corrections"` (`llm_page_correction.py:167-168`, `llm_sectionheader.py:135-136`), `"no corrections"` (`llm_complex.py:80-81`). Table retry loop exits early on score ≥4 (`llm_table.py:220-222`) but only **between** full calls, not mid-decode. Impact: marker pays full generation latency even when the model concludes "nothing to fix"; our `"defects:[]"` pass calls have the same post-decode waste (~1057/1510 zero-defect unit checks, `00-baseline.md:29`). Quality risk: streaming stop sequences would not preserve structured JSON fidelity (same as olmOCR guided-JSON avoidance, `05-web.md:47-48`).

- [HIGH] **Marker's speed lever is call topology + parallelism, not output discipline.** With `--use_llm`, nine processors register (`marker/converters/pdf.py:97-107`) but calls scale with **block inventory and gates**, not a fixed 6/paper cascade (`58-marker-llm-census.md:12-25`): e.g. **one** section-header call per document (`llm_sectionheader.py:145-163`), page correction **off** unless `block_correction_prompt` set (`llm_page_correction.py:268-270`), tables skipped above 175 rows (`llm_table.py:27-30`, `132-133`). In-document **`max_concurrency=3`** ThreadPoolExecutor fans block/table/page work (`marker/processors/llm/__init__.py:42-45`, `163-172`; `llm_meta.py:44-49`; `llm_page_correction.py:283-291`). Cross-file **`--workers`** ProcessPool with server capacity budgeting (`marker/scripts/convert.py:186-212`). Our cold fleet: **2284 calls / 381 papers = 6.0/paper**, all **serial within paper** (`00-baseline.md:22-23`, `37-42`). Impact: halving our call count (~1140 calls) saves ~**1500 s** wall at 20 s/call and 16 slots (`00-baseline.md:24-25`) — far more than halving output tokens (~3–6 min per `14-output-token-surgeon.md:18`). Quality risk: blind call cuts without router precision repeat the 70% zero-defect unit-check waste (`00-baseline.md:29-30`).

- [MED] **Structured output still wraps large free-text fields — schema ≠ short output.** All services use Pydantic `response_schema` / `response_format` (`gemini.py:66-67`, `openai.py:101`, `claude.py:81`) but fields like `corrected_html: str` and `corrected_markdown: str` are unbounded (`llm_table.py:363`, `llm_complex.py:92-93`). Merge decisions stay small (`MergeSchema` ~4 short fields, `llm_table_merge.py:453-458`). Impact: marker's "fast" hybrid path on table-heavy PDFs is decode-heavy per call; throughput comes from **fewer calls on plain papers** and **3-wide overlap**, not terse answers. Quality risk: porting marker-style full-block rewrite outputs into our judge would explode latency on DeepSeek MoE.

- [MED] **Retry and iteration multiply large outputs, not shrink them.** Service defaults: `max_retries=2`, `retry_wait_time=3` (`marker/services/__init__.py:14-17`). Table processor `max_table_iterations=2` re-invokes with prior `corrected_html` as new input when score <4 (`llm_table.py:35-38`, `256-263`). Gemini bumps temperature to 0.2 on JSON decode failure (`gemini.py:112-113`). Impact: worst-case table path = **2× full HTML decode**; our BPE retry budget is ~55 fleet-wide (~100 s, `00-baseline.md:60-61`). Quality risk: lowering marker-style iteration caps would trade speed for table fidelity on olmOCR-bench table categories (`README.md:43-45`).

- [LOW] **Thinking budget is optional and off by default on Gemini.** `thinking_budget: None` (`marker/services/gemini.py:24-26`, `72-76`). Our judge omits thinking_budget intentionally (`cli.py:1032-1033`). Impact: neither system relies on hidden reasoning tokens in the default hybrid path. Quality risk: enabling thinking on either side would dominate decode regardless of visible output caps.

## False-pass hypothesis

Adopting marker's unbounded `corrected_html` outputs for our unit checks (rewrite the whole page markdown instead of bounded defect groups) would let a model "fix" candidate text in the response without auditable `source_quote` grounding — a silent quality upgrade that bypasses `verify_defect_counts` and two-sided evidence (`unit_judge.py:448`, `686-691`), manufacturing pass-tier sidecars on corrupted conversions.

## False-fail hypothesis

Tightening our `max_tokens=1536` judge cap toward SLMJury-style ~60 total tokens (`05-web.md:88-90`) to mimic marker's *appearance* of brevity would truncate `missing_content` quotes on non-pass monolith calls, triggering `source_ungrounded` dispositions and fail-closed coverage caps — while marker avoids this failure mode by never using our quote-grounding contract at all.

## What would change my mind

Measured token histograms from a marker `--use_llm` run on the same 381 WG21 papers (block metadata `llm_tokens_used` is already recorded per call at `gemini.py:89-91`, `openai.py:104-108`) showing **median output tokens below our unit-check P50 (~77)** would flip the decode comparison and reopen output-token shrink as a primary lever.
