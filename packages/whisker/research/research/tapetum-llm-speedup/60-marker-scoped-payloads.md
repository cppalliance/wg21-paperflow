# 60 - marker-Scoped-Payloads

**Verdict:** usable-with-conditions — marker proves block-scoped LLM payloads work for extraction because it trusts an upstream layout segmentation oracle; the pattern is not directly portable to tapetum_llm unit verification without persona-13's mechanical full-document presence oracle, and even then prefill savings alone cap at ~7–14% fleet wall (personas 13/54).
**Confidence:** high

## Findings

- [CRITICAL] **`--use_llm` never sends whole-document text; each call is block- or page-local image + short instruction + block HTML/OCR snippet.** Evidence: `OpenRouterService.__call__` posts `[image_url, text(prompt)]` only (`openrouter.py:88-92`); `BaseGeminiService.__call__` puts image parts before the prompt string (`gemini.py:81-84`). Simple processors build per-block prompts in `block_prompts()` — e.g. table HTML substitution (`llm_table.py:235-237`), equation HTML (`llm_equation.py:96-98`), form HTML (`llm_form.py:81-83`), image raw OCR (`llm_image_description.py:53-55`), complex-region text (`llm_complex.py:57-58`). Block images come from `extract_image()` → `block.get_image(..., highres=True, expansion=...)` (`__init__.py:69-80`). Impact: marker pays O(detected blocks) scoped calls, not O(pages) × full markdown; quality risk N/A for marker (generation task).

- [CRITICAL] **Measured prompt templates (placeholder stripped, 2026-07-23): table 2585, image_desc 1052, equation 1969, form 1818, complex 1723, handwriting 1389, mathblock 3048, page_correction 4145, sectionheader 2389, table_merge 2716 chars.** Typical block content from marker example JSON (`data/examples/json`, n=6580 blocks): P50 **84**, P90 **362** chars HTML; table blocks only (n=35): P50 **393**, P90 **1407** chars. Combined typical table call ≈ **2669 text chars (~667 tok)** vs tapetum unit check P50 **~9259 user tok** (34336-char candidate md + ~2500-char page source, persona 13). Impact: ~**8600 tok/call prefill delta** on unit checks; at 4000 tok/s prefill ≈ **2.1 s/call saved**, fleet 1510 unit calls ≈ **198 s wall / 16 slots** (~7% of 3003 s) — matches persona 13/54 ceiling. Quality risk: HIGH if scoped without oracle (below).

- [CRITICAL] **Epistemic split: marker's LLM trusts layout-model segmentation; tapetum's judge cannot trust tomd output as the scope oracle.** Marker runs deterministic layout/OCR first (`pdf.py:194-207`, README:103-105), then LLM processors fire only on typed blocks returned by `page.contained_blocks(document, block_types)` (`__init__.py:193-198`, `llm_table.py:117-120`). The LLM task is "fix/generate this block's content against its crop," not "verify the assembler." tapetum unit checks bind ANYWHERE presence (`unit_judge.py:137-139` per persona 13) and deliberately re-embed full candidate md per call (`unit_judge.py:769-776`). **Using tomd headings as scope boundaries would circularly assume the segmentation under test is correct.** Impact: marker-style block scoping is safe for extraction, unsafe for verification without an independent presence layer. Quality risk: CRITICAL for naive section-window copy.

- [HIGH] **Call volume is sparse and element-triggered, not fixed per paper.** Default `--use_llm` processor list (`pdf.py:82-110`) gates each class on `use_llm` (`__init__.py:64-65`, `llm_meta.py:29-30`). Simple processors batch through `LLMSimpleBlockMetaProcessor` with `ThreadPoolExecutor(max_workers=max_concurrency)` default **3** (`llm_meta.py:44-48`, `__init__.py:42-45`); complex processors (table, merge, mathblock, page correction) run their own pools. Tables skip above **175 rows** or chunk at **60 rows/batch** (`llm_table.py:27-30, 132-143`). Handwriting skips text blocks that already have lines (`llm_handwriting.py:44-47`). Image description skips when `extract_images=True` (`llm_image_description.py:45-47`). Impact: most WG21 text pages likely get **zero** marker LLM calls; our lane pays **~6 calls/paper** regardless (00-baseline). Quality risk: none for marker; our fixed call graph is the bigger lever than payload shape alone.

- [HIGH] **Largest marker text scope is still page-local, optional, and metadata-heavy — not document markdown.** `LLMPageCorrectionProcessor` sends one page raster + JSON list of that page's blocks (`llm_page_correction.py:150-159`) but only when `--block_correction_prompt` is set (`llm_page_correction.py:268-270`, README:138). `LLMSectionHeaderProcessor` sends all section-header JSON in **one document-level call**, text-only, no image (`llm_sectionheader.py:122-127`, `145-163`). `LLMTableMergeProcessor` sends two adjacent table HTML snippets + two crops (`llm_table_merge.py:314-327`). Impact: even marker's broadest LLM pass is page JSON or header metadata, not 34k-char assembled markdown × N. Quality risk: page-correction scope would still break tapetum ANYWHERE unless paired with full-doc presence index (persona 13).

- [MED] **Portable translation is persona-13 hybrid, not marker copy: scoped source window + mechanical presence index + unchanged post-hoc grounding on full `raw_tomd_md`.** Marker has no analog — it never LLM-verifies assembled output (`54-docling-payload-scoper.md:18`). Docling/marker both scope **generation**; tapetum scopes **verification** (`13-payload-scoper.md:16-18`, `54-docling-payload-scoper.md:4`). Prefix-cache reorder (stable per-paper guard tag, shared candidate block last, persona 13/15) may recover comparable prefill savings **without** shrinking semantic context. Impact: hybrid + APC reorder ≈ **7–14% wall** combined ceiling before call elimination / dual-pod levers (00-baseline:88-103). Quality risk: MEDIUM if index normalization misses dehyphenated/wording-markup matches (`13-payload-scoper.md:30`).

- [LOW] **Output side is also scoped: structured pydantic schemas per processor, no full-document rewrite.** Each service call uses `response_schema` / `response_format=response_schema` (`openrouter.py:107-113`, `gemini.py:66-67`) with small fields (`TableSchema`, `ImageSchema`, etc. in processor modules). Contrast tapetum unit output cap **1536 tok** with reasoning budget (`00-baseline.md:27-28`). Impact: marker decode cost per call is bounded by block correction, not fleet-scale judge reasoning. Quality risk: none for our lane if we only borrow input scoping.

## False-pass hypothesis

Adopt marker-style unit payloads scoped to the unit's H2 section without a full-document presence index: a cross-page join tail rendered under an earlier heading (tomd join rule) is outside the window; the LLM reports `content_omission`, post-hoc grounding lacks a verbatim `source_quote`, and a join corruption passes — same failure mode persona 13 documents (`13-payload-scoper.md:26-27`, `unit_judge.py:137-139`).

## False-fail hypothesis

Mechanical presence index with strict alnum normalization while keeping ANYWHERE prompt language: dehyphenated or wording-markup-wrapped matches that `classify_candidate_evidence` treats as `present_in_candidate` stay invisible to the index; the model false-fails join fragments that exist document-wide (`13-payload-scoper.md:30`, `grounding.py:487-489` cited there).

## What would change my mind

A holdout replay showing unit checks rewritten with marker-scoped **source** windows + a full-md presence index (persona-13 hybrid) and unchanged post-hoc grounding achieves **≥30% cold-fleet wall reduction** with **≤1% verdict diff** vs control on the 48-paper holdout — that would elevate direct payload scoping above prefix-cache reorder for the 3003 s target (threshold from persona 54).
