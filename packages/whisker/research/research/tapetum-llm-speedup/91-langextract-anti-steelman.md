# 91 - langextract-Anti-Steelman

**Verdict:** usable-with-conditions — LangExtract is a text-in / structured-extract-out library with strong post-LLM alignment mechanics, but it is not a PDF pipeline, not a conversion verifier, and its default-speed story depends on cloud Gemini chunk parallelism (rate limits permitting), not on self-hosted MoE judge economics; treat it as an orchestration pattern source, not proof that "all pages with LLMs" is fast on our stack.
**Confidence:** high

## Findings

- [CRITICAL] LangExtract has zero native PDF ingestion: the public API accepts a string or `Document(text=...)` only, and I/O is CSV/JSONL text paths — no PDF parser, no page model, no conversion stage. Evidence: `extraction.py:45-46,84-87` (`text_or_documents: str | Iterable[data.Document]`; optional URL fetch is literal text); `core/data.py:130-141` (`Document.text: str` only); `io.py:50-82` (CSV → `Document(text=row[text_key])`, other extensions `NotImplementedError`); repo-wide grep for `pdf|PDF|pypdf|fitz` = 0 hits under `langextract/`. Impact: citing LangExtract as proof that "others LLM all PDF pages fast" misattributes work — PDF→text must happen upstream (tomd, pdftotext, etc.); on our fleet the 3003 s cold run already includes converted markdown + judge calls, so LangExtract does not shortcut that path. Quality risk: none if we only borrow patterns; high if we cargo-cult it as an end-to-end PDF comparator.

- [CRITICAL] LangExtract does not verify conversions — it generatively extracts entities from source text and post-hoc aligns model strings to source spans; there is no second document (candidate markdown), no source-vs-candidate diff, and no fail-closed coverage audit. Evidence: `prompting.py:126-137,174` (prompt = instruction + few-shot examples + `Q:` prefix + chunk source as question); `annotation.py:404-429` (parse model output → `resolver.align` against `text_chunk.chunk_text` only); `resolver.py:327-347` ("Aligns annotated extractions with source text" on one side). Contrast our lane: `grounding.py:50-52` (`CANDIDATE_PRESENT` / `candidate_not_found` two-sided disposition). Impact: LangExtract cannot replace tapetum's judge task (381 papers, ~2284 calls checking conversion fidelity per `00-baseline.md:22-23`); swapping it in would drop table-cell swap / missing-content / secno-drift detection that changed 16/381 merged verdicts (`00-baseline.md:29-30`). Quality risk: catastrophic false-pass if adopted as verifier.

- [CRITICAL] Default call economics invert ours on long WG21 papers: one `generate_content` per chunk, not one per paper. Evidence: `annotation.py:366-392` (batch loop → `language_model.infer` per chunk batch); `gemini.py:480-485` (one `_process_single_prompt` / API call per prompt in `batch_prompts`); `extraction.py:53,57-58,154-160` (`max_char_buffer=1000`, `batch_length=10`, `max_workers=10`, `extraction_passes=1` default). Approximate: 80k-char paper → ~80 chunks/pass vs our fixed **6 calls/paper** (`00-baseline.md:22-23`). Fleet scale: **381 × 80 ≈ 30,480 API calls** vs **2284**. Impact on 3003 s cold run: at our measured **~20 s/call** and **16 server slots** (`00-baseline.md:24-25`), naïve port → **30,480 × 20 / 16 ≈ 38,100 s (~10.6 h)** — slower, not 5–10 min. Quality risk: raising `max_char_buffer` toward our single-shot budget trades recall (README/long-text guidance at `extraction.py:95-96`).

- [HIGH] Its speed comes from cloud Gemini intra-batch thread parallelism, not self-hosted MoE serving — and that parallelism is rate-limit-gated. Evidence: `gemini.py:128-129,477-504` (`temperature=0.0`, `max_workers=10`, `ThreadPoolExecutor` over `batch_prompts`); `extraction.py:125-127` ("Supported by Gemini models"; effective parallelism `min(batch_length, max_workers)`); `gemini.py:49,351-391` (retries only on HTTP 429/503, not schema recovery). Self-hosted path: `ollama.py:291-304` (strictly sequential `for prompt in batch_prompts` — `max_workers` is a no-op); no vLLM provider in-tree (`00-baseline.md` §3 grep). Impact: on `alliance-pod` (DeepSeek V4 MoE, `--max-num-seqs 16`, `00-baseline.md:65-66`) LangExtract's default posture does not beat our cross-paper 32-wide fleet (`cli.py:125` per `00-baseline.md:34-35`); cloud Flash demos (~seconds on README-scale text, `README.md:100-110`) do not transfer. Quality risk: MoE batch-composition variance if we copy in-paper parallel unit checks without caps (`00-baseline.md:95-96`).

- [HIGH] LangExtract lacks our operational primitives for a 381-paper repeatable fleet: no incremental skip, no per-paper fingerprint, no two-sided evidence fold, no deterministic serial-within-paper contract. Evidence: LangExtract — no fingerprint/skip symbols in `extraction.py` / `annotation.py`; multi-pass merge is first-pass-wins overlap only (`annotation.py:46-84,477-509`). Ours — `cli.py:566-598` (`_compute_fingerprint`: `md_sha256`, `source_sha256`, prompt/schema/model/`_LANE_VERSION`; warm run **64.8 s**, 375/381 skipped, `00-baseline.md:18-20`); serial per-paper chain (`00-baseline.md:36-42`). Impact: cold LangExtract re-chunk → re-infer → re-align on every run; cannot explain our 50× warm speedup. Quality risk: low for pattern borrow; high if we drop fingerprinting to "match LangExtract simplicity."

- [MED] What we should still take (without cargo-culting the cloud defaults): (1) **scoped chunk payloads** — each call sends one chunk + optional prior-source tail, not full markdown × N (`annotation.py:360-375`, `context_window_chars` at `extraction.py:161-164`); directly addresses our full-markdown re-prefill (`00-baseline.md:43-47`). (2) **Mechanical alignment after LLM** — deterministic `resolve` + `align`, zero extra LLM calls (`annotation.py:404-429`, `resolver.py:327-400`). (3) **Parallel workers as default posture** — index-ordered `results[index]` yield (`gemini.py:487-504`), adoptable per tapetum opt-in without global D11 flip (`00-baseline.md:95-96`). (4) **Few-shot-first prompt ordering** — description → examples → chunk question last (`prompting.py:126-137`), compatible with prefix-cache design in `05-web.md` Q4 if guard tags stay at user-message tail not system prefix. Impact: scoped payloads + in-paper parallel unit checks could cut wall without cutting call count; alignment upgrade is locatability not speed. Quality risk: multi-unit prompt packing still cautioned by RuVerBench (`05-web.md` Q5).

- [LOW] `batch_length` improves wall-clock, not billed API calls — each chunk still invokes one provider request. Evidence: `extraction.py:97-98,122-127` ("max_workers improves processing speed without additional token costs"); `chunking.py:265-279` (batching groups prompts for one `infer()` invocation). Impact: copying `batch_length=10` without in-paper concurrency saves zero calls on tapetum's serial unit loop (`unit_judge.py:379+` per `00-baseline.md:38`). Quality risk: none for call census; medium if confused with call elimination.

## False-pass hypothesis

Running LangExtract-style generative extraction (`prompting.py:136` — chunk text as the sole `Q:` payload) over PDF text layers to "find defects" without a candidate markdown: a table with transposed cells but verbatim prose elsewhere yields zero extractions on every chunk, `suppress_parse_errors=True` drops parse failures silently (`resolver.py:309-312`, default `extraction.py:136-138`), and the run completes with empty `extractions` — the analogue of baseline PR #295 zero defect claims, invisible to LangExtract's source-only aligner.

## False-fail hypothesis

Porting LangExtract's dual-gate LCS fuzzy aligner wholesale (`resolver.py:57-58,1377-1404`: 0.75 coverage + 1/3 density) onto tapetum evidence quotes would reject valid paraphrased judge quotes that our `partial_ratio >= 0.90` document floor (`constants.py:50`, `grounding.py:51`) still accepts — advisory false alarms on good conversions, not a gate false-fail, but a quality-stability violation on the 16/381 verdict-changing unit-check path.

## What would change my mind

A measured end-to-end benchmark on our 381-paper holdout where LangExtract (or a tapetum fork using only its chunk+align orchestration) is wired as the **judge** with candidate markdown in the prompt, self-hosted on `alliance-pod`, matching our defect-class recall, and achieving ≤600 s cold wall at ≤1.2× our 2284-call budget — with per-paper fingerprints and two-sided grounding preserved. Without that, it remains a text-extraction library, not a fleet speed oracle.
