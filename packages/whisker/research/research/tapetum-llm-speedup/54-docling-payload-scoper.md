# 54 - docling-Payload-Scoper

**Verdict:** usable-with-conditions — Docling's element/page-scoped payloads are the right extraction pattern and explain why our judge lane prefills ~34k-char markdown ~6× per paper, but the pattern is not directly portable to tapetum_llm unit checks without replacing ANYWHERE semantics with a mechanical full-document presence oracle (persona 13/15).
**Confidence:** high

## Findings

- [CRITICAL] **Docling VLM convert sends one page raster + a static short text prompt; no document text enters the call.** Evidence: `VlmConvertModel.__call__` rasterizes each page via `page.get_image(scale=..., max_size=...)` and reuses the same `model_spec.prompt` for every page in the batch (`vlm_convert_model.py:157-172`, `118-127`); API path posts exactly `[image_url, text(prompt)]` (`api_image_request.py:192-207`). Typical preset prompts: `smoldocling`/`granite_docling` **29 chars** (`stage_model_specs.py:1037`, `1062`), markdown presets **86 chars** (`stage_model_specs.py:1098`, `1177`), outlier layout presets **887–2157 chars** (`vlm_prompts.py:48-64`, `36-46` via `stage_model_specs.py:1578`, `1624`). Impact: a 20-page VlmPipeline doc pays **20 scoped image calls**, not 20× full-document prefill; contrast our **~1510 unit checks** each embedding P50 **34 336-char** candidate md (`00-baseline.md:43-47`, `13-payload-scoper.md:12`). Quality risk: none for Docling (generation task); for us, copying without oracle breaks ANYWHERE (below).

- [CRITICAL] **Document-level assembly is deterministic code after all per-page VLM outputs, not another model pass over the whole doc.** Evidence: `VlmPipeline._assemble_document` parses per-page `vlm_response` into `DoclingDocument` by response format (DocTags/DocLang/Markdown/HTML/JSON) (`vlm_pipeline.py:276-319`); `PaginatedPipeline._build_document` iterates pages in `page_range` and runs `build_pipe` per batch (`base_pipeline.py:244-267`, `256-266`). Reading order, heading hierarchy, and markdown export happen in downstream non-LLM stages (`standard_pdf_pipeline.py:615-616`). Impact: Docling's "full document" exists only in Python data structures between calls; our judge inverts this by shipping the assembled markdown back into every scoped check. Quality risk: N/A for Docling; for us, post-hoc grounding already searches full on-disk md (`unit_judge.py:728-729`, `grounding.py:419-438`) while the LLM still pays prefill on the duplicate.

- [HIGH] **Enrichment VLM calls (picture description, code/formula) send bbox-cropped element images only, with token-sized prompts.** Evidence: `BaseItemAndImageEnrichmentModel.prepare_element` crops `element.prov[0].bbox` expanded by `expansion_factor` from the page raster (`base_model.py:197-218`); `CodeFormulaVlmModel` uses `images_scale=1.67`, `expansion_factor=0.18`, batch size 5, prompts `"<code>"` / `"<formula>"` (**6 / 9 chars**) (`code_formula_vlm_model.py:67-69`, `135-151`, `256-268`); `PictureDescriptionVlmEngineModel._annotate_images` sends cropped picture + preset prompt (e.g. **39 chars** `"Describe this image in a few sentences."`, `stage_model_specs.py:1441`, `picture_description_vlm_engine_model.py:120-138`, `max_new_tokens=200`). Pictures below `picture_area_threshold` (default **5%** of page area) are skipped (`picture_description_base_model.py:80-89`, `stage_model_specs.py:1463`). Impact: a text-only WG21 page may get **zero** enrichment VLM calls (`12-docling-coverage-analyst.md:14`); call count scales with detected elements, not page count. Quality risk: none for Docling extraction; mirrors why our verification cannot assume "one page in, one page out."

- [HIGH] **Default StandardPdfPipeline has no generative full-document LLM at all; scoped VLM is opt-in per stage flag.** Evidence: default `build_pipe` is OCR + layout + table structure + assemble (`standard_pdf_pipeline.py:590-616`); optional `CodeFormulaVlmModel` appended only when `do_code_enrichment` / `do_formula_enrichment` (`standard_pdf_pipeline.py:621-641`); picture description/classification/chart extraction register in `ConvertPipeline.enrichment_pipe` only when respective `do_*` flags are set (`base_pipeline.py:167-209`). Impact: Docling's speed baseline is "bounded neural stages + element-scoped optional VLM," not "LLM reads whole doc N times." Our tapetum_llm lane is verification-first and deliberately re-reads the full candidate for cross-page presence. Quality risk: adopting Docling's scope without changing task semantics would drop join-tail and reflow checks (`13-payload-scoper.md:10`, `unit_judge.py:137-139`).

- [HIGH] **Payload contrast (measured): Docling page VLM ≈ image tokens + 7–540 prompt tokens; our unit check ≈ ~9259 user tokens at P50 (2500-char source + 34 336-char md + headers).** Evidence: Docling prompts above; our `_check_one_unit` user_msg = Paper/Unit/Risk + one page source + **full** `candidate_md` (`unit_judge.py:769-776`); page escalations repeat the pattern with full md (`pdf_judge.py:389-395`). Persona 13 measured P50 md **34 336 chars** and ~**9259 tok**/call user payload. Impact: even perfect Docling-style scoping on unit checks saves at most **~7–14% fleet wall** (prefill-only; decode still ~70 tok/s × 1536 cap, `00-baseline.md:24-28`, `13-payload-scoper.md:20-21`); **prefix-cache reorder + per-paper guard tag** (persona 15) may recover comparable savings **without** shrinking semantic context. Quality risk: MEDIUM for naive section-only scoping; LOW for persona-15 reorder alone.

- [MED] **Docling verification does not use LLM payloads at all; golden replay compares structured artifacts per document.** Evidence: CI `verify_conversion_result_v2` diffs committed JSON/md/doctags/page-meta (`research/llm-readability/repo-scan/docling.md:11-20`, `verify_utils.py:355-439` cited in r04). No LLM judge compares candidate to full source. Impact: Docling optimizes **generation** scoping; our speed study optimizes **verification** scoping — analogous lever, different semantics. Persona 13's hybrid (section window + mechanical presence index + unchanged `classify_candidate_evidence` on full md) is the closest portable translation, not raw Docling copy. Quality risk: index normalization too strict → false-fail inflation (`13-payload-scoper.md:30`).

- [LOW] **Legacy vs new VLM runtime share the same payload shape; chat-template wrapping adds model-specific overhead but still no document text.** Evidence: `BaseVlmOptions.build_prompt` returns static `self.prompt` (`pipeline_options_vlm_model.py:79-95`); `formulate_prompt` wraps for Phi-4/chat templates (`base_model.py:103-136`); `VlmEngineInput` is always `(image, prompt, generation config)` (`vlm_convert_model.py:118-126`). Impact: migrating Docling presets does not change the scoped-input invariant. Quality risk: none.

## False-pass hypothesis

Adopt Docling-style section-window unit payloads without a full-document presence index: a cross-page join tail rendered under an earlier heading (tomd join rule) is invisible in the page-13 window; the LLM reports `content_omission`, but if post-hoc grounding lacks a verbatim `source_quote` the defect is under-reported — same failure mode persona 13 documents for naive scoping (`13-payload-scoper.md:26-27`, `unit_judge.py:137-139`).

## False-fail hypothesis

Mechanical presence index with strict alnum normalization while keeping ANYWHERE prompt language: dehyphenated or wording-markup-wrapped matches that `classify_candidate_evidence` would treat as `present_in_candidate` stay invisible to the index; the model false-fails join fragments that exist document-wide (`13-payload-scoper.md:30`, `grounding.py:487-489` cited there).

## What would change my mind

A holdout replay showing unit checks rewritten with Docling-scoped source windows + a full-md presence index (persona 13 hybrid) and unchanged post-hoc grounding achieves **≥30% cold-fleet wall reduction** with **≤1% verdict diff** vs control on the 48-paper holdout — that would elevate direct payload scoping above prefix-cache reorder for the 3003 s target.
