# 132 - deepeval Concurrency-Caching

**Verdict:** usable-with-conditions (deepeval's in-paper metric parallelism is the primary cold-fleet portable lever; their result cache is a strong incremental pattern but defaults OFF and does not accelerate first runs)
**Confidence:** high

## Findings

- [CRITICAL] Cross-document concurrency is bounded by `asyncio.Semaphore(max_concurrent)` with default **20** concurrent test cases; optional `throttle_value` sleep between task submissions defaults to **0** (no artificial delay). Evidence: `deepeval/evaluate/configs.py:8-11`, `deepeval/evaluate/execute/e2e.py:348-354,446`, `deepeval/evaluate/execute/loop.py:515-527,1010`. Impact: we already exceed this (`_DEFAULT_CONCURRENCY=32`, `cli.py:127`); no cold-run gain from matching deepeval's cross-paper cap. Quality risk: none (already validated at c=32 per `00-baseline.md`).

- [CRITICAL] **Within one test case, multiple metrics (judge calls) run in parallel** via `asyncio.gather` in `measure_metrics_with_indicator`, while cross-test-case work is semaphore-limited. Evidence: `deepeval/metrics/indicator.py:157-195,226-238`, contrast with our serial per-paper chain (`pdf_judge.py:753`, `unit_judge.py:379+`, `00-baseline.md:36-42`). Impact: unit checks are ~1510/2284 calls (66%); parallelizing up to 5 unit checks within a paper (keeping monolith→metadata→page-escalation serial) removes ~3–4 serial 20 s slots per multi-unit paper, estimated **900–1400 s** off the 3003 s cold run (~30–47%) if slot-bound. Quality risk: **medium-high** — MoE batch-composition variance under concurrent prefills of the same full markdown (same concern flagged in `00-baseline.md:96` and `05-web.md:9-12`).

- [HIGH] Result cache is **two-level**: (1) test-case key = canonical JSON of `input`, `actual_output`, `expected_output`, `context`, `retrieval_context`, `hyperparameters` via `serialize()` (`deepeval/test_run/cache.py:120-135`, `deepeval/utils.py:188-189`); (2) per-metric hit = metric class `__name__` + `MetricConfiguration` fields (`threshold`, `evaluation_model`, `strict_mode`, `criteria`, `evaluation_steps`, `evaluation_params`, etc.) compared in `Cache.same_metric_configs` (`deepeval/test_run/cache.py:313-379,382-404`). Impact: maps directly to our fingerprint gap — **per-unit keys** `(page_id, candidate_md_sha256, source_slice_sha256, prompt_sha256, schema_sha256, model, lane_version)` would let a one-page markdown edit skip ~5/6 calls instead of rerunning the whole cascade (`cli.py:566-619`, `00-baseline.md:57-59`). On **cold** fleet: **0 s** saved (`use_cache` defaults `False`, `deepeval/evaluate/configs.py:40-41`; CLI disables cache when `--repeat` set, `deepeval/cli/test/command.py:134-135`). On **warm/partial** reruns: could approach our measured warm 64.8 s profile for edited subsets. Quality risk: **low** if keys include prompt/schema/lane_version like our paper fingerprint; **high** if metric-config-only invalidation misses prompt edits (deepeval relies on `criteria`/`evaluation_steps` fields, not raw prompt hash).

- [HIGH] Cache persistence: writes to `.deepeval/.deepeval-cache.json` (temp file during run, merged at end) with `portalocker` file locks (`deepeval/test_run/cache.py:34-35,187-306`). `write_cache=True` by default; hits restore metric state and zero out `evaluation_cost` (`deepeval/evaluate/execute/e2e.py:220-222,621-624`). `ENABLE_DEEPEVAL_CACHE` env toggles CLI cache (`deepeval/utils.py:291-298`, `deepeval/config/settings.py:803-806`). Impact: portable pattern for sidecar-resident per-call cache entries (we already store whole-paper fingerprint in tapetum sidecar). Cold fleet unchanged; incremental/edit workflows benefit. Quality risk: low with explicit prompt/schema in key (stricter than deepeval).

- [MED] Outer task budget + nested retry: default **180 s** outer deadline per test case (`deepeval/config/settings.py:919-929,964-982`), `DEEPEVAL_RETRY_MAX_ATTEMPTS=2` (one retry), exponential backoff initial 1 s / base 2 / cap 5 s / jitter 2 s (`settings.py:743-758`), wired through `create_retry_decorator` with per-attempt `asyncio.wait_for` (`deepeval/models/retry_policy.py:630-670`). Throttling (`RateLimitError`, `throttlingexception`) is retryable (`retry_policy.py:796-798`). `ignore_errors` continues batch on metric failure (`deepeval/metrics/indicator.py:299-305`). Impact: our 55 retries ≈ 100 s (~4% of 3003 s, `00-baseline.md:60-61`); adopting outer-deadline-aware retry saves **≤100 s** on cold run, not path to 5–10 min alone. Quality risk: low (fail-closed semantics preserved if errors not swallowed).

- [MED] Gather-level timeout cancels pending tasks on fleet timeout (`deepeval/evaluate/execute/e2e.py:448-462`, `_log_gather_timeout` in `deepeval/evaluate/execute/_common.py:68-102`). Impact: prevents hung slots; marginal wall savings when calls hang near our 120 s unit timeout (`constants.py:197`). Quality risk: low if tombstone/error papers retried (matches our warm 6-error retry pattern, `00-baseline.md:19-20`).

- [LOW] Sync evaluation path runs test cases **sequentially** (`deepeval/evaluate/execute/e2e.py:323-326`); async is the throughput path. Impact: confirms async+semaphore is intentional for judge fleets; our async CLI path is aligned. Quality risk: none.

## False-pass hypothesis

Parallel in-paper unit checks (deepeval's within-case `asyncio.gather` pattern applied to our `unit_judge` loop) could silently miss a defect on page N because five concurrent judges each prefill the same full candidate markdown on a MoE endpoint with `--max-num-seqs 16`, increasing run-to-run variance; a defect visible when unit checks run serially might flip to zero-defect under concurrent batch composition, passing a paper that serial execution would flag review.

## False-fail hypothesis

Adopting deepeval's metric-config-only cache invalidation (without our `prompt_sha256` / `schema_sha256`) for per-unit entries could skip unit re-judges after a prompt wording change that does not alter `MetricConfiguration`-equivalent fields, causing stale "zero defect" cache hits on changed rubric text and unnecessary review flags on the next `--force` discovery run — not a false-fail on conversion quality, but a false-stale-skip that delays catching rubric regressions until manual invalidation.

## What would change my mind

A holdout cold-fleet A/B on 48 anchored papers (`00-baseline.md` holdout reference) with in-paper parallel unit checks (deepeval `indicator.py:195` pattern) vs current serial `unit_judge.py:379+`, reporting verdict drift ≤5% and identical defect-class recall, would upgrade the parallelism finding from estimated 900–1400 s to shippable and flip verdict to **usable** without conditions.
