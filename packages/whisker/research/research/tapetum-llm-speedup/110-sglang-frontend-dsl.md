# 110 - sglang-Frontend-DSL

**Verdict:** usable-with-conditions — the frontend `fork`/`join` DSL is the exact architectural match for our per-paper unit-check cascade (one shared document prefix, N parallel judge branches), but it requires the sglang native `/generate` runtime client, not the OpenAI-compatible API; fork alone saves on the order of ~500–700 s fleet wall, not enough for the 5–10 min target without call elimination and vLLM APC fixes first.
**Confidence:** medium

## Findings

- [CRITICAL] **Fork/join is a frontend-DSL primitive, not an HTTP/OpenAI feature.** `@sgl.function` programs call `s.fork(N)` which delegates to `StreamExecutor.fork` (`interpreter.py:888-896`, `370-402`): before splitting, `SglCommitLazy()` commits the shared prefix to server KV via `commit_lazy_operations` → `/generate` with `max_new_tokens: 0` (`interpreter.py:375-378`, `726-727`, `runtime_endpoint.py:105-114`). Each child gets a copied `text_`/`messages_`/`variables` and `fork_start_text_pos = len(parent.text_)` (`interpreter.py:391-397`), a fresh `sid` (`interpreter.py:289`), then diverges via `forks += lambda i: ...` (`interpreter.py:1084-1096`). `forks.join()` either gathers generated variables (`interpreter.py:1052-1066`) or merges branch KV with `concate_and_append` (`interpreter.py:1067-1071`, `738-752` → `runtime_endpoint.py:317-324`). `BaseBackend.fork_program` is a no-op stub (`base_backend.py:38-44`); KV sharing is implicit RadixAttention longest-prefix match on identical leading tokens, not an explicit server fork RPC. Impact: **OpenAI `/v1/chat/completions` cannot express this**; the sglang `OpenAI` backend inherits `support_concate_and_append = False` (`base_backend.py:11`). Adoption means a **sglang `RuntimeEndpoint` client** (or in-process `Engine`) inside `pipeline`/`whisker`, a major dependency and serving-stack decision.

- [HIGH] **`llm_judge` benchmark is a 1:1 analog of our unit-check shape.** Shared article in context, then `s.fork(len(dimension_prompts))` with 6 parallel dimension verdicts + `forks.join()` before a summary gen (`benchmark/llm_judge/bench_sglang.py:24-50`). The vLLM/guidance baseline re-sends the full article prefix on every serial `generate()` call (`benchmark/llm_judge/bench_other.py:31-47`). README gives run recipes only, **no checked-in sglang-vs-vLLM latency table** (`benchmark/llm_judge/README.md:1-27`; confirmed by sibling `112-sglang-benchmark-evidence.md:18`). Impact: architectural proof, not a fleet number; qualitatively eliminates ~5 redundant prefills of the shared document block per judge article (same class as our 5× `candidate_md` unit checks, `00-baseline.md:43-47`).

- [HIGH] **Measured prefix-heavy wins in clone + web cards, not fork-specific A/B tables.** README claims up to **5×** inference with RadixAttention (`README.md:56`, LMSYS blog). `benchmark_vllm_060/README.md:3-14`: median TTFT **31.98 ms (SGLang) vs 100.48 ms (vLLM)** (~3.1×), median ITL **11.93 vs 129.32 ms** (~10.8×) on ShareGPT with **radix disabled on both** (`benchmark_vllm_060/README.md:61-62`). External (05-web Q4): one shared document + 20 questions, TTFT **4343→970 ms (−78%)**, output throughput **+254%** with APC. Impact: fork's value is **prefill amortization + parallel decode batching** on shared-prefix loads; translate cautiously to our MoE DeepSeek-V4-Pro @ 16 slots — vLLM PR #43447 already shows **44→196 tok/s (~4.5×)** at **74.3%** hits on our model (05-web Q1). SGLang fork adds parallel-branch scheduling semantics vLLM HTTP lacks, but incremental over a fixed vLLM APC pod is uncertain.

- [HIGH] **Expected per-paper cost vs 6 independent prefills (quantified from 00-baseline).** Baseline: serial 6-call chain ~**120 s** paper wall at ~**20 s**/call (`00-baseline.md:38-39`, `24-25`); full `candidate_md` prefilled on every unit check (`00-baseline.md:43-47`). Fork pattern on unit checks only (monolith + metadata stay serial): **1 shared prefill + max(parallel decode)** replaces **5 serial prefill+decode cycles**. Rough model: unit portion **5×20 s = 100 s → ~40 s** (one ~20 s prefill + one ~20 s parallel-decode batch), saving **~60 s** on a 6-call paper (~**50%** of per-paper serial wall). Fleet: **381 papers × ~50 s avg save / 32 concurrent ≈ 600 s** on the 3003 s cold run — meaningful but **not sufficient alone** for 5–10 min; must combine with metadata short-circuit, call elimination, dual-pod sharding. Quality risk: **medium** — parallel unit branches on MoE change batch composition vs serial D11-exempt advisory lane (`00-baseline.md:39-42`, `83`); needs 48-paper holdout verdict diff.

- [MED] **`concate_and_append` join mode targets parallel-encoding, not our judge fork.** Used when N branches each append different context blocks that must land in one KV chain (multi-doc QA: `benchmark/multi_document_qa/bench_sglang.py:19-21`; line retrieval: `benchmark/line_retrieval/bench_sglang.py:22-25`; test: `test_programs.py:293-295`). Calls `/concate_and_append_request` (`runtime_endpoint.py:317-324`); **server handler not present elsewhere in shallow clone** (only client reference). Our unit checks need **`join()` default `gather_variable`**, not KV concatenation. Impact: using wrong join mode would corrupt prompt structure and verdicts; zero wall-clock benefit if misapplied.

- [MED] **Tree-of-thought shows nested fork for branching search, not flat judge parallelism.** `propose_plan` / `execute_plan` / `reflect_solution` each `s.fork(num_branches)` with nested `join()` (`benchmark/tree_of_thought_v0/bench_sglang.py:44-89`). README notes prompts are for throughput/latency bench, not tuned accuracy (`benchmark/tree_of_thought_v0/README.md:8`). Impact: demonstrates multi-level fork depth on sglang runtime, but our cascade is **flat N-way** (≤5 unit checks + ≤5 page escalations), not tree search; no applicable latency table in clone.

- [MED] **Adoption requirements for `pipeline`/`whisker`.** (1) Serve model on **sglang** (`launch_server`) or dual-stack alongside vLLM `alliance-pod` (`00-baseline.md:65-66`). (2) New client path: `sglang.RuntimeEndpoint` or `@sgl.function` program wrapping monolith→metadata→fork(unit checks)→join, replacing per-call `AgentBackend`/`run_task` HTTP (`packages/pipeline/src/pipeline/`). (3) Fix guard-tag placement so shared prefix includes static system + `candidate_md` before per-unit tail (`00-baseline.md:48-52`). (4) Structured output via `sgl.gen(..., json_schema=...)` (`ir.py:36`, `474-499`) with MoE determinism re-validation. (5) Operational cost: olmOCR migrated **sglang→vLLM** at v0.1.75 (05-web Q2); reversing direction doubles serving-stack surface. Impact: **2–4 engineer-weeks** for parity bake-off before fleet cutover; quality-stability gate is mandatory.

- [LOW] **`run_batch` thread pool parallelizes independent papers, not in-paper fork branches.** `run_program_batch` uses `ThreadPoolExecutor` up to `max(96, cpu×16)` threads (`interpreter.py:110-112`, `157-175`); fork branches within one program share one backend and rely on server-side continuous batching. Impact: our existing 32-paper client concurrency (`00-baseline.md:34-35`) already exploits cross-paper parallelism; fork addresses the **within-paper serial chain**, which is the actual bottleneck.

## False-pass hypothesis

Rewriting unit checks as `s.fork(5)` without fixing the random per-call guard tag (`SRC{hex}` at system-prompt tail, `00-baseline.md:48-52`): each branch still diverges before `candidate_md`, RadixAttention hit rate stays ~0%, and parallel MoE batching introduces routing variance — wall time barely improves while structured JSON outputs drift across runs, silently changing defect counts on borderline pages.

## False-fail hypothesis

Rejecting fork because `benchmark_vllm_060` shows only ~3.6% offline throughput gap with radix disabled (`benchmark_vllm_060/README.md:31-32`): that regime has **no shared prefixes** (05-web Q4). A post-guard-tag-fix unit-check fork on either engine would show large TTFT reduction; falsely concluding "fork pattern doesn't help" when the client never achieved prefix identity.

## What would change my mind

A 48-paper holdout replay on `alliance-pod` hardware comparing (A) current serial 6-call vLLM HTTP vs (B) equivalent `@sgl.function` fork program on sglang `RuntimeEndpoint` with guard-tag fixed and identical JSON schemas: if (B) cuts per-paper p50 wall ≥40% **and** verdict diff ≤25% vs (A), migrate the unit-check lane to sglang; if vLLM APC+reordered prompts achieves ≥90% of (B)'s wall savings at ≤10% verdict diff, keep vLLM and skip engine migration.
