# 43 - Grounding-CPU-Profiler

**Verdict:** usable-with-conditions (+ client-side grounding CPU sums to ~98 s on the 381-paper cold fleet, ~3.3% of the 3003 s wall; `screen_pages` dominates the PDF lane because it re-tokenizes the full markdown once per page, but the multi-MB `P2728R11` tail persona 28 cited is HTML-sourced and never runs `screen_pages` in production; `asyncio.to_thread` plus a one-line candidate-token cache recover ~30–40 s wall, not minutes)
**Confidence:** high

## Findings

- [CRITICAL] **`screen_pages` is 52% of PDF-lane CPU and is algorithmically quadratic in pages×markdown size, not because multiset recall is slow.** Evidence: fleet benchmark (`_scratch/research-tapetum-llm-speedup/bench_grounding_cpu.py`, 2026-07-23): **183/183 PDF papers**, `screen_pages` **sum=41.1 s** vs total **79.7 s**; median **0.040 s**, p90 **0.390 s**, max **7.46 s** (`P3596R1`, 214 KB md, 100 pages). Root cause: each page calls `content_recall(tomd_md, page)` (`pdf_judge.py:316`), and `content_recall` re-runs `content_tokens(candidate)` on the **full** markdown every time (`metrics.py:388-392`). Micro-benchmark on fleet tail `P3100R6` (297.7 KB, 98 pages): `content_tokens(md)` once **0.040 s**, repeated 98× **3.541 s** ≈ measured `screen_pages` **4.60 s**; cached-candidate variant **0.15 s** (same flags verified). Impact: precompute `Counter(content_tokens(tomd_md))` once inside `screen_pages` (`pdf_judge.py:306-321`) saves **38.1 s** on measured PDF fleet (**48% of PDF CPU**, **1.27% of 3003 s** cold run). Quality risk: **none** (pure refactor; benchmark confirms identical `flagged` bits).

- [HIGH] **Total client CPU per typical/large paper and fleet sum (381 papers).** Evidence: measured PDF lane (183 papers): median **0.14 s** total (`screen_pages` 0.04 + `doc_metrics` 0.03 + `ground_spans` 0.008 + `classify_candidate_evidence` 0.012 + `verify_unit_evidence` 0.022); p90 **0.75 s**; max **10.74 s** (`P3596R1`). HTML lane (198 papers, no `screen_pages`): ground+classify+verify median **0.057 s**, sum **18.2 s** (same benchmark session, sidecar-driven inputs). **Fleet CPU sum ≈ 79.7 + 18.2 ≈ 98 s** (~**3.3%** of 3003.4 s). Typical 22 KB paper: **~0.06–0.14 s**. Large in-fleet PDF (`P3100R6`, 298 KB): **8.22 s** measured. Multi-MB markdown exists (`p2728r11.md` 2481 KB) but **`P2728R11` staged source is `.html`** (`data/paperstore/p2728r11.html`), HTML lane only: synthetic `screen_pages` on that md takes **20.3 s** yet **production HTML path never calls it** (`pdf_judge.py:636`, `whisker/CLAUDE.md` "PDF lane only"). Impact: fleet-weighted CPU is bounded by ~300 KB PDFs, not 2.5 MB snapshots. Quality risk: none from measurement.

- [HIGH] **Event-loop blocking: sync CPU runs inside async coroutines with zero `asyncio.to_thread` / executor use.** Evidence: `grep` 2026-07-23 — **0** matches in `packages/whisker/src/whisker/tapetum_llm/`; `judge_pdf_extraction` calls `screen_pages`, `ground_spans`, `classify_candidate_evidence` synchronously between `await run_judge_task` (`pdf_judge.py:636-697`, `judge_task.py:68`); `run_unit_checks` awaits LLM then sync `verify_unit_evidence` / `verify_defect_counts` (`unit_judge.py:408-448`). With **32** concurrent papers (`cli.py:125`) on one asyncio thread, a **7.5 s** `screen_pages` on one PDF freezes dispatch/completion handling for **all** in-flight papers. Blocking-cost model (persona 28): fleet wall adds **serial sum(CPU) not overlapped with I/O** ≈ **98 s** upper bound when CPU bursts cluster; measured slot-saturated wall is LLM-bound (`00-baseline.md:22-25`). Impact: `asyncio.to_thread` on `screen_pages`, `ground_spans`, `classify_candidate_evidence`, `verify_unit_evidence`, `verify_defect_counts` — same inputs/outputs, determinism preserved (`Counter`/`sorted` paths are order-independent, `metrics.py:388-393`, `grounding.py:248-335`). Expected wall saving **~30–40 s (~1–1.3%)** by letting other papers' HTTP completions proceed during CPU; **not** the full 98 s unless CPU were perfectly parallelized. Quality risk: **none** for thread offload alone.

- [MED] **`ground_spans` + `classify_candidate_evidence` are cheap at fleet scale but double-work on full markdown.** Evidence: PDF fleet sums **2.3 s** + **3.8 s**; median **7.7 ms** + **12.4 ms** per paper. `classify_candidate_evidence` re-invokes `ground_spans` on the entire candidate for every source-grounded span (`grounding.py:434`). `ground_spans` fuzzy tier uses `partial_ratio` on whole-document normalized strings (`grounding.py:327-329`, rapidfuzz). Impact: **≤6 s** fleet total; memoizing candidate normalization/tokenization inside `classify_candidate_evidence` saves **~2–4 s**. Quality risk: none if caches are per-call locals.

- [MED] **`verify_unit_evidence` is third-largest CPU phase; `verify_defect_counts` is dormant on cold fleet.** Evidence: `verify_unit_evidence` sum **8.2 s**, median **21.5 ms**, max **932 ms** (`unit_judge.py:681-753`: per-defect `ground_spans` on unit source + `classify_candidate_evidence` on **full** `candidate_md`). `verify_defect_counts` sum **0.0 s** — **0** persisted countable `qualifier_omission` groups in sidecars (`unit_judge.py:604-660`, `_COUNTABLE_KEYWORDS` at `538-542`). Impact: thread offload + reusing candidate grounding cache in verify path saves **~5–8 s** wall. Quality risk: none for offload; cache must not cross papers.

- [LOW] **`doc_metrics` (`text_nid` + document `content_recall`) adds 24.3 s PDF-only before monolith.** Evidence: `pdf_judge.py:628-629`; fleet sum **24.3 s**, median **33 ms**, max **3.29 s**. Separate from per-page screen but same `content_recall`/`normalized_text` machinery. Impact: **~24 s** (~0.8% wall); candidate-side work already single-pass here. Quality risk: none.

## False-pass hypothesis

Caching `content_tokens(tomd_md)` in `screen_pages` with a module-global or cross-paper mutable cache keyed only by string length (not identity) could theoretically serve stale tokens if two papers shared a hash collision or if markdown were mutated in place between pages — use a **per-call** local `hyp = Counter(content_tokens(tomd_md))` inside `screen_pages` (`pdf_judge.py:306`) to avoid any cross-paper bleed.

## False-fail hypothesis

Moving `screen_pages` to `asyncio.to_thread` without changing thresholds cannot false-fail: `content_recall` multiset math is identical (`metrics.py:388-393`); `PAGE_RECALL_FLOOR` / `PAGE_MIN_TOKENS` unchanged (`constants.py:159-165`). A real false-fail would require lowering `EVIDENCE_FUZZY_FLOOR` or `PAGE_RECALL_FLOOR`, not CPU plumbing.

## What would change my mind

Pod-side tracing showing **>10% of 3003 s wall** with `<16` active decodes **and** timestamps proving those bubbles align with **HTML-lane** papers (198/381) running multi-second `screen_pages` — would mean my HTML/PDF source-kind split is wrong for the staged corpus. A single counter example PID in `data/whisker/llm/*.tapetum.json` with `page_screen` populated and `.html` source would flip this.
