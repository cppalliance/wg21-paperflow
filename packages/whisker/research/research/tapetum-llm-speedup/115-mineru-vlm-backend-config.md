# 115 - mineru-VLM-Backend-Config

**Verdict:** usable-with-conditions — MinerU documents explicit client↔server concurrency matching and small-dense-VLM extraction, but current HEAD is vLLM/LMDeploy-only (sglang retired), ships almost no max-num-seqs tuning, and its parallelism is page-batch not serial multi-call judge chains.
**Confidence:** high

## Findings

- [CRITICAL] HTTP-client mode defaults `max_concurrency=100` and `http_timeout=600` against a remote OpenAI-compatible vLLM/LMDeploy server; CLI passthrough maps `--http-timeout` / `--max-concurrency` via unknown-arg parsing. Evidence: `research/repos/mineru/mineru/backend/vlm/vlm_analyze.py:71-75`, `research/repos/mineru/mineru/utils/cli_parser.py:25-56`. Impact: MinerU expects up to 100 concurrent page-level VLM requests with 600 s per-call budget; we run 32 concurrent papers (`00-baseline` `cli.py:125`) with 120 s unit/page caps (`constants.py:197,241`) and serial 6-call chains per paper (`pdf_judge.py:753`, `unit_judge.py:379+`). Blindly raising our cross-paper c toward 100 on 16 server slots replays the measured slots-32 regression (+60% wall, `00-baseline` constraints); quality-stability risk under MoE batch variance.

- [HIGH] `mineru-api` / `mineru-router` admission control defaults to 3 concurrent documents; client submit concurrency is `min(local_max, server_max, task_count)`. Evidence: `research/repos/mineru/mineru/cli/api_protocol.py:3`, `research/repos/mineru/mineru/cli/fast_api.py:228-234,1142-1144`, `research/repos/mineru/mineru/cli/client.py:765-768,963-984`, `research/repos/mineru/mineru/utils/config_reader.py:172-192`. Impact: MinerU under-admits documents (3) relative to our c=32 — opposite polarity. Matching their ratio on our 381-paper fleet without adding in-paper parallelism would increase queue wait and likely **increase** cold-run wall above 3003 s; quality risk low (less server overload). Portable lesson: tune client concurrency to server slot capacity, not fleet size.

- [HIGH] Shipped vLLM server wrapper sets `--port 30000`, `--gpu-memory-utilization` 0.5 (0.7 when vllm≥0.11 and VRAM≤8 GB), optional custom logits processors; **no** default `--max-num-seqs`, `--max-num-batched-tokens`, or context length. LMDeploy wrapper defaults `--cache-max-entry-count 0.5`, port 30000. All other vLLM/LMDeploy flags passthrough on every entrypoint. Evidence: `research/repos/mineru/mineru/model/vlm/vllm_server.py:45-58`, `research/repos/mineru/mineru/backend/vlm/utils.py:83-92`, `research/repos/mineru/mineru/model/vlm/lmdeploy_server.py:50-55`, `research/repos/mineru/docs/en/usage/advanced_cli_parameters.md:7-10`, `research/repos/mineru/docker/compose.yaml:15,45,80,111`. Impact: no hidden throughput recipe to copy; operator must sweep server flags (as we already measured for DeepSeek MoE). Quality neutral if we only borrow mem-fraction discipline (0.5 vs our implicit KV use).

- [HIGH] Within-document throughput uses 64-page processing windows and `batch_two_step_extract` / `aio_batch_two_step_extract` per window (async path available); debug logs `page/s` at window completion. Evidence: `research/repos/mineru/mineru/utils/config_reader.py:158-169`, `research/repos/mineru/mineru/backend/vlm/vlm_analyze.py:446-482,509-511,577-610`. Impact: MinerU parallelizes **pages inside a window** (up to 64) while we serialize monolith→metadata→escalations→unit checks. Porting in-paper parallel unit checks (advisory lane, D11-exempt per `00-baseline:39-42`) on ~1510 unit calls could save ~80–400 s fleet-wide if 5 checks/paper overlap (~20 s each); MoE batch-composition variance is the quality-stability risk.

- [MED] Primary VLM is **MinerU2.5-Pro-2605-1.2B** (1.2 B dense); changelog rationale: sub-1 B–1.2 B specialist beats general 72 B VLMs on layout/OCR/table/formula. v2.5 migrated inference from **sglang to vLLM**; sglang only mentioned as compatible remote server. Historical claim: >10 000 tok/s peak on single 4090 via sglang (MinerU 2.0 era, not current default stack). Evidence: `research/repos/mineru/mineru/utils/enum_class.py:97-98`, `research/repos/mineru/docs/en/reference/changelog.md:131,274-276`, `research/repos/mineru/README.md:287`. Impact: supports `00-baseline` lever 5 (dense 32 B unit judge / cascade): ~1510 unit checks × faster decode could shave **300–900 s** if agreement holds; monolith/full-doc reasoning on MoE may still be needed — verdict-drift risk on subtle conversion defects.

- [MED] Pipeline (non-VLM) VRAM-scales batch_ratio to 16 @ ≥32 GB GPU; hybrid batch via `MINERU_HYBRID_BATCH_RATIO`. Transformers VLM backend batch_size 8/4/1 by VRAM tier. Evidence: `research/repos/mineru/mineru/backend/pipeline/pipeline_analyze.py:353-366`, `research/repos/mineru/mineru/backend/vlm/utils.py:95-111`, `research/repos/mineru/docs/en/usage/cli_tools.md:179-187`. Impact: orthogonal to tapetum-llm judge path but shows recurring pattern — **small models + aggressive batching + VRAM-aware ratios**; not directly applicable to DeepSeek MoE without separate slot budget.

- [LOW] Documented throughput is qualitative or historical; vendor example `vllm serve` uses `--max-model-len 16384`, `--tensor-parallel-size 2`, `--enforce-eager`, no max-num-seqs. Evidence: `research/repos/mineru/docs/zh/usage/acceleration_cards/VastAI.md:106-119`, `research/repos/mineru/README.md:105-108` (35–220% hybrid speedups, accuracy −0.13 on OmniDocBench). Impact: no pages/s set point for capacity planning; hybrid effort tradeoff is extraction-speed not judge-quality analog.

## False-pass hypothesis

Matching MinerU http-client `max_concurrency=100` against our 16-slot DeepSeek MoE without raising server capacity would shorten per-call latency variance in logs but inflate queue wait and MoE expert routing variance — the 70% zero-defect unit checks (`00-baseline:29-30`) could get faster wrong "clean" answers under load, mimicking our slots-32 false-pass ( faster wall, unchanged-looking verdicts with drift on the ~16 papers where LLM changes outcomes).

## False-fail hypothesis

Adopting MinerU's conservative `MINERU_API_MAX_CONCURRENT_REQUESTS=3` document admission literally would starve our 381-paper fleet and **lengthen** the 3003 s cold run, wrongly concluding MinerU's model proves we must reduce concurrency — their speed comes from page-parallel VLM batches on a 1.2 B model, not from throttling documents alone.

## What would change my mind

Measured `mineru_vl_utils` `batch_two_step_extract` concurrency vs vLLM `--max-num-seqs` on MinerU2.5-1.2B at our call mix (short structured JSON, repeated doc prefix), showing the same client/server ratio law holds for MoE-scale judges — not just 1.2 B page OCR.
