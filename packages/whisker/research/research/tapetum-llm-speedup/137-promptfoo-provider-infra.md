# 137 - promptfoo Provider Infra

**Verdict:** usable-with-conditions — strong retry/resume and HTTP-layer inflight coalescing, but no concurrent provider-call dedup and default concurrency (4) is far below our fleet scale.
**Confidence:** high

## Findings
- [CRITICAL] No concurrent request dedup at the provider/scheduler layer; each eval step is independent. Evidence: `research/repos/promptfoo/src/scheduler/rateLimitRegistry.ts:42-43` ("No idempotency tracking. Each call is independent."). Provider caches (e.g. Anthropic) do check-then-act `cache.get` → API → `cache.set` with no inflight map (`messages.ts:852-935`). Impact: if per-unit fingerprints create identical concurrent judge calls (e.g. two papers, same page hash), promptfoo would still fire N requests; on our 2284-call cold run even 5% accidental duplicates (~114 calls) costs ~142 s wall at 20 s/call / 16 slots. Quality risk: none from absence; wasted compute only.
- [HIGH] HTTP `fetchWithCache` coalesces identical in-flight requests via `inflightFetchResponses` Map (single upstream fetch, shared Promise). Evidence: `cache.ts:298-299,870-890`. Key = scoped SHA256 of method+URL+headers+body (`cache.ts:522-550`). Impact: portable pattern for our `judge_task.py` dispatch — wrap identical `(model, system_hash, user_hash)` in an asyncio Task map; if 10 concurrent papers share one unit hash, saves ~9×20 s = 180 s for that hash group (quality-neutral if hash excludes guard tag). Quality risk: low if hash includes full structured-output schema + source text.
- [HIGH] `--retry-errors` re-runs only ERROR tombstones via resume + `excludeErrors` on completed index pairs. Evidence: `commands/eval.ts:155`, `doEval.ts:397-484`, `cliState.ts:24-31`, `evaluator.ts:2730-2731`, `evalResult.ts:796-807`; ERROR rows deleted only after successful retry (`retry.ts:426-428`). Impact: maps directly to our warm run (64.8 s, 6/381 re-tried, 375 skipped per 00-baseline); already implemented at paper grain via fingerprint — portable refinement is per-step `(paper, call_kind, unit_id)` tombstones, not whole-paper skip. Quality risk: none if tombstone semantics match fail-closed.
- [HIGH] `--filter-failing` / `--filter-failing-only` / `--filter-errors-only` slice prior JSON/DB results before re-eval. Evidence: `filterTests.ts:7-9,89-140,267-291`, `filterTestsUtil.ts:43-250`. Impact: assertion-failure vs error split avoids re-running healthy cases on partial reruns; for our fleet, separating 43 fail vs 6 error on warm path could avoid ~43×~120 s serial paper cost if we ever re-judge failures only — not on critical cold path. Quality risk: low if filter predicates match our verdict classes.
- [MED] Layered retry/backoff: scheduler `DEFAULT_RETRY_POLICY` maxRetries=3, baseDelay=1 s, maxDelay=60 s, jitter=0.2 (`retryPolicy.ts:10-15,36-39`); fetch layer default maxRetries=4, `PROMPTFOO_REQUEST_BACKOFF_MS`=5000, exp backoff (`util/fetch/index.ts:668,671,716-717`); hard quota codes fail-fast (`retryPolicy.ts:55-61`). Impact: our 55 retries ≈100 s (~4% of 3003 s) — promptfoo's stack would behave similarly; not a 5-10 min lever. Quality risk: retrying non-idempotent judge calls could duplicate side effects (N/A for us).
- [MED] Adaptive per-provider concurrency on 429: halve slots (BACKOFF_FACTOR=0.5), recover +50% after 5 successes (`adaptiveConcurrency.ts:2-5,75-79`); queue timeout default 5 min (`rateLimitRegistry.ts:34-35`). Impact: ~0 s on our self-hosted pod (not 429-bound); portable only if we add multi-tenant cloud judges. Quality risk: none on current infra.
- [MED] Multi-provider fan-out is Cartesian: tests × var-combinations × repeat × providers × prompts (`evaluator.ts:2407-2428,2472-2473,2538-2552`); concurrent steps via `async.forEachOfLimit` at `maxConcurrency` (`evaluator.ts:3853-3855`). `ProviderGroupedCallQueue` groups deferred *grading* calls by provider id (`providerCallQueue.ts:35-56`), not target LLM dedup. Impact: promptfoo optimizes breadth (many providers/prompts), opposite of our call-reduction goal; no portable speedup. Quality risk: N/A.
- [LOW] Timeout defaults: per-HTTP `REQUEST_TIMEOUT_MS`=300_000 (`providers/shared.ts:9-10`); per-eval-step `PROMPTFOO_EVAL_TIMEOUT_MS` default 0 (disabled) (`envars.ts:558-559`); global `PROMPTFOO_MAX_EVAL_TIME_MS` default 0 (`envars.ts:568-569`). Our unit timeout 120 s is tighter. Impact: promptfoo allows hung steps up to 5 min per HTTP call — slower failure detection, not faster throughput. Quality risk: longer hangs delay fail-closed.
- [LOW] Disk response cache on by default, 14-day TTL (`cache.ts:34-40,46-47`); disable via `--no-cache` (`commands/eval.ts:95-97`). Cross-run identical prompts skip API (`messages.ts:852-882`). Impact: warm-run analog already gives 375/381 skip; cross-paper unit memo would need hash keyed without per-call guard tag (cf. 00-baseline guard tag at system-prompt tail). Potential saving = duplicate unit calls × ~20 s / 16 slots; unquantified until per-unit fingerprint lands. Quality risk: stale cache if model/prompt contract changes without cache bust.

## False-pass hypothesis
Adopting promptfoo-style disk response cache keyed on full prompt hash (without busting on model/version/guard tag) would return stale judge verdicts for unchanged hash but changed rubric or model weights, silently passing regressions on re-run.

## False-fail hypothesis
Porting adaptive concurrency halving on transient 429-like signals to our self-hosted pod could unnecessarily cap in-flight requests during MoE batch-composition blips, extending wall time without improving finding quality.

## What would change my mind
Evidence that promptfoo (or a fork) added provider-level inflight dedup (shared Promise per cache key during concurrent eval steps) and measured >20% wall reduction on a 2000+ call eval with duplicate prompts — would flip to `usable` for our per-unit memo scenario.
