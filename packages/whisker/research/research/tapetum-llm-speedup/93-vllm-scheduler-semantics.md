# 93 - vLLM-Scheduler-Semantics

**Verdict:** usable-with-conditions — vLLM V1 scheduler semantics confirm our ~20 s/call is dominated by queue wait + long-chunked prefill (~16–17 s), not decode (~2–4 s); APC + payload scoping are the primary levers, not output-token shaving or raising `--max-num-seqs`.
**Confidence:** high

## Findings

- [CRITICAL] **`--max-num-seqs` bounds concurrent running sequences (decode batch width), not tokens per step.** Evidence: `self.max_num_running_reqs = self.scheduler_config.max_num_seqs` (`vllm/v1/core/sched/scheduler.py:109`); admission gate `if num_running >= self.max_num_running_reqs: break` where `num_running = len(self.running) + self.num_waiting_for_streaming_input` (`scheduler.py:671-673`); config doc "Maximum number of sequences to be processed in a single iteration" (`vllm/config/scheduler.py:63-68`); assert `len(self.running) <= self.max_num_running_reqs` after each step (`scheduler.py:1056`). Impact: alliance-pod at 16 slots caps **16 simultaneous prefills/decodes**; client c=32 (`00-baseline.md:34-35`) leaves ~16 HTTP calls in vLLM `WAITING` at zero GPU (`docs/design/metrics.md:26,54` — `vllm:num_requests_waiting`). Quality risk: raising slots regressed wall +57% (`00-baseline.md:82-83`, persona 98).

- [CRITICAL] **`--max-num-batched-tokens` is the per-scheduler-step token budget; it caps chunked prefill chunk size and total scheduled tokens per forward pass.** Evidence: `token_budget = self.max_num_scheduled_tokens` defaulting to `max_num_batched_tokens` (`scheduler.py:110-114,444`); each request scheduled with `num_new_tokens = min(remaining_work, token_budget)` then `token_budget -= num_new_tokens` (`scheduler.py:501-508,617-618,856,1015-1016`); assert `sum(num_scheduled_tokens.values()) <= self.max_num_scheduled_tokens` (`scheduler.py:1052-1053`); config "Maximum number of tokens that can be processed in a single iteration" (`config/scheduler.py:49-54`); chunked prefill enabled by default, chunks when `num_new_tokens > token_budget` (`config/scheduler.py:74-80`, `scheduler.py:846-856`). Pod H200 API-server default **8192** when flag omitted (`vllm/engine/arg_utils.py:2441-2446`); DeepSeek recipe recommends **16384** (`05-web.md:15-16`). Impact: 40k-token median prompt requires **ceil(40000/8192)=5** scheduler steps minimum (`13-prefill-interference.md:41-48`); each step is one GPU forward. Quality risk: lowering MBT improves ITL but lengthens TTFT (`docs/configuration/optimization.md:62-65`).

- [CRITICAL] **Waiting-request admission is FCFS by default; priority mode preempts lowest-priority running request on KV pressure.** Evidence: `SchedulingPolicy.FCFS` / `PRIORITY` enum (`vllm/v1/core/sched/request_queue.py:13-18`); default `policy: SchedulerPolicy = "fcfs"` (`config/scheduler.py:99-105`); waiting queue is `FCFSRequestQueue` deque append/popleft (`request_queue.py:75-84`); `--scheduling-policy` documented in V1 guide (`docs/usage/v1_guide.md:79-82`); on KV allocation failure under PRIORITY, preempt `max(running, key=(priority, arrival_time))` else FCFS pops tail of running (`scheduler.py:575-603`). Impact: our fleet has no priority hints — long 40k prefills enter `running` in arrival order and can sit at the **front** of the FCFS running loop. Quality risk: none from FCFS itself; priority misconfiguration could starve small calls.

- [CRITICAL] **Head-of-line blocking: one in-flight prefill chunk can monopolize the entire step token budget, stalling other running decoders that step — chunked prefill mitigates but does not eliminate.** Evidence: V1 explicitly rejects decode/prefill phases — unified `{request_id: num_tokens}` catch-up (`scheduler.py:426-435`, `docs/usage/v1_guide.md:72-77`); running queue scheduled **first** FCFS (`scheduler.py:468-619`) before waiting prefills (`scheduler.py:664+`); first running prefill can take `min(remaining, token_budget)` up to full MBT (`scheduler.py:501-508`); when budget hits zero, later running decoders get **zero tokens that step** (`scheduler.py:470` loop condition); docs acknowledge tradeoff: smaller MBT → better ITL (fewer prefills slowing decodes), larger MBT → better TTFT (`docs/configuration/optimization.md:53-58,62-65`). **40k prompt @ MBT=8192:** 5 prefill-heavy steps; if one chunk schedules 8192 tokens while 15 decoders need 1 token each, those 15 decoders wait the full prefill-forward latency that step (`13-prefill-interference.md:33-39`). Chunked prefill **does** interleave: after each chunk the request stays in `running` and decoders can share subsequent steps if budget remains (`scheduler.py:1023-1025`, `is_prefill_chunk` tracking `scheduler.py:1241-1249`); it **does not** reorder running queue to decode-first — doc "prioritizes decode" applies to **waiting** prefills vs running decodes, not to reordering an early running prefill (`docs/configuration/optimization.md:53-54` vs `scheduler.py:468-619`). Optional cap: `long_prefill_token_threshold` clips chunk size (`config/scheduler.py:70-72`, `scheduler.py:506-507,842-844`). Impact: under 16-slot load with many concurrent 30–100k prefills, ITL spikes and E2E inflates even when decode is 70 tok/s per request. Quality risk: aggressive `long_prefill_token_threshold` co-tune (`40-server-flag-auditor.md:40-49`) improves fairness, not verdicts.

- [CRITICAL] **Fleet arithmetic: ~20 s/call ≈ 3 s decode + 17 s (queue + prefill); optimization program should prioritize prefill elimination, not decode tuning.** Evidence baseline: 2284 calls, 16 slots → ~20 s implied (`00-baseline.md:22-25`); decode **70 tok/s** (`00-baseline.md:27-28`, `pdf_judge.py:27`); typical output **150–300 tokens** (1536 cap, prompt caps reasoning) → decode wall **150/70 = 2.1 s** to **300/70 = 4.3 s**. **Residual per call:** 20 − 3 ≈ **17 s** = queue wait + prefill (matches `per_request_metrics.md:51-53`: `time_to_first_token_ms` = schedule→first token includes prefill; `generation_time_ms` = decode only). **Prefill solo estimate:** median ~40k prompt tokens (`00-baseline.md:46-47`, persona 97) at **~2500–4000 tok/s** effective MoE prefill (40000/4000 = **10 s**; 40000/2500 = **16 s**) accounts for most of the 17 s without queue. **Queue component:** 32 client papers × 1 serial call each vs 16 server slots → utilization ρ ≈ (2284/3003)/ (16/20) ≈ **0.95**; up to **16 requests waiting** (`77-olmocr-queue-drain.md:20` — ~one slot-time ≈ **~20 s max queue wait** at saturation). **Decomposition table (median unit-check / monolith call, saturated pod):**

  | Component | Formula | Seconds |
  | --- | --- | --- |
  | Decode | 200 tok ÷ 70 tok/s | **~2.9 s** |
  | Prefill (40k, no APC) | 40000 ÷ 3500 tok/s | **~11 s** |
  | Scheduler queue | 32 clients / 16 slots, ρ≈0.95 | **~4–6 s** |
  | **E2E check** | sum | **~18–20 s** ✓ |

  **Per paper (6 serial calls):** decode total ≈ 6 × 3 = **18 s**; prefill total ≈ 6 × 40k = **240k token-equivalents** (full md resent each call, `00-baseline.md:46-47`) → **~60–90 s serial prefill** if no APC; wall per paper ~120 s serial (`00-baseline.md:38-39`) closes with queue overlap across papers. Impact: shaving 500 output tokens saves **500/70 ≈ 7 s worst case, ~0.5 s typical** — **≤3%** of 3003 s fleet; halving prefill via APC on shared `candidate_md` (calls 2–6) saves **~5 × 10 s × (1 − hit_rate) / 16 slots ≈ 600–900 s** (persona 15 envelope). Quality risk: none from accounting; wrong lever wastes engineering.

- [HIGH] **V1 admission reserves KV for full input sequence before first chunk when `scheduler_reserve_full_isl=True` (default), preventing over-admission but not shortening prefill.** Evidence: `scheduler_reserve_full_isl: bool = True` — "checks whether the full input sequence length fits… before admitting" (`config/scheduler.py:130-134`); `full_sequence_must_fit` passed to `allocate_slots` for waiting requests (`scheduler.py:925-927`); gate in `kv_cache_manager.allocate_slots` (`vllm/v1/core/kv_cache_manager.py:468-484`). Impact: 40k-token requests occupy a running slot for entire prefill duration — slot held **5+ steps** at MBT=8192 even though KV is incremental. Quality risk: none; lowering reserve increases preemption risk.

- [HIGH] **Prometheus `vllm:num_requests_waiting > 0` under fleet load confirms queue wait is real, not a client-side artifact.** Evidence: gauge definitions (`docs/design/metrics.md:26,54`); Red Hat triage note persistent waiting inflates TTFT (`05-web.md:65-66`); queue metric separate from `time_to_first_token_ms` / `queue_time_ms` per-request (`docs/features/per_request_metrics.md:51-53`). Impact: **0 s** direct; validates prefill+queue diagnosis before bench (`101-vllm-bench-harness.md:18`). Quality risk: none.

- [MED] **`long_prefill_token_threshold=0` on pod (default) means only MBT caps chunk size — no extra decode-protection beyond chunked interleaving.** Evidence: threshold 0 disables cap (`config/scheduler.py:70-72`); applied when `0 < threshold < num_new_tokens` (`scheduler.py:506-507,842-844`); persona 40 recommends **8192** co-tuned with MBT 16384 for 3k–100k judge prompts. Impact: optional co-tune **30–80 s** fleet (`40-server-flag-auditor.md:83`). Quality risk: none.

## False-pass hypothesis

Operator treats 70 tok/s decode as proof the fleet is "decode-bound" and caps `MAX_OUTPUT_TOKENS` / suppresses thinking tokens expecting **~15–20% wall cut**: each call loses at most **~4 s decode** (**~450 s / 16 ≈ 28 s fleet**, **<1%** of 3003 s) while **unchanged 40k×6 prefill duplication** still dominates; verdict quality drops from truncated quotes/schema without meaningful speedup — silent false confidence that the speed problem was output length.

## False-fail hypothesis

Operator sets `--long-prefill-token-threshold 2048` with MBT 8192 to "protect decodes" without raising MBT: median 40k prompts need **20 steps** instead of 5, **inflating TTFT and queue depth**; papers time out at `UNIT_CHECK_TIMEOUT_SECONDS=120` (`00-baseline.md:53-54`) and tombstone as errors — good conversions falsely marked error, not fail verdicts.

## What would change my mind

Off-hours `vllm bench serve` replay (`101-vllm-bench-harness.md`) of ~100 stratified judge prompts at c=32 with `--enable-per-request-metrics` showing **median `generation_time_ms` / median E2EL > 0.45** (decode dominates) OR **median `queue_time_ms` < 500 ms** with **`time_to_first_token_ms` < 3 s** at 40k prompt tokens — that would refute the queue+prefill decomposition and restore decode/MoE-slot tuning as the primary lever.
