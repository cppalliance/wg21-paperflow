# 39 - KV-Quant-Scout

**Verdict:** usable-with-conditions — FP8 KV is already the alliance-pod default, so it is not an incremental lever on the 3003 s cold run; remaining value is operator audit of `--kv-cache-dtype-skip-layers sliding_window` and APC retention (persona 15), not flipping fp8 on.
**Confidence:** high

## Findings

- [CRITICAL] **Alliance-pod already runs `--kv-cache-dtype fp8`.** Evidence: CTO answer 2026-07-07 in `packages/whisker/research/llm-batching/CTO-REQUEST.md:9` (vLLM `cppalliance/vllm-openai:v0.24.0`, `--kv-cache-dtype fp8`); RunPod launch template `https://raw.githubusercontent.com/cppalliance/runpod/master/templates/deepseek/H200SXM.txt` (same flag alongside `--max-num-seqs 16`, `--max-model-len 393216`); matches official [DeepSeek-V4-Pro recipe](https://recipes.vllm.ai/deepseek-ai/DeepSeek-V4-Pro) default. **`GET /v1/models` does not expose KV dtype** — it only confirms the served model id (`deepseek-v4-pro`, `SERVICES.toml:68`). From the client, ask the operator for: (1) RunPod "Container start command" or the `H200SXM.txt` template diff, (2) vLLM startup stdout containing `kv-cache-dtype` and `Maximum concurrency for 393216 tokens per request: X`, (3) `GET /version` or container image tag (`v0.24.0`). Impact: **0 s expected saving on the 3003 s cold run** — the lever is baseline, not backlog.

- [HIGH] **Our workload is prefill-heavy, short-decode; FP8 KV's headline wins barely move fleet wall.** Evidence: ~2284 calls, ~20 s/call at 16 slots (`00-baseline.md:22-28`); each paper serially prefills 30–100k tokens up to 6× (`00-baseline.md:36-47`); decode ~70 tok/s with output capped at 1536 tokens (`pdf_judge.py:27`, `cli.py` judge agent). FP8 blog: decode ITL slope ~**54% of BF16**, **+14.9% output throughput** under load at concurrency 8 with ~20k-token inputs ([vLLM FP8 KV blog](https://vllm.ai/blog/2026-04-22-fp8-kvcache), Table 4). Decode is ~2–4 s of ~20 s/call; even a full 14.9% throughput gain on decode-bound steps yields **~60–120 s (2–4%)** on 3003 s, not a path to 5–10 min. Quality risk: ≤1–2 pt on reasoning benchmarks (blog §Reasoning Evaluations).

- [HIGH] **FP8 KV accuracy loss is far below the advisory lane's documented verdict-flip noise floor.** Evidence: FP8 KV + attention ≤**1–2 pt** degradation on AIME25/GPQA/MATH500/LiveCodeBench ([FP8 KV blog](https://vllm.ai/blog/2026-04-22-fp8-kvcache), Figures 7–8); long-context MRCR recovers **97–98% AUC@128k** (Figure 9). Measured advisory instability: **≥25% verdict-flip rate** on identical reruns (`packages/whisker/src/whisker/CLAUDE.md:556-558`); 20-PID sweep: 15 pass/5 review vs 10 pass/10 review on identical c=32 reruns (`packages/whisker/research/llm-batching/20-sweep-results.md:31-33`). **1–2 pt benchmark loss is ~12–50× smaller than the 25% flip budget**; FP8 precision drift is in the rerun-variance noise, not a new fidelity class. Quality risk: negligible vs existing MoE batch non-invariance (`MODELS.md:77-78`).

- [MED] **DeepSeek V4 sliding-window layers: skip flag is recommended but absent from our launch template.** Evidence: V4-Pro uses **128-token SWA** plus CSA/HCA compression (`research/slots-32-regression/10-kv-preemption.md:21`); blog recommends `--kv-cache-dtype fp8 --kv-cache-dtype-skip-layers sliding_window` for hybrid models ([FP8 KV blog](https://vllm.ai/blog/2026-04-22-fp8-kvcache), quick start + Table 3: skip-SW ITL slope **71% of BF16** vs full FP8 **80%** on gpt-oss-20b). `H200SXM.txt` sets `--kv-cache-dtype fp8` only — **no `--kv-cache-dtype-skip-layers sliding_window`**. Operator should confirm whether a newer template added it; if not, A/B skip flag on decode latency. Impact: at most low-single-digit % decode improvement (SWA KV is bounded at 128 tokens); **0 s if fp8 already optimal for V4's SWA footprint**. Quality risk: low (skip keeps SWA in BF16, blog-recommended path).

- [MED] **Prefix-cache capacity: halved KV ⇒ ~2× APC block headroom at 393216 context — synergy with persona 15, but pool is already oversized for our load.** Evidence: FP8 halves KV bytes per token ([FP8 KV blog](https://vllm.ai/blog/2026-04-22-fp8-kvcache)); at `--max-model-len 393216`, fp8 peak ~**1.85 GiB/seq** vs bf16 ~**3.7 GiB/seq** (`research/slots-32-regression/10-kv-preemption.md:46-47`); mid KV pool ~**150 GiB** → theoretical full-length slots **~81 fp8 vs ~40 bf16**. Active fleet peak at 16×100k fp8 prompts: **~7.5 GiB** vs **~111–209 GiB pool** (`10-kv-preemption.md:14-17,43-44`) — **~7–13× headroom** before exhaustion. APC block granularity **16 tokens** ([05-web.md Q4](research/tapetum-llm-speedup/05-web.md)); halving KV storage ⇒ **~2× prefix blocks storable before LRU eviction** in the same pool. Binding APC failure was DeepSeek SWA evicting APC blocks (0% hits → 74.3% after PR #43447 + retention, [05-web.md Q1](research/tapetum-llm-speedup/05-web.md)), not raw pool size. Impact: fp8 already gives persona 15 the doubled APC envelope; incremental fp8 toggle saves **0 s**; combined with APC fix + prompt reorder, persona 15 estimates **600–1100 s (20–37%)** (`15-prefix-cache-enabler.md:22`). Quality risk: none for KV dtype; reorder A/B still required.

- [LOW] **If fp8 were off (bf16), turning it on would help concurrency and APC retention, not per-call prefill latency on V4.** Evidence: V4 at 1M fp8 ≈ **4.8 GiB/seq** vs V3.2 bf16 **83.9 GiB/seq** ([vLLM DeepSeek-V4 blog appendix](https://github.com/vllm-project/vllm-project.github.io/blob/main/_posts/2026-04-24-deepseek-v4.md)); at 100k, **~0.47 GiB/seq fp8** (`10-kv-preemption.md:32-35`). Prefill TTFT on large head_dim can regress with two-level accumulation (blog §Limitations); V4 head architecture differs, but our bottleneck is call count × long prefill, not KV-OOM. Impact: hypothetical bf16→fp8 migration ≈ blog **+14.9% decode throughput** + doubled APC blocks — **secondary to call elimination and prefix-hit restructuring**. Quality risk: ≤1–2 pt (above).

## False-pass hypothesis

Operator disables FP8 KV to bf16 believing it will stabilize judge verdicts: wall time stays ~3003 s (or rises from lost decode throughput and tighter APC eviction), while the **≥25% flip rate persists** from MoE batch non-invariance (`20-sweep-results.md:31-37`), falsely attributing instability to KV precision when reruns already flip without any dtype change.

## False-fail hypothesis

Enabling full FP8 on all V4 layers (no `skip-layers sliding_window`) while APC retention is unfixed: SWA-layer FP8 overhead adds constant decode tax without memory benefit on 128-token windows (blog break-even **>700k tokens** before fixes on gpt-oss-20b, Table 3), operators see no wall improvement and conclude "KV quantization failed" when the missing pieces are skip-layers + PR #43447 retention + prompt alignment (persona 15).

## What would change my mind

vLLM startup log or RunPod command showing **`--kv-cache-dtype auto` or bf16** (not fp8) on the live pod, followed by a 381-paper A/B with fp8 enabled, `--kv-cache-dtype-skip-layers sliding_window`, and PR #43447 retention: **≥300 s wall reduction** on the 3003 s cold run with verdict diff rate **≤25%** vs control on the 48-paper holdout (`15-prefix-cache-enabler.md:34`). That would upgrade fp8 from "already captured" to "recoverable regression."
