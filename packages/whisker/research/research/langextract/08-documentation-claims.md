# 08 - Documentation-Claims

**Verdict:** usable-with-conditions — Core README marketing oversells grounding precision and schema guarantees; provider-specific limits (Ollama serial infer, OpenAI-compatible parse failures) are buried or absent while the happy-path Gemini docs are mostly accurate.
**Confidence:** high

## Findings
- [CRITICAL] README claims every extraction is mapped to its **exact** source location, but alignment is tiered and often approximate or absent. Evidence: README.md:39 ("Maps every extraction to its exact location"); README.md:94-95 (same doc admits `char_interval = None` for ungrounded items); resolver.py:786 (`MATCH_FUZZY`), resolver.py:1018 (`char_interval = None` on failed lesser match), resolver.py:1377-1404 (0.75 coverage + 1/3 density gates accept partial LCS spans). Impact: integrators treating `char_interval` as verified verbatim evidence will over-trust fuzzy spans and miss silent ungrounded extractions; contradicts the baseline's graded-alignment anchor but the README headline still reads as a guarantee.
- [HIGH] README promises schema enforcement that **guarantees** robust structured output, but Ollama and OpenAI-compatible paths only get JSON syntax mode, not field-level constraints. Evidence: README.md:40-41 ("Enforces a consistent output schema… guarantee robust, structured results"); core/schema.py:119-124 (`FormatModeSchema`: "doesn't enforce structure, only output format"); ollama.py:172-178 (`FormatModeSchema`, non-strict); openai.py:223-224 (fallback `{"type":"json_object"}` when no `openai_schema`); https://github.com/google/langextract/issues/414 (vLLM/lmdeploy OpenAI-compatible: maintainer workaround `use_schema_constraints=False`, success still <20%). Impact: self-hosted / Ollama users inherit doc-implied reliability the code cannot deliver; baseline DQ2 correctly flags no guided-decoding path — README wording still overstates parity with Gemini strict mode.
- [HIGH] README markets **parallel processing for speed** without stating it is provider-specific and capped by `batch_length`; Ollama is always serial. Evidence: README.md:41,157-158 ("parallel processing", `max_workers=20`); ollama.py:291-310 (sequential `for prompt in batch_prompts`, no `ThreadPoolExecutor`); gemini.py:476-478 / openai.py:355-357 (parallel only when `len(batch_prompts) > 1`); extraction.py:57,125-127 (`batch_length=10` default, effective parallelism `min(batch_length, max_workers)`); extraction.py:243-248 (warns when `batch_length < max_workers`). Impact: README's `max_workers=20` example uses at most 10 workers with defaults; Ollama users get zero speedup from `max_workers` despite README's general "Flexible LLM Support" local-model story (README.md:43).
- [MED] `extract()` docstring misattributes parallel support to **Gemini only**, omitting OpenAI's identical thread-pool path and Ollama's lack of support. Evidence: extraction.py:125-127 ("Supported by Gemini models"); openai.py:355-358 (same `ThreadPoolExecutor` pattern as gemini.py:476-478); ollama.py:266-291 (no parallelism). Impact: misrouting performance tuning — users may raise `max_workers` on Ollama or under-configure OpenAI expecting Gemini-only behavior.
- [MED] README OpenAI section implies turnkey structured outputs for all OpenAI-routed models, but example-derived strict `json_schema` is bypassed on OpenAI-compatible backends that only honor `json_object`. Evidence: README.md:330-334 ("uses structured outputs or JSON mode"); README.md:356-370 (`ModelConfig(provider="openai")` for compatible endpoints); openai.py:208-224 (`openai_schema` → strict `json_schema`; else `json_object` only); factory.py:280-283 (schema from examples when `use_schema_constraints=True`, default in extraction.py:56); https://github.com/google/langextract/issues/414. Impact: doc presents OpenAI-compatible routing as first-class; runtime is parse-and-pray with default `suppress_parse_errors=True` (extraction.py:365, resolver.py:309-312) dropping failed chunks silently.
- [MED] `docs/examples/output_schema.md` and README imply enum/schema reliability on OpenAI, but doc also notes provider-side validation only — no retry on schema or parse failure (baseline anchor: resolver.py:309-321). Evidence: output_schema.md:212-218 ("LangExtract validates only the output envelope locally; the provider API validates the JSON schema itself"); resolver.py:276-321 (parse/schema errors raise or return `[]`, no compliance retry loop); README.md:40 ("guarantee robust, structured results"). Impact: doc stack reads as end-to-end reliability; code fails closed per chunk or drops data without recovery — weaker than our tapetum retry lane and unstated in README marketing bullets.
- [LOW] `WordAligner.align_extractions` docstring says failed alignments set **token interval** to None, but code clears `char_interval` (and may leave extractions in output with `alignment_status=None`). Evidence: resolver.py:811-813 ("token interval is set to None"); resolver.py:1017-1019 (`token_interval = None`, `char_interval = None`); core/data.py:87 (`char_interval: CharInterval | None = None`). Impact: minor API-doc drift for anyone tuning alignment via docstrings alone.

## False-pass hypothesis
A user filters `[e for e in result.extractions if e.char_interval]` per README.md:94-95 after a fuzzy-aligned run: an extraction with `MATCH_FUZZY` at threshold 0.75 (resolver.py:786,1377-1404) covering only ~75% of tokens in a noisy span passes the filter and is treated as verified evidence even though the README "exact location" bullet (README.md:39) implies verbatim grounding.

## False-fail hypothesis
A user disables fuzzy alignment via `resolver_params={"enable_fuzzy_alignment": False}` believing README "exact text" prompts (README.md:64) suffice: valid extractions with minor tokenization or plural-stem mismatches (`resolver.py:1275-1281`) get `char_interval=None` and are dropped from visualization (`visualization.py:251-254`) despite being semantically correct extractions from the LLM.

## What would change my mind
A README revision that (1) replaces "exact location" with graded `AlignmentStatus` semantics and default fuzzy behavior, (2) documents provider capability matrix (Gemini strict / OpenAI strict vs json_object / Ollama JSON-only / compatible-endpoint caveats with Issue #414), and (3) states `max_workers` × `batch_length` × provider parallelism explicitly — verified against a single integration test matrix in CI — would flip this to **usable** for doc-trust purposes.
