# 09 - Error-Handling-Robustness

**Verdict:** usable-with-conditions   (+ default `extract()` path silently drops failed chunks and emits complete-looking documents; safe only when `suppress_parse_errors=False`, batch padding is audited, and consumers treat `char_interval=None` as unverified)
**Confidence:** high

## Findings
- [CRITICAL] `extract()` sets `suppress_parse_errors=True` by default, so any chunk whose model output fails parse or schema validation logs a warning and contributes zero extractions while the run continues. Evidence: `extraction.py:136-138,365`, `resolver.py:309-321`, baseline 00 section 3 ("logs a warning and returns `[]`"). Impact: violates root `CLAUDE.md` Fidelity ("Never produce a partial result mistakable for a complete one", `CLAUDE.md:125-127`) and lacks our `adjudicate.py` partial disclosure (`adjudicate.py:242-246` forces review when `state.partial`); downstream pipelines see an `AnnotatedDocument` with no failure marker.
- [HIGH] Gemini Batch API pads missing prompt results with empty strings, which then hit the empty-input parse path and, under the default suppress flag, become silent chunk drops. Evidence: `gemini_batch.py:650-651,704`, `format_handler.py:169-170`, `resolver.py:309-312`, baseline 00 section 3 (no schema-failure retry). Impact: after a costly batch job, one bad row can erase an entire chunk's entities without aborting; Issue #287 (https://github.com/google/langextract/issues/287) documents the batch fragility; the documented workaround (`suppress_parse_errors=True`, 05-web.md Issue #287) trades hard failure for hidden loss.
- [HIGH] Parallel real-time inference is all-or-nothing: one prompt failure inside `ThreadPoolExecutor` raises `InferenceRuntimeError` and aborts the whole `infer()` call before any chunk in that batch is resolved. Evidence: `gemini.py:490-497`, `openai.py:369-378`, `annotation.py:392-408` (no per-chunk try/except around `infer`). Impact: a single transient or parse-adjacent error after retries kills the entire document pass; prior completed batches are kept but the current batch contributes nothing and the exception propagates with no partial-result envelope. Issue #240 (https://github.com/google/langextract/issues/240, 05-web.md) shows pre-fix 503 behavior; per-chunk retry (`gemini.py:351-391`) reduces but does not eliminate whole-document abort after retry exhaustion.
- [HIGH] Failed alignment keeps extractions in the output with `char_interval=None` and `alignment_status=None`, with no document-level flag or drop. Evidence: `resolver.py:1021-1068`, `core/data.py:87-88`, `annotation.py:431-432` (all aligned yields appended regardless of grounding). Impact: consumers treating returned extractions as grounded evidence receive structurally valid objects missing verified spans; our tapetum lane drops ungrounded quotes (`adjudicate.py:234-238`) rather than passing them through.
- [MED] Gemini batch JSONL parsing silently discards malformed lines and never surfaces a skip count. Evidence: `gemini_batch.py:612-613,703-704`. Impact: corrupt batch output files shrink effective coverage without raising; combined with empty-string padding, index alignment can mask which prompts failed.
- [MED] OpenAI Batch API intentionally fails the whole job on per-item errors (no `ignore_item_errors`), while Gemini batch defaults `ignore_item_errors=False` but allows opt-in continuation that still pads failures as empty strings. Evidence: `openai_batch.py:57-58,554-557`, `gemini_batch.py:78,616-619,704`. Impact: asymmetric batch semantics across providers; Gemini's permissive mode still hides per-item loss behind empty outputs rather than marking partial completion.
- [LOW] GCS batch cache write/read failures are warning-only and skipped. Evidence: `gemini_batch.py:468-470,479-480,500-501`. Impact: no extraction corruption directly, but silent cache misses force re-inference or stale reads without surfacing degraded reliability.

## False-pass hypothesis
A 50-chunk clinical document where chunk 23 returns markdown-fenced garbage: with default `suppress_parse_errors=True`, chunk 23 contributes `[]`, the run completes, and the returned `AnnotatedDocument` looks complete while entities from that ~1000-char window are permanently absent; no `partial` bit, no raised error, only a log line.

## False-fail hypothesis
A 10-prompt parallel batch where prompt 7 exhausts Gemini retries on 503: `infer()` raises `Parallel inference error` (`gemini.py:494-496`) and the entire document annotation aborts even though prompts 0-6 and 8-9 may have succeeded inside the pool; none of their extractions reach `per_doc` because the exception occurs before the resolve loop.

## What would change my mind
A first-class `AnnotatedDocument.partial` (or per-chunk failure list) populated whenever `suppress_parse_errors` drops a chunk, batch padding supplies `""`, or alignment leaves `char_interval=None`, with tests asserting the flag is set and default `extract()` behavior flips to fail-not-partial.
