# 22 - Self-Hosting-Sovereignty-Auditor

**Verdict:** usable-with-conditions — langextract can theoretically run on a sovereignty-compliant vLLM stack only after a custom provider fork that ports our `VllmThinkingBackend` structured-output and retry patterns; the shipped library is cloud-first (Gemini default, mandatory Google SDK deps) and has no working first-class vLLM path.
**Confidence:** high

## Findings
- [CRITICAL] Default API surface targets Google Gemini cloud, not self-hosted inference. Evidence: `extraction.py:49` sets `model_id: str = "gemini-3.5-flash"`; `gemini.py:41` defines `_DEFAULT_MODEL_ID = 'gemini-3.5-flash'`; v1.5.0 release bumped default to `gemini-3.5-flash` (05-web.md Q1). Impact: naive `lx.extract()` calls violate root `CLAUDE.md:64-70` model-sovereignty mandate (open-weight self-hosted production, cloud only as dev ceiling).
- [CRITICAL] Core install unconditionally pulls Google Cloud SDKs even when only Ollama/vLLM is intended. Evidence: `pyproject.toml:35-36` lists `google-genai>=1.39.0` and `google-cloud-storage>=2.14.0` as required (not optional) dependencies; `gemini_batch.py:42-44` imports `google.genai` and `google.cloud.storage` at module load; `gemini.py:36` imports `gemini_batch`. Impact: sovereignty breach at supply-chain layer — every install carries Google Cloud footprint regardless of runtime provider choice (00-baseline.md §2).
- [CRITICAL] No first-class vLLM provider exists in-tree; maintainer closed built-in vLLM PR without merge. Evidence: grep over `langextract/` returns 0 hits for `vllm|guided_json|guided_decoding|extra_body` (00-baseline.md §3); Issue #236 accepted community `langextract-vllm` plugin, PR #393 for built-in vLLM closed unmerged (05-web.md Q3); `pyproject.toml:94-97` entry points list only `gemini`, `ollama`, `openai`. Impact: our production path (`VllmThinkingBackend`, `model_backends.py:234-247`) has no upstream counterpart; integration requires a third-party plugin or fork.
- [HIGH] Documented vLLM/lmdeploy OpenAI-compatible path fails structured extraction at scale. Evidence: Issue #414 reports `ResolverParsingError` on vLLM/lmdeploy while Ollama succeeds; maintainer workaround `fence_output=False, use_schema_constraints=False` yields success below 20% (05-web.md Q3); `openai.py:223-224` falls back to `response_format={"type": "json_object"}` without strict field constraints when no `OpenAISchema` is active. Impact: the OpenAI-compatible route our vLLM pod exposes is documented broken — opposite of our `VllmThinkingBackend` schema-in-prompt + `_RAW_JSON_MAX_ATTEMPTS=3` retry loop (`model_backends.py:76-85, 311-375`).
- [HIGH] Built-in self-hosted path is Ollama-only with non-strict JSON mode, not vLLM OpenAI-compatible. Evidence: `ollama.py:172-178` returns `FormatModeSchema` (JSON mode, non-strict); `core/schema.py:142-149` `to_provider_config()` emits only `{"format": "json"}` with no field constraints; Ollama uses native `/api/chat` at `http://localhost:11434` (`ollama.py:105`), not vLLM's OpenAI `/v1/chat/completions`. Impact: cannot point langextract at our RunPod vLLM endpoint without OpenAI provider (broken, see above) or a custom plugin; Ollama JSON mode lacks the pydantic `output_type` enforcement our D6/D10 invariants require (`CLAUDE.md:83-87`).
- [MED] Model-ID routing misaligns our open-weight model names with vLLM. Evidence: `patterns.py:42-43,57` route `^qwen`, `^deepseek`, `^deepseek-ai/` to Ollama provider (priority 10), not OpenAI-compatible; our `SERVICES.toml` serves DeepSeek/Qwen via vLLM OpenAI API. Impact: `lx.extract(model_id="deepseek-v4-pro")` resolves to Ollama HTTP API, not our pod — requires explicit `config=factory.ModelConfig(provider="openai", ...)` plus broken json_object path, or a custom entry-point plugin (`factory.py:159-162`, `providers/__init__.py:71-139`).
- [MED] Default parallel inference (`max_workers=10`) conflicts with our serial-default determinism invariant. Evidence: `extraction.py:58` defaults `max_workers: int = 10`; `gemini.py:129` and `openai.py:54` match; baseline notes multiple in-flight requests by default vs our D11 `Semaphore(1)` (`00-baseline.md §3`, `CLAUDE.md:88`). Impact: even a forked vLLM provider would need `max_workers=1` forced to meet dissect/tapetum determinism contract unless scoped as a per-package opt-in.
- [LOW] Community `langextract-vllm` plugin documents connection/sampling kwargs only, no guided decoding. Evidence: plugin README (05-web.md Q3) lists `provider_kwargs` for server connection and sampling; no `guided_json`, `structured_outputs`, or schema-constrained generation. Impact: plugin solves provider registration, not the structured-output gap that blocks sovereignty-compliant fidelity.

## False-pass hypothesis
Routing a vLLM-served DeepSeek model through the OpenAI provider with `use_schema_constraints=False` and `suppress_parse_errors=True` (Issue #414 maintainer workaround, 05-web.md) would accept runs that return empty extraction lists on most chunks while logging warnings — structurally "success" with silently dropped evidence, violating our fidelity invariant (`CLAUDE.md` Fidelity: fail not partial).

## False-fail hypothesis
A sovereignty-compliant vLLM run using strict Gemini/OpenAI cloud APIs with `use_schema_constraints=True` would parse reliably but route all inference through Google/OpenAI endpoints — passing schema checks while breaching model sovereignty; the library would appear functional while every production call is cloud-dependent.

## What would change my mind
A merged first-class vLLM provider in google/langextract that (1) passes `guided_json` or equivalent schema constraints via `extra_body` to vLLM, (2) implements a bounded schema-validation retry loop with error feedback (matching our `VllmThinkingBackend` pattern), (3) splits `google-genai`/`google-cloud-storage` into optional extras, and (4) demonstrates above 95% end-to-end extraction success on the Issue #414 reproduction case (currently below 20%, 05-web.md) on the same self-hosted stack we run in production.
