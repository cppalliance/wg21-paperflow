# 03 - Determinism-Auditor

**Verdict:** usable-with-conditions   LangExtract can yield stable *ordering* when configured for serial inference, but shipped defaults and several resolver/API paths inject run-to-run semantic variance incompatible with our D1–D11 contract unless every knob is pinned explicitly.
**Confidence:** high

## Findings
- [CRITICAL] Public `extract()` defaults activate parallel LLM inference: `batch_length=10` and `max_workers=10` (`extraction.py:57-58`), which triggers `ThreadPoolExecutor` whenever `len(batch_prompts) > 1` (`gemini.py:476-479`, `openai.py:355-358`). Baseline §3/DQ1 confirms up to 10 in-flight requests. Impact: violates our D11 serial-default invariant (`CLAUDE.md:88`, `tasks.py:30-38` `_TASK_CONCURRENCY=1`); hosted endpoints can return different extractions under concurrent load even when yield order is index-stable (`gemini.py:487-504` mirrors `runner.py:133-162` shape but without our semaphore(1) cap).
- [HIGH] OpenAI provider leaves sampling unpinned: `temperature: float | None = None` (`openai.py:53`) and `_build_chat_completions_params` only sets temperature when not None (`openai.py:204-206`); `extract()` also defaults `temperature=None` (`extraction.py:54`, filtered at `extraction.py:328`), so the model/API default applies. Impact: conflicts with our D5 (no per-call drift) and pipeline D2 (backends pin `temperature=0` internally); run-to-run extraction content can differ on the default OpenAI path while Gemini defaults to `0.0` (`gemini.py:128`).
- [HIGH] No library-level seed authority: OpenAI forwards `seed` only if caller supplies it (`openai.py:230-240`); Ollama documents `seed: If None, random seed is used` (`ollama.py:575`); Gemini path has no seed parameter at all (`gemini.py:407-421`). Impact: self-hosted/Ollama paths are explicitly non-reproducible by default; our D2 requires backends to apply `seed=0` internally (`pipeline/CLAUDE.md` D2).
- [HIGH] Resolver ordering without explicit index suffix follows JSON/dict key iteration order: `for extraction_class, extraction_value in group.items()` assigns auto-increment `extraction_index` (`resolver.py:474-517`) then sorts by that index (`resolver.py:534`). When `extraction_index_suffix` is None (documented default in `extraction.py:134-135`), a model that permutes object key order across runs permutes which entity receives index 1 vs 2, changing sorted output and downstream monotonic alignment input order (`resolver.py:1228-1242`). Impact: D7-class failure (unordered collection iteration into structured output) even when LLM returns the same multiset of fields.
- [MED] `extract()` forces `suppress_parse_errors=True` by default (`extraction.py:365`), causing parse/schema failures to return `[]` for that chunk (`resolver.py:309-321`) instead of failing the document. Impact: borderline model outputs that parse on one run and fail on the next silently drop whole chunks, producing structurally different annotation sets without surfacing fidelity failure (contrasts our fidelity invariant, `CLAUDE.md:123-127`).
- [MED] Baseline understates the default parallelism entry point: it cites `batch_length=1` on `Annotator` (`annotation.py:214`, baseline §3) but the primary API `extract()` overrides with `batch_length=10` (`extraction.py:57`, `extraction.py:393-418`). Impact: integrators reading baseline §3/DQ4 may believe serial chunk batches are default when the shipped path enables 10-wide parallel inference out of the box.
- [LOW] Gemini retry backoff uses jittered sleep (`random.uniform(0.5, 1.5)`, `gemini.py:376-377`) and historical multi-document parallel collection had an ordering bug (Issue #260, fixed PR #276 per `05-web.md`). Impact: jitter affects timing/retry scheduling only, not a direct output-order bug today; Issue #260 shows the failure class is real in this codebase's parallel annotation history.

## False-pass hypothesis
Two runs of `extract(text, examples=..., model_id="gpt-4o-mini")` with defaults (`batch_length=10`, `max_workers=10`, `temperature=None`, `suppress_parse_errors=True`) on a long document could both "succeed" while differing in extraction count and entity order: parallel hosted calls drift semantically, OpenAI default temperature adds sampling variance, and auto-index mode permutes order when the model reorders JSON keys, yet no error is raised.

## False-fail hypothesis
A user sets `max_workers=1`, `batch_length=1`, `temperature=0.0`, passes `seed` on OpenAI/Ollama, sets `resolver_params={"suppress_parse_errors": False}` and uses explicit `extraction_index_suffix` in examples; under Gemini with `temperature=0.0` (`gemini.py:128`) the pipeline is as deterministic as the upstream model allows, and index-keyed thread-pool yield (`gemini.py:487-504`) preserves chunk order like our `gather_concurrent` (`runner.py:133-162`).

## What would change my mind
A maintained contract (README + `extract()` defaults) guaranteeing serial-by-default inference (`max_workers=1`, `batch_length=1`), pinned `temperature=0` and `seed=0` on every provider, sorted iteration before any prompt/schema serialization (D7), and fail-loud on parse errors, with a regression test asserting two back-to-back runs on fixed fixtures produce identical extraction classes, order, and `char_interval` spans.
