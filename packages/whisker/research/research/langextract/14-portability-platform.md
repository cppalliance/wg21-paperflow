# 14 - Portability-Platform

**Verdict:** usable-with-conditions   Core orchestration is plain Python and can run on Windows against a remote HTTP endpoint, but defaults, dependency closure, model routing, and structured-output paths assume Google Cloud or local Ollama; RunPod vLLM requires explicit non-default wiring and still lacks reliable schema compliance.
**Confidence:** medium

## Findings
- [CRITICAL] Default `extract()` targets live Gemini, not self-hosted inference. Evidence: `extraction.py:49` (`model_id="gemini-3.5-flash"`), `gemini.py:41` (`_DEFAULT_MODEL_ID`), baseline §3 (google-genai hard dep). Impact: any caller that omits `model_id`/`config`/`model` fails offline and outside Google Cloud on first inference; the happy path is cloud-first, not sovereign/self-hosted.
- [CRITICAL] Open-weight model IDs (e.g. `qwen*`, `gemma*`, `deepseek*`) auto-route to the Ollama provider and default to `http://localhost:11434` with `/api/generate`/`/api/chat`, not OpenAI-compatible `/v1/chat/completions`. Evidence: `patterns.py:37-43`, `ollama.py:105`, `factory.py:98-101`, `ollama.py:302-307`. Impact: on Windows+RunPod, passing a Qwen model name without `provider="openai"` silently talks to localhost (usually nothing listening) instead of the RunPod vLLM endpoint; wrong API surface even if URL kwargs are forwarded.
- [HIGH] No first-class vLLM / RunPod structured-output path; OpenAI-compatible backends rely on loose `json_object` mode only. Evidence: baseline §3/DQ2 (grep 0 hits for `guided_json|vllm|extra_body`), `openai.py:223-224`, 05-web Issue #414 (https://github.com/google/langextract/issues/414, maintainer workaround `fence_output=False, use_schema_constraints=False`, success still below 20%). Impact: our RunPod lane cannot enforce extraction schema the way Gemini/OpenAI strict mode does; parse/align failures dominate off Google Cloud.
- [HIGH] Default `RegexTokenizer` does not tokenize CJK scripts; alignment `char_interval` is wrong or missing for non-ASCII source. Evidence: `annotation.py:156` (default `RegexTokenizer()`), `tokenizer.py:154-156` (`_LETTERS_PATTERN = r"[^\W\d_]+"` skips Han/Hiragana/etc.), 05-web Issue #334 (https://github.com/google/langextract/issues/334). Impact: WG21 papers with CJK author names, quoted identifiers, or mixed scripts get broken or absent spans even when extraction JSON is correct; portability of the grounding layer fails off ASCII-centric assumptions.
- [HIGH] Base wheel always installs Google Cloud SDK stack regardless of provider used. Evidence: `pyproject.toml:35-36` (`google-genai`, `google-cloud-storage`), baseline §3 ("Runtime deps are cloud-SDK-heavy"). Impact: offline/air-gapped Windows installs still pull Google client libraries and their credential discovery paths; non-Google deployments carry unnecessary supply-chain and import surface.
- [MED] OpenAI provider (the viable RunPod transport) is an optional extra, not core. Evidence: `pyproject.toml:58-59` (`openai = ["openai>=1.50.0"]`), lazy import `openai.py:135`. Impact: `pip install langextract` on Windows without `[openai]` fails at provider init when targeting RunPod; easy to miss in docs-driven setup.
- [MED] Prompt template file reads use locale default encoding, not UTF-8. Evidence: `prompting.py:70` (`pathlib.Path(prompt_path).open("rt")` with no `encoding=`). Impact: UTF-8 few-shot prompt files with non-ASCII examples mis-decode on Windows (typical cp1252 locale), breaking reproducibility off the author's UTF-8 Linux/macOS machine.
- [LOW] Maintainer/dev scripts assume Unix paths and shell. Evidence: `.github/scripts/zenodo_publish.py:186` (`/tmp/...`), CI references `./autoformat.sh` (`.github/workflows/ci.yaml:437`). Impact: Windows contributor friction only; does not block library import, but signals the project is not validated as a first-class Windows dev target.

## False-pass hypothesis
Caller sets `provider="openai"`, `base_url` to RunPod, and `model_id="gpt-4o-mini"`, receives occasional valid JSON, and treats extractions as production-ready. Default `RegexTokenizer` still mis-aligns CJK or accented spans (Issue #334 class): extractions carry non-`None` `char_interval` with `MATCH_FUZZY` status that look grounded in trace output but point at wrong source offsets.

## False-fail hypothesis
Caller passes `model_id="qwen2.5-72b"` and `model_url=<RunPod OpenAI URL>` without `provider="openai"`. Router selects Ollama (`patterns.py:42`), factory defaults `base_url` to `http://localhost:11434` (`factory.py:99-100`), and requests hit Ollama's `/api/generate` protocol against localhost. Connection refused on Windows looks like "langextract broken on Windows" when the real failure is provider mis-routing off Google's naming conventions.

## What would change my mind
A merged built-in or officially supported vLLM provider that wires RunPod/OpenAI-compatible `base_url` with schema-constrained decoding (or a documented >95% parse-success rate on vLLM with PR #444-level fence stripping plus schema retry), demonstrated on Windows PowerShell against a remote endpoint without `google-genai` in the install path.
