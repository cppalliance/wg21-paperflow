# 10 - Adversary-Evasion

**Verdict:** usable-with-conditions — default 0.75/1/3 fuzzy gates and MATCH_LESSER admit fabricated tail tokens and subsequence-stitched spans as grounded; density and post-verify hardening are mandatory before trusting char_interval as evidence.
**Confidence:** high

## Findings
- [CRITICAL] Alignment never verifies that `source[char_interval]` matches `extraction_text`; it only finds a token window whose normalized tokens overlap the extraction. On success the full LLM string is kept while `char_interval` may cover a strict subset. Evidence: `_lcs_fuzzy_align_extraction` sets intervals and returns without reading the slice back (`resolver.py:776-787`); MATCH_LESSER path does the same (`resolver.py:1009-1014`). Impact: a downstream consumer treating any non-`None` `char_interval` as "this extraction is verbatim in the source" will accept semantically wrong or partially invented strings as grounded.
- [HIGH] MATCH_LESSER (default `accept_match_lesser=True`, `resolver.py:335`) grounds extractions whose `extraction_text` is longer than the matched span. Maintainer tests encode the exploit: `"severe heart problems complications"` aligns to `"severe heart problems"` with `alignment_status=MATCH_LESSER` while `"complications"` never appears in the source (`tests/resolver_test.py:1467-1495`). Impact: attacker (or hallucinating LLM) appends a fabricated claim to a real prefix; alignment passes and the lie ships inside `extraction_text`.
- [HIGH] LCS fuzzy matching is subsequence-based, not contiguous-string equality; at the default 1/3 density gate, three matched tokens may span nine source tokens (`_accept_lcs_match`, `resolver.py:1388-1404`; unit oracle `density_ok_on_gapped`, `tests/fuzzy_alignment_cases_test.py:372-377`). The fallback-to-denser-submatch test accepts `"alpha beta gamma delta"` when only `"beta gamma delta"` is local, span `(11,14)` (`tests/fuzzy_alignment_cases_test.py:491-514`). Impact: engineer extraction text from high-frequency tokens scattered across a chunk; alignment returns a wrong composite span and still tags MATCH_FUZZY.
- [HIGH] Fuzzy tier has no monotonic occurrence constraint, unlike exact DP (`_select_monotonic_matches`, `resolver.py:1113-1124` vs fuzzy loop `resolver.py:1027-1065`). On documents with repeated boilerplate (WG21 front matter, committee names, "This paper proposes"), a fabricated extraction can fuzzy-anchor to the first occurrence while the semantic referent is elsewhere. Impact: false-pass with a plausible-looking `char_interval` pointing at the wrong mention; exact tier would map successive repeats, fuzzy does not.
- [MED] Light plural stemming in `_normalize_token` (`resolver.py:1275-1281`) widens the fuzzy equivalence class: `"heart problem"` fuzzy-matches source `"heart problems"` (`tests/resolver_test.py:1456-1484`). Attacker swaps number/tense on a shared stem so the aligned span is a different entity than the extraction claims. Impact: wrong-span acceptance on near-duplicate morphology, invisible if consumers skip slice verification.
- [MED] Our tapetum `ground_spans` is more evadable for invisible wrong-place passes: `partial_ratio(norm_quote, norm_md)` runs against the whole normalized document with no returned span (`whisker/tapetum_llm/grounding.py:49-52`, `EVIDENCE_FUZZY_FLOOR=0.90`, `constants.py:50`), and `normalized_text` strips punctuation via `clean_string` (`metrics.py:118-126`). A short generic quote can fuzzy-match anywhere in a 500k-char paper; the pass gives no `char_interval` to audit. Langextract's lower ratio (0.75, `resolver.py:57-58`) is offset by locality and span emission; ours is stricter per-quote but blind to location.
- [LOW] Legacy fuzzy (`fuzzy_alignment_algorithm="legacy"`, `resolver.py:591-715`) scans all windows up to `len(source_tokens)` with no density gate; deprecated but still reachable (`resolver.py:1050-1058`, `skills/langextract-usage/references/resolver-params.md:40-45`). Impact: operators who downgrade to legacy for compatibility inherit a strictly weaker adversary surface than LCS.

## False-pass hypothesis
Source chunk: `"LEWG reviewed P1234R5. Later LEWG forwarded P5678R0."` Attacker/LLM emits extraction_text `"LEWG reviewed P9999R9"` (fabricated paper id sharing `"LEWG reviewed"` prefix). Exact DP or difflib may partial-match `"LEWG reviewed"`; with `accept_match_lesser=True`, alignment returns MATCH_LESSER anchored at the first LEWG sentence while `P9999R9` is invented. Alternatively, four-token extraction `"LEWG reviewed P5678 forwarded"` subsequence-matches tokens across both sentences at 3/4 coverage (ceil threshold) and 1/3 density, yielding MATCH_FUZZY with `char_interval` spanning both mentions.

## False-fail hypothesis
Adversarial whitespace-only or homoglyph-padded tokens (`"warfarin\u200b"`, Cyrillic `а` vs Latin `a`) fail token equality in LCS/exact tiers; without NFKC normalization (`_tokenize_with_lowercase` lowercases only, `resolver.py:1267-1272`) a legitimate extraction can miss alignment and get `char_interval=None` while a visually identical human reading would accept it (related production pain: Issue #334 in `05-web.md`).

## What would change my mind
A mandatory post-alignment check that `source[char_interval]` fuzzy-equals `extraction_text` at equal or stricter threshold (reject on mismatch), plus default `accept_match_lesser=False`, demonstrated on the `resolver_test.py:1467-1495` and `fuzzy_alignment_cases_test.py:491-514` cases returning `char_interval=None`.
