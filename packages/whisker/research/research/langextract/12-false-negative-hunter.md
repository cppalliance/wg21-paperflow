# 12 - False-Negative-Hunter

**Verdict:** usable-with-conditions   The three-tier aligner reliably grounds contiguous verbatim extractions, but it systematically drops valid extractions when outputs overlap, when token density falls below 1/3, or when surface form diverges on punctuation, Unicode form, or CJK tokenization; consumers must treat `char_interval=None` as a first-class loss mode, not noise.
**Confidence:** high

## Findings
- [CRITICAL] Monotonic exact-match DP drops valid shorter extractions that overlap a longer winner in the same model output batch. Evidence: `_select_monotonic_matches` maximizes non-overlapping total token weight (`resolver.py:1113-1185`); `_apply_monotonic_exact_matches` leaves losers for fuzzy fallback (`resolver.py:1188-1243`), but overlapping losers stay unaligned when fuzzy also fails. Regression tests encode this as expected: `"Napro"` → `char_interval=None` when `"Naprosyn"` is present (`resolver_test.py:944-997`), `"blood pressure"` dropped when `"high blood"` wins (`resolver_test.py:1097-1131`), interleaved `"Naprosyn"` dropped when `"arthritis"` is aligned first (`resolver_test.py:1024-1057`). Impact: any schema that emits nested or overlapping entity strings (medication + brand substring, condition + symptom phrase) loses true positives silently; README tells users to filter `[e for e in result.extractions if e.char_interval]` (`README.md:94`), so these vanish from downstream pipelines.
- [HIGH] LCS fuzzy tier rejects extractions whose tokens appear in the source but fail the 1/3 density gate even at the default 0.75 coverage threshold. Evidence: `_accept_lcs_match` requires `matches >= ceil(extraction_len * threshold)` AND `matches / span_len >= min_density` with `_FUZZY_ALIGNMENT_MIN_DENSITY = 1/3` (`resolver.py:57-58`, `1377-1404`); failure returns `None` from `_lcs_fuzzy_align_extraction` (`resolver.py:773-774`). Test oracle: `"headache and fever"` vs `"Patient reports back pain and a fever."` → `char_interval=None` (`resolver_test.py:1601-1619`). Impact: LLM outputs that quote the right words with extra framing tokens, or that match a gappy source window, can be correct semantically yet ungrounded; the gapped positive case in `fuzzy_alignment_cases_test.py:213-235` shows the gate is tight, not generous.
- [HIGH] CJK and mixed-script text has no character-substring fallback at the pinned baseline SHA; token fragmentation makes multi-grapheme extractions fragile. Evidence: `UnicodeTokenizer` explicitly refuses to merge CJK graphemes (`tokenizer.py:378-386`, `463-465`); default orchestration uses `RegexTokenizer` (`annotation.py:156`), so tokenizer choice changes token boundaries; Issue #334 reports wrong/missing CJK spans (https://github.com/google/langextract/issues/334); PR #480 proposes a post-tier substring fallback for dropped CJK alignments (https://github.com/google/langextract/pull/480) but no `_try_substring` / CJK fallback exists in `resolver.py` at pinned SHA `0dff5479` (baseline §2). Impact: valid extractions in Chinese/Japanese/Korean or CJK-adjacent Latin (Issue #334) are disproportionately lost compared to ASCII contiguous spans.
- [HIGH] Unicode compatibility-form mismatch (NFC vs NFD) fails all three tiers despite visually identical text. Evidence: `UnicodeTokenizer` deliberately does NOT normalize to NFC (`tokenizer.py:329-330`); `_tokenize_with_lowercase` lowercases raw slice bytes with no `unicodedata.normalize` (`resolver.py:1246-1272`); test confirms NFD `"e\u0301"` stays two code units in `char_interval` (`tokenizer_test.py:533-544`). Impact: a model emitting composed `"café"` against decomposed source (or vice versa) yields `char_interval=None` even though our `normalized_text`/`clean_string` would collapse both to the same alnum surface (`metrics.py:118-119`, `338-340`).
- [MED] `accept_match_lesser=False` zeroes Tier-2 partial exact matches before fuzzy runs, dropping extractions whose leading tokens are verbatim. Evidence: when `extraction_text_len > n` and `accept_match_lesser` is false, intervals reset to `None` (`resolver.py:1010-1019`); fuzzy may still recover (`resolver_test.py:1524-1547`), but extractions that matched only partially in difflib and fall below fuzzy coverage stay ungrounded. Impact: stricter grounding policy (`skills/langextract-usage/references/resolver-params.md:50`) trades false positives for extra false negatives on truncated-but-correct quotes.
- [MED] Punctuation and hyphenation surface-form drift fails token exact match; fuzzy recovery depends on token count and density, not character edit distance. Evidence: `RegexTokenizer` splits `"Napro-syn"` into three tokens (`resolver_test.py:922-941`) while a model paraphrase `"Naprosyn"` aligns exactly; conversely smart quotes, em-dash vs hyphen, or `"state-of-the-art"` vs `"state of the art"` change token cardinality; aligner has no char-level `partial_ratio` equivalent (contrast `whisker/tapetum_llm/grounding.py:49-52` with `EVIDENCE_FUZZY_FLOOR=0.90`, `constants.py:50`). Impact: near-verbatim LLM paraphrases that humans would accept as grounded fail langextract while passing our document-level fuzzy floor.
- [MED] Few-shot / prompt example misalignment produces `IssueKind.FAILED` (`status=None`) on text that is substantively correct but not byte-verbatim and ordered. Evidence: Issue #246 logs `FAILED to align` on example text (https://github.com/google/langextract/issues/246); `prompt_validation.py:59`, `187-189` classifies `alignment_status is None` as `FAILED`; maintainer guidance in 05-web.md Q5 requires verbatim ordered examples. Impact: validation noise masks real mis-extractions; users who treat FAILED as "model hallucination" may discard valid extractions that only differ by punctuation or ordering.
- [LOW] Threshold tuning to recover borderline false negatives was broken in released builds: `resolver_params={'fuzzy_alignment_threshold': 0.5}` raised `TypeError` because alignment kwargs were not unpacked (Issue #245, https://github.com/google/langextract/issues/245; 05-web.md Q5). Impact: operators could not relax gates without patching `resolver.py` directly.

## False-pass hypothesis
An extraction `"heart problems"` aligned with `MATCH_FUZZY` to source `"severe heart problems today"` via plural stemming (`resolver.py:1275-1281`, `resolver_test.py:1454-1497`) while a human might reject the span if they required the word `"severe"`; langextract accepts, our `ground_spans` would also likely accept via `partial_ratio >= 0.90` on the full markdown (`grounding.py:51-52`).

## False-fail hypothesis
Model outputs two entities from `"Patient with arthritis is prescribed Naprosyn."`: extraction `"Naprosyn"` (medication) and extraction `"arthritis"` (condition). `"arthritis"` aligns exactly (`resolver_test.py:1047-1056`), but `"Naprosyn"` is left at `char_interval=None` (`resolver_test.py:1040-1044`) because the monotonic DP / difflib pass consumed the non-overlapping window; fuzzy does not recover a contiguous `"Naprosyn"` window after the overlap policy fires. Our `ground_spans` would keep both quotes: `"Naprosyn"` and `"arthritis"` are normalized substrings of the markdown with no mutual exclusion (`grounding.py:49-50`).

## What would change my mind
A merged PR #480-style character-substring fallback plus a reproducible benchmark showing <1% false-negative rate on a multilingual corpus of intentionally overlapping extractions, with `resolver_params` threshold tuning working end-to-end (Issue #245 fixed), would flip this to `usable` for production grounding.
