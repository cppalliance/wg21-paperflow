# 05 - Maintainability-Complexity

**Verdict:** usable-with-conditions (+ the alignment core is a 1213-LOC god-module with four coexisting algorithm generations; adopt patterns and constants discipline, do not vendor resolver.py wholesale)
**Confidence:** high

## Findings
- [CRITICAL] `resolver.py` is a 1213-LOC god-module fusing parse, align, and three alignment generations in one file. Evidence: baseline §2 (`resolver.py` **1213**); module defines `AbstractResolver`/`Resolver` (parse, `resolver.py:88-536`), `WordAligner` (align, `resolver.py:539-1073`), monotonic DP (`resolver.py:1113-1243`), LCS fuzzy DP (`resolver.py:1287-1404`), and legacy difflib fuzzy (`resolver.py:591-715`). Impact: every grounding bug fix (Issue #245 threshold wiring, Issue #334 CJK spans, PR #480 substring fallback per `05-web.md`) must land in this single hotspot; change blast radius exceeds our entire `tapetum_llm/grounding.py` (56 LOC, `whisker/tapetum_llm/grounding.py:24-56`).
- [HIGH] Provider realtime `infer()` loops are near-copy-pasted between Gemini and OpenAI with pylint duplicate-code waivers, not a shared primitive. Evidence: `gemini.py:475-509` and `openai.py:355-389` (identical `ThreadPoolExecutor` + index-keyed `results[]` + ordered yield); both files open with `# pylint: disable=duplicate-code` (`gemini.py:17`, `openai.py:16`). Impact: concurrency/retry fixes must be applied per provider; baseline §3 notes OpenAI mirrors Gemini exactly, and Issue #240 (`05-web.md`) was a per-chunk retry fix that had to propagate provider-by-provider.
- [HIGH] `_compat` debt is triple-layered with no v2.0 ship date, multiplying import surfaces. Evidence: `_compat/README.md:7` ("removed in LangExtract v2.0.0", no date); top-level shims `tokenizer.py:24-25`, `data.py:25`, `inference.py:23-32` delegate to `_compat/inference.py:30-60` which lazy-imports `core/`; plus `schema.py:57-78`, `registry.py:28-36`, and five `_compat/*.py` files. Impact: contributors and integrators hit multiple canonical paths for the same symbol; `_compat` README:37 forbids new code there, so the layer is frozen debt that still ships in v1.6.0.
- [HIGH] Alignment tunables are scattered and split across constructor vs runtime kwargs, producing user-facing TypeErrors. Evidence: `ALIGNMENT_PARAM_KEYS` frozenset at `resolver.py:77-85`; `Resolver.__init__` rejects any leftover kwargs at `resolver.py:261-264`; `extraction.py:359-364` pops alignment keys before construction but passes them to `Annotator` separately; duplicate default `_FUZZY_ALIGNMENT_MIN_THRESHOLD = 0.75` at `resolver.py:57` and imported into `prompt_validation.py:116`. Impact: Issue #245 (`05-web.md`) shows `resolver_params={'fuzzy_alignment_threshold': 0.5}` raised `TypeError` in released code; contrasts with our single `constants.py:50` (`EVIDENCE_FUZZY_FLOOR = 0.90`) consumed by one 56-LOC function.
- [MED] Legacy alignment algorithms remain fully implemented beside their replacements (~400 LOC of deprecated paths). Evidence: `_FUZZY_ALGORITHM_LEGACY` at `resolver.py:60-64`; deprecation warning at `resolver.py:866-868` but `_fuzzy_align_extraction` still live (`resolver.py:591-715`); `_EXACT_ALGORITHM_DIFFLIB` "legacy greedy" at `resolver.py:67-72`, `resolver.py:962-1019`. Impact: two fuzzy and two exact codepaths must be tested and kept consistent (522 tests per baseline §2, but `resolver_test.py` 37 tests on a 1213-LOC module); PR #442 (`05-web.md`) added LCS without deleting legacy, increasing permanent maintenance surface.
- [MED] Batch orchestration duplicates across provider stacks instead of sharing a batch abstraction. Evidence: `gemini_batch.py` **754** LOC vs `openai_batch.py` **482** LOC (baseline §2); separate `BatchConfig` dataclasses (`gemini_batch.py:68-80`, `openai_batch.py:51-72`); each provider embeds its own batch-vs-realtime branch in `infer()` (`gemini.py:423-473`, `openai.py:322-353`). Impact: batch failure modes (Issue #287 single bad JSONL row, `05-web.md`) require parallel fixes in two large modules.
- [LOW] Provider schema modules mirror each other under duplicate-code suppression. Evidence: `providers/schemas/gemini.py:16` and `providers/schemas/openai.py:16` both `# pylint: disable=duplicate-code`; **172** vs **279** LOC (baseline §2) with parallel `from_schema_dict` / `to_provider_config` shapes. Impact: `output_schema` v1.6.0 feature (`05-web.md` Q1) touched both files; schema drift between Gemini strict and OpenAI strict is a recurring merge tax.

## False-pass hypothesis
A ThreadPoolExecutor ordering or retry fix landed only in `gemini.py:351-391` would pass the 522-test suite (`00-baseline.md` §2) while `openai.py:244-261` silently lacks the same behavior, because both files carry `# pylint: disable=duplicate-code` rather than a shared base implementation under test.

## False-fail hypothesis
The `_compat` layer could be dismissed as dead weight, but canonical imports from `langextract.core.*` and `langextract.providers.*` work today; the debt hurts long-term change velocity, not immediate runtime for new integrators who follow current docs.

## What would change my mind
A v2.0 release that deletes `_compat/` and top-level shims, splits `resolver.py` into parse + align submodules with one algorithm generation each, and extracts a tested shared `ParallelInferMixin` used by both Gemini and OpenAI (with one test file asserting behavioral parity).
