# 19 - Schema-Compliance-Auditor

**Verdict:** garbage (+ langextract's structured-output stack is cloud-native strict mode or weak JSON-mode; it has no schema-failure retry and no vLLM guided-decoding path, so it cannot address our self-hosted DeepSeek JSON-corruption failure class)
**Confidence:** high

## Findings
- [CRITICAL] No schema-noncompliance retry: parse/schema failures raise `ResolverParsingError` or return `[]` with no re-prompt. Evidence: `resolver.py:309-321` (`suppress_parse_errors` logs and drops); HTTP retries cover only transient API codes (`gemini.py:49`, `351-391`). Baseline 00 §3 retry bullet. Impact: DeepSeek token-injection corruption (MODELS.md:121) is a hard fail or silent empty chunk, unlike our bounded recovery loop (`model_backends.py:311-421`, `_RAW_JSON_MAX_ATTEMPTS=3` at `76-85`).
- [CRITICAL] Zero vLLM `guided_json` / `guided_decoding` / `extra_body` wiring anywhere in the library. Evidence: grep over `langextract/` returns 0 hits (baseline 00 §3); built-in vLLM draft PR #393 closed without merge, community plugin only ([#236](https://github.com/google/langextract/issues/236), 05-web.md Q3). Impact: no self-hosted constraint path exists; langextract cannot retire our MODELS.md:121 workaround target (`guided_json`) because it never implements it.
- [HIGH] Self-hosted structured output degrades to format-only JSON mode with no field constraints. Evidence: `FormatModeSchema` docstring "doesn't enforce structure, only output format" (`core/schema.py:118-124`); Ollama returns this class exclusively (`ollama.py:172-178`); config is `{"format": "json"}` only (`core/schema.py:142-144`). Baseline 00 §3. Impact: guarantees syntactic JSON at best; semantic schema violations still hit resolver drop-without-retry.
- [HIGH] OpenAI-compatible providers fall back to weak `json_object` mode when no example schema is active. Evidence: `openai.py:223-224` sets `response_format={"type": "json_object"}`; README confirms OpenAI-compatible path has no schema-class constraints (05-web.md Q3, Ollama vs OpenAI card). Issue [#414](https://github.com/google/langextract/issues/414) reports vLLM/lmdeploy success below 20% even with `fence_output=False, use_schema_constraints=False`. Impact: the path our `VllmThinkingBackend` would use is documented broken.
- [HIGH] Cloud strict `json_schema` with `"strict": True` is the only real constraint mode, and it is provider-native not portable to vLLM. Evidence: `schemas/openai.py:178-188` builds `response_format` with `"strict": self.strict`; applied at `openai.py:209-211`. Gemini mirrors via `response_schema`/`response_mime_type` (`schemas/gemini.py:63-75`, wired `gemini.py:363-366`). Baseline 00 DQ2. Impact: strong for Gemini/OpenAI APIs we do not target under model sovereignty; irrelevant to self-hosted DeepSeek.
- [MED] FormatHandler strips thinking tags and parses fences but never re-issues the LLM on validation failure. Evidence: `_parse_with_fallback` strips `<think>` then `json.loads` (`format_handler.py:261-276`); fence extraction at `278-333`. No retry loop in `parse_output` or `Resolver.resolve`. Compare: our `_strip_think_block` + `_extract_json` + Pydantic validate + error-feedback retry (`model_backends.py:115-133`, `363-417`). Impact: partial overlap on reasoning-model output cleanup; none on CJK token injection requiring re-prompt with schema feedback.
- [MED] Pending vLLM fix is output post-processing (fence strip), not constrained generation. Evidence: [PR #444](https://github.com/google/langextract/pull/444) targeting Issue #414 (05-web.md Q3); `langextract-vllm` plugin documents sampling/connection kwargs only, no guided decoding (05-web.md). Impact: would not fix `"confidence": ??0.98`-class corruption that our raw-JSON retry absorbs (MODELS.md:121).
- [LOW] OpenAI strict schema builder from examples is sophisticated for cloud APIs (nullable unions for optional attrs). Evidence: `_nullable` helper (`schemas/openai.py:42-48`); `from_examples` anyOf per extraction class (`schemas/openai.py:238-290`). Impact: adoptable pattern only if we moved to OpenAI strict API; does not help vLLM and langextract does not combine it with retry.

## False-pass hypothesis
Running vLLM through the OpenAI provider with `suppress_parse_errors=True` and `use_schema_constraints=False` (Issue #414 maintainer workaround): a chunk whose output is fenced garbage or token-corrupted JSON returns `[]` extractions instead of failing the document, producing a structurally "successful" pass with zero grounded items (`resolver.py:310-312`; Issue #287 batch row behavior, 05-web.md Q2).

## False-fail hypothesis
When `use_schema_constraints=True` on an OpenAI-compatible backend that partially honors `json_schema` strict mode, OpenAI's required-key rule (`schemas/openai.py:44-46`, all properties in `required`) rejects extractions where the model omits an optional `_attributes` object, triggering `ResolverParsingError` or drop without retry even when the semantic content is recoverable.

## What would change my mind
A merged first-class vLLM provider passing `guided_json` (or equivalent `extra_body` schema constraint) plus a bounded schema-validation retry loop with error feedback, demonstrated above 95% parse success on the Issue #414 reproduction (currently below 20%, 05-web.md) on the same DeepSeek/vLLM stack we run via `VllmThinkingBackend`.
