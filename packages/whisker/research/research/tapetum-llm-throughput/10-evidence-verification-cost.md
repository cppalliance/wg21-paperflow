# 10 - Evidence-Verification-Cost-Auditor

**Verdict:** usable (+ two-sided evidence verification is deterministic and not a throughput driver; the suspected per-claim LLM failure class does not apply here)
**Confidence:** high

## Findings

- [CRITICAL] Two-sided evidence verification makes **zero LLM calls**. `grounding.py:8-12` documents "Library returns data; no writes, no LLM, no network." Source grounding is `ground_spans(...)` (`grounding.py:248-335`); candidate classification is `classify_candidate_evidence(...)` (`grounding.py:419-585`). Both are pure Python + rapidfuzz. Impact: the baseline back-of-envelope item "~1-3 (evidence verification) calls per paper" (`00-baseline.md:104-108`) **over-counts LLM volume**; verification is not part of the 4.2x regression call explosion.

- [HIGH] Verification work scales with **claim count, not paper count**, but claim count is **capped**, not unbounded. Monolith/page missing-content quotes cap at `MAX_MISSING_QUOTES=5` (`constants.py:77`, `pdf_judge.py:694`). Page escalations cap at `MAX_PAGE_ESCALATIONS=5` pages × 5 quotes (`constants.py:191`). Unit checks cap at `MAX_UNIT_CHECKS=5` LLM calls, each emitting defects with one `source_quote` verified in `verify_unit_evidence` (`unit_judge.py:656-728`, `constants.py:223`). Impact: worst-case verification is O(tens of claims), not O(papers × open-ended findings).

- [HIGH] Tonight's fleet aggregate (377 successful sidecars, 4 errors): **1,206 total verified claims**, mean **3.2 claims/paper** (median 2, max 19). Disposition totals: `present_in_candidate=516`, `candidate_not_found=218`, `ambiguous=216`, `source_ungrounded=256`. Distribution: 133 papers with 0 claims, 116 with 1-3, 53 with 4-6, 49 with 7-10, 26 with 11+. Checked units mean 4.01 (max 5). Page escalations fired on 13 papers only (fleet mean 0.04). Impact: verification CPU work is concentrated in unit-check defects (~95% of claims); monolith/page paths are sparse.

- [MED] Measured CPU cost is **milliseconds per paper**, not seconds. Batch path (3 claims, 64k-char candidate, production `classify_candidate_evidence` shape): **~62 ms** per verification pass (runtime benchmark on P2583R3). Extrapolated mean fleet CPU if run serially inside each paper: ~**25-75 s** total across 377 papers (<3% of **2883 s** wall from `00-baseline.md:28`). Per-claim sequential `ground_spans` on a multi-MB paper can reach seconds (worst-case microbench: ~7.5 s for 19 isolated full-doc scans), but production batches spans in one `ground_spans` call and unit source text is page-scoped. Impact: verification is not a candidate for the 692 s → 2886 s regression.

- [MED] Synchronous verification **does run inside the async cascade without `await`**, e.g. `pdf_judge.py:696-701` (monolith), `783-786` (page), `unit_judge.py:412` (unit batch). Measured cost scales with candidate size (5-quote batch, runtime benchmark): 118 ms at 65 KB (P2583R3), 517 ms at 305 KB (P3100R6), **3.24 s at 2.5 MB (P2728R11)**; a degenerate 19-sequential-claim pass on the 2.5 MB paper costs 7.85 s. Because this CPU runs without an `await`, it blocks the event loop for **all 32 in-flight papers** for that duration. Only ~6 corpus papers exceed `MAX_PAPER_MD_CHARS=500_000` (`constants.py:60-62`), so total fleet-wide blocking is bounded to roughly 20-50 s of the 2883 s wall (`00-baseline.md:28`), against decode-dominated ~25-30 s LLM calls (`00-baseline.md:59-60`). Impact: real but bounded; worth an `asyncio.to_thread` wrap on the giant-paper path, not a regression driver. A second benchmark run confirms batch cost is **flat in claim count** (19-claim batch 1.27 s vs 3-claim batch 1.38 s on the same 2.5 MB paper): the cost is dominated by document tokenization/normalization in `ground_spans` (`grounding.py:273-283`), so verification scales with **paper size, not finding count**, the inverse of the mandated failure class.

- [MED] **`IdealVerificationError` is a separate stage**, not two-sided missing-content verification. `ideal_verify.py:134-160` makes **one LLM call** (`run_task` → `IdealVerification`), then deterministic post-check `_require_raw_exact_evidence` (`ideal_verify.py:114-131`). Only **4 papers** have tomd ideals in this workspace; ideal verify ran on all 4 (1 success P4020R0, 2 IdealVerificationError, 1 not reached). Impact: do not conflate ideal-verify LLM cost with evidence grounding cost.

- [HIGH] The 4 fleet errors split into two unrelated classes. **IdealVerificationError (2):** P4182R0 completed full PDF lane (log: `verdict=review`, 5 unit checks in `partial_progress`) then failed ideal post-grounding on a fabricated multi-heading quote; P4228R0 completed text tier-1 (`adjudicate` debug, no tier-2 escalation) then failed similarly. LLM spend before failure: **~8 calls** (P4182R0: monolith + metadata + 5 units + ideal) and **~2 calls** (P4228R0: tier-1 + ideal). **PdfLaneError (2):** P3400R3 failed at metadata/outline (`partial_progress.phase=metadata`, 0 units); P3977R0 failed at monolith JSON validation (`phase=monolith`, 0 units). Neither is verification-related. Impact: fail-not-partial (`cli.py:1339-1353` writes error tombstone, discards judge result) wastes completed judge work on ideal failures specifically.

- [LOW] Retrying **only** the deterministic verification step is cheap but **insufficient for IdealVerificationError**. The failure is ungrounded LLM-emitted quotes after the ideal LLM call already completed; `_require_raw_exact_evidence` has no retry budget. Fix requires re-running `verify_against_ideal` (another full LLM call) or skipping ideal attach while persisting the independent judge result. Impact: a verification-only retry policy would not recover the 2 errored ideal papers without re-spend.

## False-pass hypothesis

A unit-check defect whose `source_quote` grounds fuzzily in the PDF unit text but not exactly could survive as `candidate_not_found` with `source_status=fuzzy`, folding to review (`unit_judge.py:451-458`) rather than pass. A harder case: `classify_candidate_evidence` marks a genuinely missing quote as `ambiguous` via sanctioned-format guards (`grounding.py:545-581`), abstaining instead of refuting, which caps at review but could leave a false fail signal in `candidate_not_found` if guards misfire.

## False-fail hypothesis

`source_ungrounded` drops (256 fleet-wide) remove hallucinated quotes before they become missing-content evidence, but a quote that fails source grounding despite being paraphrased-close could drop real defects, forcing review cap via `evidence_summary["source_ungrounded"] > 0` (`unit_judge.py:451-453`). Cosmetic fuzzy-only matches abstain as `ambiguous`, preventing a false hard fail but inflating review.

## What would change my mind

A profile showing `ground_spans`/`classify_candidate_evidence` consuming >10% of per-paper wall time on the 19-claim tail (e.g. cProfile on P2728R11 with max sidecar claim count) would elevate CPU blocking from negligible to fleet-relevant; tonight's microbench and sidecar distribution do not show that.
