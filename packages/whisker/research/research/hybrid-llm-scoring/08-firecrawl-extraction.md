# 08 - Firecrawl extraction

**Verdict:** usable-with-conditions   (one genuinely portable hybrid det+LLM verdict pattern exists in engpicker; the extraction pipeline itself has no quality scoring, and its abandoned confidence gate is itself instructive)
**Confidence:** high

All firecrawl paths below are relative to `packages/whisker/research/repos/firecrawl/`.

## Findings

- [HIGH] Firecrawl ships exactly one live hybrid deterministic+LLM verdict, and it is a three-way enum, not a fused number. `engpicker.ts` scrapes each URL with 4 engine configs, has GPT-4o-mini emit a binary `is_successful` judgment per scrape (`apps/api/src/lib/engpicker.ts:70-103`), then fuses those with a deterministic Rust Levenshtein comparison via named thresholds (`SIMILARITY_THRESHOLD = 0.85`, `SUCCESS_RATE_THRESHOLD = 0.7`, `CDP_FAILURE_THRESHOLD = 0.5`, `apps/api/src/lib/engpicker.ts:288-296`) into a verdict of `"TlsClientOk" | "ChromeCdpRequired" | "Uncertain"` that is persisted to a DB table (`apps/api/src/lib/engpicker.ts:301-305`).
  Impact: this is the closest thing in the repo to goal 3. The fusion shape is: deterministic metric gates, LLM judgment filters which samples count, threshold constants are named at module level (matches C4), and the merged output is an enum with an explicit "Uncertain" third state rather than an averaged score. A merged whisker verdict with an explicit `uncertain`/`llm-absent` state (rather than silently degrading to the deterministic verdict) directly handles the 6 tapetum error papers from the 2026-07-06 run (baseline line ~52).

- [HIGH] Firecrawl tried numeric LLM self-confidence gating and abandoned it: the `extraction_confidence < 3` skip is commented out in `apps/api/src/lib/extract/extraction-service.ts:540-543`, and an entire LLM validate-and-deduplicate pass over the final result is likewise commented out (`apps/api/src/lib/extract/extraction-service.ts:944-984`). What survived in production are binary/enum LLM judgments only: `is_successful` (`engpicker.ts:73`), `extract: boolean` (`apps/api/src/lib/extract/fire-0/completions/checkShouldExtract-f0.ts:29-36`), `shouldUseSmartscrape: boolean` (`apps/api/src/scraper/scrapeURL/lib/extractSmartScrape.ts:18-23`), `isMultiEntity: boolean` (`apps/api/src/lib/extract/completions/analyzeSchemaAndPrompt.ts:53-63`).
  Impact: for goal 3, this is field evidence AGAINST arithmetically merging tapetum's `confidence [0..1]` into a composite number. Firecrawl converged on categorical LLM judgments feeding rule-based fusion, which is exactly the shape of whisker's `_decide` (baseline: verdict = rules, NOT a score). A merged lane should stay categorical (pass/review/fail + uncertain), with confidence displayed but not folded into arithmetic.

- [HIGH] Schema conformance is enforced pre-flight and by the provider, never post-validated. `normalizeSchema` rewrites every user schema to `required: <all keys>` and `additionalProperties: false` before the call (`apps/api/src/scraper/scrapeURL/transformers/llmExtract.ts:106-154`), and the call sets `openai: { strictJsonSchema: true }` (`llmExtract.ts:730-732`). Ajv is imported and `ajv.compile(multiEntitySchema)` is invoked (`apps/api/src/lib/extract/extraction-service.ts:22-23, 467`), but the compiled validator is never called on LLM output; it only sanity-checks that the schema itself is valid.
  Impact: firecrawl's "deterministic check" for LLM output is delegated entirely to constrained decoding. Whisker's D6/D10 (pydantic `output_type` + `output_retries`) is already stronger than this. Nothing to adopt here for goal 1; it confirms tapetum's existing schema strategy is at or above industry practice.

- [MED] Failure ladder for malformed LLM output is repair-then-salvage, not fail: (1) deterministic string repair strips markdown fences (`llmExtract.ts:594-624`), (2) a second LLM call repairs the JSON (`llmExtract.ts:627-711`), (3) on `NoObjectGeneratedError` the fenced JSON is salvage-parsed out of the error object itself (`llmExtract.ts:877-905`), (4) model fallback fires only on quota/rate-limit errors (`llmExtract.ts:830-877`). A hard refusal becomes a typed `LLMRefusalError` (`llmExtract.ts:97-104, 943-945`) that propagates as a scrape failure (`apps/api/src/scraper/scrapeURL/index.ts:843, 1365-1369`), never a partial document.
  Impact: for goal 1, step (1) (cheap deterministic fence-stripping before burning a model retry) is directly portable to tapetum's retry path and would likely have recovered some of the 118 model retries / 6 truncated-JSON errors from the 2026-07-06 run (baseline line ~48-52). The typed-refusal-as-hard-failure pattern matches C5 exactly.

- [MED] The LLM reranker is the repo's only numeric LLM scoring, and it is threshold-consumed, deliberately fail-open, and biased toward acceptance. Schema requires `relevanceScore` plus a mandatory `reason` string per item (`apps/api/src/lib/extract/reranker.ts:60-81`), the prompt embeds an explicit numeric rubric with "If you are not sure ... give it a score of 1.0" (`reranker.ts:119-137`), scores are filtered against per-mode named constants (`THRESHOLD_FOR_SINGLEPAGE = 0.6`, `THRESHOLD_FOR_MULTIENTITY = 0.45`, `reranker.ts:8-9`), and after `MAX_RETRIES = 2` a failed chunk returns `[]` (`reranker.ts:45, 212-215`).
  Impact: two portable mechanics for goals 1 and 3: (a) forcing a per-score `reason` field gives auditability, which tapetum already has via `axis_findings`/`evidence_spans`; (b) anchored rubrics inside the prompt reduce score drift on small models (relevant to model sovereignty). The fail-open default is the anti-pattern: for whisker it would violate C5.

- [MED] Extraction metadata persistence is operational, not qualitative, and it is ephemeral. Per-extract state is a Redis record with a steps array (`step, startedAt, finishedAt, error, discoveredLinks`) capped and TTL'd at 6 hours (`apps/api/src/lib/extract/extract-redis.ts:25-50, 52-75`); the durable record is a Postgres row via `logExtract` carrying `is_successful`, `credits_cost`, `model_kind`, and full `cost_tracking` JSON (`extraction-service.ts:1020-1030`), plus per-call cost entries tagged with call identity (`gcDetails`, `llmExtract.ts:812-829`). No per-document quality score is ever persisted.
  Impact: for goal 2, the absence is the lesson: a production extraction system at firecrawl's scale never persists per-document LLM quality verdicts, so whisker's `<pid>.whisker.tapetum.json` sidecar (baseline, tapetum `_persist_result`) is already ahead of this repo. The one adoptable detail is the append-only per-call identity tagging, which whisker's debug artifact already mandates ("labeled by call identity", root CLAUDE.md trace/debug rules).

- [LOW] Judge failure degrades to a hardcoded safe default rather than an error: when the schema-analysis LLM output fails Zod parsing, `analyzeSchemaAndPrompt` logs a warning and returns `{ isMultiEntity: false, multiEntityKeys: [], ... }` (`apps/api/src/lib/extract/completions/analyzeSchemaAndPrompt.ts:100-117`).
  Impact: marks the portability boundary. Fail-open defaults are fine for a routing decision (worst case: a slower path) but would be a C5 violation if used for a quality verdict. In a merged whisker score, an errored LLM lane must surface as `error/absent`, never as an implicit "pass".

- [LOW] Model routing by input complexity: `selectModelForSchema` sends recursive schemas to gpt-4.1 and simple schemas to gpt-4o-mini, with the reason string logged (`llmExtract.ts:43-66`).
  Impact: same shape as tapetum's fast-triage/deep-escalate cascade (baseline, `adjudicate.py`); confirms the two-tier design, adds the small refinement of recording WHY a tier was chosen (`reason: "recursive_schema_detected"`) into persisted metadata.

- [LOW] No eval harness exists in this clone. Glob for `*eval*`/`*benchmark*` across the repo returned zero files; the only "eval" hits are the engpicker judge and a comment referencing `eval/scaling/` measurements living in a different repo (`apps/api/src/lib/fire-privacy-client.ts:78`).
  Impact: the mandate's premise "(they have eval harnesses)" is not true of this codebase; extraction quality evals, if any, are external. Pivoted findings above accordingly lean on what the absence teaches.

## False-pass hypothesis
Adopting firecrawl's fail-open judge pattern (analyzeSchemaAndPrompt.ts:100-117, reranker.ts:212-215) into the merge: a paper where the deterministic lane says `review` (e.g. coverage 0.88, in the soft band) and the tapetum lane errors out after retries (like the 6 truncated-JSON papers on 2026-07-06, e.g. P2728R11) would merge as "LLM raised no objection" and tip the combined verdict to pass, when in fact the LLM lane never rendered a verdict at all.

## False-fail hypothesis
Adopting engpicker's severity-free binary fusion (`is_successful: boolean`, engpicker.ts:73) instead of tapetum's severity-aware fold (`worst_axis_verdict`, chunking.py ~34-51): a paper with deterministic `pass` and a single minor-severity tables finding would collapse to LLM `fail` under a binary judge, and a merged verdict that lets any LLM fail dominate would wrongly reject a paper the current severity-aware lane correctly keeps at review.

## What would change my mind
Finding firecrawl's actual extraction eval harness (the external repo hinted at by `fire-privacy-client.ts:78` or a CI eval suite) showing they DO score extraction output per-document against ground truth with a fused metric; that would upgrade the verdict to usable and supply the numeric-fusion evidence this clone lacks.
