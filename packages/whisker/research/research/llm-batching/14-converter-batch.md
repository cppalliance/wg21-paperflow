# 14 - Converter-Batch

**Verdict:** usable-with-conditions — marker, MinerU, and docling all split **document parallelism** from **LLM/HTTP inflight**; whisker already has the first knob (`--concurrency`) but lacks the second, and the conservative defaults (3–8) plus bounded async schedulers are the portable patterns worth adopting.
**Confidence:** high

## Findings

- [CRITICAL] **Two-layer throttling is the mature converter pattern; whisker has only layer one.** Marker caps block-level LLM fan-out at `max_concurrency: int = 3` via `ThreadPoolExecutor(max_workers=self.max_concurrency)` in both `BaseLLMComplexBlockProcessor.rewrite_blocks` (`marker/processors/llm/__init__.py:42-45,163-172`) and `LLMSimpleBlockMetaProcessor` (`marker/processors/llm/llm_meta.py:44-49,67-73`). Cross-document work is separate: `mp.Pool(processes=total_processes)` where `total_processes = max(1, min(len(files), workers))` and `workers = vram // 7` (`marker/scripts/convert.py:170-177,189-195`; `marker/utils/batch.py:4-8`). Docling remote client defaults `DEFAULT_MAX_CONCURRENCY = 8` (`docling/service_client/client.py:114`) with bounded async workers in `_run_bounded` (`docling/service_client/_scheduler.py:28-43,73-74`). MinerU http-client passes `max_concurrency` default **100** into `MinerUClient` (`mineru/backend/vlm/vlm_analyze.py:71-75,230-235). Whisker has paper-level `asyncio.Semaphore(concurrency)` only (`tapetum_llm/cli.py:409-416,470`). **Impact:** baseline c=3 yields 10.8 s/paper while pod likely accepts more (`00-baseline.md:12-19`); raising `--concurrency` without a second inflight cap risks timeout storms (see persona 15). **Adopt:** whisker-only `--max-inflight` (default 8, sweep 8/16/32) as `BoundedSemaphore` around LLM calls inside `adjudicate_paper`, independent of paper `--concurrency`.

- [HIGH] **Marker LLM services are strictly serial per call: no HTTP batching, no async, fresh client each time.** Every provider (`openai.py`, `gemini.py`, `claude.py`, `azure_openai.py`) implements `BaseService.__call__` as a synchronous loop: one `client.*.parse` / `generate_content` per invocation (`marker/services/openai.py:76-101`, `marker/services/__init__.py:46-55`). Retry is linear backoff on rate limits: `wait_time = tries * self.retry_wait_time` with `max_retries=2`, `retry_wait_time=3` (`marker/services/__init__.py:14-17`; `marker/services/openai.py:109-122`). `OpenAIService.get_client()` constructs a new `openai.OpenAI` every call (`marker/services/openai.py:129-130`). Parallelism exists only because processors submit many blocking calls to a 3-thread pool, not because the service batches requests. **Impact:** mirrors our pipeline fresh-`AsyncOpenAI`-per-call path (`00-baseline.md:52-55`, read-only). **Already-have:** per-call retry in `model_backends.py`. **Not-applicable:** marker's sync `ThreadPoolExecutor` inside a sync PDF pipeline (tapetum is already async at paper level).

- [HIGH] **Docling's remote-API path is the closest architectural analog to tapetum: shared httpx client + bounded async fan-out + urllib3 retry.** `ApiVlmModel` fans out page images with `ThreadPoolExecutor(max_workers=self.concurrency)` where `ApiVlmOptions.concurrency` defaults to **1** (`docling/models/vlm_pipeline_models/api_vlm_model.py:42,185-186`; `docling/datamodel/pipeline_options_vlm_model.py:401-410`). Each page is an independent `api_image_request` POST (`docling/utils/api_image_request.py:29-46`, `_RETRY_TOTAL=5`, `backoff_factor=0.1`, status `{429,500,502,503,504}`). For docling-serve batch conversion, `convert_all` drives `submit_and_retrieve_each(..., max_in_flight=in_flight)` through `_run_bounded` with one shared `httpx.AsyncClient` (`docling/service_client/client.py:892-901,2109-2114`; `_scheduler.py:28-43`). Remote CLI exposes `--max-concurrency` default 8 (`docling/cli/remote.py:266-272`). **Impact:** docling treats remote LLM as **N concurrent single-request POSTs**, not provider batch APIs — same as our vLLM `/v1/chat/completions` path. **Adopt:** docling's `_run_bounded` queue-worker pattern for whisker if we split paper concurrency from HTTP inflight; **Adopt:** retry status list + `respect_retry_after_header=True` as reference for any whisker-side retry wrapper (pipeline retry is read-only). **Already-have:** paper-level semaphore + ordered `gather` persistence (`cli.py:416-470`).

- [HIGH] **MinerU http-client concurrency is aggressive (default 100) but scoped to page-window batching inside one document, not naive document fan-out.** `ModelSingleton.get_model` sets `max_concurrency = kwargs.get("max_concurrency", 100)` for http-client backend only (`mineru/backend/vlm/vlm_analyze.py:71-75,230-235`). VLM analysis processes pages in windows (`get_processing_window_size(default=64)`, `vlm_analyze.py:546-547,562-581`) calling `await predictor.aio_batch_two_step_extract(images=images_pil_list)` once per window under `aio_predictor_execution_guard` (`vlm_analyze.py:577-581`). The guard serializes only MLX backends via a threading lock (`vlm_analyze.py:379-410`); http-client has no lock. CLI multi-document parallelism uses a separate asyncio queue pool: `execute_planned_tasks(..., concurrency=resolve_submit_concurrency(effective_max, len(tasks)))` (`mineru/cli/client.py:781-815,981-984`). **Impact:** MinerU separates (a) server-side task submission concurrency, (b) in-document page-window batch RPCs, (c) http-client max_concurrency inside `MinerUClient` (external `mineru_vl_utils`, not vendored here). **Not-applicable:** page-window VLM batching (tapetum is ~1 structured JSON call per paper post data-URI strip, `00-baseline.md:21-22`). **Adopt:** CLI pattern of `min(server_max, local_max, task_count)` when we add dual-pod sharding (`00-baseline.md:37-39`).

- [MED] **Cross-document parallelism in marker/docling targets local GPU/CPU inference, not remote LLM batching.** Marker `chunk_convert.sh` launches one `marker` process per GPU with `--num_chunks $NUM_DEVICES --workers $NUM_WORKERS` (`marker/scripts/chunk_convert.sh:33-44`; `marker/scripts/convert.py:107-112,145-150`). MinerU pipeline `BatchAnalyze` scales **local** model batch sizes via `batch_ratio` (`mineru/backend/pipeline/batch_analyze.py:38-41,56-65,429,449`) — layout/OCR/table recognition, not HTTP LLM. Docling `doc_batch_concurrency` defaults to **1** with explicit GIL warning (`docling/datamodel/settings.py:30-31`) and only activates `ThreadPoolExecutor` when `doc_batch_size > 1` (`docling/document_converter.py:639-645). Enrichment models batch **elements** locally at `elements_batch_size=16` (`docling/datamodel/settings.py:34-36`; `docling/pipeline/base_pipeline.py:122-131`) — serial HTTP inside each batch for API enrichment (`docling/models/stages/picture_description/picture_description_api_model.py:54-55` comment: "vllm won't allow more than 1"). **Impact:** GPU worker math and OCR batch_ratio do not transfer to RunPod HTTP adjudication. **Not-applicable** for tapetum throughput work.

- [MED] **Retry/backoff maturity varies; none use provider async batch APIs.** Marker: sync `time.sleep(tries * retry_wait_time)`, max 2 retries, returns `{}` on failure (silent empty block, `marker/services/openai.py:117-127`). Docling: urllib3 `Retry(total=5, backoff_factor=0.1)` on POST (`docling/utils/api_image_request.py:24-40`). MinerU http-client: `max_retries=3`, `retry_backoff_factor=0.5` passed to `MinerUClient` (`vlm_analyze.py:74-75,234-235`). No repo implements OpenAI `/v1/batches` or Anthropic Message Batches for conversion LLM steps. **Impact:** speedup levers are concurrency + shorter outputs, not offline batch jobs (consistent with persona 05b/05d). **Already-have:** pipeline transient retry on `APITimeoutError`/`APIConnectionError` (`00-baseline.md:52-55`). **Adopt (whisker-only):** pre-batch `/models` health gate (docling/MinerU CLI both probe server readiness before fan-out).

- [LOW] **Marker `LLMSimpleBlockMetaProcessor` submits all futures then drains in submission order, not `as_completed`.** Evidence: `for future in pending: result = future.result()` (`marker/processors/llm/llm_meta.py:51-53`) vs `BaseLLMComplexBlockProcessor` using `as_completed` (`marker/processors/llm/__init__.py:164-171`). Thread pool still runs 3 workers, but result processing latency is suboptimal. **Impact:** negligible for tapetum (1–2 calls per paper). **Not-applicable.**

## False-pass hypothesis

Copying MinerU's http-client default `max_concurrency=100` or docling-serve's unbounded-in-principle scheduler without a pod knee test would flood the RunPod proxy/vLLM queue; borderline papers could receive truncated JSON that passes pydantic retry then exits the ambiguous confidence band — same distribution-drift risk as raising `--concurrency` alone (persona 15), not artifact corruption.

## False-fail hypothesis

Copying marker's conservative `max_concurrency=3` as a hard whisker cap while also keeping paper `--concurrency=1` would leave pod capacity idle (baseline already shows only ~2–3× at c=3, `00-baseline.md:18-19`); papers would not fail, but the 36-min wall time target would not move.

## What would change my mind

A whisker-only sweep at fixed paper `--concurrency=8` with `--max-inflight` ∈ {3, 8, 16, 32} measuring p50/p95 per-call latency, timeout rate, and verdict distribution delta vs c=3 baseline — if p95 stays flat and timeout rate is zero at inflight=16, the dual-knob pattern upgrades from "adopt" to "ship default inflight=16".
