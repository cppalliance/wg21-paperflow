# 13 - Extraction-Parallelism

**Verdict:** usable-with-conditions — langextract proves a transferable within-batch chunk parallel pattern (`batch_length` × `max_workers` + index-stable merge); firecrawl's extract path is mostly serial LLM calls behind multi-tenant job/team gates, not client-side LLM batching we lack.
**Confidence:** high

## Findings

- [CRITICAL] **langextract parallelizes WITHIN a document (and across documents) at chunk granularity via `batch_length` + provider `ThreadPoolExecutor`, not asyncio.** `Annotator` batches chunks with `make_batches_of_textchunk(chunk_iter, batch_length)` (`annotation.py:351`), then calls `language_model.infer(batch_prompts=prompts)` once per batch (`annotation.py:392`). OpenAI/Gemini providers fan out with `ThreadPoolExecutor(max_workers=min(self.max_workers, len(batch_prompts)))` (`openai.py:355-357`, `gemini.py:476-478`). Chunks from different documents can land in the same batch because `_document_chunk_iterator` streams all documents into one iterator (`annotation.py:118-160`, `226-227`). **Whisker:** **adopt** the two-knob model for the rare chunked-paper path; we currently triage chunks **serially** (`adjudicate.py:193-209`). Implement with `asyncio.gather` + a chunk semaphore, not threads. **Impact:** only bites when papers chunk again (pre-filter: 755.8 s for 2 chunked papers); irrelevant to the 197 single-chunk corpus today.

- [CRITICAL] **langextract restores deterministic output order despite `as_completed` completion chaos.** Provider code pre-allocates `results: list[...] = [None] * len(batch_prompts)` and writes by `future_to_index[future]` (`openai.py:366-372`, `gemini.py:487-493`); annotation zips `batch` with `outputs` in batch order (`annotation.py:396-432`) and merges extractions into `per_doc[document_id]` while emitting completed documents in captured `doc_order` (`annotation.py:307-346`). **Whisker:** **adopt** the index-slot pattern if we add chunk-parallel triage; **already-have** the same property at paper level via `asyncio.gather` returning input order (`cli.py:470-475`). **Impact:** safe to raise paper concurrency without reordering sidecars; chunk parallel would need the same guard.

- [HIGH] **langextract defaults: `batch_length=10`, `max_workers=10`; effective parallelism = `min(batch_length, max_workers, prompt_count)` and warns when `batch_length < max_workers`.** Public API (`extraction.py:57-58`, `122-127`, `243-248`); SKILL.md documents "keep `batch_length >= max_workers`" (`skills/langextract-usage/SKILL.md:118-126`). Ollama is explicitly sequential — `for prompt in batch_prompts` (`ollama.py:291`). **Whisker:** **adopt** the mismatch warning if we expose separate paper-concurrency and chunk-concurrency knobs; **already-have** paper-level `--concurrency` only (`cli.py:158`, `409-416`). **Impact:** mis-tuned knobs silently cap throughput (langextract caps at `batch_length`; we cap at `Semaphore(N)`).

- [HIGH] **Whisker paper-level fan-out already matches the "across documents" axis langextract achieves indirectly.** `asyncio.Semaphore(concurrency)` + `asyncio.gather` over per-paper workers (`cli.py:409-472`); baseline measured at `--concurrency 3` → 36 min / 200 papers (`00-baseline.md:12-14`). **Whisker:** **already-have**. Langextract does not add a second cross-document pool — it only batches chunks that happen to come from different docs. **Impact:** the immediate 36→single-digit lever remains raising `N`, not porting langextract's executor.

- [MED] **langextract Gemini provider: per-chunk transient retry with exponential backoff + jitter (OpenAI provider has none).** `_process_single_prompt` loops `max_retries+1` times; classifies 408/429/5xx and connection errors (`gemini.py:316-349`, `351-391`); sleep `min(delay * uniform(0.5,1.5), max_retry_delay)` then `delay *= 2`. OpenAI `_process_single_prompt` is single-shot, raises on failure (`openai.py:244-261`). **Whisker:** **adopt** backoff classification for burst parallelism; retry today lives in pipeline (read-only) — whisker only counts retry warnings in batch footer (`cli.py:65-77`). **Impact:** raising concurrency without backoff risks spurious errors under pod saturation; baseline saw only 1/200 retries post-upgrade (`00-baseline.md:14`).

- [MED] **langextract provider async Batch API (threshold 50 prompts) is a different lane from real-time parallel.** `_DEFAULT_THRESHOLD = 50` (`openai_batch.py:38`); OpenAI `infer` switches to batch API above threshold (`openai.py:348-346`). **Whisker:** **not-applicable** — vLLM pod is consumed via real-time `/v1` streaming (`00-baseline.md:28-34`, `67-68`); no shell for offline `vllm run-batch`.

- [MED] **firecrawl extract LLM calls are single-shot `generateObject` / `generateText`; "batchExtract" is a misnomer (one doc, one completion).** `batchExtractPromise` builds one `generateCompletions` call per document (`batchExtract.ts:72-123`); `generateCompletions` awaits a single `generateObject` (`llmExtract.ts:811`). Rate-limit recovery swaps to `retryModel`, not backoff (`llmExtract.ts:832-876`). **Whisker:** **not-applicable** as a missing LLM-batch pattern — confirms firecrawl is not the reference for inference parallelism.

- [LOW] **firecrawl parallelism is infrastructure/job orchestration, not LLM batching.** Team slot limit via Redis ZSET + `concurrentJobDone` promotion (`concurrency-limit.ts:199-284`, `307-315`); worker acquire uses Redis semaphore with blocking backoff `base_delay_ms=25`, `max_delay_ms=250`, 1.5× growth + jitter (`team-semaphore.ts:73-127`, `298-303`). Extract RabbitMQ consumer `prefetch(1)` — one job at a time (`extract-queue.ts:88-89`). Multi-entity path: scrape all URLs with `Promise.all` (`extraction-service.ts:372-403`), then LLM extractions in **chunks of 50** with `Promise.all` inside each chunk but **sequential across chunks** (`extraction-service.ts:437-461`, `558-559`). API rate limits per mode, extract default 100/min (`rate-limiter.ts:19-26`). **Whisker:** **not-applicable** — single-tenant CLI, no team queues; **adopt** only the bounded burst idea (50-wide inner, sequential outer) if we ever fan out chunk calls.

## False-pass hypothesis

Chunk-parallel triage (langextract-style) could surface different per-chunk axis findings than serial order; `aggregate_adjudications` folds by worst-axis/min-confidence (`chunking.py:226-285`), so verdict distributions could shift slightly even when the merged gate outcome looks stable. Raising paper concurrency without measuring pod knee could look faster while latency per call inflates, masking quality drift in confidence bands.

## False-fail hypothesis

Burst chunk or paper parallelism without Gemini-style jittered backoff could convert transient 429/503 into hard paper errors; firecrawl's model-swap retry (`llmExtract.ts:832-876`) avoids that differently and is not portable to self-hosted vLLM. Parallel retries stacking (langextract guards against SDK+client retry double-stacking: `gemini.py:256-260`) could amplify load if we add whisker-side retries atop pipeline retries.

## What would change my mind

A post-filter corpus audit showing **zero** papers still chunking **and** a pod knee curve where paper-level `--concurrency 16+` holds ~10 s/paper effective would flip this to "paper concurrency only; chunk parallel is garbage for us." Conversely, any paper >500k chars returning to the corpus with 5+ serial chunks would elevate langextract's within-batch pattern from conditional to critical.
