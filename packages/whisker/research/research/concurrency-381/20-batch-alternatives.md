# 20 - Batch-Submission-Scout

**Verdict:** fanout-stays-best — For an API-only client against a `vllm serve` 0.24 pod, bounded concurrent `/v1/chat/completions` at the server knee (~8–16 inflight) is the optimal submission pattern; no stock server-side batch API or offline engine path beats it without infra changes we do not have.
**Confidence:** high

## Findings

- [CRITICAL] **vLLM 0.24 has no OpenAI `/v1/batches` or `/v1/files` on the online server.** Evidence: `packages/whisker/research/llm-batching/05b-web-batch-endpoint.md:7,17-19,23-27`; https://docs.vllm.ai/en/stable/examples/features/openai_batch/ ("not the complete Batch (REST) API"); https://github.com/vllm-project/vllm/issues/8567 (maintainer: use offline `run_batch`, online returns 404); https://github.com/vllm-project/vllm/issues/8631 (feature request closed `not_planned`). Impact: "submit everything as a batch job and poll" is unavailable on our RunPod URL; client must use concurrent single-request POSTs.

- [CRITICAL] **Offline batch (`LLM.generate`, `vllm run-batch`) requires direct engine access on the pod host, not our client contract.** Evidence: `05b-web-batch-endpoint.md:27-29,78`; https://github.com/vllm-project/vllm/issues/8567 ("starts a new model instance", "why it is called offline inference"); https://docs.vllm.ai/en/stable/cli/run-batch/ (CLI boots its own engine). Impact: switching to offline batch is an infra/CTO change (replace or augment `vllm serve` with host-side `run-batch` or in-process `LLM`); out of scope for whisker client work and incompatible with hourly pod-as-a-service billing where we only hold an API key.

- [HIGH] **PR #44445 (online `/v1/batches` + `--enable-batch-api`) is not in vLLM 0.24.0.** Evidence: https://github.com/vllm-project/vllm/pull/44445 (open, merge conflicts as of 2026-07-08); https://github.com/vllm-project/vllm/releases/tag/v0.24.0 (no batch-API mention in release notes). Impact: even future server-side batch jobs would be opt-in gateway state (`--enable-batch-api`, bounded-concurrency chunks per PR description), not a throughput multiplier over continuous batching on today's pod.

- [HIGH] **The only native online batch primitive in 0.24 is synchronous `POST /v1/chat/completions/batch`, which does not beat N concurrent singles and conflicts with our stack.** Evidence: https://docs.vllm.ai/en/v0.24.0/examples/generate/batched_chat_completions_online/ ("messages as a list of conversations", "Streaming is not supported"); `00-baseline.md:30,68` (`stream = true` on alliance-pod; every call streams). Impact: one HTTP round-trip still blocks until all conversations finish; same `max_num_seqs` scheduler cap applies; no streaming means tapetum would need a non-streaming code path (pipeline read-only) for marginal transport savings.

- [HIGH] **olmocr and docling bulk jobs use HTTP concurrency, not offline engine mode, for remote vLLM.** Evidence: `12-olmocr-orchestrator.md:8,14` (external `--server` path: `BoundedSemaphore` inflight cap + per-page HTTP `apost()`); `14-converter-batch.md:12` (docling `ApiVlmModel` + `submit_and_retrieve_each` via `_run_bounded`, default `max_concurrency=8`). Neither repo reports an offline-vs-HTTP throughput delta for remote inference; olmocr's queue-depth hook (`vllm_queued_requests` from local stderr) is **not-applicable** with external server (`12-olmocr-orchestrator.md:14`). Impact: mature converter pattern is "bounded HTTP fan-out at server knee", identical to our lever; no precedent for offline batch winning on a remote pod.

- [HIGH] **Offline `LLM` class can be ~3× faster than HTTP serve, but the gap is IPC/serialization overhead, not GPU scheduling; on a decode-saturated pod it shrinks toward noise.** Evidence: https://github.com/vllm-project/vllm/issues/7956 (maintainer: "`LLM` will be faster than the openai api server, because you don't need to send the request data across processes"; measured 3× on Llama2-70B AWQ TP=4); `17-latency-decomposer.md:12,28-31` (decode 82–92% of ~30.4 s/call; HTTP setup <1%). Impact: even eliminating all HTTP overhead saves ~0.5–2% wall time on our workload; the 3× figure does not transfer to "flood 381 vs c=16" on the same running server.

- [HIGH] **HTTP client flood at N >> `max-num-seqs` does not approximate offline batch throughput; it only deepens the waiting queue.** Evidence: https://discuss.vllm.ai/t/to-understand-max-num-seqs-better/2609 (`max-num-seqs` caps sequences per scheduler iteration; excess waits in queue); `05a-web-concurrency-knee.md:31,41-42` (H200×8 DeepSeek-V4-Pro community config `--max-num-seqs 8`; client N above cap adds queue depth, not GPU parallelism); `19-steelman.md:18-22` (c=16/32 without server change ≈ c=8 wall time). Impact: submitting all 381 papers at once against `--max-num-seqs 16` still runs at most 16 sequences on GPU; remaining 365 queue, inflating p99 latency and 600 s httpx timeout risk (`15-concurrency-safety.md` cited in `SYNTHESIS.md:82-83`).

- [MED] **Bounded fan-out at the knee (c=8–16) approximates what offline batch would achieve on the same engine under continuous batching.** Evidence: https://amineayari.com/blog/vllm-in-production/ (32 concurrent users: stable TPOT, improved aggregate tok/s via dynamic continuous batching); `00-baseline.md:18-19` (c=3 already yields ~2–3× vs serial, proving server absorbs concurrency); `11-throughput-auditor.md:8` (CLI semaphore is sole client throttle; `runner.py:266-272` has no global lock on `run_agent`). Impact: raising `--concurrency` from 3→8–16 feeds the same continuous-batching scheduler that offline `LLM.generate` would use on identical hardware; expected 200-paper wall drops from 36 min to ~9–14 min (`19-steelman.md:13-16`) without any batch API.

- [MED] **Provider-style async batch APIs (OpenAI/Anthropic 24h jobs) are the wrong abstraction for an hourly pod.** Evidence: `SYNTHESIS.md:16-20` (pod billed per uptime hour, not per token; discount irrelevant); `05b-web-batch-endpoint.md:84` ("raise client concurrency … not OpenAI Batch SDK"). Impact: batch-job semantics add latency (poll windows) without cost benefit; self-hosted throughput = concurrent requests into continuous batching.

- [LOW] **`/v1/chat/completions/batch` pod exposure on alliance-pod is unverified.** Evidence: `05b-web-batch-endpoint.md:47-49,79` (documented in 0.24, pod exposure unknown); `00-baseline.md:33-34` (we probed `/version` only). Impact: even if present, sync/no-stream batch endpoint is a transport convenience for multi-convo RPCs, not a substitute for knee-tuned fan-out on 381 independent papers with tier-1/tier-2 serial chains (`11-throughput-auditor.md:12`).

## What would change my mind

1. **Live probe:** `POST /v1/batches` or `POST /v1/files` on alliance-pod returns 200 with `--enable-batch-api` enabled, and a 20-paper A/B shows ≥20% wall-time reduction vs bounded fan-out at the same inflight count (not just queue depth shift).
2. **Infra flip:** CTO deploys offline `vllm run-batch` or in-process `LLM.generate` on the pod with measured ≥1.5× throughput vs c=16 HTTP on the same 381-paper corpus at equal `max-num-seqs`.
3. **Knee sweep failure:** Empirical sweep (`19-steelman.md:46-58`) shows c=8 wall time ≥ c=3 projection with superlinear retry/error growth, proving the bottleneck is not client submission pattern but pod-side saturation — would reopen server reconfig or dual-pod sharding before any batch API work.
